`[卷四·纵深·第二章]` -- 上一章我们拆解了配置系统——Agent 怎么知道自己的名字、怎么连接 Telegram、上下文压缩比例是多少。这些信息在 Agent 启动时就加载好了，像一个员工入职时领到的工牌。

但有一个问题：工牌上不会写你昨天跟客户谈了什么、上周做的决策是什么、三个月前踩过什么坑。这些信息需要另一个系统来管理——记忆。

你有没有这样的经历？跟一个 AI 助手聊了半天，告诉它你的项目背景、技术偏好、团队约定。第二天再打开对话，它全忘了，你得从头再来一遍。这就是"没有记忆"的 AI。

QwenPaw 的记忆系统要解决的问题就是：**让 Agent 能跨越对话边界记住信息，而且不是什么都记——只记重要的。** 它像一座精心设计的"记忆宫殿"：短期记忆放在最容易拿到的地方，长期记忆存进结构化的档案库，主动记忆则像一个贴心的管家，在你还没开口时就准备好你可能需要的信息。

这一章，我们走进这座宫殿，看看记忆是怎么存进去、怎么取出来、怎么被整理优化的。

## 问题：Agent 怎么记住你昨天说过的话？

想象这个场景：

```
第一天 14:00  你：「我们项目用的是 React 19 + TypeScript，后端是 Go。」
              Agent：「好的，我记下了。」

第一天 14:30  你：「帮我写一个用户列表组件。」
              Agent：（基于刚才的记忆，直接用 React + TS 写了组件）

第二天 09:00  你：「昨天那个列表组件，加个排序功能。」
              Agent：？？？「什么列表组件？」
```

第三行就是"无记忆 Agent"的典型表现。QwenPaw 怎么避免这个问题？具体来说：

- 对话历史太长，Context 放不下怎么办？（短期记忆的压缩）
- 压缩之后，重要信息怎么保留？（长期记忆的沉淀）
- Agent 闲着的时候，能不能主动帮你查点有用的信息？（主动记忆）
- 所有这些记忆存在哪？怎么搜索？（存储和检索）

这四个问题，对应了 QwenPaw 记忆系统的四个层次。

---

## 术语其实很简单

> **术语：短期记忆（Short-term Memory）**
>
> 想象你浏览器的标签页。你打开了一堆网页，正在对比不同方案的优劣。这些信息你此刻能看到、能引用，但一旦关掉浏览器就没了。短期记忆就是对话的"标签页"——当前对话的完整历史。它是最详细的，但 Context 窗口有限，装不下太多。QwenPaw 用 `compact_memory()` 来压缩它。

> **术语：长期记忆（Long-term Memory）**
>
> 想象你书桌上那本笔记本。每次做完项目，你会把重要的决策、踩过的坑、确认的偏好写进去。下次做类似项目时翻一翻。QwenPaw 的长期记忆存在 `MEMORY.md` 和 `memory/*.md` 文件中，通过 `summary_memory()` 沉淀。Agent 在新对话开始时可以搜索这些文件，找回"昨天说过的话"。

> **术语：主动记忆（Proactive Memory）**
>
> 想象你的桌面贴了一张便签条：「记得查一下 React 19 的新 API」。这是你自己（或你的助手）主动写的提醒，不是被动回答问题时产生的。QwenPaw 的主动记忆系统会在你沉默一段时间后，主动分析你的对话历史和屏幕内容，推测你可能需要什么，然后提前去查找信息。

> **术语：梦境优化（Dream Optimization）**
>
> 想象你睡了一觉，第二天醒来发现昨晚乱的笔记被整理得整整齐齐——重复的合并了，过时的删了，重要的高亮了。QwenPaw 的 `dream_memory()` 做的就是这件事：在配置的时间点（默认每天 23:00），Agent 进入"梦境状态"，读取长期记忆和当天日志，去冗余、合并、覆写，让记忆保持精简和最新。

在深入每个层次之前，先看全景。QwenPaw 的记忆系统由三层组成，每一层有不同的职责、生命周期和存储介质。

这个三层架构的精妙之处在于：**每一层都由 `BaseMemoryManager` 这个统一的抽象基类管理。** 打开 `src/qwenpaw/agents/memory/base_memory_manager.py`，第 21-236 行定义了这个接口：

```python
class BaseMemoryManager(ABC):
    @abstractmethod
    async def compact_memory(self, messages, previous_summary="", ...):
        """压缩消息为摘要"""

    @abstractmethod
    async def summary_memory(self, messages, **kwargs):
        """生成综合摘要"""

    @abstractmethod
    async def memory_search(self, query, max_results=5, min_score=0.1):
        """搜索记忆"""

    @abstractmethod
    async def dream_memory(self, **kwargs):
        """梦境优化"""
```

注意，`BaseMemoryManager` 只定义了短期记忆和长期记忆的操作。主动记忆是一个独立的子系统（`proactive/` 目录），有自己的触发逻辑和执行流程。但它依赖于长期记忆中的信息——如果 Agent 记不住你之前在做什么，就无法推测你现在可能需要什么。

## 探索：ReMe-Light 引擎——记忆管理的核心

`BaseMemoryManager` 是接口，真正的实现在 `ReMeLightMemoryManager`。打开 `src/qwenpaw/agents/memory/reme_light_memory_manager.py`，第 41-143 行是初始化。

ReMe-Light 是一个外部库（`reme-ai`，QwenPaw 期望的版本是 `0.3.1.8`，见第 37 行）。QwenPaw 通过**组合模式**把它嵌入自己的架构：`ReMeLightMemoryManager` 持有一个 `self._reme`（ReMeLight 实例），所有操作都委托给它。

### 初始化：选择存储后端

初始化时第一个重要的决策是：**用哪种存储后端？** 第 74-95 行：

```python
backend_env = EnvVarLoader.get_str("MEMORY_STORE_BACKEND", "auto")
if backend_env == "auto":
    if platform.system() == "Windows":
        memory_backend = "local"
    else:
        try:
            import chromadb
            memory_backend = "chroma"
        except Exception:
            memory_backend = "local"
```

逻辑很清晰：

1. 用户可以通过 `MEMORY_STORE_BACKEND` 环境变量显式指定。
2. 如果设为 `auto`（默认），Windows 直接用 `local`（因为 Windows 的 SQLite 版本可能不满足 ChromaDB 要求）。
3. 其他系统尝试导入 `chromadb`：成功就用 `chroma`（向量数据库），失败就降级到 `local`。

为什么 `local` 是兜底方案？因为 ChromaDB 需要 SQLite >= 3.35，而一些老旧的 Linux 服务器或 macOS 系统自带的 SQLite 版本不够。代码里还贴心地写了错误提示（第 83-92 行），告诉用户如何升级。

### 初始化：向量搜索和全文搜索

存储后端选好后，还要决定启用哪些搜索能力（第 99-112 行）：

```python
emb_config = self.get_embedding_config()
vector_enabled = bool(emb_config["base_url"]) and bool(emb_config["model_name"])
fts_enabled = EnvVarLoader.get_bool("FTS_ENABLED", True)
```

这里有两种搜索模式：

- **向量搜索**（`vector_enabled`）：需要配置 Embedding 模型（API 地址 + 模型名）。它把文本转成向量，然后做语义相似度搜索。好处是能找到"意思相近"的内容，不局限于精确关键词匹配。
- **全文搜索**（`fts_enabled`）：默认开启。基于关键词的搜索，速度快，不需要外部 API。

如果用户没有配置 Embedding 模型，向量搜索会被自动关闭，系统仍然可以用全文搜索工作。这是一个优雅的降级设计。

### 初始化：版本哨兵

有一个有趣的设计：**版本哨兵文件**。第 119-124 行和第 160-197 行的 `_resolve_rebuild_on_start()` 方法：

```python
sentinel_name = f".reme_store_{store_version}"
sentinel_path = Path(working_dir) / sentinel_name

if sentinel_path.exists():
    return rebuild_on_start      # 哨兵存在，尊重配置

# 哨兵不存在 → 强制重建索引
sentinel_path.touch()
return True
```

想象你搬进了一间新办公室（首次启动），你需要重新整理所有档案（重建索引）。整理完后，你在门口贴一张"已整理"的便签（哨兵文件）。下次再来，看到便签就知道不需要重新整理了。

但如果你升级了归档系统（`_REME_STORE_VERSION` 从 `v1` 变成 `v2`），旧便签就失效了——系统会删掉旧哨兵、创建新哨兵、强制重建。这样确保索引格式升级时不会出现兼容性问题。

## 探索：短期记忆——对话压缩的魔法

一场长对话的消息可能会非常长。LLM 的 Context 窗口有限（通常几万到十几万 token），不可能无限增长。当消息累积到接近上限时，就需要"压缩"。

### 什么时候触发压缩？

压缩不是随意的，而是在每次需要向 LLM 发送消息前检查。`check_context()` 方法（第 304-309 行）负责判断当前 Context 是否"满了"：

```python
async def check_context(self, **kwargs):
    if self._reme is None:
        return None
    return await self._reme.check_context(**kwargs)
```

它返回一个三元组 `(messages_to_compact, remaining_messages, is_valid)`：
- `messages_to_compact`：需要压缩的旧消息。
- `remaining_messages`：保留不压缩的近期消息。
- `is_valid`：整体是否仍然有效。

### 压缩是怎么做的？

`compact_memory()`（第 311-386 行）是短期记忆的核心操作。它不是简单地"删掉旧消息"，而是**让 LLM 把旧消息浓缩成一段摘要**：

```python
result = await self._reme.compact_memory(
    messages=messages,
    as_llm=self.chat_model,
    compact_ratio=cc.memory_compact_ratio,
    previous_summary=previous_summary,
    return_dict=True,
)
```

关键参数是 `compact_ratio`（压缩比例）和 `previous_summary`（之前的摘要）。

- `compact_ratio` 控制压缩的程度——比如 0.3 意味着把旧消息压缩到原始长度的 30%。
- `previous_summary` 让压缩是**增量的**：不是每次从零开始总结，而是在之前的摘要基础上，融入新消息的信息。

这就像你整理会议纪要：不是每次把所有会议重新写一遍，而是在上一版纪要的基础上补充新内容。

压缩的结果是一个字典，包含 `history_compact`（压缩后的摘要文本）和 `is_valid`（压缩是否成功）。如果压缩失败（LLM 返回了无效内容），QwenPaw 会把完整的原始数据保存到一个 `compact_invalid_*.json` 文件中（第 364-384 行），方便事后排查。这是一个非常实用的调试设计——压缩失败的上下文不会无声无息地丢失。

### 工具返回值的单独压缩

除了对话消息，工具的返回值（如 `read_file` 读取的一个 2MB 的文件）也会单独压缩。`compact_tool_result()` 方法（第 297-302 行）处理这个场景。它的策略是：**只保留工具返回值的最近 N 字节**，其余截断。

这个 N 由 `recent_max_bytes` 控制，并通过 Context 模式传递（还记得上一章的 `set_current_recent_max_bytes()` 吗？）。

## 探索：长期记忆——从对话到知识档案

短期记忆压缩后的摘要仍然在内存中，对话结束就没了。真正让 Agent "记住昨天的事"的是长期记忆。

### 摘要沉淀：summary_memory()

`summary_memory()` 方法（第 388-412 行）负责把对话中的重要信息提取出来，写入磁盘文件。

它和 `compact_memory()` 的区别在于目标不同：

- `compact_memory()`：压缩旧消息，为了**腾出 Context 空间**。输出是简短的摘要，仍然用于当前对话。
- `summary_memory()`：生成综合摘要，为了**长期保存**。输出写入 Markdown 文件，供未来对话检索。

`summary_memory()` 还注册了一组工具（第 145-148 行）：

```python
self.summary_toolkit = Toolkit()
self.summary_toolkit.register_tool_function(read_file)
self.summary_toolkit.register_tool_function(write_file)
self.summary_toolkit.register_tool_function(edit_file)
```

为什么摘要需要文件操作工具？因为摘要引擎本身是一个 ReAct Agent——它可以主动读取现有的 MEMORY.md、对比新旧信息、然后覆写或编辑文件。这比简单的"追加写入"灵活得多。

### 摘要任务的异步执行

注意到 `BaseMemoryManager` 有一个 `add_async_summary_task()` 方法（第 127-149 行）：

```python
def add_async_summary_task(self, messages, **kwargs):
    # 先清理已完成的旧任务
    remaining_tasks = []
    for task in self.summary_tasks:
        if task.done():
            # 检查结果或错误
        else:
            remaining_tasks.append(task)
    self.summary_tasks = remaining_tasks

    # 创建新的异步任务
    task = asyncio.create_task(
        self.summary_memory(messages=messages, **kwargs),
    )
    self.summary_tasks.append(task)
```

这是一个聪明的优化：摘要不需要同步完成。用户发送一条消息后，Agent 可以先回复，然后在后台悄悄生成摘要。用户不需要等摘要写完才看到响应。这就像服务员先把菜端上桌，然后趁你吃的时候收拾厨房。

### 记忆文件的结构

长期记忆存在 Agent 的 workspace 目录下：

```
~/.qwenpaw/workspaces/default/
├── MEMORY.md              ← 核心长期记忆（手动 + 自动维护）
├── memory/                ← 每日日志目录
│   ├── 2026-05-09.md      ← 昨天的对话摘要
│   ├── 2026-05-10.md      ← 今天的对话摘要
│   └── ...
├── backup/                ← MEMORY.md 的备份
│   └── memory_backup_20260510_230000.md
└── .reme_store_v1         ← 版本哨兵文件
```

`MEMORY.md` 是最关键的文件。它不是对话的完整记录，而是经过提炼的**知识档案**——只包含核心决策、确认的偏好、高价值的可复用经验。

`AgentMdManager`（`src/qwenpaw/agents/memory/agent_md_manager.py`）提供了对这些文件的读写能力。它把 workspace 目录分为两个区域：`working_dir`（根目录，存 MEMORY.md）和 `memory_dir`（`memory/` 子目录，存日志）。两者都有 `list_*_mds()`、`read_*_md()`、`write_*_md()` 三组方法。

### 记忆搜索：memory_search()

有了长期记忆文件，Agent 怎么在需要时找到相关内容？`memory_search()` 方法（第 414-435 行）提供了语义搜索能力：

```python
async def memory_search(self, query, max_results=5, min_score=0.1):
    if self._reme is None or not getattr(self._reme, "_started", False):
        return ToolResponse(content=[TextBlock(type="text",
            text="ReMe is not started, report github issue!")])

    return await self._reme.memory_search(
        query=query, max_results=max_results, min_score=min_score,
    )
```

这个搜索被包装成了一个工具函数。打开 `src/qwenpaw/agents/tools/memory_search.py` 第 7-69 行，`create_memory_search_tool()` 创建了一个 Agent 可以调用的 `memory_search` 工具。Agent 在 ReAct 循环中可以像调用其他工具一样调用它：

```
Agent 内心独白：「用户问了我昨天讨论的排序需求。
我需要搜索一下记忆。调用 memory_search(query="排序功能 用户列表组件")」
→ 返回相关记忆片段
→ Agent 基于记忆回答用户
```

搜索底层由 ReMe-Light 驱动，支持前面提到的向量搜索和全文搜索两种模式。如果配置了 Embedding 模型，搜索是语义级的——即使你搜索"项目用什么框架"，也能找到之前说过的"我们用 React 19"。

### 混合搜索的分数融合

两种搜索模式不是简单并列，而是通过加权融合计算最终分数：

| 搜索模式 | 权重 | 作用 |
|---------|------|------|
| 向量搜索 | 0.7 | 语义相似度匹配，捕获"意思相近"的内容 |
| BM25 全文搜索 | 0.3 | 关键词精确匹配，确保专业术语不被遗漏 |

融合过程分三步（`chroma_file_store.py` 第 507-605 行）：先计算候选池大小（`limit * candidate_multiplier`，默认 3 倍），然后并行执行向量搜索和关键词搜索，最后合并分数——向量结果乘以 0.7，BM25 结果乘以 0.3，重叠的条目分数相加。

向量搜索使用 ChromaDB 的 HNSW 索引做余弦距离计算，分数转换为 `1.0 - distance / 2.0`。BM25 搜索则用 ChromaDB 的 `$contains` 操作符做大小写不敏感的匹配，分数由 `match_count / n_words + phrase_bonus(0.2)` 计算。

这个 0.7/0.3 的权重分配是有道理的：语义搜索是主力，能捕获"表达不同但意思相近"的内容；BM25 兜底确保精确术语（如项目名、文件名）不会因为语义偏差被遗漏。

还有一个有趣的配置项：`force_memory_search`（`MemorySummaryConfig` 第 595-597 行）。如果开启，Agent 会在**每一轮对话**都自动搜索记忆，不等用户明确提问。这对于需要频繁参考历史决策的场景很有用，但会增加 token 消耗。

## 探索：梦境优化——深夜的档案整理员

长期记忆会不断积累。如果不整理，MEMORY.md 会越来越长、越来越乱——重复的条目、过时的信息、矛盾的状态。`dream_memory()` 就是解决这个问题的。

### 触发时机

梦境优化由 CronManager 调度，配置项是 `dream_cron`（`MemorySummaryConfig` 第 589-593 行）：

```python
dream_cron: str = Field(
    default="0 23 * * *",
    description="Cron expression for dream-based memory optimization job",
)
```

默认每天 23:00 执行一次。这个名字起得很有画面感：深夜了，Agent 进入"梦境"，开始整理一天的记忆。

`src/qwenpaw/app/crons/manager.py` 第 430-440 行定义了梦境回调：

```python
async def _dream_callback(self) -> None:
    try:
        await self._runner.memory_manager.dream_memory()
    except asyncio.CancelledError:
        raise
    except Exception as e:
        logger.error(f"Failed to execute dream task: {e}", exc_info=True)
```

### 梦境做了什么？

打开 `reme_light_memory_manager.py` 第 451-534 行。梦境优化的流程如下：

1. **备份**：先备份现有的 MEMORY.md 到 `backup/` 目录（第 493-508 行）。万一"梦境"出了问题，还能回滚。
2. **构建梦境提示词**：`_get_dream_prompt()` 方法（第 536-598 行）生成一段精心设计的中文提示词。
3. **创建梦境 Agent**：一个临时的 ReActAgent，配备文件读写工具。
4. **执行梦境**：梦境 Agent 读取 MEMORY.md 和当天日志，按照提示词中的优化原则整理记忆。

梦境提示词的设计非常讲究（第 543-561 行）。它定义了四条优化原则：

```
【梦境优化原则】
1. 极简去冗：严禁记录流水账，仅保留核心决策、确认偏好、高价值经验
2. 状态覆写：发现状态变更时，用新状态替换旧状态，禁止矛盾信息并存
3. 归纳整合：将零碎的相似规则提炼、合并为通用性强的条目
4. 废弃剔除：主动删除已证伪的假设或不再适用的陈旧条目
```

以及四个执行步骤：

```
步骤 1 [加载]：读取 MEMORY.md + 当天的日志文件
步骤 2 [梦境提纯]：按原则去重、替换、剔除和合并
步骤 3 [落盘]：覆写 MEMORY.md
步骤 4 [苏醒汇报]：简短汇报新增了什么、删除了什么
```

这个设计的精妙之处在于：**梦境优化不是简单的文本压缩，而是由 LLM 驱动的智能整理。** LLM 能理解语义——它知道"我们之前用 React 18"和"现在升级到了 React 19"是状态变更，应该用后者替换前者，而不是两条都保留。

### 梦境 Agent 的执行细节

梦境优化的执行者不是主 Agent 本身，而是一个临时创建的 `ReActAgent`（`reme_light_memory_manager.py` 第 493-510 行），名叫 `DreamOptimizer`。它配备了文件读写工具（`read_file`、`write_file`、`edit_file`），能够自主读取 MEMORY.md 和当天日志、分析内容差异、然后直接覆写文件。

提示词模板（`_get_dream_prompt()`，第 536-598 行）根据语言（中文/英文）动态生成，包含当前日期信息，确保梦境 Agent 能准确识别"今天的日志"。整个流程在 `dream_memory()` 方法中完成：备份 → 构建提示 → 创建梦境 Agent → 执行 → 汇报。

## 探索：主动记忆——沉默时的贴心助手

前面三层（短期/长期/梦境）都是"被动"的——你问，Agent 答或者整理。主动记忆（Proactive）是唯一的"主动出击"层：**在你沉默的时候，Agent 会主动推测你可能需要什么，然后去查找信息。**

### 触发机制：沉默检测

打开 `src/qwenpaw/agents/memory/proactive/proactive_trigger.py`。第 203-277 行的 `proactive_trigger_loop()` 是一个后台轮询循环：

```python
async def proactive_trigger_loop(session_id):
    while True:
        await asyncio.sleep(30)          # 每 30 秒检查一次

        config = proactive_configs[session_id]
        if not config.enabled:
            continue

        if await is_agent_busy(workspace):  # Agent 正忙？跳过
            continue

        # 检查是否沉默超过阈值
        if not _should_trigger_proactive(config, last_interaction, now):
            continue

        # 触发主动响应
        await _handle_proactive_trigger(...)
```

触发条件在 `_should_trigger_proactive()`（第 110-130 行）中定义：

```python
elapsed_minutes = (current_time - last_interaction).total_seconds() / 60.0
if elapsed_minutes < config.idle_minutes:    # 默认 30 分钟
    return False
```

只有用户沉默超过 `idle_minutes`（默认 30 分钟）且 Agent 没有在忙时，才会触发。

还有一个防抖机制（第 146-150 行）：两次触发尝试之间至少间隔 60 秒。这避免了频繁触发导致的资源浪费。

### 上下文构建：读取历史 + 屏幕分析

触发后，系统会构建一个"主动记忆上下文"。`proactive_utils.py` 第 39-80 行的 `build_proactive_memory_context()` 负责这个工作：

```python
async def build_proactive_memory_context(workspace, agent):
    # 1. 如果支持多模态，截取屏幕分析当前活动
    if get_active_model_supports_multimodal():
        screen_analysis = await _analyze_screen_activity(agent)

    # 2. 读取最近 7 天的对话会话
    sessions = await _read_chat_sessions_metadata(workspace)
    filtered = _filter_recent_sessions(sessions, days=7)

    # 3. 收集并格式化消息
    all_messages = await _collect_messages(filtered, workspace)
    context = _format_session_messages(all_messages, max_messages=100)

    return combined_context
```

这个上下文构建过程涉及两个信息源：

1. **屏幕截图**（如果支持多模odal）：截取用户桌面，让 LLM 分析当前在做什么。
2. **对话历史**：读取最近 7 天的对话，按时间倒序排列，最多 100 条消息，50000 字符。

`_filter_recent_sessions()` 方法（第 333-351 行）有一个兜底逻辑：如果最近 7 天不到 5 个会话，就放宽条件，取最近 5 个会话。这确保即使用户不活跃，主动记忆也有足够的上下文来工作。

### 任务提取：LLM 推测你需要什么

有了上下文，系统会用 LLM 提取 1-3 个高优先级任务。`proactive_responder.py` 第 136-159 行的 `_extract_tasks_from_memory()` 方法负责：

提示词定义在 `proactive_prompts.py` 第 5-42 行，核心要求是：

```
1. 从用户近期的对话中找到 1-3 个可能的高层目标
2. 为每个目标生成一个具体的、可执行的查询
3. 查询必须是有帮助的——不是重复过去的搜索
4. 按优先级排序（频率和近因）
```

LLM 返回一个 JSON 结构：

```json
{
  "tasks": [
    {
      "task": "React 19 排序功能实现",
      "query": "React 19 table sorting best practices",
      "why": "用户昨天多次提到列表排序需求"
    }
  ]
}
```

### 执行查询并推送

提取任务后，系统会逐个执行查询（`_execute_query()`，第 178-208 行）。它使用 `browser_use`、`execute_shell_command` 等工具实际去查找信息。如果某个查询成功返回了结果，就停止执行后续任务。

最后，`_generate_final_message()`（第 211-233 行）把查询结果转成一条用户友好的消息，通过 HTTP API 推送给用户。消息以 `[PROACTIVE]` 标记开头，让系统能区分这是主动消息还是用户触发的响应。

### 中断检测：用户回来了怎么办？

整个主动记忆流程中，有一个贯穿始终的中断检测机制（`_was_interrupted()`，第 309-343 行）：

```python
async def _was_interrupted(baseline_timestamp, workspace):
    # 1. Agent 正在忙？（处理用户的新请求）
    if await is_agent_busy(workspace):
        return True

    # 2. 有对话在 baseline 之后更新了？
    for chat in chats:
        if chat_updated > baseline_timestamp:
            return True
```

在上下文构建前、任务提取后、每个查询执行前后，都会检查是否被中断。如果用户回来了、发了新消息，主动记忆流程会立刻停止——不需要的推送比没有推送更糟糕。

## 工程权衡：记忆系统的设计选择

### 文件存储 vs 数据库

QwenPaw 的长期记忆存储在 Markdown 文件中（`MEMORY.md` + `memory/*.md`），而不是数据库。这是一个有意为之的设计选择：

- **优点**：人可读。用户可以直接打开文件查看和编辑 Agent 的记忆。调试时一目了然。不需要安装额外的数据库。
- **缺点**：搜索效率不如数据库。文件写入没有事务保证（虽然梦境优化有备份机制）。并发写入可能导致数据丢失。

但对于 QwenPaw 的使用场景（单用户或小团队的个人 AI 助手），文件存储的简单性远远胜过数据库的性能优势。

### 异步摘要 vs 同步摘要

摘要任务通过 `add_async_summary_task()` 异步执行，不阻塞用户对话。这意味着：

- **优点**：用户体验更流畅，不需要等摘要写完。
- **缺点**：如果进程在摘要完成前崩溃，这段记忆可能丢失。

QwenPaw 接受了这个权衡——毕竟摘要丢失只是"少记了一次"，不是"数据损坏"。而且下一次对话的摘要会覆盖性地包含这些信息。

### 主动记忆的资源消耗

主动记忆每 30 秒轮询一次，触发后需要 LLM 调用来提取任务和执行查询。这意味着：

- **优点**：Agent 在你沉默时也能提供价值，像一个真正的助手。
- **缺点**：消耗额外的 LLM token 和 API 调用。如果配置不当，可能产生不必要的打扰。

QwenPaw 通过多层防抖（30 秒轮询、30 分钟沉默阈值、60 秒冷却、中断检测）来控制资源消耗和打扰频率。用户可以通过 `idle_minutes` 参数调节触发阈值。

### 版本锁定的风险

`_EXPECTED_REME_VERSION = "0.3.1.8"` 硬编码了 ReMe-Light 的版本号（第 37 行）。每个操作前都会检查版本是否匹配（`_warn_if_version_mismatch()`）。这确保了行为一致性，但也意味着升级 ReMe-Light 需要同步修改 QwenPaw 的代码。

## 动手：观察 Agent 的记忆文件

cat ~/.qwenpaw/workspaces/default/MEMORY.md
