## 问题：代码写好了，怎么提交给项目？

你在本地写了一个漂亮的新 Channel，测试也通过了。下一步呢？直接 push 到 main 分支？当然不行——大型开源项目都有严格的贡献流程：Fork、分支、提交、CI 检查、代码审查、合并。这套流程不只是"走形式"，它保护了项目的代码质量和稳定性。

QwenPaw 作为一个活跃的开源项目，拥有完整的 CI/CD 体系和详细的贡献指南。这一章，我们就要拆解这套体系：从 Fork 仓库到 PR 合并的每一步，以及每一步背后的原理。

## 术语其实很简单

> **术语：Fork（分叉）**
>
> 想象你在图书馆看到一本好书，想在书页上做笔记。你当然不能在原书上写——那本是公共的。你会先复印一份，然后在你的复印件上随意涂写。Fork 就是这个"复印"动作：你在 GitHub 上把别人的仓库完整复制到自己的账号下。原件不受影响，你的副本可以随便改。改好了，你把"笔记"提交回给原书作者，请他采纳。

> **术语：Pull Request（PR，拉取请求）**
>
> 继续"图书馆"的比喻。你在复印件上做了出色的笔记，现在你想让原书作者把这些笔记纳入正式版本。你不会直接去改原书——你会写一封信给作者说："我在第 42 页做了一个很有用的批注，请考虑采纳。"这封信就是 Pull Request。你"请求"作者把你的改动"拉取"到他的原版中。作者可以接受、拒绝，或者让你修改后再提交。

> **术语：CI/CD（持续集成/持续部署）**
>
> 想象一家汽车工厂。每辆新车组装完成后，不会直接出厂——它要经过一系列自动检测：刹车灵不灵、灯光亮不亮、轮胎紧不紧。只有全部通过才能盖章放行。CI/CD 就是代码世界的"自动检测线"：你提交代码后，系统自动运行格式检查、静态分析、单元测试、集成测试……全部通过才能进入下一步。CI（Continuous Integration，持续集成）关注的是"合并代码前自动验证"，CD（Continuous Deployment，持续部署）关注的是"验证通过后自动发布"。QwenPaw 主要使用 CI 部分。

> **术语：Pre-commit（预提交钩子）**
>
> 想象你出门前习惯看一眼镜子：头发乱了没有、衣服有没有污渍。这不是别人强制要求你做的——是你自己的好习惯。Pre-commit 就是代码世界的"出门照镜子"：在你执行 `git commit` 之前，它自动帮你检查代码格式、语法错误、敏感信息泄露等。如果有问题，它会阻止提交并告诉你怎么修。这样，你不会把"脏代码"提交到仓库里。

> **术语：Code Review（代码审查）**
>
> 想象你写了一篇论文投稿到学术期刊。编辑不会直接发表——他会请同行专家审阅，给出修改意见。代码审查也是一样：项目维护者会仔细阅读你提交的每一行代码，检查逻辑是否正确、风格是否一致、是否有潜在的 bug 或安全问题。他们会留下评论，你根据评论修改代码。这个过程可能来回几轮，最终审查通过后代码才能合并。这不是在为难你——这是在保护项目的质量，也是在帮助你成长。

## 探索：从 Fork 到 Merge 的完整流程

### 第一步：Fork 仓库

在 GitHub 上打开 `agentscope-ai/QwenPaw` 仓库，点击右上角的 "Fork" 按钮。GitHub 会在你的账号下创建一份完整拷贝：`your-username/QwenPaw`。

然后克隆你的 Fork 到本地：

```bash
git clone https://github.com/your-username/QwenPaw.git
cd QwenPaw
```

设置上游仓库，以便同步最新改动：

```bash
git remote add upstream https://github.com/agentscope-ai/QwenPaw.git
```

这样你就有两个远程仓库：`origin`（你的 Fork）和 `upstream`（原仓库）。

### 第二步：创建功能分支

永远不要在 `main` 分支上直接开发。为每个功能或修复创建独立分支：

```bash
git checkout -b feat/channels/telegram main
```

分支命名建议遵循 `<type>/<scope>/<description>` 格式，与项目的 Conventional Commits 规范保持一致（见 `CONTRIBUTING.md` 第 28-49 行）。常见的 type 有：

| Type | 用途 | 示例 |
|------|------|------|
| `feat` | 新功能 | `feat/channels/telegram` |
| `fix` | Bug 修复 | `fix/skills/parsing` |
| `docs` | 文档 | `docs/getting-started` |
| `refactor` | 重构 | `refactor/providers/validation` |
| `test` | 测试 | `test/channels/telegram` |

### 第三步：安装开发环境

QwenPaw 在 `CONTRIBUTING.md` 第 70-76 行给出了明确的本地验证步骤。让我们来拆解每一步：

```bash
# 安装项目及其开发依赖（含 pytest、pre-commit 等）
pip install -e ".[dev,full]"

# 安装 pre-commit 钩子到你的本地仓库
pre-commit install

# 运行所有预提交检查
pre-commit run --all-files

# 运行测试
pytest
```

`pip install -e ".[dev,full]"` 这条命令做了两件事：

1. `-e` 表示"可编辑安装"（editable install）。你修改源码后不需要重新安装就能生效。
2. `.[dev,full]` 表示安装 `pyproject.toml` 中定义的 `dev` 和 `full` 可选依赖。

打开 `pyproject.toml` 第 82-89 行，可以看到 `dev` 依赖列表：

```toml
[project.optional-dependencies]
dev = [
    "pytest>=8.3.5",
    "pytest-asyncio>=0.23.0",
    "pre-commit>=4.2.0",
    "pytest-cov>=6.2.1",
    "hypothesis>=6.0.0",
]
```

这些就是项目要求的开发工具链：测试框架（pytest）、异步测试支持（pytest-asyncio）、预提交钩子（pre-commit）、覆盖率（pytest-cov）、属性测试（hypothesis）。

### 第四步：编写代码并提交

在功能分支上开发。每完成一个小功能就提交一次，提交信息遵循 Conventional Commits：

```bash
git add src/qwenpaw/app/channels/telegram/
git commit -m "feat(channels): add Telegram channel stub"
```

提交信息的格式是 `<type>(<scope>): <subject>`（`CONTRIBUTING.md` 第 28-49 行）。这条规范让项目的历史记录像一本结构清晰的日记——看提交信息就知道每个改动做了什么。

### 第五步：Pre-commit 检查

当你执行 `git commit` 时，pre-commit 钩子会自动运行。你也可以手动触发：

```bash
pre-commit run --all-files
```


注意一个细节：所有检查都排除了 `skills/` 目录（`.pre-commit-config.yaml` 第 6 行 `exclude: '(.*/skills/.*)'`）。这是因为 Skill 是用户创建的内容，项目不对用户自定义的 Skill 做强制格式要求——只对核心代码执行检查。

```bash
git add .
git commit -m "style: apply pre-commit auto-fixes"

```

### 第六步：运行测试

QwenPaw 的测试结构清晰地分成了五个层次（`tests/` 目录）：

```
tests/
├── conftest.py          ← 全局 fixture（mock、临时目录等）
├── unit/                ← 单元测试：测试单个函数/类
│   ├── agents/          ← Agent 相关
│   ├── app/             ← 应用核心
│   ├── channels/        ← 频道相关
│   ├── cli/             ← 命令行工具
│   ├── providers/       ← 模型提供者
│   ├── security/        ← 安全模块
│   ├── utils/           ← 工具函数
│   └── workspace/       ← 工作区
├── contract/            ← 契约测试：验证接口合规
│   ├── channels/        ← 每个 Channel 一个契约测试
│   └── providers/       ← Provider 契约测试
├── integration/         ← 集成测试：多模块协作
├── e2e/                 ← 端到端测试：完整用户流程
└── fixtures/            ← 测试数据和 fixture
    └── channels/        ← Channel 测试 fixture
```

`Makefile` 提供了快捷命令（第 13-25 行）：

```bash
make test            # 运行所有测试
make test-unit       # 只跑单元测试
make test-contract   # 只跑契约测试
make quick           # 快速检查（失败即停，精简输出）
make coverage-full   # 完整覆盖率报告
```

`pytest.ini` 的配置（`pyproject.toml` 第 100-111 行）设定了 `asyncio_mode = "auto"`，意味着异步测试函数不需要额外标记就能自动识别——这对 QwenPaw 这种大量使用 async/await 的项目来说非常方便。

### 第七步：推送并创建 PR

代码在本地验证通过后，推送到你的 Fork：

```bash
git push origin feat/channels/telegram
```

然后在 GitHub 上创建 Pull Request。QwenPaw 提供了 PR 模板（`.github/PULL_REQUEST_TEMPLATE.md`），包含以下必填部分：

| 模板部分 | 内容 | 重要性 |
|----------|------|--------|
| Description | 这个 PR 做了什么、为什么 | 必须 |
| Related Issue | 关联的 Issue 编号 | 建议 |
| Type of Change | 变更类型（Bug/Feature/Docs...） | 必须 |
| Component(s) Affected | 影响的组件 | 必须 |
| Checklist | pre-commit 通过、测试通过 | 必须 |
| Testing | 如何测试这些变更 | 必须 |
| Local Verification Evidence | 本地验证结果 | 必须 |

特别注意：如果你改的是 Channel，模板还有额外的 Checklist（第 37-43 行）：

```markdown
### For Channel Changes
- [ ] I ran `./scripts/check-channels.sh` and it passes
- [ ] Contract test exists in `tests/contract/channels/test_<channel>_contract.py`
- [ ] All 19 contract verification points pass
```

这是 Channel 贡献的硬性要求——必须通过 19 项契约验证点。契约测试（Contract Test）的概念我们在第十二章接触过：它验证的是"接口合规性"，即你的 Channel 是否正确实现了 BaseChannel 要求的所有方法。

让我们逐一看看这些 Workflow 的设计。

### 1. PR Welcome Bot（`.github/workflows/pr-welcome.yml`）

这是你创建 PR 后第一个"迎接"你的机器人。它做了很多贴心的事（第 16-317 行）：

- **识别首次贡献者**：查询你在这个仓库的历史 PR 数量，如果是第一个，自动打上 `first-time-contributor` 标签
- **检查 PR 模板**：验证你是否使用了标准模板（检查是否包含 `## Description`、`## Type of Change` 等）
- **检测中文**：如果 PR 标题包含中文字符，用中英双语回复
- **里程碑庆祝**：如果你提交了第 10/50/100 个 PR，会有特殊的奖牌图标
- **提醒给 Star**：如果你还没给仓库点 Star，它会温柔地提醒你

这个机器人体现了 QwenPaw 社区的开放态度——每一个 PR 都被认真对待，每一个新贡献者都被热情欢迎。

### 2. Pre-commit Checks（`.github/workflows/pre-commit.yml`）

在 CI 环境中重新运行你在本地跑过的 pre-commit 检查（第 27-41 行）。它使用 Python 3.10，安装项目开发依赖，然后执行 `pre-commit run --all-files`。

一个巧妙的设计在第 35-39 行：它不直接让 pre-commit 的退出码决定结果，而是把输出存到日志文件，然后用 `grep` 检查是否包含 "Failed"。这样即使某些检查有问题，也能给出更清晰的错误提示。

### 3. Tests（`.github/workflows/tests.yml`）

这是最核心的 CI Workflow。它的结构像一个金字塔：

**第一层：维护者审批（approval-gate）**

```yaml
approval-gate:
  runs-on: ubuntu-latest
  environment: maintainer-approved
```

这是一个环境保护规则——PR 必须获得维护者的审批才能运行测试。这防止了恶意 PR 浪费 CI 资源。

**第二层：单元测试 + 集成测试**

运行在三个操作系统（Ubuntu、macOS、Windows）和两个 Python 版本（3.10、3.13）的组合上。为什么要跨平台？因为 QwenPaw 的用户可能用任何操作系统，而 Channel 的实现往往依赖平台特定的行为。

注意一个细节（第 59-71 行）：测试之前需要先构建 Console 前端：

```yaml
- name: Build console frontend
  run: |
    cd console && npm ci && npm run build
- name: Copy console build into package
  run: |
    cp -R console/dist/* src/qwenpaw/console/
```

这说明 QwenPaw 的 Python 包内嵌了前端构建产物——测试时需要完整的前后端环境。

**第三层：覆盖率报告**

在 PR 上自动评论覆盖率信息（第 218-225 行），让维护者一眼就能看到改动对覆盖率的影响。

**第四层：汇总**

`test-summary` Job 收集所有结果，给出最终的通过/失败判断（第 227-251 行）。

### 4. Channel Tests（`.github/workflows/channel-tests.yml`）

这是 QwenPaw 最精巧的 CI Workflow，专门为 Channel 代码设计。它有五个阶段：

**阶段一：检测变更范围（detect-changes）**

不盲目运行所有测试——而是先看你改了什么。它通过 `git diff` 分析变更文件：

- 如果你改了 `base.py`、`registry.py` 等核心文件 → 触发所有 Channel 的测试
- 如果你只改了某个具体 Channel → 只跑那个 Channel 的测试

这个设计大大节省了 CI 资源。假设你只是修了一个 Telegram Channel 的 bug，为什么要重跑 Discord 的测试呢？

**阶段二：条件化单元测试（channel-unit-tests）**

根据阶段一检测到的变更范围，动态构建测试矩阵。只有被变更影响到的 Channel 才会运行单元测试。

**阶段三：覆盖率报告（channel-coverage）**

生成受影响 Channel 的覆盖率报告，并在 PR 上评论。这里有一个重要的设计决策（第 243-244 行）：

```yaml
thresholdNew: 55.0
thresholdModified: 55.0
```

新增和修改的代码要求 55% 的覆盖率。但这个阈值是"软卡点"（soft gate）——覆盖率不达标不会阻断 PR，只是给出建议。这是一个务实的权衡：强求高覆盖率会让贡献者望而却步。

**阶段四：契约合规检查（contract-compliance）**

这是唯一的**强卡点**（hard gate）。它做两件事：

1. 运行 `tests/contract/channels/` 下所有契约测试
2. 用 Python 脚本动态检查每个 Channel 是否实现了所有必需方法（`from_env`、`from_config`、`send`、`start`、`stop`、`build_agent_request_from_native`）

如果契约测试失败，PR 被直接阻断（第 409-413 行）：

```bash
if [ "${{ needs.contract-compliance.result }}" = "failure" ]; then
  echo "❌ Contract compliance FAILED - PR blocked"
  exit 1
fi
```

**阶段五：汇总结果**

区分硬卡点和软卡点：
- 契约测试失败 → 阻断 PR（硬卡点）
- 单元测试失败、覆盖率不足 → 只是警告（软卡点）

### 5. NPM Format（`.github/workflows/npm-format.yml`）

如果你改了 `console/` 或 `website/` 目录下的前端代码，这个 Workflow 会检查格式。它分别用 pnpm（website）和 npm（console）运行格式检查。

### 6. PR Under Review（`.github/workflows/pr-under-review.yml`）

当维护者评论或审查你的 PR 时，自动添加 `Under Review` 标签。这个 Workflow 有细致的权限检查（第 68-98 行）：只统计 admin、maintain、write 权限的用户，忽略机器人评论和 PR 作者自己的评论。

## 工程权衡：为什么 CI 设计成这样？

QwenPaw 的 CI 体系体现了几个深思熟虑的权衡。

### 强卡点 vs 软卡点

Channel 测试的设计（`channel-tests.yml`）明确区分了"必须通过"和"建议通过"：

- **硬卡点**：契约测试。如果你的 Channel 没有正确实现 BaseChannel 的接口，PR 直接被阻断。因为接口不兼容意味着你的代码根本无法正常工作。
- **软卡点**：单元测试覆盖率。55% 的建议阈值不阻断 PR。因为强求覆盖率会让简单的贡献（比如修复一个拼写错误）变得不必要地复杂。

这种设计在"保证质量"和"降低贡献门槛"之间找到了平衡。新贡献者不会因为覆盖率差 2% 就被拒之门外，但如果他们的代码连接口都没实现对，CI 会明确阻止。

### 跨平台矩阵的策略

Tests Workflow 在三个操作系统和两个 Python 版本上运行，但不是所有组合都测试。完整的矩阵是 3 x 2 = 6 种组合，但实际只测 4 种（`tests.yml` 第 38-47 行）：

```yaml
matrix:
  python-version: ["3.10", "3.13"]
  os: [ubuntu-latest]
  include:
    - os: macos-latest
      python-version: "3.10"
    - os: windows-latest
      python-version: "3.10"
```

Linux 测两个 Python 版本（3.10 和 3.13），macOS 和 Windows 只测 Python 3.10。这是一种资源优化——完整的 6 组合矩阵会消耗双倍的 CI 时间，而大部分跨版本问题在 Linux 上就能捕获。

### 变更检测的智能取舍

Channel Tests 的 `detect-changes` 阶段不是无脑跑所有测试，而是分析你改了哪些文件，只运行受影响的测试。这大大减少了 CI 时间——从"跑所有 Channel 的测试"变成"只跑你改动的那个 Channel 的测试"。

但有一个例外：如果你改了 `base.py`（所有 Channel 的基类），系统会自动切换到"全量测试"模式（`channel-tests.yml` 第 93-94 行）。因为基类的改动可能影响每一个 Channel。

### Pre-commit 的宽松配置

Pylint 的配置（`.pre-commit-config.yaml` 第 80-113 行）禁用了大量检查项，包括缺失模块文档字符串（C0114）、缺失类文档字符串（C0115）、缺失函数文档字符串（C0116）。这意味着 QwenPaw 选择的是"快速开发优先"而不是"文档完备优先"。你可以写出没有文档字符串的函数而不会触发检查失败。

同时，Black 的行长设置为 79（第 58 行 `args: [ --line-length=79 ]`），比常见的 88 或 120 更严格。79 是 Python PEP 8 的传统行长，在终端分屏阅读时更友好。

## 动手项目：把你的作品整理成一个 PR

从第十五章到第十八章，你依次构建了四个组件：

| 章节 | 组件类型 | 你创建了什么 |
|------|----------|-------------|

### 开发环境准备

在开始动手之前，确保你的开发环境满足以下要求：

| 软件 | 版本 | 说明 |
|------|------|------|
| Python | 3.10 - 3.13 | 核心开发语言 |
| Git | 2.0+ | 版本控制 |
| VS Code | 最新版 | 推荐编辑器 |
| Node.js | 18+ | 前端构建 |

验证安装：

```bash
python --version && git --version && node --version
```

### 选择一个组件

除非你有充足的时间和精力，否则不建议把四个组件塞进一个 PR。选择你最有信心的那一个，单独提交。一个聚焦的 PR 比一个包罗万象的 PR 更容易被接受。

### 添加测试

根据你选择的组件类型，添加对应的测试：

**如果你提交的是 Channel：**

```bash
# 创建契约测试（必需）
touch tests/contract/channels/test_your_channel_contract.py
```

契约测试必须继承 `ChannelContractTest` 基类（定义在 `tests/contract/channels/__init__.py`），实现 `create_instance()` 方法，并确保通过 19 项契约验证点。

```bash
# 可选：创建单元测试（如果内部逻辑复杂）
touch tests/unit/channels/test_your_channel.py
```

**如果你提交的是 Provider：**

参考 `tests/contract/providers/` 和 `tests/unit/providers/` 的现有测试结构。

**如果你提交的是 Skill 或 Tool：**

Skill 通常不需要测试（它是 Markdown 指令，不是代码），但如果你写了辅助脚本，需要为脚本添加测试。

### 实战参考：DailyNews 技能项目

如果你想看一个完整的"从零到 PR"实战案例，可以参考教学材料中的"DailyNews 每日资讯技能"项目。它展示了一个端到端的技能开发流程：

测试部分覆盖了配置验证（合法/非法参数）、去重逻辑、格式化输出和异步执行（mock 外部 API）。提交时遵循 `feat(skills): add DailyNews skill` 的 Conventional Commits 格式，PR 描述包含功能概述、测试清单和本地验证截图。

这个项目的要点是：**用 Pydantic 做配置验证、用 httpx 做异步请求、用 pytest + mock 做单元测试**。这三个模式在 QwenPaw 的技能开发中很常见。
