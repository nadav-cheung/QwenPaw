## 回望：第一卷走过的八站路

在展开地图之前，让我们先回望一下第一卷走过的路。

还记得第八章结尾的那张全景图吗？一条请求从浏览器出发，经过八个站点，最终回到浏览器。八个站点，每一个都是一次跨越：

```
  [1] 浏览器 ─→ HTTP ─→ FastAPI ─→ [2] Runner ─→ [3] Agent ─→ [4] Prompt
                                                                    |
  [8] 浏览器渲染 ←─ SSE ←─ StreamingResponse ←─ TaskTracker ←─ [5] ReAct
                                               |                  |
                                               |            [6] LLM API
                                               |                  |
                                               +───── [7] Tool ←─┘
```

这八个站点涉及了哪些源码目录？让我们按站点清点：

```
  站点               源码目录
  ────────────────────────────────────────────────
  [1] HTTP 入口       app/
  [2] Runner 分发     app/runner/
  [3] Agent 诞生      agents/
  [4] 提示词拼装      agents/
  [5] ReAct 循环      agents/
  [6] LLM 调用        providers/
  [7] 工具执行        agents/tools/
  [8] 响应归途        app/runner/ + app/routers/
```

数一数，八个站点只涉及了四个目录：`app/`、`agents/`、`providers/`、以及少数几个文件。

但是当你打开 `src/qwenpaw/` 这个目录时，会看到十几二十个子文件夹。第一卷只走过了其中四个。剩下的那些是什么？它们之间是什么关系？为什么需要这么多模块？

这一章，我们要做的就像登山者终于爬到了山顶，回头望见来时的蜿蜒小路，同时看见了群山的全貌。我们不再追踪一条请求，而是俯瞰整片代码的大地。

二十个条目。第一卷走过了 `agents/`、`app/`、`providers/` 三个大目录。剩下的十几个文件夹，每一个都有一句话就能说清的职责。但问题是：它们之间是什么关系？谁依赖谁？有没有乱成一团的循环依赖？

这就是本章要回答的问题。

## 术语其实很简单

> **术语：模块化单体（Modular Monolith）**
> 想象一座大楼。它不是好几栋分散的小楼，而是一栋完整的大楼。但大楼内部被划分成了明确的区域：一楼是接待大厅，二楼是办公区，三楼是机房，地下室是仓库。每个区域有自己的功能，但共享同一栋楼的电、水、空调。
>
> QwenPaw 就是一座"模块化单体"——它不是拆成好几个独立部署的微服务，而是一个 Python 包。但这个包内部被划分成了十几个"区域"（模块），每个模块有自己的职责边界，模块之间有清晰的依赖方向。
>
> 好处是简单：一个进程、一份配置、一条命令启动。坏处是所有模块共享同一份内存和进程——如果某个模块出了问题（比如内存泄漏），整个应用都会受影响。

> **术语：依赖方向（Dependency Direction）**
> 想象一条河。水从高处流向低处，不会倒流。代码模块之间的依赖也应该像河水一样，有明确的方向，不能打转。
>
> 如果模块 A 依赖模块 B，模块 B 又依赖模块 A，这就是"循环依赖"——像一条蛇咬住了自己的尾巴。Python 的 import 机制遇到循环依赖会报错，或者导致初始化顺序混乱。所以好的架构会规定：外层模块可以依赖内层，内层不能依赖外层。水往低处流，不往回流。

## 探索：从一条路到一张地图

### 第一步：把每个目录的职责写成一句话

让我们先给每一个目录写一句"名片"——只说它做什么，不说怎么做：

```
  目录              一句话职责
  ──────────────────────────────────────────────────────────────────────────────
  agents/           Agent 的核心：推理、工具、技能、记忆、ACP、任务
  app/              Web 应用骨架：FastAPI 服务、Runner、路由、频道、MCP
  cli/              命令行入口：所有 qwenpaw xxx 子命令的实现
  config/           配置读写：加载 config.json，校验，提供配置对象
  providers/        LLM 提供商：对接 OpenAI、Anthropic、Gemini 等模型 API
  security/         安全守卫：工具调用审查、技能扫描、密钥加密存储
  plugins/          插件系统：发现、加载、注册第三方扩展
  envs/             环境变量：持久化存储和加载 .env 变量
  constant.py       全局常量：工作目录、文件路径、超时值等硬编码配置
  exceptions.py     异常体系：统一错误类型和 LLM 错误转换
  agent_stats/      代理统计：对话数、频道使用量等运营指标
  backup/           备份管理：创建、导入、导出、恢复工作空间备份
  local_models/     本地模型：下载和管理 llama.cpp 等本地推理引擎
  token_usage/      Token 追踪：记录每次 LLM 调用的 token 消耗
  tokenizer/        分词器：文本 token 计数（与模型无关的估算）
  tunnel/           内网穿透：Cloudflare Tunnel 驱动，暴露本地服务
  utils/            共享工具：日志、系统信息、命令执行、遥测
```

十七个模块。每个模块都可以用一句话说清它做什么。

但"一句话职责"还不够。真正理解一个模块，还需要知道它在整个系统中的位置：谁调用它？它调用谁？它能不能独立存在？

### 第二步：依赖方向——谁依赖谁

让我们用实际的 import 关系来画出模块之间的依赖箭头。以下分析基于源码中真实的 `from ..xxx import` 语句：

```
  app/ ─────依赖────→ agents/
  app/ ─────依赖────→ providers/
  app/ ─────依赖────→ security/
  app/ ─────依赖────→ config/
  app/ ─────依赖────→ constant.py
  app/ ─────依赖────→ utils/
  app/ ─────依赖────→ envs/
  app/ ─────依赖────→ local_models/
  app/ ─────依赖────→ backup/
  app/ ─────依赖────→ plugins/
  app/ ─────依赖────→ agent_stats/
  app/ ─────依赖────→ token_usage/

  agents/ ──依赖────→ providers/   （通过 model_factory 间接使用）
  agents/ ──依赖────→ constant.py
  agents/ ──依赖────→ security/    （tool_guard_mixin 审查工具调用）

  providers/ ─依赖──→ constant.py
  providers/ ─依赖──→ config/
  providers/ ─依赖──→ security/    （secret_store 读取 API 密钥）
  providers/ ─依赖──→ exceptions.py

  cli/ ─────依赖────→ app/
  cli/ ─────依赖────→ agents/
  cli/ ─────依赖────→ config/
  cli/ ─────依赖────→ providers/
  cli/ ─────依赖────→ constant.py
  cli/ ─────依赖────→ utils/

  security/ ─依赖──→ constant.py

  config/ ──依赖────→ constant.py

  utils/ ───依赖────→ constant.py
```

注意一个关键模式：`constant.py` 出现在几乎所有依赖链的末端。它是"最底层"的模块——只被依赖，不依赖任何人。这是因为 `constant.py` 只定义常量，不做任何逻辑。

再看一个关键模式：没有任何一个箭头是反向的。`agents/` 不依赖 `app/`，`providers/` 不依赖 `agents/`，`config/` 不依赖 `cli/`。依赖关系像河水一样，只往一个方向流。

### 第三步：三层架构——外层、中间层、内层

把上面的依赖关系整理一下，就能看到三层清晰的架构：

```
  ┌─────────────────────────────────────────────────────────────┐
  │                      外层（Entry Points）                     │
  │                                                             │
  │    ┌───────┐    ┌──────────────────────────────────────┐    │
  │    │ cli/  │    │              app/                      │    │
  │    │ 命令行 │    │  FastAPI + Runner + 路由 + 频道 + MCP   │    │
  │    └───┬───┘    └──────────┬───────────────────────────┘    │
  │        │                   │                                │
  │        │  用户从终端        │  用户从浏览器                    │
  │        │  或脚本启动        │  或 API 调用                    │
  │        │                   │                                │
  └────────┼───────────────────┼────────────────────────────────┘
           │                   │
           v                   v
  ┌─────────────────────────────────────────────────────────────┐
  │                    中间层（Domain Logic）                      │
  │                                                             │
  │  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐  │
  │  │ agents/  │  │providers/│  │security/ │  │ plugins/ │  │
  │  │ Agent    │  │ LLM      │  │ 安全守卫  │  │ 插件系统  │  │
  │  │ 推理+工具 │  │ 提供商    │  │          │  │          │  │
  │  └────┬─────┘  └────┬─────┘  └────┬─────┘  └────┬─────┘  │
  │       │              │              │              │        │
  └───────┼──────────────┼──────────────┼──────────────┼────────┘
          │              │              │              │
          v              v              v              v
  ┌─────────────────────────────────────────────────────────────┐
  │                    内层（Foundation）                          │
  │                                                             │
  │  ┌────────┐ ┌────────┐ ┌────────┐ ┌──────┐ ┌───────────┐  │
  │  │config/ │ │ envs/  │ │ utils/ │ │backup│ │agent_stats│  │
  │  └───┬────┘ └───┬────┘ └───┬────┘ └──┬───┘ └─────┬─────┘  │
  │      │          │          │         │           │          │
  │      v          v          v         v           v          │
  │  ┌─────────────────────────────────────────────────────┐   │
  │  │           constant.py  +  exceptions.py              │   │
  │  │           全局常量        统一异常                       │   │
  │  └─────────────────────────────────────────────────────┘   │
  │                                                             │
  └─────────────────────────────────────────────────────────────┘
```

这就是经典的"洋葱架构"（Onion Architecture）。它有三条核心规则：

**规则一：外层可以依赖内层，内层不能依赖外层。**

`cli/` 可以调用 `agents/` 的代码，但 `agents/` 绝不会调用 `cli/` 的代码。`app/` 可以使用 `providers/`，但 `providers/` 不知道 `app/` 的存在。水往低处流。

**规则二：内层越稳定越好。**

`constant.py` 和 `exceptions.py` 在最核心的位置。它们几乎不会改变——常量名可以变，但"有一个集中存放常量的文件"这件事不会变。内层的稳定，是外层能够自由演化的前提。

**规则三：同一层内的模块尽量不互相依赖。**

`agents/` 和 `providers/` 在同一层（中间层）。`agents/` 对 `providers/` 的依赖是有限的——它通过 `model_factory` 间接创建模型实例，而不是直接操作 `ProviderManager`。`security/` 和 `plugins/` 之间完全没有依赖。同层模块的独立性，使得任何一个模块都可以独立测试、独立修改。

### 第六步：几个值得注意的跨层关系

全景地图上，有几个依赖关系值得单独拎出来说：

**agents/ 依赖 security/——为什么？**

`agents/` 中有一个 `tool_guard_mixin.py` 文件。它的职责是：在大模型决定调用某个工具之后、实际执行之前，让安全守卫审查一下"这个调用是否安全"。比如，大模型试图执行一条 `rm -rf /` 的 shell 命令，安全守卫会拦截并要求用户确认。

这个依赖是合理的：Agent 是"行动者"，security 是"审查者"。行动者在行动前需要咨询审查者。它们在同一层，但 security 不依赖 agents——审查者不需要知道行动者是谁。

**providers/ 依赖 security/——为什么？**

`providers/` 中的 `provider_manager.py` 需要从 `security/secret_store.py` 中读取 API 密钥。密钥不是明文存储的——它们被加密存储在磁盘上，使用 Fernet 对称加密，密钥由操作系统的 keychain 管理。

这个依赖也是合理的：Provider 需要密钥才能调用 API，密钥由安全模块管理。

**cli/ 依赖几乎所有模块——为什么？**

`cli/` 是命令行入口。`qwenpaw init` 需要 `config/`，`qwenpaw app start` 需要 `app/`，`qwenpaw providers list` 需要 `providers/`，`qwenpaw skills install` 需要 `agents/skills_manager`。

CLI 是"最外层"的入口——它像一个大管家，可以根据用户的命令调度任意一个内部模块。所以它依赖几乎所有模块是合理的。但关键是：没有模块依赖 CLI。CLI 是"消费者"，不是"提供者"。

**constant.py 被所有人依赖——为什么？**

`constant.py` 定义了 `WORKING_DIR`、`PROJECT_NAME`、`CONFIG_FILE` 等全局常量。它被几乎所有模块 import。这不是设计缺陷，而是有意为之：全局常量需要一个唯一的"真相来源"（single source of truth）。如果每个模块自己定义工作目录的路径，就会出现不一致。

而且 `constant.py` 非常稳定——它只是定义变量，没有任何逻辑。改变全局常量的值不会影响依赖它的模块（只要类型不变）。所以它适合放在最内层。

### 第七步：第二卷要探索的模块

第一卷走过了 `agents/`、`app/`、`providers/` 的主要路径。第二卷将深入以下区域：

## 工程权衡：为什么这样设计？

### 为什么用模块化单体，而不是微服务？

把 QwenPaw 拆成十几个独立的微服务（一个 Agent 服务、一个 Provider 服务、一个 Security 服务......），每个独立部署，听起来很"现代"。为什么 QwenPaw 没有这样做？

**因为复杂度不对等。** 微服务引入的运维复杂度（服务发现、网络通信、数据一致性、分布式调试）远大于它解决的问题。QwenPaw 是一个本地优先的应用——它跑在用户的电脑上，甚至跑在树莓派上。用户不需要 Kubernetes 集群来运行一个聊天机器人。

**因为模块边界已经通过代码结构划清了。** `agents/` 不依赖 `app/`，`providers/` 不依赖 `agents/`——这些边界不是靠网络隔离来保证的，而是靠代码结构和 import 规则来保证的。模块化单体享受了"逻辑隔离"的好处，又不需要支付"物理隔离"的代价。

**但这个选择也有代价。** 所有模块共享同一个进程。如果 `providers/` 中的某个 Provider 实现引发了未捕获的异常，整个进程都会崩溃。如果某个模块有内存泄漏，整个应用的内存都会增长。微服务在故障隔离方面天然优于单体。

QwenPaw 的选择反映了它的定位：一个轻量的、本地部署的 AI Agent 平台。如果它是一个需要支撑百万级并发用户的云服务，微服务可能是更好的选择。

### 为什么禁止循环依赖？

循环依赖（A import B，B import A）在 Python 中会导致两种问题：

**初始化顺序问题。** Python 在执行 `import A` 时，如果 A 的顶层代码 import 了 B，而 B 的顶层代码又 import 了 A，Python 会在 B 中看到 A 的"半初始化状态"——A 中在 `import B` 语句之后定义的变量和函数都不存在。这会导致 `AttributeError` 或 `None` 值。

**认知负担问题。** 两个互相依赖的模块，你无法单独理解其中任何一个。修改 A 可能影响 B，修改 B 又可能影响 A。这会让代码的维护成本急剧上升。

QwenPaw 通过洋葱架构来避免循环依赖：依赖只能从外向内。这条规则简单、明确、容易验证——你只需要在代码审查时检查 import 语句的方向。

### 为什么内层要放最稳定的东西？

洋葱架构的核心思想是：越往内层，代码变化越慢。

`constant.py` 定义了 `WORKING_DIR = ~/.qwenpaw` 这样的常量。这个值可能在一年内都不会变。`config/` 定义了配置文件的数据结构——配置的格式可能几周调整一次。而 `agents/` 中的 ReAct 循环逻辑可能每天都有人改进。

把最稳定的东西放在最内层，意味着：
- 内层模块的接口（被别人调用的函数签名）几乎不变
- 外层模块可以自由演化，只要遵守内层的接口就行
- 测试时可以 mock 外层，只测内层；也可以用真实的内层，只测外层

这就是"依赖方向决定稳定性方向"的原则。

## 小结

这一章，我们从第一卷走过的那条"U 形线"上抬起头来，看见了整片源码的大地。

三个核心结论：

**第一，QwenPaw 是一个模块化单体。** 十几个模块，共享一个进程，但通过代码结构划清了边界。不是微服务，也不是一团乱麻。

**第二，依赖方向是从外向内的。** 外层（cli、app）可以调用中间层（agents、providers、security），中间层可以调用内层（config、constant），但反过来不行。没有循环依赖。

**第三，越内层越稳定。** `constant.py` 和 `exceptions.py` 在最核心的位置，几乎不会变。外层模块可以自由演化，只要遵守内层的接口。

这三条规则——模块化单体、单向依赖、内层稳定——是理解 QwenPaw（以及大多数设计良好的 Python 项目）的钥匙。
