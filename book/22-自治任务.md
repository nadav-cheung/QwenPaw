`[卷四·纵深·第三章]` -- 上一章我们拆解了记忆系统——Agent 怎么记住你昨天说过的话、怎么整理长期知识、怎么在你沉默时主动出击。这些能力让 Agent 变得越来越像一个"贴心的助手"。

但助手再贴心，本质上还是被动的：你问一句，它答一句。如果你说"帮我实现一个完整的用户认证系统，包含 JWT、数据库迁移和单元测试"，它可能回答得很好，但在普通的对话模式下，它只是一次性给出方案或代码。方案合不合理？代码跑不跑得通？它不知道——因为对话到此就结束了。

如果你想要的是：Agent 自己分析项目结构，自己把任务拆成若干小步骤，自己一步一步实现，每做完一步自己验证，直到全部完成——这就是 **Mission 模式**。

这一章，我们走进 QwenPaw 的 `src/qwenpaw/agents/mission/` 目录，看看 Agent 怎么从"被动回答"变成"主动干活"。

---

## 问题：给 Agent 一个复杂任务，它怎么自己分步骤完成？

想象这个场景：

```
你：「帮我给项目加一个通知系统，包含数据库表、后端服务、
     前端铃铛图标和通知面板。」

普通对话模式：
  Agent：（一次性吐出一大段代码）
  你：（复制粘贴，发现跑不通，回去问 Agent）
  Agent：（修改代码）
  你：（又跑不通...循环往复）
  ── 耗时 2 小时，来回 10 轮 ──

Mission 模式：
  Agent：「我来拆解这个任务...」
         1. US-001: 创建通知表和迁移
         2. US-002: 实现通知服务
         3. US-003: 添加铃铛图标
         4. US-004: 创建通知面板
         5. US-005: 标记已读功能
  你：「确认。」
  Agent：（自己派 Worker 干活，自己验证，循环迭代）
         ✅ US-001 通过
         ✅ US-002 通过
         ✅ US-003 通过
         ...
  ── 耗时 30 分钟，你来去自由 ──
```

Mission 模式的核心问题是：**怎么让 Agent 像一个项目经理一样，自己规划、派工、验收，而且不会失控？** 具体来说：

- 普通对话和 Mission 模式有什么区别？为什么不能在普通对话里递归调用 Agent？
- Agent 怎么把一个大任务拆成可以独立完成的小任务？
- 拆完之后，怎么派给"Worker"去做？Worker 做完怎么验证？
- Agent 自己跑起来了，会不会失控？怎么设安全边界？
- 用户在哪个环节介入？什么时候可以放手让 Agent 自己跑？

这五个问题，对应了 Mission 模式的五个设计维度。

---

## 术语其实很简单

> **术语：Mission 模式（Mission Mode）**
>
> 想象你是一个项目经理。平时你亲自写代码（普通对话模式），但遇到一个大项目时，你会先写一份 PRD（产品需求文档），然后按模块分派给不同的开发者（Worker），每个开发者做完后你安排测试人员（Verifier）验收，全部通过后项目结束。Mission 模式就是让 Agent 进入这种"项目经理"角色——它不再亲自动手写代码，而是规划、派工、验收。

> **术语：PRD（Product Requirements Document）**
>
> 想象建筑开工前的蓝图。你不会让工人直接砌墙——先画好图纸，标注哪些墙先砌、哪些后砌、每面墙的验收标准。Mission 模式的 PRD 存在 `prd.json` 文件中，它是一份结构化的任务清单：每个任务（Story）有 ID、标题、描述、验收标准和优先级。Agent 按照 PRD 的顺序逐步执行。

> **术语：Worker / Verifier**
>
> 想象工厂流水线上的工人和质量检验员。Worker 是被派出去干活的独立 Agent 会话——它拿到一个 Story 的描述，独立完成编码。Verifier 是另一个独立会话——它不写代码，专门挑毛病：跑测试、检查边界条件、尝试破坏。Worker 和 Verifier 都是"一次性"的，没有记忆，所有上下文都通过提示词传递。

> **术语：人机协作（Human-in-the-Loop）**
>
> 想象自动驾驶的级别。L0 是完全手动，L5 是完全自动。Mission 模式不是 L5——Agent 在关键节点会停下来请你确认：PRD 写好后等你拍板，某个 Story 三次验证失败后请你介入。你是方向盘后面的那个人，Agent 是你的自动驾驶系统。

## 探索：Mission 模式 vs 普通对话——从"问答"到"自治"

在深入代码之前，先理解 Mission 模式和普通对话的根本区别。

### 普通对话：单轮 ReAct 循环

前面章节拆解过 ReAct 循环：Agent 接收一条消息，进入"思考→行动→观察"的循环，直到产出最终回复。这个循环有几个特点：

1. **单次执行**：Agent 回复一条消息后，循环结束，等待用户的下一条消息。
2. **工具全部可用**：Agent 可以读文件、写文件、执行命令——所有能力都向它开放。
3. **无持久计划**：Agent 没有结构化的"待办清单"，所有计划都在 Context 中隐含。

这意味着普通对话适合"一次性的、单一的、不太复杂"的任务。比如"帮我写一个函数"或"解释这段代码"。

### Mission 模式：双阶段自治引擎

Mission 模式彻底改变了执行模型。打开 `mission_runner.py` 第 4-29 行的模块文档：

```
Phase 1 — PRD generation: Agent 探索代码库并生成 prd.json。
           所有工具可用。Phase 结束后交还用户确认。

Phase 2 — Execution loop: 用户确认后，进入代码控制的迭代循环。
           实现工具被禁用（Agent 物理上无法执行 npm/pip 等命令）。
           每次迭代：
           a. Agent 运行一轮
           b. 引擎读取 prd.json，检查每个 story 的 passes 状态
           c. 全部通过 → 完成。否则注入继续消息，回到 (a)
```

两个关键区别：

1. **两阶段设计**：Phase 1（规划）和 Phase 2（执行）是严格分离的。用户在中间确认——这是人机协作的关键锚点。
2. **工具限制**：Phase 2 中，实现类工具（`edit_file`、`browser_use`、`desktop_screenshot`）被物理禁用。Agent 无法自己写代码——它**必须**通过 Worker 来实现。这不是"建议"，是"强制"。

### 触发入口

Mission 模式的触发入口在 `handler.py`。第 35 行定义了触发命令：

```python
MISSION_COMMANDS = frozenset({"/mission"})
```

用户在对话中输入 `/mission <任务描述>` 时，Runner 会识别这个命令，调用 `maybe_handle_mission_command()`（定义在 `src/qwenpaw/app/runner/mission_dispatch.py` 第 33-71 行），进入 Mission 流程。

`is_mission_command()` 函数（handler.py 第 43-48 行）做了简单的字符串匹配——取用户输入的第一个 token，判断是否为 `/mission`。

## 探索：Phase 1——从模糊描述到结构化 PRD

Mission 模式的第一个阶段是**规划**。Agent 接收用户的任务描述，探索代码库，然后生成一份结构化的 PRD。

### 创建 Mission 环境

触发 Mission 命令后，`handle_mission_command()`（handler.py 第 101-280 行）做的第一件事是**创建隔离的工作环境**。

第 222-242 行：

```python
loop_dir = create_loop_dir(workspace_dir)
write_task_md(loop_dir, task_text)
init_progress_txt(loop_dir)

git_ctx = await detect_git_context(workspace_dir)

loop_config: dict[str, Any] = {
    "git_installed": git_ctx["git_installed"],
    "is_git_repo": git_ctx["is_git_repo"],
    "current_phase": "prd_generation",
    "session_id": session_id,
    ...
}
write_loop_config(loop_dir, loop_config)
```

每个 Mission 会在 workspace 下的 `missions/` 目录创建一个独立子目录，命名格式为 `mission-YYYYMMDD-HHMMSS`。打开 `state.py` 第 134-140 行：

```python
def create_loop_dir(workspace_dir: Path) -> Path:
    loop_id = f"mission-{_ts()}"
    loop_dir = workspace_dir / "missions" / loop_id
    loop_dir.mkdir(parents=True, exist_ok=True)
    return loop_dir
```

每个 Mission 目录包含四个文件：

```
missions/mission-20260510-143025/
├── loop_config.json   ← 环境元数据（git 状态、路径、当前阶段）
├── prd.json           ← 结构化任务清单（Agent 生成、Worker 更新）
├── progress.txt       ← 迭代日志（Worker 追加学习记录）
└── task.md            ← 原始任务描述（只读，不可修改）
```

为什么要隔离？因为多个 Mission 可能同时运行，每个 Worker 都在自己的 loop_dir 里工作，互不干扰。这就像给每个项目团队分配了独立的会议室。

### Git 环境探测

在创建环境的同时，`state.py` 的 `detect_git_context()` 函数（第 57-128 行）会异步探测 Git 环境。它做了三件事：

1. 检查 `git` 是否安装（`shutil.which("git")`）。
2. 检查 workspace 是否在一个 Git 仓库内（`git rev-parse --is-inside-work-tree`）。
3. 如果是仓库，并发获取仓库根目录、当前分支、默认分支（main/master）。

这些信息会写入 `loop_config.json`，在后续阶段决定 Worker 是否使用 Git 来提交代码。`_git_cmd()`（第 38-55 行）使用了 `asyncio.create_subprocess_exec` 异步执行 Git 命令，超时设为 10 秒——不会因为 Git 操作卡死整个流程。

### Master Prompt：给 Agent 的"项目经理手册"

Phase 1 的核心是 `build_master_prompt()`（prompts.py 第 828-872 行）。它渲染了 `MASTER_PROMPT` 模板（第 14-473 行），这是一份长达 400 多行的"项目经理手册"，告诉 Agent：

**你的角色是 CONTROLLER（控制器），不是 IMPLEMENTER（实现者）。** 第 19-33 行反复强调：

```
YOUR ROLE: CONTROLLER ONLY — NOT AN IMPLEMENTER

What you MUST NOT do:
- Run implementation commands (npm, pip, cargo, make, etc.)
- Create/edit project source files
- Install dependencies
- Run tests/linters yourself

If you catch yourself about to do implementation work — STOP immediately
and dispatch a worker instead.
```

为什么要在提示词中反复强调？因为大语言模型有"顺手就做"的倾向——当你问它"帮我写个函数"时，它会直接写代码。在 Mission 模式下，这种行为是危险的：Controller 如果自己写代码，就没有独立的 Worker-Verifier 验证环节，质量无法保证。

提示词模板通过参数化渲染适应不同的 Git 环境。`_build_git_sections()` 函数（prompts.py 第 590-674 行）有三级降级策略：

```
Level 1: Git 已安装且在仓库内 → 完整的分支管理、提交指令
Level 2: Git 已安装但不在仓库内 → 提示 Worker 先 git init
Level 3: Git 未安装 → 提示 Worker 尝试安装，不行就跳过
```

### PRD 的结构：Story 是基本单位

PRD 的核心是 `userStories` 数组。每个 Story 代表一个**可以在一次 Worker 会话中完成的最小任务单元**。prompts.py 第 180-205 行的"Story size"规则是这个设计的关键：

```
每个 Story 必须能在一个 Worker 迭代（一个 Context 窗口）内完成。
Worker 是全新的会话，没有记忆。如果 Story 太大，Worker 的 Context
会溢出，产出损坏的输出。

合适的 Story 大小：
- 添加一个数据库列和迁移
- 给已有页面添加一个 UI 组件
- 实现一个 API 端点

太大的 Story（需要拆分）：
- "构建整个仪表盘" → 拆成 schema、查询、UI、过滤器
- "添加认证" → 拆成 schema、中间件、登录 UI、会话管理
```

每条 Story 有严格的字段要求（mission_runner.py 第 113-119 行）：

```python
_REQUIRED_STORY_FIELDS = {
    "id",                  # US-001, US-002, ...
    "title",               # 简短标题
    "description",         # 作为 <角色>，我想要 <功能>，以便 <价值>
    "acceptanceCriteria",  # 可验证的验收标准列表
    "priority",            # 优先级数字（相同 = 可并行）
}
```

### PRD 验证：严格的结构校验

Agent 生成的 PRD 不一定靠谱。`mission_runner.py` 第 129-156 行的 `validate_prd()` 会对 PRD 做严格校验：

```python
def validate_prd(prd: dict[str, Any]) -> list[str]:
    problems: list[str] = []
    if not isinstance(prd, dict):
        return ["prd.json is not a JSON object"]
    if "userStories" not in prd:
        problems.append("Missing top-level 'userStories' array")
    for i, story in enumerate(stories):
        missing = _REQUIRED_STORY_FIELDS - set(story.keys())
        if missing:
            problems.append(f"userStories[{i}] missing fields: ...")
    return problems
```

如果 PRD 不合法，引擎不会直接报错退出，而是自动注入一条修正提示词（第 259-297 行的 `_PRD_FIX_PROMPT`），让 Agent 按正确格式重写。最多尝试 2 次（`_MAX_PRD_FIX_ATTEMPTS = 2`）。这体现了 Mission 模式的设计哲学：**能自动修复的就不打扰用户。**

### 人机协作的锚点：用户确认

Phase 1 结束时，Agent 会向用户报告 PRD 的内容，然后**停下来等用户确认**。这不是代码控制的——是提示词要求的。prompts.py 第 292-306 行：

```
写完 prd.json 后，向用户报告：
- PRD 摘要（story 数量、优先级层级）
- 展示前 2-3 个 Story 作为示例
- 请用户确认

当用户确认时：
1. 更新 loop_config.json，设置 current_phase 为 "execution_confirmed"
2. 系统会检测到这个信号，自动过渡到 Phase 2
```

这个"确认锚点"是 Mission 模式最重要的安全边界。在 Agent 开始自动执行之前，你有机会：

- 检查任务拆分是否合理。
- 调整优先级和顺序。
- 删掉不需要的 Story。
- 补充遗漏的验收标准。

## 探索：Phase 2——迭代执行的自治引擎

用户确认 PRD 后，系统自动进入 Phase 2。这是 Mission 模式的核心——一个代码控制的迭代循环。

### 工具限制：物理隔离 Controller 和 Worker

Phase 2 的第一条规则是：**Controller（主 Agent）不能自己写代码。** `set_phase2_tool_restrictions()` 函数（mission_runner.py 第 187-195 行）物理禁用了实现类工具：

```python
def set_phase2_tool_restrictions(agent: Any) -> None:
    migrate_tools_to_group(agent)
    agent.toolkit.update_tool_groups([MISSION_IMPL_GROUP], active=False)
```

被禁用的工具列表在第 103-109 行定义：

```python
IMPLEMENTATION_TOOLS = frozenset({
    "edit_file",
    "browser_use",
    "desktop_screenshot",
})
```

注意 `execute_shell_command` 和 `write_file` 没有被禁用——因为 Controller 需要用 `execute_shell_command` 来派发 Worker（`qwenpaw agents chat --background`），需要 `write_file` 来更新 `prd.json` 和提示词文件。

这个设计的关键洞见是：**不是靠提示词"建议"Agent 不要写代码，而是通过工具系统物理限制它。** 提示词可以被忽略，但工具不存在就无法调用。这是"安全即架构"的思路——不信任 Agent 的自律性，而从机制上保证安全。

### 迭代循环：代码驱动的状态机

Phase 2 的执行引擎在 `run_mission_phase2()` 函数（mission_runner.py 第 470-625 行）。它不是一个 Agent 自己决定的循环，而是**代码控制的状态机**：

```
for iteration in range(1, max_iterations + 1):
    # 1. 让 Agent 运行一轮（派工、监控、验收）
    async for msg in agent(msgs):
        yield msg

    # 2. 代码层面检查 prd.json
    prd = read_prd(loop_dir)
    stories = prd.get("userStories", [])

    # 3. 全部通过？
    if all(s.get("passes") for s in stories):
        yield 完成消息
        return

    # 4. 没全部通过 → 注入继续消息
    continuation = _remaining_summary(prd, iteration, max_iterations)
    msgs = [新的继续消息]
```

注意第 555-556 行的 `prd = read_prd(loop_dir)`——这是从磁盘文件读取的，不是从 Agent 的 Context 中获取。这意味着**完成状态的判定权在代码手中**，Agent 无法伪造"全部通过"的结果——它必须真的把 `prd.json` 里的每个 Story 的 `passes` 字段设为 `true`，而只有 Verifier 才能触发这个更新。

### 迭代注入：不让 Agent "停下来"

普通对话中，Agent 回复一条消息后就停了。Phase 2 不能让 Agent 停——否则每轮迭代都需要用户手动发送"继续"。解决方案在第 592-600 行：如果还有未完成的 Story，代码自动注入一条"继续消息"：

```python
continuation = _remaining_summary(prd, iteration, max_iterations)
msgs = [
    Msg(name="user", role="user",
        content=[TextBlock(type="text", text=continuation)])
]
```

`_remaining_summary()` 函数（第 233-253 行）生成的消息包含了当前进度、剩余 Story 列表，以及明确的指令："继续 Worker → Verifier 流水线"。

### 最大迭代次数：安全阀

循环有上限：`max_iterations`，默认 20，最大 100。如果达到上限，循环终止并报告进度（第 602-622 行）。用户可以通过 `--max-iterations` 参数调整。

这个安全阀是必要的——如果某个 Story 反复验证失败，没有上限的循环会无限消耗 token 和时间。到达上限后，用户可以查看进度、修正问题、然后启动新的 Mission。

### Phase 1 到 Phase 2 的自动过渡

一个精妙的细节是：Phase 1 和 Phase 2 之间有**自动过渡机制**。在 `run_mission_phase1()` 中（第 324-372 行），每次 Agent 运行完一轮后，代码会检查 `loop_config.json` 的 `current_phase` 字段：

```python
cfg = read_loop_config(loop_dir)
if cfg.get("current_phase") == "execution_confirmed":
    # 验证 PRD
    prd = read_prd(loop_dir)
    problems = validate_prd(prd)
    if not problems:
        # 自动进入 Phase 2
        async for msg, last in run_mission_phase2(...):
            yield msg, last
        return
```

这意味着用户确认 PRD 后，Agent 会更新 `loop_config.json`，系统检测到变化，**无缝过渡**到 Phase 2——用户不需要输入任何命令，整个流程是连续的。

### Session 绑定：多 Mission 并发不混乱

`detect_active_mission_phase()`（mission_dispatch.py 第 74-116 行）通过 `session_id` 查找活跃的 Mission。`get_active_loop_dir()`（state.py 第 206-249 行）扫描最近 20 个 Mission 目录，匹配当前 session：

```python
for loop_dir in dirs[:20]:
    cfg = read_loop_config(loop_dir)
    loop_session = cfg.get("session_id", "")
    if loop_session == session_id:
        return loop_dir
```

这确保了不同 session 的 Mission 互不干扰。你在终端 A 开了一个 Mission，终端 B 不会被误捕获。

## 探索：Worker 和 Verifier——流水线上的工人和质检员

Phase 2 中，Controller 不自己干活，而是派 Worker 和 Verifier 执行。它们的关系像一条流水线：

```
Controller ──→ Worker（实现代码）──→ Verifier（验证代码）──→ 更新 prd.json
   │                                                            │
   └──────────────── 迭代循环 ←────────────────────────────────┘
```

### Worker：一次性实现者

Worker 的提示词模板在 `WORKER_PROMPT_TEMPLATE`（prompts.py 第 479-582 行）。Worker 的核心特征：

1. **无记忆**：每个 Worker 是一个全新的 Agent 会话。第 481 行明确告知："这是一个全新的会话，你对之前的工作没有记忆。"
2. **单任务**：一个 Worker 只负责一个 Story。第 505 行："实现这个**单独的 Story**。"
3. **自我验证**：Worker 必须自己跑质量检查（lint、test、typecheck），确保代码可用。
4. **不判分**：Worker **不能**设置 `passes: true`。第 511 行强调："不要自己在 prd.json 中设置 passes: true。一个独立的验证 Agent 会决定是否通过。"

Worker 的产出除了代码变更外，还会**追加学习记录到 progress.txt**（prompts.py 第 518-527 行）：

```
## [日期/时间] - [Story ID]
- 实现了什么
- 修改了哪些文件
- **给未来迭代的学习：**
  - 发现的模式（如"这个代码库用 X 处理 Y"）
  - 遇到的坑（如"改 W 时别忘了更新 Z"）
```

这些学习记录会被后续的 Worker 读取（prompts.py 第 497-499 行："在写任何代码之前，**先读 Codebase Patterns 部分**"）。这是一个简单但有效的**跨迭代知识传递**机制——每个 Worker 虽然没有记忆，但可以通过 progress.txt 继承前人的经验。

### Verifier：对抗式验证者

Verifier 的提示词模板在 `VERIFIER_PROMPT_TEMPLATE`（prompts.py 第 682-801 行）。它被设计为一个"专门找茬的质检员"：

第 683-684 行定义了它的使命：

```
你的工作不是确认实现能工作——而是**尝试破坏它**。
```

提示词特别警告了两种常见的"假验证"模式（第 690-695 行）：

1. **验证回避**：读代码，口头叙述"看起来没问题"，然后写 PASS，但实际上什么都没运行。
2. **被前 80% 蒙蔽**：看到一个漂亮的 UI 或通过的测试套件，就不再深究——没注意到按钮一半是坏的、刷新后状态丢失、后端在异常输入时崩溃。

Verifier 的输出必须是结构化的（第 762-799 行）：每个检查都要附带**实际运行的命令**和**实际的终端输出**。没有命令的检查不算 PASS——是 SKIP。最后必须以 `VERDICT: PASS`、`VERDICT: FAIL` 或 `VERDICT: PARTIAL` 结尾，这些关键字会被 Controller 解析。

### 并行派工：同优先级的 Story 同时执行

prompts.py 第 209-220 行定义了并行规则：

```
相同 priority 值的 Story 是独立的，必须并行派工。
不同 priority 值的 Story 有依赖关系，按顺序执行。

例：
  Priority 1: [US-001, US-002] → 同时派工
  Priority 2: [US-003]         → 等上一批完成后派工
  Priority 3: [US-004, US-005] → 等上一批完成后同时派工
```

为什么能并行？因为同优先级的 Story 之间没有依赖关系——比如"创建数据库表"和"添加配置文件"可以同时做。而"实现 API 端点"依赖"数据库表已创建"，所以排在后面。

Controller 通过 `qwenpaw agents chat --background` 命令派工（prompts.py 第 363-375 行）。`--background` 标志让 Worker 在后台独立运行，Controller 用 `--task-id` 轮询状态。

## 探索：安全边界——怎么防止 Agent 失控？

自治系统的最大风险是**失控**。Agent 如果"跑飞了"——无限循环、胡乱删文件、消耗大量 token——后果很严重。QwenPaw 通过多层机制来防范这个风险。

### 第一层：工具物理隔离

前面提到的 `set_phase2_tool_restrictions()` 是最硬的安全边界。Controller 在 Phase 2 中**物理上无法**执行实现类操作。这就像你把经理的代码编辑器密码改了——他想自己写也写不了。

`migrate_tools_to_group()`（mission_runner.py 第 162-184 行）把实现工具移到一个专用分组，然后禁用这个分组：

```python
toolkit.create_tool_group(MISSION_IMPL_GROUP, active=True)
for tool_name in IMPLEMENTATION_TOOLS:
    if tool_name in toolkit.tools:
        toolkit.tools[tool_name].group = MISSION_IMPL_GROUP

# Phase 2 开始时禁用
agent.toolkit.update_tool_groups([MISSION_IMPL_GROUP], active=False)
```

Phase 2 结束后，`restore_tools()`（第 198-202 行）会恢复这些工具。整个限制是临时性的，不影响 Agent 的正常对话能力。

### 第二层：迭代上限

`max_iterations` 参数（默认 20，范围 1-100）是硬性上限。handler.py 第 38-40 行：

```python
_DEFAULT_MAX_ITERATIONS = 20
_MIN_MAX_ITERATIONS = 1
_MAX_MAX_ITERATIONS = 100
```

超出范围的值会被自动 clamp（第 82-96 行）。这保证了无论 Agent 做了什么，循环最终会终止。

### 第三层：人机协作锚点

- **PRD 确认**：Phase 1 结束后，Agent 不会自动进入 Phase 2——必须等用户确认。
- **Story 三次失败后介入**：prompts.py 第 432 行规定："如果同一个 Story 重试 3 次都失败，停下来问用户。"
- **完成汇报**：每个 batch 完成后，Agent 都会向用户报告进度。

### 第四层：Worker 的安全栅栏

Worker 通过 `--background` 模式运行。在 runner.py 第 557-558 行，Mission 模式会绕过工具守卫（`_headless_tool_guard: false`），这意味着 Worker 可以执行命令而不需要用户手动批准。这也是为什么 Mission 模式的帮助信息（handler.py 第 186-193 行）会明确警告：

```
⚠️ 安全警告：
- Worker Agent 绕过安全守卫（通过 --background 自动禁用）
- 敏感操作（shell、文件写入）无需审批即执行
- 只在受信任的代码库中使用
```

### 第五层：状态文件可审计

所有状态都存在磁盘文件中（`prd.json`、`progress.txt`、`loop_config.json`）。任何时候你都可以查看这些文件，了解 Agent 在做什么、做到了哪一步。这是"黑盒自治"和"白盒自治"的区别——QwenPaw 的 Mission 模式是白盒的。

## 探索：人机协作——你不是旁观者

Mission 模式不是"按下按钮就走开"的全自动模式。用户在整个流程中有多个介入点。

### 介入点一：任务描述

`/mission <任务描述>` 中的描述直接决定了 PRD 的质量。如果描述太模糊（"做个好用的东西"），Agent 拆解的 Story 可能南辕北辙。handler.py 第 174-193 行对描述做了基本的校验：

```python
if not task_text or len(task_text.strip()) < 5:
    return "**Mission Mode**\n\nUsage:\n..."
```

描述必须至少 5 个字符。而且第 196-219 行会检测"元问题"——如果你输入的是"Mission 是什么"而不是真正的任务描述，系统会引导你正确使用。

### 介入点二：PRD 审查和修改

Agent 生成 PRD 后，你可以：

- 要求修改 Story 的顺序。
- 合并或拆分某些 Story。
- 补充或修改验收标准。
- 删掉不需要的 Story。

这些修改是通过自然语言对话完成的——你不需要直接编辑 JSON 文件。

### 介入点三：Phase 2 跟踪

Phase 2 执行过程中，你可以随时查看进度：

```
/mission status    ← 查看当前 Mission 的进度
/mission list      ← 列出所有 Mission
```

`/mission status` 会显示每个 Story 的通过状态、当前阶段、Git 分支等信息（handler.py 第 121-154 行）。

### 介入点四：异常介入

如果某个 Story 反复失败（3 次以上），Agent 会停下来请你介入。你可以：

- 提供额外的上下文或提示。
- 手动修复问题后让 Agent 继续。
- 取消当前 Mission，重新开始。

## 工程权衡：Mission 模式的设计选择

### 为什么用文件而不是数据库做状态管理？

Mission 的所有状态存在 JSON 和 Markdown 文件中（`prd.json`、`progress.txt`、`loop_config.json`），而不是数据库。这个选择和记忆系统的设计哲学一致：

- **优点**：人可读、可直接编辑、无需额外依赖、调试直观。
- **缺点**：并发写入可能冲突、搜索效率不如数据库、没有事务保证。

但对于 Mission 模式的场景（通常同时只有一个活跃 Mission），文件存储的简单性远远胜过数据库的性能优势。

### 为什么 Controller 不能自己写代码？

这是一个刻意的设计决策，有两层考量：

1. **质量保证**：如果 Controller 自己写代码，就没有独立的验证环节。"自己写、自己验证"本质上是"没有验证"。Worker-Verifier 的分离确保了"实现者"和"验证者"是不同的 Agent 会话——它们有不同的视角和激励。
2. **安全隔离**：Controller 在一个长会话中运行，积累了大量的 Context。如果它在这个 Context 中直接操作文件系统，一个"思路偏差"可能导致连锁错误。Worker 是一次性会话，Context 干净，行为更可预测。

### 为什么 Worker 是"无记忆"的？

每个 Worker 是全新的 Agent 会话，没有记忆。这看起来像是缺点——为什么不"复用"之前的 Worker？原因是：

- **Context 隔离**：一个 Worker 的 Context 只包含它需要的信息，不会被之前的无关信息干扰。
- **Story 大小约束**：因为 Worker 的 Context 是有限的，这迫使 PRD 中的 Story 不能太大——如果一个 Story 放不进一个 Context 窗口，说明它需要拆分。
- **可重现性**：每个 Worker 的行为只取决于它的提示词和代码库状态，不受之前会话的影响。

但"无记忆"也意味着每个 Worker 需要**完整的上下文**——这就是为什么 Worker 提示词要包含 PRD、Story 详情、Codebase Patterns、Git 信息等一切必要内容。

### 迭代上限：20 次够不够？

默认的 20 次迭代上限是一个经验值。一个典型的 5-Story Mission 可能需要 7-10 次迭代（包含重试）。但对于特别复杂的任务，20 次可能不够。用户可以通过 `--max-iterations 100` 放宽上限。

不过，如果 20 次迭代还没完成，通常意味着任务拆解有问题、Story 太大、或者代码库本身有阻碍性问题。与其无限制地循环，不如停下来让用户诊断。
