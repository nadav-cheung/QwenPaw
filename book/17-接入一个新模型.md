## 问题：市场上出了新的 LLM 服务，怎么让 QwenPaw 支持它？

大语言模型的生态在飞速演进。每隔几个月就有新的模型服务上线——有的擅长代码，有的擅长推理，有的价格低廉，有的支持多模态。QwenPaw 的设计哲学是"不绑定任何一家模型服务商"，所以系统需要一个灵活的机制来接入新的模型。

这个机制就是 **Provider**（服务提供者）。

我们在卷二的第十一章已经从设计模式的角度拆解过 Provider 的策略模式。这一章，我们要从实践角度出发，亲手实现一个新的 Provider。具体来说：

Provider 的接口契约是什么样的？OpenAI 兼容协议为什么重要？流式响应怎么实现？配置是怎么从磁盘加载到运行时的？这一章，我们带着这些问题，从零接入一个新模型。

## 术语其实很简单

> **术语：Provider（服务提供者）**
>
> 想象你开了一家餐厅（QwenPaw）。你的后厨需要食材，但你不自己种菜——你从多个供应商那里进货：张三家的蔬菜、李四家的肉类、王五家的海鲜。每个供应商的配送方式不同（有的打电话下单，有的用 App），但你只需要告诉采购经理"我要什么"，他来处理跟各家供应商的对接。Provider 就是这些"供应商"在 QwenPaw 里的抽象。每个 Provider 封装了一家模型服务商的通信细节（API 地址、认证方式、请求格式），上层代码只需要说"我要用 gpt-5.2"，Provider 负责把请求发到正确的服务器、把响应翻译成统一的格式。

> **术语：OpenAI 兼容协议（OpenAI-Compatible API）**
>
> 想象 USB 接口。在 USB 出现之前，键盘用 PS/2 口、打印机用并口、鼠标用串口——每种设备一个接口。USB 统一了它们：只要你遵守 USB 标准，任何设备都能插在任何电脑上。OpenAI 兼容协议就是大模型领域的"USB 接口"。OpenAI 公司定义了一套 HTTP API 格式（`/v1/chat/completions`、`/v1/models` 等），后来几乎所有的模型服务商（DeepSeek、Moonshot、Ollama、LM Studio……）都选择兼容这套格式。这意味着你用同一套客户端代码，只要改一下 `base_url` 和 `api_key`，就能调用不同服务商的模型。

> **术语：流式响应（Streaming Response）**
>
> 想象你在看一部网络视频。如果等整个视频下载完才能看，你需要等很久。但流式播放让你一边下载一边看——几秒钟就能开始。流式响应是同样的道理：模型生成回答时不是等全部内容生成完才返回，而是每生成一小段就立即发送给客户端。对于大语言模型来说，一个完整的回答可能有几千字，生成需要几十秒。如果不用流式，用户盯着空白屏幕等 30 秒；用了流式，一两个字就开始显示，体验完全不同。QwenPaw 的所有 Provider 都要求支持流式响应（`stream=True`）。

## 探索：Provider 的接口契约

要接入一个新的模型服务，你需要理解 Provider 和系统之间的"契约"——也就是 Provider 基类定义的接口。

### Provider 的继承结构

打开 `src/qwenpaw/providers/provider.py`，第一眼就能看到 Provider 的继承关系：

```
ProviderInfo (Pydantic BaseModel)
    │   ← 存储 Provider 的配置信息（id、name、base_url、api_key...）
    │
    └── Provider (ABC)
            ← 在 ProviderInfo 的基础上增加抽象方法
               定义与模型服务交互的接口契约
```

`Provider` 同时继承 `ProviderInfo` 和 `ABC`（抽象基类）。这意味着每个 Provider 既是数据容器（持有配置信息），又是行为定义（必须实现抽象方法）。

`provider.py` 第 147 行定义了 Provider 类：

```python
class Provider(ProviderInfo, ABC):
    """Represents a provider instance with its configuration."""
```

### 四个必须实现的抽象方法

Provider 基类定义了**四个抽象方法**，这是每个新 Provider 必须实现的接口契约：

| 方法 | 行号 | 用途 | 返回类型 |
|------|------|------|----------|
| `check_connection()` | 150-152 | 检查与服务商的网络连通性 | `tuple[bool, str]` |
| `fetch_models()` | 154-156 | 从服务商拉取可用模型列表 | `List[ModelInfo]` |
| `check_model_connection()` | 158-163 | 检查某个具体模型是否可用 | `tuple[bool, str]` |
| `get_chat_model_instance()` | 309-312 | 创建一个 ChatModel 实例 | `ChatModelBase` |

画成一张接口契约图：

```
┌──────────────────────────────────────────────────────────────────────┐
│                    Provider 接口契约                                   │
│                                                                      │
│  ┌─────────────────────── ProviderInfo（数据）─────────────────────┐ │
│  │  id: str               ← Provider 标识（如 "openai"）          │ │
│  │  name: str             ← 显示名称（如 "OpenAI"）               │ │
│  │  base_url: str         ← API 地址                               │ │
│  │  api_key: str          ← 认证密钥                               │ │
│  │  chat_model: str       ← ChatModel 类名                        │ │
│  │  models: List[ModelInfo] ← 预定义模型列表                       │ │
│  │  extra_models: List     ← 用户添加的模型                        │ │
│  │  ...还有十几个配置字段                                            │ │
│  └─────────────────────────────────────────────────────────────────┘ │
│                                                                      │
│  ┌─────────────────────── ABC（行为）─────────────────────────────┐  │
│  │                                                                 │  │
│  │  ★ check_connection(timeout)     → (bool, str)                │  │
│  │    "能连上服务器吗？"                                             │  │
│  │                                                                 │  │
│  │  ★ fetch_models(timeout)         → List[ModelInfo]            │  │
│  │    "告诉我你有哪些模型"                                           │  │
│  │                                                                 │  │
│  │  ★ check_model_connection(id, t) → (bool, str)                │  │
│  │    "这个具体模型能用吗？"                                         │  │
│  │                                                                 │  │
│  │  ★ get_chat_model_instance(id)   → ChatModelBase              │  │
│  │    "给我一个能对话的模型实例" ← 最核心的方法                      │  │
│  │                                                                 │  │
│  └─────────────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────────┘
```

此外还有一个**可选覆盖**的方法：

| 方法 | 行号 | 用途 |
|------|------|------|
| `probe_model_multimodal()` | 314-335 | 探测模型是否支持图片/视频输入 |

基类提供了一个默认实现，直接返回"不支持"。如果你接入的服务商支持多模态，可以覆盖这个方法。

### 已有方法：Provider 基类帮你做好的事

除了四个必须实现的抽象方法，Provider 基类还提供了一批**已实现的方法**，每个子类自动继承：

- `add_model()` / `delete_model()`（第 166-193 行）——增删模型
- `update_config()`（第 196-232 行）——更新配置
- `has_model()`（第 303-307 行）——检查模型是否存在
- `get_effective_generate_kwargs()`（第 270-284 行）——合并 Provider 级和模型级的生成参数
- `get_info()`（第 337-367 行）——导出 ProviderInfo（隐藏敏感字段）

这意味着你实现一个新 Provider 时，只需要关注**四个核心方法**。其他功能（模型管理、配置更新、序列化）基类已经帮你做好了。

## 探索：OpenAI 兼容协议——一个 Provider 如何服务多个厂商

QwenPaw 支持二十多个内置 Provider。如果你去看 `provider_manager.py`，会发现一个有趣的事实：**其中大部分都使用了同一个实现类 `OpenAIProvider`**。

`provider_manager.py` 第 490-592 行定义了这些内置 Provider：

```python
PROVIDER_MODELSCOPE = OpenAIProvider(
    id="modelscope", name="ModelScope",
    base_url="https://api-inference.modelscope.cn/v1",
    ...
)
PROVIDER_DASHSCOPE = OpenAIProvider(
    id="dashscope", name="DashScope",
    base_url="https://dashscope.aliyuncs.com/compatible-mode/v1",
    ...
)
PROVIDER_OPENAI = OpenAIProvider(
    id="openai", name="OpenAI",
    base_url="https://api.openai.com/v1",
    ...
)
PROVIDER_DEEPSEEK = OpenAIProvider(
    id="deepseek", name="DeepSeek",
    base_url="https://api.deepseek.com",
    ...
)
```

ModelScope、DashScope、OpenAI、DeepSeek、Kimi、SiliconFlow、OpenCode、Azure OpenAI……它们全部使用 `OpenAIProvider`！区别仅仅是 `id`、`name`、`base_url` 和预定义模型列表不同。

这就是 OpenAI 兼容协议的威力：**只要你遵守了这套协议，你不需要写一行新代码，只需配置不同的 URL 和密钥**。

### OpenAI Provider 的参考实现

`src/qwenpaw/providers/openai_provider.py` 是所有 OpenAI 兼容服务的参考实现。让我们逐个拆解它的四个核心方法。

**方法一：`check_connection()`**（第 71-83 行）

```python
async def check_connection(self, timeout: float = 5) -> tuple[bool, str]:
    client = self._client()
    try:
        await client.models.list(timeout=timeout)
        return True, ""
    except APIError:
        return False, f"API error when connecting to `{self.base_url}`"
    except Exception:
        return False, f"Unknown exception ..."
```

逻辑非常简单：调用 OpenAI SDK 的 `models.list()` 接口。如果能返回结果，说明网络通了、密钥有效。返回 `(True, "")` 表示成功，`(False, "错误消息")` 表示失败。

**方法二：`fetch_models()`**（第 85-95 行）

```python
async def fetch_models(self, timeout: float = 5) -> List[ModelInfo]:
    try:
        client = self._client(timeout=timeout)
        payload = await client.models.list(timeout=timeout)
        models = self._normalize_models_payload(payload)
        return models
    except APIError:
        return []
```

调用 `/v1/models` 接口拉取可用模型列表，然后用 `_normalize_models_payload()` 把原始数据转换成 `ModelInfo` 对象。`_normalize_models_payload()` 在第 50-69 行，它从返回的 `data` 数组中提取 `id` 和 `name`，去重后返回。

**方法三：`check_model_connection()`**（第 97-136 行）

```python
async def check_model_connection(self, model_id, timeout=5):
    client = self._client(timeout=timeout)
    res = await client.chat.completions.create(
        model=model_id,
        messages=[{"role": "user", "content": [{"type": "text", "text": "ping"}]}],
        max_tokens=1,
        stream=True,
    )
    async for _ in res:
        break
    return True, ""
```

注意一个细节：它用 `stream=True` 创建请求，然后只消费流的第一个 chunk（`async for _ in res: break`）。这是"最小代价验证"策略——发送一个只需 1 个 token 的请求，确保模型真的能响应。

**方法四：`get_chat_model_instance()`**（第 138-175 行）

```python
def get_chat_model_instance(self, model_id: str) -> ChatModelBase:
    from .openai_chat_model_compat import OpenAIChatModelCompat
    client_kwargs = {"base_url": self.base_url}
    # ... 处理 DashScope 特殊 header
    return OpenAIChatModelCompat(
        model_name=model_id,
        stream=True,
        api_key=self.api_key,
        stream_tool_parsing=False,
        client_kwargs=client_kwargs,
        generate_kwargs=self.get_effective_generate_kwargs(model_id),
    )
```

这是最核心的方法。它创建一个 `OpenAIChatModelCompat` 实例，这个实例就是 Agent 在 ReAct 循环中实际用来调用的模型对象。注意几个关键参数：

- `stream=True`：流式响应，Agent 的回复会逐字输出
- `generate_kwargs`：从 `get_effective_generate_kwargs()` 获取合并后的生成参数（Provider 级 + 模型级）
- `client_kwargs`：传给底层 OpenAI 客户端的额外参数（主要是 `base_url`）

### 什么时候不能用 OpenAIProvider

OpenAI 兼容协议覆盖了大部分场景，但有些服务商使用完全不同的 API 格式，需要单独实现：

| Provider | 实现类 | 原因 |
|----------|--------|------|
| Anthropic / MiniMax | `AnthropicProvider` | 使用 Anthropic Messages API 格式 |
| Google Gemini | `GeminiProvider` | 使用 Gemini 原生 API 格式 |
| Ollama | `OllamaProvider` | 继承 `OpenAIProvider`，但需要处理本地 URL |
| LM Studio | `LMStudioProvider` | 继承 `OpenAIProvider`，本地部署特殊处理 |
| OpenRouter | `OpenRouterProvider` | 继承 `OpenAIProvider`，但有特殊的模型路由逻辑 |

`OllamaProvider` 的实现很精妙（`ollama_provider.py` 第 13-72 行）。它直接继承 `OpenAIProvider`，只覆盖了 `_client()` 和 `get_chat_model_instance()` 两个方法来处理 URL 的 `/v1` 后缀问题，其余方法全部复用。这展示了继承策略的威力：

```
┌──────────────────────────────────────────────────────────────────┐
│              Provider 继承体系                                     │
│                                                                    │
│  Provider (ABC)                                                    │
│    ├── OpenAIProvider         ← 主力实现，服务 ~15 个厂商           │
│    │     ├── OllamaProvider   ← 本地部署，URL 处理不同               │
│    │     ├── LMStudioProvider ← 本地部署，URL 处理不同               │
│    │     └── OpenRouterProvider← 模型路由，额外参数                   │
│    ├── AnthropicProvider      ← 完全不同的 API 格式                  │
│    └── GeminiProvider         ← Google 原生 API                     │
│                                                                    │
│  原则：能用 OpenAIProvider 就用，只有 API 格式本质不同才写新的        │
└──────────────────────────────────────────────────────────────────┘
```

## 探索：从配置到实例化——Provider 的生命周期

一个 Provider 从磁盘上的 JSON 配置文件变成运行时的实例，经历了一条清晰的生命周期。让我们追踪这条链路。

### 第一步：ProviderManager 初始化

`provider_manager.py` 的 `ProviderManager.__init__()`（第 726-744 行）做了三件事：

```
__init__()
  │
  ├── _prepare_disk_storage()      ← 创建目录结构
  │     ~/.qwenpaw/providers/
  │       ├── builtin/             ← 内置 Provider 配置
  │       ├── custom/              ← 用户自定义 Provider
  │       └── plugin/              ← 插件 Provider
  │
  ├── _init_builtins()             ← 加载代码中定义的内置 Provider
  │     把 PROVIDER_OPENAI、PROVIDER_DEEPSEEK 等
  │     注册到 self.builtin_providers 字典
  │
  └── _init_from_storage()         ← 从磁盘加载用户配置
        读取 JSON 文件，覆盖内置 Provider 的密钥等字段
```

### 第二步：反序列化——从 JSON 到 Provider 实例

`_provider_from_data()`（第 1315-1328 行）是关键的反序列化方法。它根据配置数据中的 `id` 和 `chat_model` 字段决定创建哪种 Provider 实例：

```python
def _provider_from_data(self, data: Dict) -> Provider:
    provider_id = str(data.get("id", ""))
    chat_model = str(data.get("chat_model", ""))
    if provider_id == "openrouter":
        return OpenRouterProvider.model_validate(data)
    if chat_model == "AnthropicChatModel":
        return AnthropicProvider.model_validate(data)
    if chat_model == "GeminiChatModel":
        return GeminiProvider.model_validate(data)
    if provider_id == "ollama":
        return OllamaProvider.model_validate(data)
    return OpenAIProvider.model_validate(data)
```

默认 fallback 到 `OpenAIProvider`。这意味着用户创建的**自定义 Provider**（通过 UI 添加的 OpenAI 兼容服务）会自动使用 OpenAI 兼容协议——无需写任何代码。

### 第三步：配置合并

`_init_from_storage()`（第 1504-1536 行）从磁盘读取用户保存的配置，合并到内存中的内置 Provider：

```python
for builtin in self.builtin_providers.values():
    provider = self.load_provider(builtin.id, is_builtin=True)
    if provider:
        builtin.api_key = provider.api_key         # 用户填写的密钥
        builtin.extra_models = provider.extra_models  # 用户添加的模型
        builtin.generate_kwargs.update(...)            # 用户调整的参数
```

内置 Provider 的代码定义提供了"出厂默认值"，磁盘上的 JSON 文件保存了"用户定制"。两者合并后才是运行时看到的完整状态。

### 第四步：创建 ChatModel 实例

当 Agent 需要调用模型时，`model_factory.py` 的 `create_model_and_formatter()`（第 930-1019 行）通过 ProviderManager 找到 Provider，然后调用 `get_chat_model_instance()`：

```
create_model_and_formatter()
  │
  ├── 获取 agent_id → 查找 agent 专属模型配置
  │     如果有: model_slot.provider_id + model_slot.model
  │     如果没有: 使用全局 active_model
  │
  ├── manager.get_provider(provider_id)
  │     返回 Provider 实例
  │
  ├── provider.get_chat_model_instance(model_id)
  │     返回 ChatModelBase 实例（如 OpenAIChatModelCompat）
  │
  ├── 创建 Formatter（消息格式化器）
  │     根据 ChatModel 类型选择 OpenAI/Anthropic/Gemini Formatter
  │
  └── 包装: TokenRecordingModelWrapper + RetryChatModel
        记录 token 用量 + 失败自动重试
```

## 探索：流式响应的实现要求

Provider 创建的 ChatModel 实例必须支持流式响应。这一点在 OpenAI Provider 中体现为 `stream=True` 参数。

但"支持流式"不只是传一个参数那么简单。QwenPaw 的 Agent 使用 ReAct 循环——它会连续多次调用 LLM，每次调用都需要流式输出中间结果（比如"正在思考……"、"正在调用工具……"）。如果模型不支持流式，用户会看到长时间的空白等待。

AgentScope 框架定义了 `ChatModelBase` 作为所有模型实例的基类。`OpenAIChatModelCompat`（`src/qwenpaw/providers/openai_chat_model_compat.py`）继承自 `OpenAIChatModel`，它的 `stream=True` 参数告诉底层客户端使用 Server-Sent Events (SSE) 接收响应。

流式响应的数据流：

```
Agent 调用 model(messages=[...])
  │
  ▼
OpenAIChatModelCompat → OpenAI SDK → HTTP POST /v1/chat/completions
  │                                        │  stream=True
  │                                        ▼
  │                                  服务端返回 SSE 流:
  │                                  data: {"choices":[{"delta":{"content":"你"}}]}
  │                                  data: {"choices":[{"delta":{"content":"好"}}]}
  │                                  data: [DONE]
  │                                        │
  ▼                                        ▼
Agent 逐字接收流式 chunk，实时展示给用户
```

当你实现 `get_chat_model_instance()` 时，确保传 `stream=True`。这是 Provider 接口契约中"隐含"但关键的要求。

## 探索：配置集成——用户怎么添加自定义 Provider

用户添加一个 OpenAI 兼容的新模型服务，不需要改任何代码。QwenPaw 提供了"自定义 Provider"机制。

`ProviderManager.add_custom_provider()`（第 958-974 行）处理这个过程：

```python
async def add_custom_provider(self, provider_data: ProviderInfo):
    provider_payload = provider_data.model_dump()
    provider_payload["id"] = self._resolve_custom_provider_id(
        provider_data.id,
    )
    provider_payload["is_custom"] = True
    provider = self._provider_from_data(provider_payload)
    provider.support_connection_check = False
    self.custom_providers[provider.id] = provider
    self._save_provider(provider, is_builtin=False)
    return await provider.get_info()
```

注意 `_provider_from_data()` 的 fallback 逻辑——如果配置中没有指定特殊的 `chat_model`，它会创建 `OpenAIProvider` 实例。这意味着用户通过 UI 填入一个新的 `base_url` 和 `api_key`，系统会自动用 OpenAI 兼容协议去对接。

自定义 Provider 的配置保存在 `~/.qwenpaw/providers/custom/` 目录下，每个 Provider 一个 JSON 文件。敏感字段（如 `api_key`）会被加密后存储。

## 工程权衡：实现新 Provider 的三个决策

在动手写代码之前，让我们思考实现新 Provider 时的几个关键决策。

### 权衡一：继承 OpenAIProvider vs 从零实现

大多数新模型服务都兼容 OpenAI 协议。这意味着你有两个选择：

**选择 A：直接用 OpenAIProvider**。不需要写新类，只需在 `provider_manager.py` 中添加一个配置实例（像 `PROVIDER_DEEPSEEK` 那样）。优点是零代码量、立即生效；缺点是无法定制任何行为。

**选择 B：继承 OpenAIProvider 并覆盖部分方法**。像 `OllamaProvider` 那样，只覆盖需要定制的方法（比如 URL 处理）。优点是既能复用大部分逻辑，又能处理特殊需求；缺点是需要写新类。

**选择 C：直接继承 Provider ABC**。像 `AnthropicProvider` 那样，从零实现所有抽象方法。只有当新服务的 API 格式与 OpenAI 完全不同时才需要。代价最大，但灵活性最高。

一个好的判断标准：**如果你的服务能通过改 `base_url` 直接用 openai Python SDK 调通，就选 A；如果需要少量适配（比如 URL 格式处理），选 B；如果 API 格式完全不同，选 C。**

### 权衡二：预定义模型列表 vs 动态发现

Provider 有两种获取模型列表的方式：

- **预定义**：在代码中硬编码模型列表（如 `OPENAI_MODELS`）。优点是启动快、信息完整（可以预填 `supports_image` 等字段）；缺点是新增模型时需要更新代码。
- **动态发现**：通过 `fetch_models()` 在运行时调用 API 获取。优点是永远是最新的；缺点是依赖网络、启动时需要额外请求。

QwenPaw 的做法是**两者结合**：内置 Provider 预定义一份模型列表（包含多模态等元信息），同时 `fetch_models()` 用于获取最新列表。`support_model_discovery` 字段控制 UI 是否显示"刷新模型列表"按钮。

### 权衡三：多模态探测的必要性

`probe_model_multimodal()` 是一个可选方法。它的作用是自动探测模型是否支持图片和视频输入。

对于已知能力的模型（如 GPT-5），你可以直接在 `ModelInfo` 中标注 `supports_image=True`，不需要运行时探测。但对于新模型或者能力不确定的模型，探测机制可以避免"发了一张图片但模型当作忽略"的问题。

探测的代价是：每次探测需要发送一次真实的图片/视频请求，消耗 token 和时间。OpenAI Provider 的探测策略（`openai_provider.py` 第 219-318 行）使用了一张 16x16 的纯色图片和一个极短视频来最小化探测成本。

## 动手：实现一个最小化 Provider

理论讲够了。现在让我们从零实现一个最小化的 Provider。假设市场上线了一家名为 "NovaAI" 的新模型服务，它兼容 OpenAI 协议，地址是 `https://api.novaai.example.com/v1`。

### 场景分析

NovaAI 兼容 OpenAI 协议——这意味着我们可以直接使用 `OpenAIProvider`，不需要写新类。这是最常见的情况。

### 方式一：作为内置 Provider 添加（需要改代码）

如果你是 QwenPaw 的开发者，想把 NovaAI 加为内置支持，只需要改一个文件。

**第一步：在 `provider_manager.py` 中定义模型列表**

在文件的模型列表区域（约第 47-488 行之间）添加：

```python
NOVA_MODELS: List[ModelInfo] = [
    ModelInfo(
        id="nova-3-ultra",
        name="Nova 3 Ultra",
        supports_image=True,
        supports_video=False,
        probe_source="documentation",
    ),
    ModelInfo(
        id="nova-3-mini",
        name="Nova 3 Mini",
        supports_image=False,
        supports_video=False,
        probe_source="documentation",
    ),
]
```

**第二步：创建 Provider 实例**

在第 490 行（`PROVIDER_MODELSCOPE`）附近添加：

```python
PROVIDER_NOVA = OpenAIProvider(
    id="nova",
    name="NovaAI",
    base_url="https://api.novaai.example.com/v1",
    api_key_prefix="nova-",
    models=NOVA_MODELS,
    freeze_url=True,
)
```

**第三步：注册到 `_init_builtins()`**

在 `_init_builtins()` 方法中（第 760-784 行）添加一行：

```python
self._add_builtin(PROVIDER_NOVA)
```

就这样。三个步骤，只改了一个文件。NovaAI 的所有通信逻辑（连接检查、模型发现、流式对话、多模态探测）全部复用 `OpenAIProvider` 已有的实现。

### 方式二：作为自定义 Provider 添加（用户操作，不改代码）

如果你是 QwenPaw 的用户（不是开发者），可以通过 UI 或 API 添加自定义 Provider。底层调用的是 `add_custom_provider()`，等价于保存一份这样的 JSON 配置：

```json
{
  "id": "nova",
  "name": "NovaAI",
  "base_url": "https://api.novaai.example.com/v1",
  "api_key": "nova-your-key-here",
  "chat_model": "OpenAIChatModel",
  "is_custom": true,
  "models": [],
  "extra_models": [
    {"id": "nova-3-ultra", "name": "Nova 3 Ultra"},
    {"id": "nova-3-mini", "name": "Nova 3 Mini"}
  ]
}
```

`_provider_from_data()` 看到 `chat_model: "OpenAIChatModel"` 后，会创建 `OpenAIProvider` 实例。所有 OpenAI 兼容协议的通信逻辑自动生效。

### 方式三：实现一个全新的 Provider 类（API 不兼容的场景）

如果 NovaAI 使用了完全不同的 API 格式（假设它的接口不是 `/v1/chat/completions`），我们就需要从零实现。这种情况在 `AnthropicProvider` 中可以看到完整的范例。

以下是实现一个全新 Provider 的最小骨架：

```python
# nova_provider.py
from agentscope.model import ChatModelBase
from qwenpaw.providers.provider import ModelInfo, Provider

class NovaProvider(Provider):
    """Provider for NovaAI service."""

    async def check_connection(self, timeout: float = 5) -> tuple[bool, str]:
        # 发送一个 HTTP 请求检查连通性
        # 返回 (True, "") 表示成功，(False, "错误消息") 表示失败
        ...

    async def fetch_models(self, timeout: float = 5) -> list[ModelInfo]:
        # 调用 NovaAI 的模型列表 API
        # 返回 ModelInfo 列表
        ...

    async def check_model_connection(
        self, model_id: str, timeout: float = 5,
    ) -> tuple[bool, str]:
        # 发送一个最小的推理请求验证模型可用
        # 建议使用 stream=True + 只消费第一个 chunk
        ...

    def get_chat_model_instance(self, model_id: str) -> ChatModelBase:
        # 创建并返回一个 ChatModelBase 实例
        # 确保传入 stream=True 支持流式响应
        ...
```

这个骨架只需要实现四个方法。其他所有功能（模型增删、配置更新、序列化、多模态探测）都由 Provider 基类提供默认实现。

然后，在 `provider_manager.py` 的 `_provider_from_data()` 中添加一条路由规则：

```python
if provider_id == "nova":
    return NovaProvider.model_validate(data)
```

并在 `_init_builtins()` 中注册。

### 每个方法的实现要点

基于对 OpenAI 和 Anthropic 两个参考实现的分析，每个方法都有一些值得注意的实现要点：

**`check_connection()`**：

- 使用最轻量的 API 调用（如 `models.list()`），避免消耗 token
- 捕获两类异常：已知 API 错误和未知异常
- 返回的字符串应该是用户友好的错误描述

**`fetch_models()`**：

- API 失败时返回空列表（`[]`），不要抛异常——这不是关键路径
- 做好去重（同一个模型 ID 可能出现多次）
- 如果 API 不支持模型列表接口，可以返回预定义的 `self.models`

**`check_model_connection()`**：

- 发送一个极小的推理请求（`max_tokens=1`、内容 "ping"）
- 使用流式请求 + 只消费第一个 chunk 来最小化等待时间
- 先检查 `model_id` 是否为空字符串

**`get_chat_model_instance()`**：

- 这是**最核心的方法**，Agent 每次对话都会通过它获取模型实例
- 确保传入 `stream=True`
- 使用 `self.get_effective_generate_kwargs(model_id)` 合并生成参数
- 返回的对象会被 `TokenRecordingModelWrapper` 和 `RetryChatModel` 包装

## 回顾：接入一个新模型的完整路径

这一章，我们从 Provider 的接口契约出发，追踪了配置加载、实例化、流式响应的完整链路，最终实践了三种接入新模型的方式。

```
理解 Provider 接口契约
    │
    │  Provider = ProviderInfo（数据）+ ABC（行为）
    │  四个必须实现的方法 + 若干可选方法
    │
    ▼
判断 API 兼容性
    │
    │  OpenAI 兼容 → 直接用 OpenAIProvider（零代码）
    │  小幅差异   → 继承 OpenAIProvider，覆盖部分方法
    │  完全不同   → 继承 Provider ABC，从零实现
    │
    ▼
实现四个核心方法
    │
    │  check_connection()       → 能连上吗？
    │  fetch_models()           → 有哪些模型？
    │  check_model_connection() → 这个模型能用吗？
    │  get_chat_model_instance()→ 给我模型实例（最核心）
    │
    ▼
注册到 ProviderManager
    │
    │  内置: _init_builtins() + _provider_from_data()
    │  自定义: add_custom_provider()（用户通过 UI 操作）
    │
    ▼
从配置到实例化
    │
    │  代码默认值 + 磁盘用户定制 → 运行时合并
    │  activate_model() → get_chat_model_instance()
    │  → TokenRecording + Retry 包装 → Agent 使用
    │
    ▼
（可选）覆盖 probe_model_multimodal()
    │
    │  如果模型支持图片/视频，提供探测实现
    │  否则使用基类默认实现（返回不支持）
```

关键文件清单：

| 文件 | 角色 | 改动 |
|------|------|------|
| `src/qwenpaw/providers/provider.py` | Provider 基类（ABC） | 只读，理解接口契约 |
| `src/qwenpaw/providers/openai_provider.py` | OpenAI 兼容参考实现 | 只读，学习实现模式 |
| `src/qwenpaw/providers/provider_manager.py` | Provider 注册与管理 | 添加内置 Provider 时需要改 |
| `src/qwenpaw/agents/model_factory.py` | 模型实例化工厂 | 通常不需要改 |

核心经验：**大部分新模型服务都兼容 OpenAI 协议。在决定写新代码之前，先试试只改配置。** QwenPaw 的 Provider 体系已经把"协议兼容"这个信息隐藏得很好——上层代码不关心底层用的是哪家服务商，只关心"给我一个能对话的模型实例"。

## 延伸：本地模型 Provider——在自家机器上跑大模型

除了云端 API 服务，QwenPaw 还支持完全在本机运行的模型。这适用于隐私敏感场景（医疗、财务数据不出本机）、离线环境（内网、边缘设备）和成本优化（大量简单推理不消耗 API 额度）。

### 本地模型的三种接入方式

| 方式 | Provider ID | 说明 |
|------|------------|------|
| Ollama | `ollama` | 跨平台，自动发现本地模型，兼容 OpenAI 格式 |
| LM Studio | `lmstudio` | 跨平台，API 兼容 OpenAI，图形界面管理模型 |
| QwenPaw 内置 llama.cpp | `qwenpaw-local` | 无需额外软件，QwenPaw 内置 llama.cpp 后端 |

前两者是外部服务——你需要先安装 Ollama 或 LM Studio，然后 QwenPaw 通过网络连接它们。第三个是 QwenPaw 自带的方案，完全内置。

### LocalModelManager：内置 llama.cpp 的管理器

`src/qwenpaw/local_models/manager.py` 第 41 行定义了 `LocalModelManager`——一个单例 Facade，管理 llama.cpp 服务器的下载、模型下载和服务器生命周期。

它的架构分为两层：

```
LocalModelManager（单例 Facade）
    ├── ModelManager — 模型文件的下载、存储和元数据管理
    └── LlamaCppBackend — llama-server 进程的启动、健康检查和关闭
```

#### 服务器生命周期

启动一个本地模型分几步（`LlamaCppBackend.setup_server()`，`llamacpp.py` 第 217 行）：

1. **解析模型路径**：支持单个 `.gguf` 文件或 HuggingFace 仓库目录（自动搜索 `.gguf` 文件，识别 `mmproj*.gguf` 多模态投影器）
2. **查找空闲端口**或使用固定端口
3. **启动子进程**：`llama-server --host 127.0.0.1 --port <port> --model <path> --gpu-layers auto`
4. **轮询 `/health` 端点**等待就绪（最多 120 秒）

如果切换到不同模型，会先关闭当前服务器再启动新的。服务器状态通过 `get_server_status()` 查询，返回运行状态、端口、PID 和模型名。

#### 平台检测与后端选择

`LlamaCppBackend` 初始化时（第 59 行）自动检测运行环境：操作系统（Windows/macOS/Linux）、CPU 架构（x64/arm64）、CUDA 版本。根据检测结果选择后端：

| 环境 | 后端 | 说明 |
|------|------|------|
| macOS | CPU | Metal GPU 加速待后续版本 |
| Linux | CPU | 依赖 CPU 推理 |
| Windows + CUDA 12.4+ | CUDA | GPU 加速推理 |
| Windows 无 CUDA | CPU | 回退到 CPU |

下载的 llama.cpp 二进制文件名也根据平台自动构建（`_build_filename()`，第 820 行）：macOS 用 `.tar.gz`，Linux 用 `.tar.gz`，Windows 用 `.zip`（区分 CPU 和 CUDA 版本）。

#### 模型下载管理

模型文件从 HuggingFace 或 ModelScope 下载（`DownloadSource` 枚举支持 `huggingface`、`modelscope`、`auto`）。下载进度通过 `DownloadProgressTracker` 追踪，它是线程安全的（`threading.Lock`），实时计算下载速度（`speed = (downloaded_bytes - last_sample) / elapsed_time`）。下载任务在子进程中执行，通过队列向主进程汇报进度，状态机遵循 `IDLE → PENDING → DOWNLOADING → COMPLETED/FAILED/CANCELLED` 生命周期。

`ProcessDownloadController`（`download_manager.py` 第 368 行）管理这个过程：它在一个独立进程中启动下载任务，同时运行一个监控线程轮询消息队列，将进度更新和最终结果转发给 `DownloadProgressTracker`。这种进程隔离的设计确保了即使下载库阻塞了整个线程（如 `httpx` 同步下载），也不会阻塞主事件循环。

#### 推荐模型选择

按系统内存选择合适的模型：

| 内存 | 推荐模型 | 量化 | 适用场景 |
|------|----------|------|----------|
| <=8GB | QwenPaw-Flash-2B | Q4_K_M 或 Q8_0 | 轻量任务 |
| <=16GB | QwenPaw-Flash-4B | Q4_K_M | 常规对话 |
| >16GB | QwenPaw-Flash-9B | Q4_K_M | 复杂推理 |
