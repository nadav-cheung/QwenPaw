# 第三章 系统提示词的拼装

```
浏览器 ─→ HTTP ─→ Runner ─→ Agent ─→ [Prompt拼装] ─→ ReAct ─→ LLM ─→ Tool ─→ 响应
                                        |
                                     你在这里
```

## 问题：Agent 怎么知道自己是"谁"？

上一章，请求穿过了 Runner 的调度层，终于到达了一个叫 `QwenPawAgent` 的对象。这个 Agent 就是真正和 AI 大模型打交道的"员工"。

但你有没有想过一个问题：当你对 AI 说"你好"的时候，大模型收到的不只是你的"你好"两个字。在你说的话前面，还贴着一大段"背景说明"——告诉 AI 你是谁、能做什么、该遵守什么规则。这段背景说明，叫做**系统提示词**（System Prompt）。

问题来了：这段系统提示词是从哪里来的？它是写死在代码里的吗？如果我想让 AI 的性格变得活泼一点，或者想让它在回复时用日语，我该改哪里？

这一章，我们就来追踪系统提示词是怎么被"拼装"出来的。你会看到一段看似简单的过程——读几个 Markdown 文件，处理一下格式，拼在一起——实际上藏着不少精心设计的细节。

准备好了吗？让我们打开文件柜，看看 Agent 的"人设档案"是怎么被组装起来的。

---

## 术语其实很简单

> **术语：System Prompt（系统提示词）**
> 想象你去一家公司上班。入职第一天，HR 会给你一份"员工手册"，上面写着公司的规章制度、你的岗位职责、行为准则。System Prompt 就是给 AI 的"员工手册"——在它开始回复你的消息之前，系统会先"喂"给它一段文字，告诉它"你是谁、你能做什么、你该怎么做"。这段文字对你不可见，但 AI 的每一个回答都受它影响。

> **术语：模板拼装（Template Assembly）**
> 想象你在搭乐高——你有好几袋零件（AGENTS.md、SOUL.md、PROFILE.md），每袋提供不同类型的积木（规则、性格、身份）。拼装过程就是按顺序打开每一袋，把有用的零件挑出来，最终搭成一个完整的作品（System Prompt）。如果某一袋是空的（文件不存在），没关系，跳过就好。

> **术语：工作区（Working Directory）**
> 想象你有一个专属的办公桌。桌面上放着你的笔记本（AGENTS.md）、日记本（MEMORY.md）、名片（PROFILE.md）。每个 Agent 都有自己的办公桌，互不干扰。这个办公桌在文件系统里就是一个目录——叫做"工作区"。系统提示词就是从这个目录下的 Markdown 文件里读出来的。

## 探索：追踪系统提示词的拼装过程

### 第一步：三个文件，三个层次

QwenPaw 的系统提示词不是写死在代码里的，而是从工作区目录下的三个 Markdown 文件中"拼装"出来的。打开 `src/qwenpaw/agents/prompt.py`，第 29 行，你会看到一个叫 `PromptConfig` 的类：

```python
class PromptConfig:
    DEFAULT_FILES = [
        "AGENTS.md",    # 工作流、规则、指南
        "SOUL.md",      # 核心身份、行为准则
        "PROFILE.md",   # 身份信息、用户资料
    ]
```

三个文件，各有分工：

- **AGENTS.md**：Agent 的"操作手册"。里面写着它能做什么（记忆管理、安全规则、工具使用指南）、该怎么做（先读文件再改、破坏性命令要确认）、哪些事不能做（绝不泄露私密数据）。这是最"硬"的部分——不关乎性格，关乎规则。

- **SOUL.md**：Agent 的"灵魂"。里面写着它的核心性格——要有自己的观点、行动胜过废话、不是公司螺丝钉。这一段决定了 AI 是冷冰冰的机器还是有"人味"的助手。

- **PROFILE.md**：Agent 的"名片"。里面写着它的名字、定位、风格，以及用户的名字、偏好、背景。这是最"软"的部分——用户可以随时修改，让 Agent 更了解自己。

```
系统提示词的结构：

+-----------------------------------+
| AGENTS.md    (规则 / 工作流)       |  ← "你能做什么、该怎么做"
+-----------------------------------+
| SOUL.md      (性格 / 行为准则)     |  ← "你是什么样的人"
+-----------------------------------+
| PROFILE.md   (身份 / 用户资料)     |  ← "你是谁、你了解谁"
+-----------------------------------+
```

你可能会问：为什么不把所有内容放在一个文件里？分三个文件有什么好处？这个问题很好，我们后面在"工程权衡"里详细讨论。

### 第二步：从 Agent 创建到 Prompt 构建

Agent 创建的时候，系统提示词是怎么被触发的？让我们打开 `src/qwenpaw/agents/react_agent.py`，找到 `QwenPawAgent.__init__` 方法（第 96 行）。在初始化过程中，你会看到这样一行：

```python
sys_prompt = self._build_sys_prompt()
```

这行代码调用了 `_build_sys_prompt()` 方法（第 345 行），它是系统提示词拼装的总入口。让我们看看它的完整逻辑：

```python
def _build_sys_prompt(self) -> str:
    # 从请求上下文中获取 agent_id
    agent_id = self._request_context.get("agent_id")

    # 检查 heartbeat 和 memory 的配置
    heartbeat_enabled = self._agent_config.heartbeat.enabled
    memory_prompt_enabled = (
        self._agent_config.running.memory_summary.memory_prompt_enabled
    )

    # 核心：从工作区文件构建系统提示词
    sys_prompt = build_system_prompt_from_working_dir(
        working_dir=self._workspace_dir,
        agent_id=agent_id,
        heartbeat_enabled=heartbeat_enabled,
        memory_prompt_enabled=memory_prompt_enabled,
    )

    # 注入多模态能力提示
    multimodal_hint = build_multimodal_hint()
    if multimodal_hint:
        sys_prompt = sys_prompt + "\n\n" + multimodal_hint

    # 注入环境上下文
    if self._env_context is not None:
        sys_prompt = sys_prompt + "\n\n" + self._env_context

    return sys_prompt
```

四步，条理分明：

1. **读配置**：查出 agent_id、heartbeat 是否开启、memory 提示是否开启。
2. **拼装核心**：调用 `build_system_prompt_from_working_dir()`，从三个 Markdown 文件中读取内容并拼接。
3. **加多模态提示**：如果当前使用的模型不支持图片/视频，额外加一段提醒，让 AI 主动告诉用户。
4. **加环境上下文**：如果有额外的环境信息（比如当前的系统环境描述），追加到末尾。

拼装的全景图是这样的：

```
_build_sys_prompt()

  |
  v
build_system_prompt_from_working_dir()
  |
  ├── 读 AGENTS.md    ─→ 剥掉 YAML ─→ 过滤 heartbeat ─→ 过滤 memory
  ├── 读 SOUL.md      ─→ 剥掉 YAML
  ├── 读 PROFILE.md   ─→ 剥掉 YAML
  |
  ├── 如果有 agent_id → 在最前面加上 Agent Identity 段
  |
  └── 拼接所有部分 → 返回核心 Prompt

  |
  v
+ build_multimodal_hint()  → 如果模型不支持多模态，追加提示
+ env_context              → 如果有环境上下文，追加到末尾

  |
  v
最终的 System Prompt
```

现在让我们深入每一步的细节。

### 第三步：build_system_prompt_from_working_dir——拼装的总调度

打开 `prompt.py` 第 222 行的 `build_system_prompt_from_working_dir()` 函数。这是拼装过程的"总调度"——它创建一个 `PromptBuilder` 对象，把所有参数传进去，然后调用 `build()` 方法：

```python
def build_system_prompt_from_working_dir(
    working_dir, enabled_files, agent_id,
    heartbeat_enabled, memory_prompt_enabled,
) -> str:
    # 确定要加载哪些文件
    if enabled_files is None:
        # 从配置或默认列表中获取
        enabled_files = 从配置文件或 PromptConfig.DEFAULT_FILES 获取

    # 创建 Builder 并构建
    builder = PromptBuilder(
        working_dir=working_dir,
        enabled_files=enabled_files,
        heartbeat_enabled=heartbeat_enabled,
        memory_prompt_enabled=memory_prompt_enabled,
    )
    prompt = builder.build()

    # 如果有 agent_id，在最前面加上身份标识
    if agent_id:
        identity_header = (
            "# Agent Identity\n\n"
            f"Your agent id is `{agent_id}`.\n\n"
        )
        prompt = identity_header + prompt

    return prompt
```

注意最后一个细节——如果请求来自多 Agent 场景（有 agent_id），系统会在 Prompt 最前面加一段 `# Agent Identity`，告诉 AI "你在多 Agent 系统中的编号是 xxx"。这个信息让 AI 知道自己不是唯一的，需要和其他 Agent 协作。

还有一个有趣的地方：`enabled_files` 参数。默认是加载 AGENTS.md、SOUL.md、PROFILE.md 三个文件，但你可以通过配置指定只加载其中几个，或者加载额外的文件。这种灵活性在多 Agent 场景下特别有用——不同的 Agent 可以有不同的"人设文件"组合。

### 第四步：PromptBuilder——文件加载的执行者

`PromptBuilder` 是实际干活的类。它的核心是 `build()` 方法（第 187 行），逻辑非常简单：

```python
def build(self) -> str:
    files_to_load = self.enabled_files or PromptConfig.DEFAULT_FILES

    # 挨个加载文件
    for filename in files_to_load:
        self._load_file(filename)

    # 如果什么都没加载到，返回默认提示词
    if not self.prompt_parts:
        return DEFAULT_SYS_PROMPT    # "You are a helpful assistant."

    # 拼接所有部分
    return "\n\n".join(self.prompt_parts)
```

三步走：遍历文件列表、加载每个文件、拼接。如果所有文件都不存在（比如工作区是空的），就用一句默认的 "You are a helpful assistant." 兜底——Agent 永远不会"裸奔"，至少有一个最基础的提示词。

### 第五步：_load_file——单个文件的处理流水线

`_load_file()` 方法（第 78 行）是整个拼装过程中最精细的部分。每个文件都要经过一条"处理流水线"：

```python
def _load_file(self, filename: str) -> None:
    file_path = self.working_dir / filename

    # 1. 文件不存在？跳过（所有文件都是可选的）
    if not file_path.exists():
        return

    # 2. 读取文件内容（支持多种编码）
    content = read_text_file_with_encoding_fallback(file_path).strip()

    # 3. 剥掉 YAML frontmatter
    if content.startswith("---"):
        parts = content.split("---", 2)
        if len(parts) >= 3:
            content = parts[2].strip()

    # 4. 对 AGENTS.md 做特殊处理
    if filename == "AGENTS.md":
        content = self._process_heartbeat_section(content)
        content = self._process_memory_section(content)

    # 5. 内容非空？加入拼装列表
    if content:
        self.prompt_parts.append(f"# {filename}")
        self.prompt_parts.append("")
        self.prompt_parts.append(content)
```

让我们逐步理解这条流水线。

**流水线第 1 站：文件存在吗？**

三个文件全部是**可选的**。如果 AGENTS.md 存在但 SOUL.md 不存在，系统不会报错，只会默默跳过。这种"宽容"设计让用户可以从最简单的配置开始——只有一个 AGENTS.md 也能跑起来。

**流水线第 2 站：读取文件，兼容各种编码**

`read_text_file_with_encoding_fallback()` 这个函数名很长，但它做的事很实用：按 UTF-8、GBK、CP1252 等编码依次尝试读取文件。为什么需要这个？因为 Windows 的记事本默认保存为 GBK 编码，而 macOS/Linux 默认用 UTF-8。如果没有这个兼容处理，一个在 Windows 上编辑的配置文件拿到 Mac 上可能就是一堆乱码。

**流水线第 3 站：剥掉 YAML frontmatter**

打开工作区目录下的 AGENTS.md，你会看到文件开头有这样一段：

```markdown
---
summary: "AGENTS.md 工作区模板"
read_when:
  - 手动引导工作区
---

## 记忆

每次会话都是全新的。工作目录下的文件是你的记忆延续：
...
```

开头的 `---` 之间那段 YAML 就是 frontmatter——它是给人类看的元信息（描述这个文件是干什么的、什么时候读），对 AI 没有意义。`_load_file` 的处理方式很直接：如果文件以 `---` 开头，就按 `---` 分割，把前两段（frontmatter 的开头标记和内容）丢掉，只保留第三段（真正的正文）：

```python
if content.startswith("---"):
    parts = content.split("---", 2)
    if len(parts) >= 3:
        content = parts[2].strip()
```

分割的逻辑是这样的：

```
原始文件内容：
"---\nsummary: ...\n---\n## 记忆\n..."

按 "---" 分割（最多分 2 次）：
parts[0] = ""           ← 第一个 --- 前面的内容（空）
parts[1] = "\nsummary: ...\n"  ← frontmatter 的 YAML 内容
parts[2] = "\n## 记忆\n..."    ← 正文！

取 parts[2] → 剥掉 frontmatter 的结果
```

如果文件没有 frontmatter（不是以 `---` 开头），这步直接跳过，内容原样保留。

**流水线第 4 站：过滤 heartbeat 和 memory 区段**

这一站只对 AGENTS.md 生效。AGENTS.md 中有些内容是用 HTML 注释标记包裹的"条件区段"——只在特定条件下才应该出现在系统提示词里。

先看 heartbeat 区段。在 AGENTS.md 中，你会看到这样的结构：

```markdown
<!-- heartbeat:start -->
## Heartbeats - 要主动！
...（一大段关于 heartbeat 的说明）
<!-- heartbeat:end -->
```

`_process_heartbeat_section()` 方法（第 136 行）处理这个区段。它的逻辑是：

```
heartbeat 区段处理逻辑：

AGENTS.md 中没有 heartbeat 标记？
  └→ 保持不变（向后兼容旧版文件）

heartbeat 功能已开启？
  └→ 保留内容，但剥掉标记本身
     "<!-- heartbeat:start -->" 和 "<!-- heartbeat:end -->" 删掉
     正文保留

heartbeat 功能未开启？
  └→ 整段删除（包括标记和中间的所有内容）
```

为什么要这样做？因为 heartbeat（心跳轮询）是一种定时检查机制——系统每隔一段时间自动发送一条消息给 Agent，让它检查邮箱、日历等。如果 heartbeat 没开，关于 heartbeat 的说明就是"废话"——AI 看了也不知道怎么用。把这些无用信息从系统提示词里删掉，可以节省 Token，也让 AI 更专注。

memory 区段的处理完全类似（第 163 行的 `_process_memory_section()`）。它处理的是 `<!-- memory:start -->` 和 `<!-- memory:end -->` 之间的内容——关于记忆管理的说明。如果 `memory_prompt_enabled` 为 False（比如用户关闭了记忆功能），这段也会被整段删除。

**流水线第 5 站：加入拼装列表**

经过前面四站处理后，如果内容非空，就把它加入 `prompt_parts` 列表。注意，每个文件的内容会被加上一个标题——`# AGENTS.md`、`# SOUL.md`、`# PROFILE.md`。这个标题让 AI 知道"接下来这段内容来自哪个文件"，有助于它区分不同来源的指令。

### 第七步：多模态提示——最后的"安全网"

拼装完核心的三个文件之后，`_build_sys_prompt()` 还会做一件事：检查当前模型是否支持多模态（图片、视频）。如果不支持，就在系统提示词末尾追加一段提醒。

这个逻辑在 `build_multimodal_hint()` 函数（第 435 行）中：

```python
def format_multimodal_hint(model_info, _model_name):
    # 如果模型支持图片或视频，不需要提示
    if model_info.supports_image or model_info.supports_video:
        return ""

    # 如果不确定是否支持，也不提示（宁可漏报不可误报）
    if model_info.supports_multimodal is None:
        return ""

    # 确认不支持 → 加一段提醒
    return (
        "It appears that you can only understand text content. "
        "Please honestly inform the user about this when "
        "their input includes multimodal information."
    )
```

这段提示的意思是："看起来你只能理解文字内容。当用户的输入包含图片或视频时，请诚实地告知用户。"

为什么要加这段？想象一个场景：你发给 AI 一张图片问"这是什么"，但模型根本看不到图片。如果没有这段提示，AI 可能会"瞎编"一个回答。有了这段提示，AI 就会诚实地说"抱歉，我只能处理文字，无法查看图片"。

注意这里的判断逻辑很谨慎——只有在**确认不支持**的情况下才加提示。如果不确定（`supports_multimodal is None`），宁可不加，避免给 AI 错误的暗示。这是"宁可漏报不可误报"的策略。

## 实验：打印 Agent 实际收到的 System Prompt

### 实验 1：添加调试日志，打印 System Prompt

## 工程权衡：为什么这样设计？

### 为什么把系统提示词拆成三个文件？

把所有提示词写在一个文件里不是更简单吗？为什么要拆成 AGENTS.md、SOUL.md、PROFILE.md 三个文件？

**第一个原因：关注点分离。**

三个文件各管一件事。AGENTS.md 管"规则"——安全准则、工具使用、工作流。SOUL.md 管"性格"——核心行为准则、风格、边界。PROFILE.md 管"身份"——名字、用户资料、个人偏好。

这种分离让不同类型的内容互不干扰。如果你只想改 AI 的性格，只改 SOUL.md 就行，不用担心不小心碰坏了安全规则。如果你只想更新用户资料，只改 PROFILE.md 就行。

**第二个原因：配置灵活性。**

QwenPaw 支持多 Agent——你可以同时运行好几个 Agent，每个有自己的性格和规则。不同的 Agent 可以共享某些文件、替换某些文件。比如，两个 Agent 可以共用同一份 AGENTS.md（规则相同），但有不同的 SOUL.md（性格不同）和 PROFILE.md（身份不同）。

这种设计通过 `enabled_files` 参数实现——每个 Agent 可以配置自己要加载哪些文件。

**第三个原因：独立进化。**

SOUL.md 是"慢变化"的——一旦确定了 AI 的核心性格，很少改动。PROFILE.md 是"快变化"的——用户的偏好会随时间不断更新。把它们分开放，你改用户资料的时候不需要担心误触核心性格设定。

### 为什么支持 YAML frontmatter？

工作区下的 Markdown 文件开头经常有一段 YAML frontmatter，像这样：

```yaml
---
summary: "AGENTS.md 工作区模板"
read_when:
  - 手动引导工作区
---
```

这段信息是给人类和其他工具看的——它可以被编辑器、文档生成器、搜索工具解析利用。但对 AI 来说，这段信息毫无意义，放在系统提示词里只会浪费 Token。

所以 QwenPaw 在拼装时会自动剥掉 frontmatter。这意味着你可以放心地在文件里加 frontmatter 做元数据管理，不用担心影响 AI 的行为。

### 为什么用 HTML 注释做条件区段标记？

heartbeat 和 memory 区段用 `<!-- -->` HTML 注释来标记，而不是用某种特殊的语法。为什么？

**第一个好处：对 AI 不可见。** 如果 heartbeat 功能关闭了，整个区段（包括标记本身）都会被删掉。AI 永远不会看到 `<!-- heartbeat:start -->` 这样的内容，不会被奇怪的标记弄混淆。

**第二个好处：在编辑器里不显眼。** 你用 VS Code 或任何 Markdown 编辑器打开 AGENTS.md 时，HTML 注释通常会以灰色显示或折叠。它不会干扰你阅读正文。

**第三个好处：向后兼容。** 如果一个旧版的 AGENTS.md 没有加任何标记，过滤逻辑会检测到"标记不存在"，直接返回原文。这意味着你不需要为了升级系统而修改现有的配置文件。

## 小结

这一章，我们追踪了系统提示词从分散的 Markdown 文件到最终拼装成完整文本的全过程：

```
工作区目录
  |
  ├── AGENTS.md ──→ 读文件 → 剥 YAML → 过滤 heartbeat → 过滤 memory
  |
  ├── SOUL.md   ──→ 读文件 → 剥 YAML
  |
  └── PROFILE.md──→ 读文件 → 剥 YAML
  |
  v
PromptBuilder.build() ──→ 拼接所有部分
  |
  ├── + Agent Identity 段（多 Agent 场景）
  ├── + 多模态提示（模型不支持时）
  └── + 环境上下文（有额外信息时）
  |
  v
最终 System Prompt ──→ 传给 LLM
```

你学到了：

- **系统提示词**的作用：告诉 AI "你是谁、你能做什么、你该怎么做"，是一切对话的基础
- **三个文件的分工**：AGENTS.md 管"规则"，SOUL.md 管"性格"，PROFILE.md 管"身份"
- **拼装流水线**：读文件、剥 frontmatter、过滤条件区段、拼接——每一步都做了"只保留有用信息"的工作
- **条件过滤**：heartbeat 和 memory 区段根据配置决定是否保留，用 HTML 注释标记实现向后兼容
- **多模态安全网**：在末尾追加提示，让 AI 诚实告知自己的能力边界

## 钩子系统：在推理之前"插一手"

系统提示词拼装完了，Agent 就准备开始推理了。但在每次推理（`_reasoning()`）之前，还有两个"钩子"会先执行。它们注册在 Agent 初始化的最后一步（`_register_hooks()`），属于 `pre_reasoning` 类型——在 LLM 被调用之前触发。

### BootstrapHook：第一次聊天的引导

当你刚创建一个新 Agent，工作目录下可能有一个 `BOOTSTRAP.md` 文件——里面写着欢迎语、使用说明之类的引导内容。`BootstrapHook` 的职责是：检测到这是用户和 Agent 的**第一次交互**，就把 `BOOTSTRAP.md` 的内容悄悄注入到用户消息前面。

触发条件有三条全满足才行：
1. `.bootstrap_completed` 标记文件不存在（说明引导还没做过）
2. `BOOTSTRAP.md` 存在于工作目录
3. 这是第一条用户消息（`user_msg_count == 1` 且 `assistant_msg_count == 0`）

引导完成后，Hook 会创建 `.bootstrap_completed` 标记文件，以后就不再触发了。

### MemoryCompactionHook：上下文快满了自动压缩

这个钩子解决一个实际问题：对话太长，大模型的上下文窗口装不下了。它每次推理前检查 token 数是否超过阈值。如果超了，就做三件事：

1. **压缩旧的工具结果**：把早期工具调用的冗长输出截短
2. **压缩对话历史**：把旧消息总结成一段摘要
3. **标记已压缩的消息**：让后续推理跳过它们

它有一个重入保护机制（`_REENTRANCY_ATTR`），防止因为 agentscope 框架的 metaclass 机制导致同一个钩子被重复触发。这是一个典型的工程防御——代码里有些"看起来多余"的保护，往往是因为框架的行为比你想的复杂。

两个钩子的执行顺序是固定的：BootstrapHook 先执行，MemoryCompactionHook 后执行。BootstrapHook 只在第一次触发，之后每轮推理只有 MemoryCompactionHook 有机会介入。

系统提示词拼装完成之后，这段文字会和用户的消息一起被发送给大语言模型。但大模型不是直接拿到文字就能用的——消息需要先经过"格式化"，变成模型 API 要求的格式。这个过程涉及消息格式化器（Formatter）——我们将在下一章看到它是怎么工作的。
