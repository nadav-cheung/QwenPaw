`[卷四·纵深·第四章]` -- 上一章我们拆解了 Mission 模式——Agent 怎么像项目经理一样规划、派工、验收，完成复杂的自治任务。Mission 模式中的 Worker 和 Verifier 其实已经是"多个 Agent 协作"的雏形了，但那是一种"控制器—执行者"的强管理关系。

如果两个 Agent 不存在上下级关系呢？比如你有一个写代码的 Agent 和一个做代码审查的 Agent，你想让它们直接对话、交换意见、达成共识——这就是更广泛的**多智能体协作**问题。

这一章，我们走进 QwenPaw 的多智能体世界，看看两个 Agent 怎么找到彼此、怎么通信、怎么安全地合作完成任务。

## 问题：两个 Agent 怎么合作完成任务？

想象这个场景：

```
你：「帮我用 Agent A 写一个 Python 函数，然后让 Agent B 审查代码质量。」

单 Agent 模式：
  Agent A：（写代码）
  你：（复制代码，粘贴给 Agent B）
  Agent B：（审查代码，给出意见）
  你：（把意见复制给 Agent A）
  Agent A：（修改代码）
  ── 你是"人肉中转站"，来回搬运信息 ──

多智能体协作：
  Agent A：（写代码）──→ 直接发给 Agent B
  Agent B：（审查代码）──→ 直接把意见返回 Agent A
  Agent A：（根据意见修改代码）
  ── 你说一句话，它们自己沟通 ──
```

在 QwenPaw 中，这个问题涉及三个核心子问题：

1. **多个 Agent 怎么共存？** —— `MultiAgentManager` 管理多个独立的 Workspace，每个 Agent 有自己的记忆、工具、配置。
2. **同一进程内的 Agent 怎么通信？** —— `agent_management.py` 提供了 `chat_with_agent` 等工具，Agent 通过内部 HTTP API 互相发消息。
3. **跨进程的外部 Agent 怎么通信？** —— ACP（Agent Communication Protocol）通过 stdio JSON-RPC 让 QwenPaw 与 Claude Code、OpenCode 等外部 Agent 协作。

这三个问题分别对应 QwenPaw 的两种协作模式：**内部协作**和**外部协作**。

## 术语其实很简单

> **术语：MultiAgentManager（多智能体管理器）**
>
> 想象一个公司里有多位员工。每个员工有自己的办公桌（Workspace）、自己的工具箱（ToolKit）、自己的笔记本（Memory）。MultiAgentManager 就是 HR 部门——它知道公司有哪些员工、谁在哪、谁在忙、谁空闲。新员工入职时它安排座位（创建 Workspace），员工离职时它回收资源（停止 Workspace），员工换岗时它无缝交接（零停机重载）。

> **术语：ACP（Agent Communication Protocol，智能体通信协议）**
>
> 想象不同国家的外交官需要交流。他们不说同一种语言，不在同一个办公室。ACP 就像是"联合国通用语"——不管你是 QwenPaw、Claude Code 还是 OpenCode，只要大家都说 ACP，就能互相理解、协作完成任务。具体来说，ACP 定义了一组 JSON-RPC 方法（initialize、new_session、prompt、cancel 等），通过标准输入/输出（stdio）传输，让不同实现的 Agent 可以互操作。

> **术语：Workspace（工作空间）**
>
> 想象一个完整的办公室。它不是一张桌子，而是一个楼层——里面有 Runner（前台）、ChannelManager（通信系统）、MemoryManager（档案室）、MCPClientManager（工具仓库）、CronManager（定时任务看板）。每个 Agent 都有一个独立的 Workspace，互不干扰。Workspace 是 MultiAgentManager 管理的基本单位。

> **术语：Session（会话）**
>
> 想象一次面谈。你和 Agent 之间的一次连续对话就是一个 Session。Session 有开始（new_session）和结束（close_session），可以暂停和恢复（resume_session）。Session 内的上下文（你说了什么、Agent 回了什么）由 MemoryManager 管理。不同 Agent 之间的通信也通过 Session ID 来关联上下文。

## 探索：多智能体架构——多个 Agent 怎么共存？

### MultiAgentManager：多 Agent 的"HR 部门"

QwenPaw 的多智能体核心在 `src/qwenpaw/app/multi_agent_manager.py`。第 22-32 行定义了 `MultiAgentManager` 类：

```python
class MultiAgentManager:
    """Manages multiple agent workspaces.

    Features:
    - Lazy loading: Workspaces are created only when first requested
    - Lifecycle management: Start, stop, reload workspaces
    - Thread-safe: Uses async lock for concurrent access
    - Hot reload: Reload individual workspaces without affecting others
    - Parallel startup: Multiple agents start concurrently via
      fine-grained locking (lock released during slow workspace init)
    """
```

这个类只有两个关键的数据结构（第 34-39 行）：

```python
def __init__(self):
    self.agents: Dict[str, Workspace] = {}
    self._lock = asyncio.Lock()
    self._pending_starts: Dict[str, asyncio.Event] = {}
    self._cleanup_tasks: Set[asyncio.Task] = set()
```

- `self.agents`：一个字典，key 是 agent_id（如 `"default"`、`"coder"`），value 是已加载的 Workspace 实例。
- `self._lock`：一个异步锁，保护并发访问 `agents` 字典。
- `self._pending_starts`：防止同一个 Agent 被重复启动——如果 Agent A 正在启动中，其他请求 A 的线程会等待而不是再启动一个。

### 懒加载：用到才启动

`get_agent()`（第 42-136 行）是 MultiAgentManager 最核心的方法。它实现了**懒加载**——Agent 不在服务启动时全部初始化，而是在第一次被请求时才创建。

流程如下：

```
请求 Agent A
    │
    ├── 快速路径：A 已在 self.agents 中 → 直接返回
    │
    └── 慢路径：A 还没加载
         │
         ├── 加锁，检查是否有人在启动 A
         │    ├── 是：注册等待事件
         │    └── 否：验证配置，注册启动事件
         │
         ├── 释放锁（关键！其他 Agent 可以同时启动）
         │
         ├── 创建 Workspace 并启动（耗时操作）
         │
         ├── 加锁，写入 self.agents
         │
         └── 通知等待者
```

第 61-63 行的"快速路径"没有加锁——如果 Agent 已经加载了，直接返回字典中的引用。只有第一次访问时才需要加锁和创建。

这个设计的精妙之处在于**细粒度锁**：锁只在字典操作（检查和写入）时持有，Workspace 的创建和启动（最耗时的部分）在锁外执行。这意味着多个 Agent 可以**真正并行启动**。第 107 行的注释说得很清楚：

```python
# We are the starter — create outside the lock for parallelism
```

### 启动所有 Agent：真正的并行

`start_all_configured_agents()`（第 454-515 行）在服务启动时调用。它读取配置中所有 `enabled=True` 的 Agent，然后用 `asyncio.gather()` 并行启动：

```python
results = await asyncio.gather(
    *[start_single_agent(agent_id) for agent_id in agent_ids],
    return_exceptions=False,
)
```

每个 `start_single_agent()` 调用 `get_agent()`。由于 `get_agent()` 在启动期间释放了锁，多个 Agent 的 Workspace 创建可以同时进行——不会因为一个 Agent 启动慢而阻塞其他 Agent。

### 零停机重载：无缝交接

`reload_agent()`（第 255-366 行）实现了零停机的 Agent 重载。这在修改 Agent 配置后特别有用——不需要停掉整个服务。

流程分为五步：

```
Step 1: 加锁检查 Agent 是否存在
Step 2: 加载新配置（锁外）
Step 3: 创建并启动新 Workspace 实例（锁外）
Step 3.5: 从旧实例迁移可复用的服务组件
Step 4: 加锁，原子替换 self.agents[agent_id]
Step 5: 优雅停止旧实例（锁外）
```

Step 4 的"原子替换"是关键：从这一刻起，新的请求全部路由到新实例，而旧的实例如果还有活跃任务（比如正在进行的对话），不会立即销毁。`_graceful_stop_old_instance()`（第 138-233 行）会检查旧实例是否有活跃任务：

- 有活跃任务：启动一个后台清理任务，等任务完成（最多 60 秒）后再停止。
- 无活跃任务：立即停止。

这个设计保证了：**正在进行的对话不会因为重载而中断**。

## 探索：内部协作——同进程 Agent 之间的通信

MultiAgentManager 管理着多个 Workspace，但它们之间怎么通信？答案是 `agent_management.py` 中定义的四个工具。

### Agent 发现：list_agents

`list_agents()`（agent_management.py 第 382-393 行）让 Agent 知道系统中有哪些"同事"：

```python
async def list_agents(base_url=None) -> ToolResponse:
    result = await asyncio.to_thread(list_agents_data, base_url)
    return _tool_text_response(_json_text(result))
```

它调用内部的 HTTP API（`/api/agents`），返回所有已配置的 Agent 列表，包含每个 Agent 的 ID、名称、描述和工作目录。底层是 `list_agents_data()` 函数（第 155-163 行），使用 `httpx` 客户端发送 GET 请求。

### 前台通信：chat_with_agent

`chat_with_agent()`（第 396-465 行）是最直接的通信方式——Agent A 发消息给 Agent B，**等待 B 回复**，然后返回 B 的回复。

核心流程（简化）：

```
1. 验证目标 Agent 存在（agent_exists()）
2. 构建请求（build_agent_chat_request()）
   - 生成或复用 session_id
   - 在消息前加上来源标识 "[Agent A requesting]"
3. 通过 HTTP 发送到 /api/agent/process
   - 使用 SSE（Server-Sent Events）流式接收
   - 收集最后一个 SSE 事件作为最终回复
4. 格式化并返回回复文本
```

`build_agent_chat_request()`（第 189-212 行）做了两件重要的事：

1. **生成 session ID**：格式为 `{from_agent}:to:{to_agent}:{timestamp}:{uuid}`（第 74-78 行）。这个 ID 确保了不同 Agent 对之间的会话互不干扰。
2. **添加来源标识**：第 107-121 行的 `ensure_agent_identity_prefix()` 会在消息前加上 `[Agent xxx requesting]`，让接收方知道这条消息来自哪个 Agent。

### 后台通信：submit_to_agent + check_agent_task

如果 Agent A 不想等 Agent B 回复（比如 B 的任务很耗时），可以用 `submit_to_agent()`（第 468-531 行）提交一个**后台任务**，然后通过 `check_agent_task()`（第 534-569 行）轮询状态。

```
submit_to_agent:
  POST /api/agent/process/task → 返回 task_id

check_agent_task:
  GET /api/agent/process/task/{task_id} → 返回状态
    - "submitted" → 已提交
    - "running"   → 运行中
    - "finished"  → 已完成（包含最终回复或错误）
```

这种"提交—轮询"模式在前面的 Mission 模式中出现过——Controller 派工给 Worker 时就是用这种方式。底层 `submit_agent_chat_task()`（第 270-285 行）发送同步 POST 请求，而 `stream_agent_chat()`（第 219-242 行）则使用 SSE 流式接收。

### 消息路由：agent_context.py

当一条 Agent 间消息到达 `/api/agent/process` 时，服务器怎么知道该路由给哪个 Agent？答案是 `agent_context.py`。

`get_agent_for_request()`（agent_context.py 第 28-112 行）按以下优先级确定目标 Agent：

```
1. 函数参数 agent_id（显式指定）
2. request.state.agent_id（Agent 作用域路由设置）
3. X-Agent-Id HTTP 头（前端设置）
4. 配置中的 active_agent（默认值）
```

`X-Agent-Id` 头是在 `agent_management.py` 的 `_request_headers()` 函数（第 215-216 行）设置的：

```python
def _request_headers(to_agent):
    return {"X-Agent-Id": to_agent} if to_agent else {}
```

而当前 Agent 的身份通过 Python 的 `contextvars.ContextVar` 传递（agent_context.py 第 16-18 行）：

```python
_current_agent_id: ContextVar[Optional[str]] = ContextVar(
    "current_agent_id", default=None,
)
```

这意味着在异步调用链的任何位置，都可以通过 `get_current_agent_id()` 知道"我是谁"。`resolve_calling_agent_id()`（agent_management.py 第 81-92 行）用这个机制自动填充 `from_agent` 参数——调用者不需要显式指定自己是谁。

## 探索：外部协作——ACP 协议详解

内部协作解决了同一进程中多个 QwenPaw Agent 之间的通信问题。但如果想让 QwenPaw 和 Claude Code、OpenCode 等其他应用协作呢？这就需要 ACP（Agent Communication Protocol）。

### ACP 是什么？

ACP 是一个开放协议，定义了 Agent 之间如何通过 stdio JSON-RPC 通信。QwenPaw 的 ACP 实现在 `src/qwenpaw/agents/acp/` 目录下，包含七个文件：

```
src/qwenpaw/agents/acp/
├── __init__.py        ← 模块导出
├── core.py            ← 错误类型、SuspendedPermission 数据类
├── service.py         ← ACPService：高层会话管理
├── client.py          ← ACPHostedClient：客户端回调实现
├── server.py          ← QwenPawACPAgent：ACP Agent 服务端
├── tool_adapter.py    ← ToolResponse 适配器
└── permissions.py     ← 权限处理
```

### 双向角色：QwenPaw 既是 Client 又是 Server

QwenPaw 在 ACP 中有两个角色：

**作为 Client**（调用外部 Agent）：
- `service.py` 中的 `ACPService` 管理 ACP 会话。
- 当 Agent A 调用 `delegate_external_agent(action="start", runner="claude_code")` 时，ACPService 会通过 `spawn_agent_process()` 启动 Claude Code 的子进程，通过 stdio JSON-RPC 通信。

**作为 Server**（被外部 Agent 调用）：
- `server.py` 中的 `QwenPawACPAgent` 暴露 ACP 协议接口。
- 外部客户端（如 Zed 编辑器）可以通过 `qwenpaw acp` 命令启动 QwenPaw 的 ACP 服务端，然后通过 stdio 与它交互。

### ACP 协议的生命周期

`ACPService._open_conversation()`（service.py 第 254-307 行）展示了 ACP 协议的完整生命周期：

```python
# 1. 创建客户端回调
client = ACPHostedClient(...)

# 2. 启动外部 Agent 子进程
conn, process = await exit_stack.enter_async_context(
    spawn_agent_process(client, agent_config.command, ...)
)

# 3. 初始化协议
initialized = await conn.initialize(
    protocol_version=PROTOCOL_VERSION,
    capabilities=ClientCapabilities(),
    client_info=Implementation(name="qwenpaw-acp-service", version="0.1.0"),
)

# 4. 版本协商
if initialized.protocol_version != PROTOCOL_VERSION:
    raise ACPSessionError(...)

# 5. 创建新会话
new_session = await conn.new_session(cwd=cwd)
```

对应的消息时序如下：

```
QwenPaw (Client)                      External Agent (Server)
     │                                        │
     │──── initialize(protocol_version) ────→│
     │                                        │
     │←── InitializeResponse ────────────────│
     │     (capabilities, agent_info)         │
     │                                        │
     │──── new_session(cwd) ────────────────→│
     │                                        │
     │←── NewSessionResponse ────────────────│
     │     (session_id, config_options)       │
     │                                        │
     │──── prompt(prompt_blocks) ───────────→│
     │                                        │
     │←── session_update(AgentThoughtChunk) ─│  ← 思考中
     │←── session_update(ToolCallStart) ─────│  ← 调用工具
     │←── session_update(ToolCallProgress) ──│  ← 工具执行中
     │←── session_update(AgentMessageChunk) ─│  ← 回复文本
     │                                        │
     │←── PromptResponse(stop_reason) ───────│  ← 完成
     │                                        │
     │──── close_session() ─────────────────→│
     │                                        │
     │←── CloseSessionResponse ──────────────│
```

### 权限处理：安全的人机协作

ACP 的一个重要特性是**权限请求**（Permission Request）。当外部 Agent 想执行敏感操作（如执行命令、修改文件）时，它不是直接执行，而是向 QwenPaw 请求权限。

`ACPHostedClient.request_permission()`（client.py 第 94-131 行）处理这个流程：

```
外部 Agent 想执行 "rm temp.txt"
    │
    ├── 外部 Agent 调用 request_permission()
    │
    ├── QwenPaw 检查是否为硬阻止
    │    (如 "rm -rf /" 直接拒绝)
    │
    ├── 构造 SuspendedPermission 数据
    │    包含：工具名称、类型、目标文件、可选操作
    │
    ├── 发送 permission_request 事件给前端
    │
    ├── 暂停，等待用户选择
    │    用户看到：
    │    "Claude Code 想要删除 temp.txt"
    │    选项: [允许] [拒绝] [始终允许]
    │
    └── 用户选择后，返回选择结果
```

`permissions.py` 中的 `ACPPermissionAdapter` 负责**硬阻止**检查（第 90-91 行和第 205-220 行）：

```python
BLOCKED_COMMAND_PATTERNS = (
    "rm -rf /",
    "sudo rm -rf",
    "mkfs",
    "dd if=",
)
```

任何匹配这些模式的命令会被直接拒绝，不会传给用户。同样，任何试图访问 Workspace 目录之外的文件操作也会被阻止（第 210-219 行）。

### delegate_external_agent：ACP 的工具入口

`delegate_external_agent()`（delegate_external_agent.py 第 431-589 行）是 Agent 调用外部 Agent 的工具接口。它支持四种操作：

```python
action="start"    → 启动新的 ACP 会话
action="message"  → 向已有会话发消息
action="respond"  → 回复权限请求
action="close"    → 关闭会话
```

配置中的 ACP Agent 定义在 `config.py` 第 71-102 行。默认支持四种外部 Agent：

```python
"opencode":    ACPAgentConfig(command="opencode", args=["acp"], ...)
"qwen_code":   ACPAgentConfig(command="qwen", args=["--acp"], ...)
"claude_code": ACPAgentConfig(command="npx", args=["-y", "@zed-industries/claude-agent-acp"], ...)
"codex":       ACPAgentConfig(command="npx", args=["-y", "@zed-industries/codex-acp"], ...)
```

每个 ACPAgentConfig 指定了启动命令、参数、环境变量、是否受信任等属性。`trusted=True` 意味着这个外部 Agent 是可信的，但仍然需要用户批准敏感操作。

### 服务端：QwenPawACPAgent

`QwenPawACPAgent`（server.py 第 327-888 行）让 QwenPaw 本身可以作为 ACP 服务端被外部调用。它的核心是 `prompt()` 方法（第 513-607 行），将 ACP 的 prompt 请求转换为 QwenPaw 内部的 Runner 调用：

```python
async def prompt(self, prompt, session_id, ...):
    text = _extract_text(prompt)
    runner = await self._ensure_workspace()
    # ... 构建 AgentRequest ...
    tracker = _StreamTracker()
    async for msg, _is_last in runner.query_handler(msgs, request=request):
        updates = _msg_to_updates(msg, tracker)
        for upd in updates:
            await self._conn.session_update(session_id=session_id, update=upd)
    return PromptResponse(stop_reason="end_turn")
```

`_StreamTracker`（第 100-138 行）是一个精巧的类，它将 agentscope 的**快照式**消息（每条消息包含完整状态）转换为 ACP 的**增量式**事件流（每次只发送新增的部分）。这对于流式体验至关重要——用户不需要等到 Agent 完全回复完毕才看到内容。

## 多智能体协作架构图

```
┌─────────────────────────────────────────────────────────────────────┐
│                        QwenPaw 多智能体架构                          │
│                                                                     │
```

## 探索：两种协作模式的选择

QwenPaw 提供了两种多智能体协作模式，各有适用场景。

### 内部协作 vs 外部协作

| 维度 | 内部协作 (agent_management) | 外部协作 (ACP) |
|------|---------------------------|---------------|
| 通信方式 | 内部 HTTP API | stdio JSON-RPC |
| Agent 类型 | 都是 QwenPaw Agent | 可以是任意 ACP 兼容 Agent |
| 进程模型 | 同进程，不同 Workspace | 不同进程，通过管道通信 |
| 隔离性 | 共享进程资源 | 完全隔离 |
| 权限控制 | 统一的工具守卫 | ACP 权限请求机制 |
| 延迟 | 低（进程内调用） | 较高（进程间通信） |
| 适用场景 | 内部分工、角色协作 | 跨工具协作、外部工具集成 |

### 什么时候用内部协作？

内部协作适合以下场景：

1. **角色分工**：你有一个专门写代码的 Agent 和一个专门做审查的 Agent，它们共享同一个代码库和项目上下文。
2. **任务分解**：一个 Agent 负责理解用户意图并分解任务，然后把子任务分派给其他 Agent。
3. **专业能力互补**：不同 Agent 配置了不同的系统提示词和工具集，各有专长。

内部协作的优势是低延迟、共享状态、统一管理。缺点是所有 Agent 必须在同一个 QwenPaw 实例中运行。

### 什么时候用外部协作？

外部协作适合以下场景：

1. **跨工具集成**：你想让 QwenPaw 利用 Claude Code 的代码能力，或让 OpenCode 调用 QwenPaw 的推理能力。
2. **沙箱隔离**：外部 Agent 在独立进程中运行，即使崩溃也不影响主服务。
3. **不同权限模型**：外部 Agent 的敏感操作需要通过 ACP 权限机制逐个审批。

外部协作的优势是灵活性高、隔离性强。缺点是通信开销较大，而且需要外部 Agent 支持 ACP 协议。

## 工程权衡：多智能体架构的设计选择

### 为什么用懒加载而不是预加载所有 Agent？

`MultiAgentManager` 默认使用懒加载——Agent 在第一次被请求时才创建。配置中虽然有 `start_all_configured_agents()`（第 454 行），但只有在启动参数指定时才会调用。

权衡点：

- **懒加载的优点**：启动快、资源占用低。如果你配置了 10 个 Agent 但只用了 2 个，另外 8 个不会浪费内存。
- **懒加载的缺点**：第一次请求有延迟（需要创建和启动 Workspace）。
- **预加载的优点**：所有 Agent 都准备好了，第一次请求没有额外延迟。
- **预加载的缺点**：启动慢、资源占用高。如果配置了很多 Agent，启动可能需要几十秒。

QwenPaw 的选择是：启动时并行预加载所有 `enabled=True` 的 Agent（利用 `asyncio.gather`），但也支持懒加载作为后备。对于禁用的 Agent（`enabled=False`），它们完全不会启动（第 469-473 行的过滤逻辑）。

### 为什么内部通信走 HTTP 而不是直接函数调用？

`agent_management.py` 中的 `chat_with_agent` 通过 HTTP API（`/api/agent/process`）与目标 Agent 通信，而不是直接调用 Workspace 的方法。这个选择看起来多了一层网络开销，但有几个好处：

1. **一致性**：所有 Agent 的请求都通过同一个 API 层，享受统一的认证、日志、监控。
2. **隔离性**：调用者和被调用者之间通过 HTTP 解耦，不会因为一个 Agent 的异常而影响另一个。
3. **可扩展性**：未来如果 Agent 部署在不同进程甚至不同机器上，HTTP 天然支持。
4. **可测试性**：可以通过 curl 或 Postman 直接测试 Agent 间的通信。

`base_url` 的解析（第 22-38 行）也体现了这种灵活性：优先使用显式参数，然后回退到配置中记录的地址，最后回退到 `localhost:8088`。

### 为什么 ACP 用 stdio 而不是 TCP？

ACP 协议使用 stdio（标准输入/输出）而不是 TCP 端口。这个选择来自 ACP 协议的设计，有几个原因：

1. **简单性**：不需要端口管理、防火墙配置、端口冲突处理。
2. **安全性**：stdio 管道是进程本地的，不暴露到网络。
3. **生命周期绑定**：父进程（QwenPaw）和子进程（外部 Agent）的生命周期通过管道自然绑定——父进程退出时，子进程也会收到 EOF。
4. **通用性**：几乎所有编程语言和命令行工具都支持 stdio。

缺点是只支持父子进程通信，不支持跨机器。但对于 Agent 协作的典型场景（同一台机器上的不同工具），stdio 已经足够。

### 权限机制的"双保险"

QwenPaw 的权限控制有两个层次：

1. **QwenPaw 内部的工具守卫**（前面章节讲过的 Tool Guard）：对内部 Agent 的工具调用做权限检查。
2. **ACP 的权限请求机制**：对外部 Agent 的操作做权限检查，且多了一层"硬阻止"——危险命令和越界路径直接拒绝，不传给用户。

这两层是独立的——即使你信任了 ACP Agent（`trusted=True`），它执行敏感操作时仍然需要用户确认。`QwenPawACPAgent` 还支持 `bypassPermissions` 模式（server.py 第 341 行），但这个模式只应在不涉及敏感操作的场景使用。

## 动手：配置两个 Agent，让它们协作完成任务

这一节的动手练习是"评估级"的——你需要配置两个内部 Agent 并让它们通过 `chat_with_agent` 工具协作。

### 第一步：创建两个 Agent 的配置

在 QwenPaw 的配置文件中，添加两个 Agent profile：

```yaml
agents:
  active_agent: "writer"
  profiles:
    writer:
      name: "写手"
      description: "负责撰写内容"
      workspace_dir: "~/.qwenpaw/workspaces/writer"
      enabled: true
      system_prompt: |
        你是一个写手。你的任务是撰写高质量的文章。
        当你需要审查文章质量时，使用 chat_with_agent 工具
        联系 reviewer。
      # ... 其他配置

    reviewer:
      name: "审稿人"
      description: "负责审查文章质量"
      workspace_dir: "~/.qwenpaw/workspaces/reviewer"
      enabled: true
      system_prompt: |
        你是一个严格的审稿人。你的任务是审查文章的
        逻辑性、可读性和准确性。给出具体的修改建议。
      # ... 其他配置
```

### 第二步：启动服务

```bash
qwenpaw serve
```

观察启动日志，确认两个 Agent 都被预加载：

```
Starting 2 enabled agent(s) (0 disabled)
Agent started successfully: writer
Agent started successfully: reviewer
Agent startup complete: 2/2 agents started successfully
```

### 第三步：触发协作

在 writer Agent 的对话中：

```
请写一篇关于 Python 装饰器的教程，写完后让审稿人审查。
```

writer Agent 会：

1. 撰写文章。
2. 调用 `list_agents()` 确认 reviewer 存在。
3. 调用 `chat_with_agent(to_agent="reviewer", text="请审查以下文章...")`。
4. 等待 reviewer 返回审查意见。
5. 根据意见修改文章。
