## 问题：Skill 和 Tool 有什么区别？怎么写一个新闻摘要 Skill？

上一章末尾我们留下了一个悬念：两种"扩展 Agent 能力"的机制——Tool 和 Skill——各有适用场景。我们已经知道怎么写 Tool 了：一个 Python async 函数、一段 docstring、一个 ToolResponse 返回值，三个文件改完就上线。

但 Tool 有一个天然的门槛：你需要写 Python 代码。这意味着你需要开发环境、需要理解源码结构、需要重新部署。有没有一种方式，让不懂编程的用户也能扩展 Agent 的能力？

这就是 Skill 存在的意义。一个 Skill 不需要写一行 Python。它是一份 Markdown 文件，用自然语言告诉 Agent "在什么场景下做什么事、怎么做"。用户可以在运行时随时创建、修改和删除 Skill，不需要重启服务。

那么问题来了：

Skill 和 Tool 的定位到底有什么不同？Skill 的目录结构是什么样的？Markdown 指令怎么写？技能怎么通过 Cron 实现定时调度？这一章，我们带着这些问题，造一个完整的新闻摘要 Skill。

## 术语其实很简单

> **术语：Skill（技能）**
>
> 想象你在公司招了一位新员工（Agent）。这位员工很聪明，什么都能学。但刚入职时他不知道公司的报销流程，也不知道每天早上该查看哪些网站获取行业动态。你会给他一份"操作手册"——上面写着"当需要报销时，走这个流程；当需要看新闻时，打开这几个网站"。Skill 就是这份操作手册。它不是代码，而是一份用 Markdown 写的指令文档。Agent 阅读这份文档后，就"学会"了一项新技能。

> **术语：Cron 调度**
>
> 想象你家有一个定时插座。你设好"每天早上 7:00 通电，7:30 断电"，它就会忠实地每天重复这个动作。Cron 调度就是 Agent 世界里的"定时插座"。你可以告诉 Agent"每天早上 9 点帮我看看有什么新闻"，Agent 会创建一个 Cron 任务，到时间自动执行。Cron 的名字来自 Unix 系统的 `cron` 守护进程，它使用一种精简的时间表达式（比如 `0 9 * * *` 表示"每天 9:00"）来定义执行计划。

> **术语：YAML Frontmatter（前置元数据）**
>
> 想象一份档案袋。袋子外面有一个标签页，上面写着档案的名称、编号、日期等关键信息；袋子里面装的是完整的文件内容。YAML Frontmatter 就是 Markdown 文件的"标签页"——文件开头用 `---` 包裹的一段 YAML 格式的键值对，声明文件的名字、描述、版本等元数据。后面的 Markdown 正文才是完整内容。这种格式最早由 Jekyll 博客系统流行开来，现在被广泛用于给文本文件附加结构化元数据。

## 探索：Skill 与 Tool 的能力对比

在动手造 Skill 之前，让我们先彻底搞清楚 Skill 和 Tool 的区别。这不是一个理论问题——理解两者的边界，决定了你面对一个需求时该选哪个。

### 定位对比图

```
┌─────────────────────────────────────────────────────────────────────┐
│                    Skill vs Tool 定位对比                             │
├──────────────────┬────────────────────────┬─────────────────────────┤
│     维度         │        Tool            │        Skill             │
├──────────────────┼────────────────────────┼─────────────────────────┤
│ 实现语言         │ Python                 │ Markdown                 │
│ 文件位置         │ src/.../tools/         │ workspace/skills/        │
│ 修改后生效       │ 需要重启/重新部署       │ 下次请求自动生效          │
│ 创建者           │ 开发者                 │ 开发者或用户              │
│ 能力类型         │ 原子操作（执行代码）    │ 组合指令（指导行为）      │
│ 输入输出         │ 类型严格（JSON Schema） │ 自然语言描述              │
│ 调用方式         │ 模型决定调用 → 执行代码 │ 模型阅读指令 → 自主行动   │
│ 安全性           │ 高（需审核源码）        │ 高（Markdown 不执行代码） │
│ 典型示例         │ get_current_time       │ cron（定时任务管理）      │
│                  │ execute_shell_command  │ news（新闻查询）          │
│                  │ read_file              │ pdf（PDF 处理）          │
└──────────────────┴────────────────────────┴─────────────────────────┘
```

用一个比喻来说：**Tool 是 Agent 的手**——它能精确地执行一个操作（读文件、跑命令、查时间）；**Skill 是 Agent 的脑子里的知识**——它知道"什么场景下该做什么"。一个 Skill 经常会指导 Agent 调用多个 Tool 来完成一项复合任务。

比如 `news` 技能。它的 SKILL.md 里写了一张新闻源 URL 表格，告诉 Agent："当用户问新闻时，用 `browser_use` 工具打开这些 URL，抓取内容，然后汇总。"Agent 按照这份"操作手册"来组合使用浏览器工具，最终完成新闻查询——一个 Skill 协调了多个 Tool。

### 技能加载链：从目录到 Agent 脑中

一个 Skill 从磁盘上的文件夹变成 Agent "脑子里的知识"，经历了一条清晰的加载链。这条链路我们在第十四章已经拆解过，现在快速回顾关键节点，重点关注"加载"这个环节的代码实现：

**第一步：发现**。`skills_manager.py` 第 1509-1595 行的 `reconcile_workspace_manifest()` 扫描工作区的 `skills/` 目录，找出所有含 `SKILL.md` 的子目录：

```python
discovered = {
    path.name: path
    for path in workspace_skills_dir.iterdir()
    if path.is_dir() and (path / "SKILL.md").exists()
}
```

这行代码的哲学是：**文件系统就是注册表**。只要目录里有 `SKILL.md`，它就会被发现。

**第二步：注册**。`react_agent.py` 第 309-343 行的 `_register_skills()` 把"有效的"技能注册到 Agent 的工具集：

```python
effective_skills = resolve_effective_skills(
    workspace_dir, channel_name,
)
for skill_name in effective_skills:
    skill_dir = working_skills_dir / skill_name
    if skill_dir.exists():
        toolkit.register_agent_skill(str(skill_dir))
```

`resolve_effective_skills()` 只返回满足两个条件的技能：在 `skill.json` 中被标记为 `enabled: true`，且该技能的 `channels` 列表包含当前请求的渠道名。

**第三步：注入**。`register_agent_skill()` 把 SKILL.md 的内容注入到 Agent 的系统提示词中。从此，Agent 在 ReAct 循环中就能"看到"这份指令，并据此行动。

### Skill 的目录结构规范

每个 Skill 就是一个文件夹，核心是 `SKILL.md`。让我们看看系统里真实的 Skill 目录长什么样。

最简形态——`news-en` 技能：

```
news-en/
  SKILL.md        ← 唯一必需的文件
```

复杂形态——`pdf-en` 技能，带参考文档和脚本：

```
pdf-en/
  SKILL.md          ← 技能定义
  reference.md      ← 参考文档
  forms.md          ← 表单填写指南
  LICENSE.txt       ← 许可证
  scripts/          ← 辅助脚本
    check_bounding_boxes.py
    extract_form_field_info.py
    fill_pdf_form_with_annotations.py
```

画成一张结构图：

```
┌─────────────────────────────────────────────┐
│            Skill 目录结构规范                 │
├─────────────────────────────────────────────┤
│                                             │
│  my_skill/                    ← 技能根目录  │
│    │                                        │
│    ├── SKILL.md               ← [必需] 核心指令│
│    │     ├── YAML frontmatter ← 元数据       │
│    │     └── Markdown body    ← 指令正文     │
│    │                                        │
│    ├── references/            ← [可选] 参考文档│
│    │     ├── api_guide.md                    │
│    │     └── examples.md                     │
│    │                                        │
│    ├── scripts/               ← [可选] 辅助脚本│
│    │     ├── helper1.py                      │
│    │     └── helper2.sh                      │
│    │                                        │
│    └── *.txt / *.md           ← [可选] 其他文件│
│                                             │
└─────────────────────────────────────────────┘
```

**必需的文件只有一个：`SKILL.md`**。其他都是可选的。`references/` 下的文件会作为参考文档提供给 Agent，`scripts/` 下的文件是 Agent 可以通过命令行调用的辅助脚本。

### SKILL.md 的解剖：YAML 头 + Markdown 身

SKILL.md 的格式是 YAML Frontmatter + Markdown 正文。让我们用 `cron-en/SKILL.md` 做一次完整解剖。

文件位置：`src/qwenpaw/agents/skills/cron-en/SKILL.md`，第 1-8 行是 YAML 头：

```yaml
---
name: cron
description: Use this skill only for scheduled or recurring tasks.
metadata:
  builtin_skill_version: "1.4"
  qwenpaw:
    emoji: "..."
---
```

YAML 部分的字段含义：

| 字段 | 用途 | 必需 |
|------|------|------|
| `name` | 技能的逻辑名称（目录名才是运行时标识） | 是 |
| `description` | 技能的功能描述，用于界面展示和模型理解 | 是 |
| `metadata.builtin_skill_version` | 版本号，用于判断是否需要更新 | 否 |
| `metadata.qwenpaw.emoji` | 界面展示用的图标 | 否 |
| `metadata.qwenpaw.requires` | 系统依赖声明（bins/env） | 否 |

第 10 行往后是 Markdown 正文。它是给 Agent 阅读的"操作手册"。正文的结构一般包含：

1. **When to Use**：明确说明什么场景该用这个技能，什么场景不该用
2. **Hard Rules**：必须遵守的铁律
3. **Common Commands**：常用命令参考
4. **Creating Tasks**：创建任务的步骤和示例
5. **Common Mistakes**：常见错误和规避方法

这个结构不是强制的——你可以按任何方式组织 Markdown 正文。但上面这个结构经过了实践验证，效果最好。特别是 "When to Use" 部分里的 "Should Use / Should Not Use" 分类，能显著提高模型的判断准确率。

cron-en 的 "When to Use" 部分（第 12-25 行）是这样的：

```markdown
### Should Use
- User asks to do something "daily / weekly / hourly"
- User asks for automatic reminders or execution
  "tomorrow at 9 AM / next Monday / at a specific time"

### Should Not Use
- The task only needs to be executed once right now
- It is just a normal reply within the current session
```

这种写法等价于给 Agent 装了一个"条件触发器"。模型在 ReAct 循环中读到这段指令后，就能准确判断"用户说'每天早上提醒我'→应该用 cron 技能"和"用户说'帮我查一下时间'→不应该用 cron 技能"。

### 系统怎么加载 SKILL.md

当 `_register_skills()` 调用 `toolkit.register_agent_skill(str(skill_dir))` 时，底层发生了什么？

系统使用 `python-frontmatter` 库来解析 SKILL.md。解析发生在 `skills_manager.py` 第 1971-2014 行的 `_read_skill_from_dir()` 中：

```python
def _read_skill_from_dir(skill_dir, source):
    skill_md = skill_dir / "SKILL.md"
    content = read_text_file_with_encoding_fallback(skill_md)
    post = frontmatter.loads(content)
    description = str(post.get("description", "") or "")
    # ... 读取 references/ 和 scripts/ 目录树
    return SkillInfo(
        name=skill_dir.name,
        description=description,
        content=content,       # 完整的 SKILL.md 内容
        ...
    )
```

注意：`SkillInfo` 的 `content` 字段保存了 SKILL.md 的**完整内容**（YAML 头 + Markdown 正文）。这个完整内容最终会被注入到 Agent 的系统提示词中。Agent 在 ReAct 循环中能看到这段内容，就像一个人类员工翻开了操作手册。

### 双语技能的命名规则

如果你浏览内置技能目录（`src/qwenpaw/agents/skills/`），会发现每个技能都有 `-en` 和 `-zh` 两个变体：

```
skills/
  cron-en/          ← 英文版
  cron-zh/          ← 中文版
  news-en/
  news-zh/
  pdf-en/
  pdf-zh/
```

这不是约定俗成的命名习惯，而是系统强制的格式。`skills_manager.py` 第 65-67 行定义了一个正则表达式：

```python
_BUILTIN_SKILL_DIR_RE = re.compile(
    r"^(?P<name>.+)-(?P<language>en|zh)$",
)
```

目录名必须是 `{技能名}-{语言代码}` 格式。系统根据用户的语言偏好来选择合适的变体。你创建自定义技能时不需要遵循这个命名规则——它只对内置技能有约束。自定义技能的目录名可以是任何合法的名字（如 `my_news_digest`）。

## 工程权衡：Skill 设计中的三个决策

在动手写代码之前，让我们思考 Skill 设计中的几个权衡。

### 权衡一：指令精确度 vs 灵活性

Skill 的 Markdown 正文是给大语言模型看的自然语言指令。这就带来一个张力：指令越精确，Agent 执行越可靠；但指令越灵活，Agent 能处理的场景越广。

`cron-en` 选择了高精确度的路线。它的 "Hard Rules" 部分列出了几条铁律，比如"所有命令必须带 `--agent-id`"。这种写法几乎消除了模型犯错的空间，但也限制了灵活性——如果用户想用一种非标准的方式创建定时任务，Agent 可能会拒绝。

`news-en` 选择了更灵活的路线。它只给了 Agent 一张 URL 表格和几个步骤，没有严格的格式要求。Agent 可以自由决定怎么组织回复内容。这更灵活，但也意味着不同 Agent 可能用不同风格回复。

一个好的实践是：**涉及系统命令和安全操作的部分要精确，涉及内容生成的部分可以灵活**。cron 技能中"必须带 `--agent-id`"是精确的（因为不带会出错），但"回复内容的格式"是灵活的。

### 权衡二：单文件 vs 多文件

最简单的 Skill 只有一个 SKILL.md。但有些 Skill（比如 pdf-en）带了大量参考文档和脚本。

**单文件的好处**：简单、维护成本低、加载快。Agent 不需要阅读额外文件就能完成任务。

**多文件的好处**：SKILL.md 可以保持精简（只写核心指令），详细的参考信息放在 references/ 目录下按需加载。对于复杂技能（比如 PDF 处理有几十种操作），把所有细节塞进一个文件会让 Agent 信息过载。

`pdf-en` 的做法值得借鉴：SKILL.md 只写核心流程和常见操作，详细的 API 说明放在 `reference.md`，表单填写指南放在 `forms.md`。Agent 按需读取这些文件，而不是一次读完所有内容。

### 权衡三：内置 vs 用户自定义

QwenPaw 的 Skill 有两个来源：

1. **内置技能**：随源码发布在 `src/qwenpaw/agents/skills/` 下，有 `-en`/`-zh` 双语变体，通过 `import_builtin_skills()` 导入到技能池
2. **自定义技能**：用户在工作区的 `skills/` 目录下创建，不需要双语变体

内置技能走了一条"源码 → 技能池 → 工作区"的分发路径（`skills_manager.py` 第 1224-1358 行的 `import_builtin_skills()`）。用户自定义技能则直接在工作区目录下生效。

这个设计的好处是：**内置技能可以被所有工作区共享**（通过技能池），而自定义技能只属于一个工作区。代价是内置技能的更新需要走 import 流程，不如自定义技能那样"改了就生效"。

## 动手：从零写一个新闻摘要 Skill

理论讲够了。现在让我们造一个完整的 Skill——一个新闻摘要技能。和系统内置的 `news` 技能不同，我们这个技能专注于英文科技新闻摘要，并且支持通过 Cron 定时推送。

### 步骤一：创建 Skill 目录

假设你的工作区在 `workspaces/my_agent/`。在该工作区的 `skills/` 目录下创建技能文件夹：

```
workspaces/my_agent/skills/tech_news_digest/
  SKILL.md
```

只需要创建一个文件夹和一个文件。

### 步骤二：编写 SKILL.md

这是整个 Skill 的核心。我们来写一份完整的 SKILL.md：

```markdown
---
name: tech_news_digest
description: Fetch and summarize the latest English-language tech news
  from Hacker News and TechCrunch. Provides categorized headlines
  with source links.
metadata:
  qwenpaw:
    emoji: "📡"
    requires:
      bins: []
      env: []
---

# Tech News Digest

## When to Use

Use this skill when the user asks for:
- "latest tech news"
- "what's happening in technology"
- "tech news digest"
- "show me Hacker News headlines"
- "what's trending on TechCrunch"

### Should Not Use
- User asks for non-tech news (use general news skill instead)
- User asks about a specific stock price (use financial tools)
- User only wants weather or time info

## News Sources

| Source         | URL                              | Focus              |
|----------------|----------------------------------|---------------------|
| Hacker News    | https://news.ycombinator.com/    | Startups & coding   |
| TechCrunch     | https://techcrunch.com/          | Startups & venture  |
| Ars Technica   | https://arstechnica.com/         | Science & tech      |

## How to Fetch News

1. Use **browser_use** with `{"action": "open", "url": "<URL>"}`
   to open each source.
2. Then call **browser_use** with `{"action": "snapshot"}`
   to capture page content.
3. Extract the top 5-10 headlines and summaries.
4. Organize the reply as a numbered list:
   **Headline** - one-sentence summary _(Source)_

## Summary Format

Reply with:

```
📡 Tech News Digest - [Today's Date]

1. **Headline** - Brief summary _(Source)_
2. **Headline** - Brief summary _(Source)_
...

Trending topics: [list 2-3 keywords]
```

## Cron Scheduling

When the user asks for recurring news digests (e.g. "send me tech
news every morning"), create a cron job:

```bash
qwenpaw cron create \
  --agent-id <agent_id> \
  --type agent \
  --name "Daily Tech News" \
  --cron "0 9 * * *" \
  --channel <channel> \
  --target-user <user> \
  --target-session <session> \
  --text "Show me today's tech news digest"
```

Confirm the schedule, channel, and target with the user
before creating the job.

## Notes

- If a source is unreachable, skip it and note the failure.
- Keep summaries concise (1-2 sentences per headline).
- Always include source links so the user can read more.
```

这就是一个完整的 SKILL.md。让我们拆解它的结构：

**YAML 头部**（第 1-12 行）声明了元数据：
- `name: tech_news_digest` -- 技能名称
- `description` -- 一句话描述，模型靠它判断"要不要用这个技能"
- `metadata.qwenpaw.emoji` -- 界面展示的图标
- `metadata.qwenpaw.requires` -- 系统依赖（这里为空，因为不需要额外的系统命令）

**Markdown 正文**（第 14 行起）是给 Agent 的操作手册：
- **When to Use**：明确触发条件，减少误触发
- **News Sources**：新闻源 URL 表格——这是 Skill 的核心数据
- **How to Fetch News**：操作步骤，指导 Agent 用 browser_use 工具抓取
- **Summary Format**：回复格式模板，确保输出一致
- **Cron Scheduling**：定时调度指令，告诉 Agent 怎么创建 Cron 任务
- **Notes**：注意事项

### 步骤三：理解 Cron 调度的集成

上面的 SKILL.md 中有一个 "Cron Scheduling" 部分。它展示了 Skill 和 Cron 调度之间的协作方式。

当用户说"每天早上 9 点帮我看看科技新闻"时，Agent 的处理流程是：

```
用户: "每天早上 9 点帮我看看科技新闻"
        │
        ▼
Agent 读到 cron 技能的 When to Use:
  "User asks for automatic execution on a schedule"
  → 判断: 应该使用 cron 技能
        │
        ▼
Agent 读到 tech_news_digest 技能的 Cron Scheduling 部分:
  → 获得 cron create 命令模板
  → 确认参数: 时间、渠道、目标用户、目标会话
        │
        ▼
Agent 执行:
  qwenpaw cron create \
    --agent-id xxx \
    --type agent \
    --name "Daily Tech News" \
    --cron "0 9 * * *" \
    --channel console \
    --target-user user \
    --target-session session \
    --text "Show me today's tech news digest"
        │
        ▼
Cron 系统在每天 9:00 触发:
  → 向 Agent 发送 "Show me today's tech news digest"
  → Agent 读到 tech_news_digest 技能
  → 用 browser_use 抓取新闻
  → 返回摘要
```

Cron 表达式 `0 9 * * *` 的含义：

```
┌──────── 分钟 (0-59)
│ ┌────── 小时 (0-23)
│ │ ┌──── 日 (1-31)
│ │ │ ┌── 月 (1-12)
│ │ │ │ ┌ 星期 (0-6, 0=周日)
│ │ │ │ │
0 9 * * *   → 每天 9:00
0 */2 * * * → 每 2 小时
30 8 * * 1-5 → 工作日 8:30
0 0 * * 0   → 每周日 0:00
*/15 * * * * → 每 15 分钟
```

cron-en 技能（`src/qwenpaw/agents/skills/cron-en/SKILL.md`，第 145-153 行）提供了一张速查表：

```markdown
## Cron Expression Examples

0 9 * * *      Every day at 9:00
0 */2 * * *    Every 2 hours
30 8 * * 1-5   Weekdays at 8:30
0 0 * * 0      Every Sunday at midnight
*/15 * * * *   Every 15 minutes
```

Agent 不需要记住这些表达式——它只需要在 Cron Scheduling 部分引用这个表格，把用户的需求翻译成对应的表达式。

### 步骤四：Skill 如何被发现和注册

你把 SKILL.md 放在工作区的 `skills/` 目录下后，系统会在下次请求时自动发现它。这个过程我们再来细化一下：

1. 用户发消息 → Agent 收到请求
2. Agent 调用 `_register_skills()`（`react_agent.py` 第 309 行）
3. 该方法调用 `ensure_skills_initialized()`（`skills_manager.py` 第 1665 行）
4. 这触发了 `reconcile_workspace_manifest()`（第 1509 行）
5. 对账函数扫描 `workspace/skills/` 目录，发现了 `tech_news_digest/SKILL.md`
6. 解析 SKILL.md 的 frontmatter，提取元数据
7. 写入 `workspace/skill.json` 清单（新增 `tech_news_digest` 条目）
8. 回到 `_register_skills()`，技能被注册到 Toolkit
9. SKILL.md 的完整内容被注入到系统提示词中

整个过程不需要你做任何额外操作——文件放进去就够了。不过有一点需要注意：**新发现的技能默认是 `enabled: false`**。你需要手动启用它。

### 步骤五：启用和配置技能

启用技能有两种方式：

**方式一：通过 API**

QwenPaw 的 HTTP API 提供了技能管理端点。调用启用接口：

```
POST /api/skills/tech_news_digest/enable
```

**方式二：手动修改清单**

直接编辑 `workspaces/my_agent/skill.json`：

```json
{
  "skills": {
    "tech_news_digest": {
      "enabled": true,
      "channels": ["all"],
      "source": "customized"
    }
  }
}
```

`channels` 字段控制技能在哪些渠道生效。`["all"]` 表示所有渠道。如果你只想让这个技能在 Discord 渠道可用，可以设为 `["discord"]`。

`resolve_effective_skills()` 函数（`skills_manager.py` 第 1647-1662 行）在每次请求时检查这两个字段：

```python
def resolve_effective_skills(workspace_dir, channel_name):
    manifest = read_skill_manifest(workspace_dir)
    resolved = []
    for skill_name, entry in sorted(manifest.get("skills", {}).items()):
        if not entry.get("enabled", False):
            continue                        # 跳过未启用的
        channels = entry.get("channels") or ["all"]
        if "all" in channels or channel_name in channels:
            skill_dir = get_workspace_skills_dir(workspace_dir) / skill_name
            if skill_dir.exists():
                resolved.append(skill_name)
    return resolved
```

这段代码的逻辑非常清晰：遍历所有技能 → 过滤掉未启用的 → 过滤掉渠道不匹配的 → 检查目录是否存在 → 返回有效技能列表。

## 进阶：写好一个 Skill 的五个要点

写完新闻摘要技能之后，让我们总结写好一个 Skill 的五个关键要点。这些要点来自阅读系统内置技能的经验。

### 要点一：触发条件要写得明确且排他

"When to Use" 部分是 Skill 最重要的部分。它决定了模型会不会在正确的时机选择你的技能。

内置技能 `cron-en` 给出了好的范例（第 13-25 行）：

```markdown
### Should Use
- User asks to do something "daily / weekly / hourly"
- User asks for automatic reminders or execution
  "tomorrow at 9 AM / next Monday"

### Should Not Use
- The task only needs to be executed once right now
- It is just a normal reply within the current session
```

"Should Not Use" 部分经常被忽视，但它非常重要。如果没有它，模型可能会在用户说"帮我设个闹钟"时错误地触发 cron 技能（因为 cron 和闹钟有相似的时间调度语义）。明确的排除条件能大幅减少误触发。

### 要点二：提供具体的命令模板

如果你的 Skill 需要执行系统命令（如 `qwenpaw cron create`），一定要在 Markdown 中提供完整的命令模板，包括所有参数。

`cron-en` 在这方面做得非常好。它不仅列出了命令格式（第 55-76 行），还给出了完整的创建示例（第 100-122 行）：

```bash
qwenpaw cron create \
  --agent-id <agent_id> \
  --type text \
  --name "Daily Greeting" \
  --cron "0 9 * * *" \
  --channel imessage \
  --target-user "CHANGEME" \
  --target-session "CHANGEME" \
  --text "Good morning!"
```

`CHANGEME` 占位符告诉 Agent "这里需要向用户确认"。这比写 "请填写目标用户" 更精确——模型看到 CHANGEME 就知道必须停下来问用户。

### 要点三：描述常见错误

"Common Mistakes" 部分可以帮助模型规避典型的坑。`cron-en` 列出了四个常见错误（第 159-179 行）：

```markdown
### Mistake 1: Creating a cron job for a one-time immediate execution
### Mistake 2: Not passing --agent-id
### Mistake 3: Creating a task without complete information
### Mistake 4: Modifying existing tasks without checking first
```

这些错误来自实际运维经验。把它们写进 SKILL.md，相当于给 Agent 装了一个"避坑指南"。模型读到"Mistake 2: Not passing --agent-id"后，在执行 cron 命令时会特别注意检查是否包含了 `--agent-id` 参数。

### 要点四：控制 SKILL.md 的长度

SKILL.md 的内容会被注入到系统提示词中。系统提示词的长度直接影响每次 LLM 调用的 token 消耗和推理质量。

一个实用的原则：**SKILL.md 的正文控制在 200 行以内**。如果内容太多，把详细资料放在 `references/` 目录下，让 Agent 按需读取。

`news-en` 是一个好例子——它的 SKILL.md 只有 48 行，但包含了所有必要信息（新闻源表格、操作步骤、注意事项）。详细的数据源信息都在表格里了，不需要额外展开。

### 要点五：YAML 头部的 description 要一句话说清

YAML 头部的 `description` 字段有两个用途：在界面上展示技能列表，以及帮助模型快速判断技能是否相关。

好的 description：

```yaml
description: Use this skill only for scheduled or recurring tasks.
```

不好的 description：

```yaml
description: This skill helps manage cron jobs.
```

区别在于前者是**行为导向**的（"什么场景下用"），后者是**功能导向**的（"这个技能能做什么"）。模型在 ReAct 循环中需要快速判断"该不该用这个技能"，行为导向的描述更直接。

## 回顾：造一个新 Skill 的完整路径

这一章，我们从 Tool 和 Skill 的对比出发，最终造出了一个完整的新闻摘要技能。让我们回顾关键路径：

```
理解 Skill vs Tool 的定位区别
    │
    │  Tool = Python 代码，原子操作
    │  Skill = Markdown 指令，组合行为
    │
    ▼
创建 Skill 目录结构
    │
    │  my_skill/SKILL.md（必需）
    │  my_skill/references/（可选）
    │  my_skill/scripts/（可选）
    │
    ▼
编写 SKILL.md
    │
    │  YAML 头部: name + description + metadata
    │  Markdown 正文: When to Use + 操作步骤 + 常见错误
    │
    ▼
系统自动发现（reconcile）
    │
    │  文件系统就是注册表
    │  下次请求时自动生效
    │
    ▼
启用技能
    │
    │  skill.json 中 enabled: true
    │  配置 channels 渠道范围
    │
    ▼
Agent 在 ReAct 循环中使用
    │
    │  SKILL.md 内容注入系统提示词
    │  Agent 按指令行动
    │
    ▼
（可选）配置 Cron 定时调度
    │
    │  qwenpaw cron create ...
    │  定时触发 Agent 执行技能
```

整个过程涉及的文件：

| 文件 | 角色 | 操作 |
|------|------|------|
| `workspace/skills/tech_news_digest/SKILL.md` | 技能定义 | 新增 |
| `workspace/skill.json` | 技能清单 | 自动更新 + 手动启用 |

对比上一章造 Tool 的改动清单（三个文件），造 Skill 只需要创建一个文件。这就是 Markdown 指令集的核心优势：**创建成本极低，修改即时生效，不需要编程能力**。

当然，Skill 也有它的局限性。它不能执行任意的 Python 代码——它只能指导 Agent 使用已有的 Tool。如果你的需求超出了现有 Tool 的能力范围（比如"调用一个自定义的图像识别 API"），你需要先造一个 Tool（上一章的内容），然后再用 Skill 把它编排起来。
