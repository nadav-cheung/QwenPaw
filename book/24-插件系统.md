第十四章我们拆解了 Skill——一种以 Markdown 为载体的扩展机制。Skill 让用户可以在不写 Python 代码的情况下给 Agent 添加新能力。但 Skill 有一个根本的局限：**它不能引入新的 LLM Provider**。如果你想让 QwenPaw 支持一个新的模型提供商（比如 Groq、Mistral、或者你自己部署的私有模型），光靠 Markdown 指令是做不到的——你需要真正的 Python 代码。

这就是 Plugin 登场的理由。QwenPaw 有一套完整的插件系统（`src/qwenpaw/plugins/`），它允许第三方开发者用 Python 代码扩展系统的核心能力。

于是自然引出了本章的核心问题：**Plugin 和 Skill 到底有什么区别？为什么不只用其中一种？**

## 问题：Plugin 和 Skill 有什么区别？

如果你读了第十四章，你可能会困惑：QwenPaw 已经有了 Skill 作为扩展机制，为什么还要搞一套 Plugin？这不是重复造轮子吗？

答案藏在两种机制的设计目标中：

```
你：「我想让 Agent 会用 cron 定时任务。」

  方案 A（Skill）：
    写一份 Markdown 操作手册，告诉 Agent 怎么用 cron
    → 纯文本，零代码，热插拔
    → Agent"理解"手册后自己行动

  方案 B（Plugin）：
    写一个 Python 模块，向系统注册新的 Provider / Hook / Command
    → 真正的代码，可以调 API、发 HTTP 请求
    → 系统直接加载并执行
```

Skill 是"教 Agent 学新知识"，Plugin 是"给系统装新零件"。一个是教脑子，一个是换硬件。

更具体地说：

| 维度 | Skill | Plugin |
|------|-------|--------|
| 载体 | Markdown 文件（SKILL.md） | Python 代码 + JSON 清单（plugin.json） |
| 扩展对象 | Agent 的知识和行为 | 系统的核心能力（Provider、Hook、Command） |
| 能做什么 | 指导 Agent 使用已有工具 | 注册新的 LLM Provider、启动/关闭钩子、控制命令 |
| 安全性 | 高（纯文本，不执行代码） | 需要信任（执行任意 Python 代码） |
| 开发门槛 | 低（会写 Markdown 就行） | 中（需要写 Python 并遵循接口规范） |
| 热插拔 | 支持（每次请求重新扫描） | 不支持（需要重启服务） |
| 存放位置 | 工作目录的 `skills/` 子目录 | 全局 `plugins/` 目录（`~/.qwenpaw/plugins/`） |
| 典型用途 | cron 定时任务、PDF 操作、新闻抓取 | 接入新的模型提供商、自定义启动逻辑 |

它们不是竞争关系，而是互补关系。Skill 扩展的是 Agent 的"软实力"，Plugin 扩展的是系统的"硬实力"。一个好的 QwenPaw 扩展可能同时包含一个 Plugin（注册新的 Provider）和一个 Skill（教 Agent 怎么用好这个 Provider）。

## 术语其实很简单

> **术语：插件沙箱（Plugin Sandbox）**
>
> 想象你在一个商场里租了一个摊位。你可以卖自己的东西，但你不能拆商场的水管、不能改商场的电路、不能去别的摊位拿货。插件沙箱就是这个"摊位规则"——Plugin 可以自由定义自己的功能，但只能通过 PluginApi 提供的接口与系统交互。它不能直接访问其他模块的内部状态，不能修改系统核心的运行逻辑。QwenPaw 的沙箱是"接口级"的——通过限制 Plugin 可调用的 API 来约束其行为，而不是操作系统级的进程隔离。

> **术语：插件生命周期（Plugin Lifecycle）**
>
> 想象一个员工从入职到离职的全过程。入职：HR 审核简历、安排座位、办理工牌。工作：执行任务、参加例会、使用公司资源。离职：交接工作、归还设备、注销工牌。插件也有类似的完整周期：发现（扫描插件目录）→ 加载（读取清单、动态 import）→ 注册（调用插件的 `register()` 方法）→ 运行（提供能力）→ 卸载（从系统中移除）。QwenPaw 目前实现了前四个阶段，卸载需要重启服务。

| 文件 | 类 | 职责 |

| `architecture.py` | `PluginManifest`, `PluginRecord` | 数据结构定义 |

## 探索：第一阶段——发现（Discover）

### 插件的物理形态

一个插件的物理形态是一个目录，里面至少包含一个 `plugin.json` 文件。典型的结构如下：

```
my-provider/
  plugin.json      ← 清单文件（必需）
  plugin.py        ← 后端入口（Python 代码）
  requirements.txt ← 可选，Python 依赖
```

`plugin.json` 是插件的"身份证"。它声明了插件的基本信息：

```json
{
  "id": "my-provider",
  "name": "My Custom Provider",
  "version": "1.0.0",
  "description": "A custom LLM provider plugin",
  "author": "developer@example.com",
  "entry": {
    "backend": "plugin.py",
    "frontend": "index.js"
  },
  "dependencies": [],
  "min_version": "0.1.0",
  "meta": {}
}
```

注意 `entry` 字段。它指定了后端入口文件（`backend`）和前端入口文件（`frontend`）。`backend` 是 Python 文件，`frontend` 是 JavaScript 文件。一个插件可以只有后端、只有前端、或者两者都有。

### 数据结构：PluginManifest

`plugin.json` 的内容会被解析为 `PluginManifest` 数据类（architecture.py 第 18-58 行）：

```python
@dataclass
class PluginManifest:
    id: str
    name: str
    version: str
    description: str = ""
    author: str = ""
    entry: PluginEntryPoints = field(default_factory=PluginEntryPoints)
    dependencies: List[str] = field(default_factory=list)
    min_version: str = "0.1.0"
    meta: Dict[str, Any] = field(default_factory=dict)
```

`PluginEntryPoints`（第 10-12 行）是一个嵌套数据类，分别持有 `frontend` 和 `backend` 入口路径：

```python
@dataclass
class PluginEntryPoints:
    frontend: Optional[str] = None
    backend: Optional[str] = None
```

值得注意的是第 42-45 行的兼容处理：如果清单中没有 `entry` 字段但有旧的 `entry_point` 字段，它会被映射到 `entry.backend`。这保证了旧格式的插件清单仍然可以正常加载：

```python
legacy_entry_point = data.get("entry_point", "plugin.py")
entry = PluginEntryPoints(
    frontend=entry_data.get("frontend"),
    backend=entry_data.get("backend") or legacy_entry_point,
)
```

### 扫描目录

`PluginLoader.discover_plugins()`（loader.py 第 32-65 行）负责扫描插件目录：

```python
for item in plugin_dir.iterdir():
    if not item.is_dir():
        continue
    manifest_path = item / "plugin.json"
    if not manifest_path.exists():
        continue
    try:
        manifest = self._load_manifest(manifest_path)
        discovered.append((manifest, item))
    except Exception as e:
        logger.error(f"Failed to load manifest: {e}")
```

逻辑非常直接：遍历插件目录的每个子目录，如果里面有 `plugin.json` 文件，就解析它并加入"已发现"列表。和 Skill 的发现机制类似——**文件系统就是注册表**。但有一个关键区别：Skill 的发现发生在**每次请求**时（热插拔），而 Plugin 的发现只发生在**服务启动时**。

## 探索：第二阶段——加载（Load）

### 动态导入：让插件代码活起来

发现只是读取了 `plugin.json`，知道"有这个插件"。加载才是真正让插件的 Python 代码活起来的过程。

`PluginLoader.load_plugin()`（loader.py 第 84-228 行）是整个插件系统最复杂也最有趣的方法。它的核心是 Python 的 `importlib` 动态导入机制。

首先，它检查入口文件是否存在（第 112-140 行）。一个插件必须至少有一个入口文件（后端或前端），否则抛出 `FileNotFoundError`。如果只有前端没有后端，系统会跳过后端加载，作为"纯前端插件"处理。

对于有后端的插件，真正的魔法发生在第 149-215 行。核心代码如下：

```python
module_name = f"plugin_{plugin_id.replace('-', '_')}"
spec = importlib.util.spec_from_file_location(
    module_name,
    backend_entry_file,
    submodule_search_locations=[plugin_dir_str],
)
module = importlib.util.module_from_spec(spec)
sys.modules[module_name] = module
module.__package__ = module_name
module.__path__ = [plugin_dir_str]
spec.loader.exec_module(module)
```

这六行代码做了什么？让我们逐步拆解。

**第一行**：生成唯一的模块名。把插件 ID 中的连字符替换为下划线，加上 `plugin_` 前缀。比如 `my-provider` 变成 `plugin_my_provider`。这避免了不同插件之间的模块名冲突。

**第二行**：创建模块规格（spec）。`spec_from_file_location()` 从文件路径创建一个模块规格，而不是从标准的 Python 搜索路径。`submodule_search_locations` 参数特别重要——它允许插件目录中的相对导入。比如插件内部可以 `from .helpers import utils`。

**第三行**：从规格创建模块对象。

**第四行**：把模块注册到 `sys.modules`。这步是必需的，否则 Python 不知道这个模块的存在。

**第五行**：设置 `__package__` 和 `__path__`。这是让相对导入正确工作的关键。

**第六行**：执行模块代码。这一步真正读取 `.py` 文件并运行其中的代码。

### 模块契约：plugin 对象和 register 方法

加载的最后一步是检查插件模块是否遵循了"契约"。loader.py 第 177-208 行：

```python
if not hasattr(module, "plugin"):
    raise AttributeError(
        "Plugin module must export 'plugin' object",
    )
plugin_def = module.plugin

# ...创建 PluginApi 实例...

if hasattr(plugin_def, "register"):
    result = plugin_def.register(api)
    if inspect.iscoroutine(result):
        await result
else:
    raise AttributeError(
        "Plugin must implement 'register(api)' method",
    )
```

这段代码定义了每个插件必须满足的两个条件：

1. **导出 `plugin` 对象**：模块必须有一个名为 `plugin` 的顶级变量。它可以是任何对象（类实例、模块、对象等）。
2. **实现 `register(api)` 方法**：这个 `plugin` 对象必须有 `register()` 方法。该方法接收一个 `PluginApi` 实例，插件通过它向系统注册自己的能力。

一个典型的插件入口文件（`plugin.py`）长这样：

```python
class MyProviderPlugin:
    def register(self, api):
        api.register_provider(
            provider_id="my-provider",
            provider_class=MyProvider,
            label="My Custom Provider",
            base_url="https://api.example.com/v1",
        )

plugin = MyProviderPlugin()
```

注意 `register()` 方法支持同步和异步两种形式。loader.py 第 199-204 行用 `inspect.iscoroutine()` 检测返回值——如果是协程就 `await`，否则直接执行。这意味着插件可以在 `register()` 中使用 `async def`。

### PluginRecord：加载结果的封装

加载成功后，系统创建一个 `PluginRecord`（architecture.py 第 62-69 行）：

```python
@dataclass
class PluginRecord:
    manifest: PluginManifest    # 清单信息
    source_path: Path           # 插件目录路径
    enabled: bool               # 是否启用
    instance: Optional[Any]     # plugin 对象实例
    diagnostics: List[str]      # 诊断信息
```

这个数据结构是插件在内存中的"档案"。`instance` 字段保存了 `module.plugin` 的引用——如果系统后续需要与插件交互（比如调用生命周期钩子），就通过这个引用。

## 探索：第三阶段——注册（Register）

### PluginApi：插件开发者的工具箱

`PluginApi`（api.py 第 10-186 行）是插件系统暴露给插件开发者的接口。每个插件在加载时获得一个独立的 `PluginApi` 实例。

它的构造函数（第 17-33 行）接收三个参数：

```python
def __init__(self, plugin_id, config, manifest=None):
    self.plugin_id = plugin_id
    self.config = config
    self.manifest = manifest or {}
    self._registry = None
```

- `plugin_id`：插件的唯一标识，来自 `plugin.json` 的 `id` 字段。
- `config`：用户为这个插件提供的配置（来自全局配置文件的 `plugins` 字段）。
- `manifest`：清单信息的字典形式。

`_registry` 初始为 `None`，通过 `set_registry()` 方法注入（api.py 第 35-40 行）。这种"先创建、后注入"的设计让 `PluginApi` 可以在不依赖 `PluginRegistry` 的情况下被实例化——方便测试。

### 四个注册方法

`PluginApi` 提供了四个注册方法，每个方法都遵循相同的模式：检查 `_registry` 是否存在，调用 registry 的对应方法，记录日志。让我们逐一看看。

**register_provider()**（api.py 第 43-87 行）

这是最核心的注册方法。它让插件可以向系统注册一个新的 LLM Provider：

```python
def register_provider(self, provider_id, provider_class,
                      label="", base_url="", **metadata):
    merged_metadata = dict(metadata)
    if "meta" in self.manifest:
        merged_metadata["meta"] = self.manifest["meta"]
    self._registry.register_provider(
        plugin_id=self.plugin_id,
        provider_id=provider_id,
        provider_class=provider_class,
        label=label or provider_id,
        base_url=base_url,
        metadata=merged_metadata,
    )
```

注意第 72-74 行的元数据合并逻辑：插件的 `plugin.json` 中的 `meta` 字段会被合并到 Provider 的元数据中。这意味着插件开发者可以在清单中声明一些通用的元信息（比如 API Key 的获取地址、提示信息），而不用在 Python 代码中硬编码。

**register_startup_hook() / register_shutdown_hook()**（api.py 第 89-151 行）

这两个方法让插件可以注册在系统启动或关闭时执行的回调函数。`priority` 参数控制执行顺序——数字越小越早执行（默认 100）。

**register_control_command()**（api.py 第 153-174 行）

让插件注册一个控制命令处理器。控制命令是系统级的指令，比如管理 Agent、修改配置等。`priority_level` 参数控制命令的优先级。

### PluginRegistry：能力的中央存储

`PluginRegistry`（registry.py 第 42-254 行）是插件系统的"中央仓库"。所有插件注册的能力都存储在这里。

它是一个**单例**（registry.py 第 49-55 行）：

```python
class PluginRegistry:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance._initialized = False
        return cls._instance
```

单例模式保证了整个系统只有一个 Registry 实例。无论你在哪里创建 `PluginRegistry()`，拿到的都是同一个对象。这是为了让 `PluginApi` 和 `_app.py` 中的启动逻辑可以共享同一个注册表。

Registry 内部用三个数据结构存储注册信息：

```python
self._providers: Dict[str, ProviderRegistration] = {}
self._startup_hooks: List[HookRegistration] = []
self._shutdown_hooks: List[HookRegistration] = []
self._control_commands: List[ControlCommandRegistration] = []
```

每种注册信息都有对应的数据类（registry.py 第 12-39 行）：`ProviderRegistration`、`HookRegistration`、`ControlCommandRegistration`。它们是简单的数据容器，存储注册的详细信息。

### Provider 注册的冲突检测

`register_provider()`（registry.py 第 73-112 行）有一个重要的安全检查——**冲突检测**：

```python
if provider_id in self._providers:
    existing = self._providers[provider_id]
    raise ValueError(
        f"Provider '{provider_id}' already registered "
        f"by plugin '{existing.plugin_id}'",
    )
```

如果两个插件试图注册同一个 `provider_id`，后注册的会失败并抛出 `ValueError`。这防止了命名冲突——你不能用别人的 Provider ID 覆盖别人的注册。

### Hook 的优先级排序

`register_startup_hook()` 和 `register_shutdown_hook()` 在注册时自动按 `priority` 排序（registry.py 第 171-172 行）：

```python
self._startup_hooks.append(hook)
self._startup_hooks.sort(key=lambda h: h.priority)
```

这意味着你不需要手动控制 Hook 的执行顺序。如果你想让你的 Hook 在所有其他 Hook 之前执行，只需要设置一个很小的 `priority`（比如 0）。

## 探索：第四阶段——注入系统（Inject）

插件的能力注册到 `PluginRegistry` 之后，还需要被注入到系统核心才能真正生效。这个过程发生在 `_app.py` 的 `_background_startup()` 函数中（第 303-349 行）。

### 启动时序

```
服务启动
    │
    ├── 1. 启动所有配置的 Agent
    │      await multi_agent_manager.start_all_configured_agents()
    │
    ├── 2. 初始化插件系统
    │      plugin_loader = PluginLoader([get_plugins_dir()])
    │
    ├── 3. 加载所有插件（发现 + 加载 + 注册到 Registry）
    │      loaded_plugins = await plugin_loader.load_all_plugins(configs)
    │
    ├── 4. 创建 RuntimeHelpers，注入到 Registry
    │      runtime_helpers = RuntimeHelpers(provider_manager)
    │      plugin_loader.registry.set_runtime_helpers(runtime_helpers)
    │
    ├── 5. 把 Registry 中的 Provider 注入到 ProviderManager
    │      for provider_id, provider_reg in registry.get_all_providers():
    │          provider_manager.register_plugin_provider(...)
    │
    └── 6. 保存 plugin_loader 到 app.state
           app.state.plugin_loader = plugin_loader
```

第 329-344 行是把插件 Provider 注入到 ProviderManager 的关键代码：

```python
runtime_helpers = RuntimeHelpers(provider_manager=provider_manager)
plugin_loader.registry.set_runtime_helpers(runtime_helpers)

for provider_id, provider_reg in \
    plugin_loader.registry.get_all_providers().items():
    provider_manager.register_plugin_provider(
        provider_id=provider_id,
        provider_class=provider_reg.provider_class,
        label=provider_reg.label,
        base_url=provider_reg.base_url,
        metadata=provider_reg.metadata,
    )
```

这里有一个微妙的顺序依赖：**RuntimeHelpers 必须在 Provider 注册之前注入**。为什么？因为如果一个插件的 `register()` 方法内部调用了 `api.runtime`，而 RuntimeHelpers 还没有设置好，它会返回 `None`。

### ProviderManager 的对接

`ProviderManager.register_plugin_provider()`（provider_manager.py 第 1632-1674 行）把插件提供的 Provider 和内置 Provider 放在同一个管理层级。它创建一个 `ProviderInfo` 对象，从中提取默认模型列表：

```python
default_models = []
if hasattr(provider_class, "get_default_models"):
    default_models = provider_class.get_default_models()

provider_info = ProviderInfo(
    id=provider_id,
    name=label,
    base_url=base_url,
    api_key="",  # 稍后由用户配置
    chat_model=metadata.get("chat_model", "OpenAIChatModel"),
    models=default_models,
    require_api_key=metadata.get("require_api_key", True),
    meta=metadata.get("meta", {}),
)
```

注意 `api_key=""`。插件注册的 Provider 默认没有 API Key——用户需要在设置界面手动配置。另外，`is_custom=False` 意味着插件 Provider 被视为"内置级别"的 Provider，不能通过界面删除（只能卸载整个插件）。

### RuntimeHelpers：安全的系统访问

`RuntimeHelpers`（runtime.py 第 10-67 行）是插件访问系统能力的"安全窗口"。它提供三个功能：

```python
class RuntimeHelpers:
    def get_provider(self, provider_id): ...   # 获取 Provider 实例
    def list_providers(self) -> List[str]: ...  # 列出所有 Provider ID
    def log_info(self, message): ...            # 写日志
    def log_error(self, message, exc_info=False): ...
    def log_debug(self, message): ...
```

这些功能看似简单，但它们的实现有一个重要特征：**所有方法都通过 `provider_manager` 间接访问系统资源，而不是直接操作内部数据结构**。插件拿不到 `ProviderManager` 本身——它只能通过 `RuntimeHelpers` 的方法来查询信息。

这就是"接口级沙箱"的实现方式：插件能做什么，完全由 `PluginApi` 和 `RuntimeHelpers` 的公开方法决定。

## Plugin vs Skill：为什么两者都需要

回到本章的核心问题。现在我们已经深入理解了两种机制，可以从设计层面回答"为什么不只用一种"了。

### 能力层级不同

```
┌───────────────────────────────────────────────────────────────┐
│                    扩展能力金字塔                                │
│                                                               │
│                     ┌─────────┐                               │
│                     │  修改    │                               │
│                     │ 核心逻辑 │ ← 需要直接改源码                │
│                    ┌┴─────────┴┐                              │
│                    │  添加新    │                               │
│                    │ Provider  │ ← 需要 Plugin                  │
│                   ┌┴───────────┴┐                             │
│                   │  注册 Hook  │ ← 需要 Plugin                  │
│                   │  /Command  │                               │
│                  ┌┴─────────────┴┐                            │
│                  │   教 Agent    │                             │
│                  │   新知识      │ ← Skill 就够了                 │
│                 ┌┴───────────────┴┐                           │
│                 │  使用已有工具    │                            │
│                 │  完成新任务      │ ← Skill 就够了               │
│                 └─────────────────┘                           │
│                                                               │
│  越往上层，能力越强，但安全风险和开发门槛也越高                      │
└───────────────────────────────────────────────────────────────┘
```

Skill 只能利用系统已有的能力（Tool、MCP 工具等），通过自然语言指导 Agent 使用它们。Plugin 可以向系统添加全新的能力——新的 Provider、新的启动/关闭逻辑、新的控制命令。

### 安全模型不同

Skill 是纯文本，不执行任何代码。即使一个恶意的 Skill 文件，最坏的情况也不过是给 Agent 错误的指令。Plugin 是真正的 Python 代码，它可以在注册阶段做任何事情——访问文件系统、发起网络请求、修改进程状态。

这就是为什么 Plugin 需要更多的安全考虑：

1. **安装需要确认**：`qwenpaw plugin install` 命令会明确告诉用户正在安装什么。
2. **运行时需要重启**：不像 Skill 可以热插拔，Plugin 的加载需要重启服务——这是一个隐式的"确认步骤"。
3. **接口级沙箱**：`PluginApi` 只暴露有限的注册方法，`RuntimeHelpers` 只暴露安全的查询和日志方法。

### 开发体验不同

Skill 的开发者只需要会写 Markdown。Plugin 的开发者需要写 Python 代码、理解 `PluginApi` 接口、遵循模块契约（导出 `plugin` 对象、实现 `register` 方法）。两者的开发门槛和灵活性的权衡正好处于频谱的两端。

## 工程权衡：插件系统的设计选择

### 为什么用 importlib 而不是 exec？

`loader.py` 使用 `importlib.util.spec_from_file_location()` 来加载插件模块，而不是简单的 `exec()`。这个选择有几个理由：

1. **模块隔离**：每个插件被加载为独立的 Python 模块（`plugin_{id}`），有自己的命名空间。如果用 `exec()`，所有插件代码会在同一个全局命名空间中执行，变量名可能冲突。

2. **相对导入支持**：`submodule_search_locations` 参数（第 157-160 行）允许插件目录中的模块使用相对导入。这意味着一个复杂的插件可以分成多个 Python 文件，用标准的包导入机制组织代码。

3. **sys.modules 注册**：第 168 行把插件模块注册到 `sys.modules`，这样其他代码可以通过 `import plugin_my_provider` 来引用它（虽然目前没有使用这个特性，但它为未来留下了可能）。

### 为什么 Registry 是单例？

`PluginRegistry` 使用单例模式（registry.py 第 49-55 行）。这意味着：

- **好处**：全局唯一的注册表，任何地方创建 `PluginRegistry()` 都拿到同一个实例。`PluginApi` 和 `_app.py` 中的注入逻辑天然共享状态。
- **代价**：单例在测试中是已知的痛点——测试之间需要清理状态。当前实现通过 `_initialized` 标志来避免重复初始化，但没有提供"重置"方法。

一个替代方案是把 Registry 作为依赖注入的参数传递，而不是让每个使用者自己去创建。当前的单例设计是"够用就行"的实用主义选择。

### 为什么不提供热插拔？

Skill 支持热插拔，Plugin 不支持。这不是疏忽，而是有意为之。

Skill 的热插拔之所以安全，是因为 Skill 不执行代码——它只是一段文本，注入到提示词中。加载和卸载只是"读取/不读取"的区别。

Plugin 的热插拔要复杂得多：

1. 一个已注册的 Provider 可能正在被活跃使用（有正在进行的 LLM 请求）。
2. 已注册的 Hook 可能正在执行中。
3. 插件模块中创建的对象可能被系统其他部分持有引用。
4. 动态卸载 Python 模块是不安全的——`sys.modules` 中的引用、全局状态、C 扩展等都无法干净地清理。

要实现 Plugin 的热插拔，需要类似第 23 章的 MultiAgentManager 的"零停机重载"机制——创建新实例、原子替换、优雅停止旧实例。目前的插件系统还没有达到这个复杂度。

### 前端插件的设计空间

`PluginManifest` 中的 `entry.frontend` 字段（architecture.py 第 14 行）暗示了前端插件的存在。一个插件可以同时注册后端能力（Provider、Hook）和前端能力（UI 组件、设置页面）。

当前的后端加载逻辑会跳过没有后端入口的纯前端插件（loader.py 第 143-147 行）。前端插件的加载机制（如何在 Web UI 中动态加载 JavaScript 模块）是一个待完善的设计空间。
