## 问题：改了这里，会不会破坏那里？

假设你修改了 `BaseChannel.resolve_session_id()` 的返回格式——原来返回 `"console:user123"`，现在你想改成 `"console/user123"`。这是一个看起来很小的改动，对吧？

但 QwenPaw 有 12 个 Channel 子类（Telegram、Discord、钉钉、飞书、QQ、Matrix、Mattermost、MQTT、iMessage、WeCom、WeChat、XiaoYi），每个都依赖这个方法。还有 Agent 的 session 管理、消息路由、权限检查……

改一行代码，12 个 Channel 可能全部挂掉。

如果没有测试，你只有两种选择：要么手动测试每一个 Channel（不现实），要么祈祷没出问题（更不现实）。这就是为什么一个 411 个文件的项目需要系统化的测试策略。

---

## 术语其实很简单

> **术语：测试金字塔（Test Pyramid）**
>
> 想象一座金字塔。底部最宽，代表数量最多、运行最快的单元测试（Unit Test）；中间是集成测试（Integration Test）；顶部最窄，代表数量最少、运行最慢的端到端测试（E2E Test）。为什么要是金字塔而不是倒金字塔？因为底部的单元测试最便宜：它们不依赖外部服务、不启动网络服务器、几毫秒就能跑完。如果底部不牢，整个金字塔就会头重脚轻——你花了大量时间等待缓慢的 E2E 测试，却发现只是一个简单的字符串拼接错误。

> **术语：pytest**
>
> pytest 是 Python 世界的测试框架王者。你不需要继承任何基类、不需要写一堆样板代码——只要创建一个以 `test_` 开头的函数，写一个 `assert` 语句，pytest 就能帮你运行它。它的魔法在于：`assert result == expected` 如果失败了，pytest 会告诉你 `result` 的实际值是什么、`expected` 是什么，而不是只抛一个 "AssertionError"。它还有 fixture（共享测试环境）、marker（标记慢测试/快测试）、parametrize（一次测试多组数据）等强大功能。

> **术语：覆盖率（Coverage）**
>
> 想象你用荧光笔在一本书上划线——划了多少页，覆盖率就是多少。代码覆盖率测量的是"测试代码执行了多少生产代码"。100% 覆盖率不代表没有 Bug（你可能在测试里没检查边界条件），但 30% 覆盖率意味着有 70% 的代码从未被测试验证过。QwenPaw 把覆盖率门槛设在 30%——这是务实的起点，确保核心路径被覆盖，而不是追求不切实际的 100%。

> **术语：CI/CD（持续集成/持续部署）**
>
> 想象一家汽车工厂。每条流水线上的零件都要通过质检才能进入下一道工序——你不能等整车组装完了才发现螺丝没拧紧。CI（Continuous Integration）就是这条质检流水线：每次有人提交代码，自动运行测试、检查覆盖率、验证代码风格。如果测试失败，代码就不能合并。CD（Continuous Deployment）是后半段——测试通过后自动部署到服务器。QwenPaw 的 CI 由 GitHub Actions 驱动，每次 Pull Request 都会自动跑完整测试套件。

### 第二层：pytest 配置

QwenPaw 的 pytest 配置在 `pyproject.toml` 中：

```toml
# pyproject.toml (第 100-111 行)
[tool.pytest.ini_options]
asyncio_mode = "auto"
asyncio_default_fixture_loop_scope = "function"
markers = [
    "slow: marks tests as slow",
    "unit: marks tests as unit tests",
    "contract: marks tests as contract tests",
    "integration: marks tests as integration tests",
]
testpaths = ["tests"]
```

几个关键设置：

- **`asyncio_mode = "auto"`**：QwenPaw 大量使用 async/await（因为 LLM API 调用都是异步的），这个设置让你直接写 `async def test_xxx()` 就行，不需要额外装饰器。
- **`markers`**：测试标记。你可以在命令行用 `-m "not slow"` 来跳过慢测试，或者用 `-m unit` 只跑单元测试。
- **`testpaths`**：告诉 pytest 去哪里找测试文件。

覆盖率配置也在这里：

```toml
# pyproject.toml (第 113-135 行)
[tool.coverage.run]
source = ["src/qwenpaw"]
omit = ["*/tests/*", "*/test_*"]

[tool.coverage.report]
fail_under = 30        # 覆盖率低于 30% 就报错
show_missing = true    # 显示哪些行没被覆盖
```

`fail_under = 30` 意味着如果覆盖率掉到 30% 以下，CI 就会失败。这不是一个很高的门槛，但对于一个快速成长的项目来说，这是一个务实的起点。

### 第三层：conftest.py——测试的公共厨房

如果说测试文件是"餐厅"，那么 `conftest.py` 就是"中央厨房"——所有共享的原材料（fixtures）都在这里准备好。

`tests/conftest.py` 提供了几个关键 fixture：

**temp_workspace**——一个干净的临时目录，测试结束后自动清理：

```python
# tests/conftest.py (第 41-61 行)
@pytest.fixture
def temp_workspace() -> Generator[Path, None, None]:
    temp_dir = tempfile.mkdtemp(prefix="copaw_test_")
    try:
        yield Path(temp_dir)
    finally:
        shutil.rmtree(temp_dir, ignore_errors=True)
```

**temp_copaw_home**——一个隔离的"家"环境。它做了三件重要的事：

1. 创建临时目录，设置 `HOME` 和 `COPAW_HOME` 环境变量
2. 创建标准的 `.copaw/skills/`、`.copaw/logs/` 子目录
3. **清除所有敏感 API Key**（OpenAI、Anthropic、DingTalk 等），防止测试意外调用真实 API

```python
# tests/conftest.py (第 100-112 行)
sensitive_vars = [
    "OPENAI_API_KEY", "ANTHROPIC_API_KEY",
    "DASHSCOPE_API_KEY", "DINGTALK_APP_KEY",
    "FEISHU_APP_ID", "DISCORD_TOKEN",
    "TELEGRAM_BOT_TOKEN",
]
for var in sensitive_vars:
    monkeypatch.delenv(var, raising=False)
```

这段代码是"测试安全"的典范。想象一下：你在测试消息发送逻辑，但因为环境变量里有一个真实的 Telegram Bot Token，测试意外地给一个真实群组发了消息。清除敏感变量就是防止这种灾难。

**mock_llm_provider**——一个假的 LLM 提供者：

```python
# tests/conftest.py (第 126-175 行)
@pytest.fixture
def mock_llm_provider() -> MagicMock:
    mock = MagicMock()
    mock.chat.return_value = "Mock response"
    mock.chat_stream.return_value = iter(["Hello", " ", "world"])
    mock.embed.return_value = [0.1] * 1536
    mock.is_available.return_value = True
    return mock
```

这是一个 MagicMock，伪装成一个 LLM Provider。调用 `mock.chat()` 返回 "Mock response"，调用 `mock.embed()` 返回一个 1536 维的假向量。测试不需要真的去调用 GPT-4 API——那太慢、太贵、还可能因为网络问题随机失败。

还有一个巧妙的 trick 在文件开头：

```python
# tests/conftest.py (第 26-33 行)
_MISSING_MODULES = {
    "aibot",       # WeCom AI Bot SDK
    "lark_oapi",   # Feishu Lark SDK
}
for _module in _MISSING_MODULES:
    if _module not in sys.modules:
        sys.modules[_module] = MagicMock()
```

WeCom 的 `aibot` SDK 和飞书的 `lark_oapi` SDK不是所有开发者都装了。这段代码在 pytest 启动时把缺失的模块替换成 MagicMock，这样即使你没有安装 WeCom SDK，也能跑 Telegram Channel 的测试。这是一个"不要让别人的依赖阻塞你的开发"的实践。

### 第四层：单元测试——精确打击

单元测试是金字塔的底座。让我们看一个典型例子——`tests/unit/providers/test_openai_provider.py`。

这个文件测试的是 `OpenAIProvider` 类。看第一个测试：

```python
# tests/unit/providers/test_openai_provider.py (第 21-37 行)
async def test_check_connection_success(monkeypatch) -> None:
    provider = _make_provider()  # 创建一个假的 provider
    calls: list[float | None] = []

    class FakeModels:
        async def list(self, timeout=None):
            calls.append(timeout)
            return SimpleNamespace(data=[])

    fake_client = SimpleNamespace(models=FakeModels())
    monkeypatch.setattr(provider, "_client", lambda timeout=5: fake_client)

    ok, msg = await provider.check_connection(timeout=2.5)

    assert ok is True
    assert msg == ""
    assert calls == [2.5]
```

这个测试做了什么？

1. 创建一个 `OpenAIProvider` 实例（使用 mock URL 和 fake API Key）
2. 用 `monkeypatch` 把 `_client` 属性替换成一个假对象——这个假对象的 `models.list()` 方法不联网，直接返回空列表
3. 调用 `check_connection(timeout=2.5)`
4. 验证返回值是 `(True, "")`，并且 timeout 参数被正确传递了

注意 `monkeypatch`——这是 pytest 的内置 fixture，用于临时替换对象的属性或环境变量。测试结束后自动恢复，不会影响其他测试。

这个测试不依赖任何外部服务、不启动网络、不连接数据库。它只验证了一件事：**"如果 API 返回了正常响应，`check_connection` 会返回 True"**。整个执行时间不到 1 毫秒。

再看一个边界条件的测试：

```python
# tests/unit/providers/test_openai_provider.py (第 57-78 行)
async def test_list_model_normalizes_and_deduplicates(monkeypatch):
    rows = [
        SimpleNamespace(id="gpt-4o-mini", name="GPT-4o Mini"),
        SimpleNamespace(id="gpt-4o-mini", name="dup"),      # 重复 ID
        SimpleNamespace(id="gpt-4.1", name=""),              # 空名称
        SimpleNamespace(id="   ", name="invalid"),           # 空白 ID
    ]
    # ... mock setup ...
    models = await provider.fetch_models(timeout=3)

    assert [m.id for m in models] == ["gpt-4o-mini", "gpt-4.1"]
    assert [m.name for m in models] == ["GPT-4o Mini", "gpt-4.1"]
```

这个测试验证了 `fetch_models` 的去重和规范化逻辑：重复的模型 ID 被去重了、空名称被替换成了 ID、空白 ID 被过滤掉了。这些边界条件是 Bug 的高发区。

### 第五层：契约测试——防止"修了这里，坏了那里"

契约测试是 QwenPaw 测试体系中最精巧的部分。让我用 Channel 作为例子来解释。

还记得前面说的场景吗？你修改了 `BaseChannel` 的某个方法，12 个 Channel 子类可能全部挂掉。契约测试就是防止这种"蝴蝶效应"的机制。

它的原理是：定义一个基类 `ChannelContractTest`，里面写满了"所有 Channel 都必须满足的条件"。然后每个 Channel（Telegram、Discord、钉钉……）写一个子类，只需要提供 `create_instance()` 方法。pytest 会自动为每个子类运行基类里的所有测试。

```
ChannelContractTest (基类，20+ 个测试)
    │
    ├── test_no_abstract_methods_remaining
    ├── test_has_start_method
    ├── test_has_stop_method
    ├── test_has_send_method
    ├── test_has_from_config_method
    ├── test_resolve_session_id_returns_str
    ├── test_start_method_signature_compatible
    └── ... (更多契约)
    │
    ├── TestTelegramChannelContract
    │   └── create_instance() → TelegramChannel(...)
    │
    ├── TestDiscordChannelContract
    │   └── create_instance() → DiscordChannel(...)
    │
    └── ... (12 个 Channel)
```

来看看实际的契约测试代码：

```python
# tests/contract/channels/__init__.py (第 52-68 行)
def test_no_abstract_methods_remaining(self, instance):
    """CRITICAL: 所有抽象方法必须被实现"""
    cls = instance.__class__
    abstract_methods = getattr(cls, "__abstractmethods__", set())

    if abstract_methods:
        pytest.fail(
            f"{cls.__name__} has unimplemented abstract methods: "
            f"{', '.join(abstract_methods)}"
        )
```

这段代码检查一个 Channel 实例是否有未实现的抽象方法。如果 `BaseChannel` 新增了一个 `@abstractmethod`，所有 12 个 Channel 的这个测试都会失败——你不可能遗漏任何一个。

再看方法签名兼容性检查：

```python
# tests/contract/channels/__init__.py (第 193-215 行)
def test_start_method_signature_compatible(self, instance):
    """start() 不能有必填参数（除了 self）"""
    sig = inspect.signature(instance.start)
    params = list(sig.parameters.values())

    for param in params:
        if param.name in ("self", "cls"):
            continue
        if param.default is inspect.Parameter.empty:
            pytest.fail(
                f"{instance.__class__.__name__}.start() has "
                f"required parameter '{param.name}'"
            )
```

这验证的是：`start()` 方法不能要求额外的必填参数。如果某个 Channel 的 `start()` 需要 `start(config_file)`，那它就违反了基类契约——ChannelManager 调用 `channel.start()` 时不会传任何参数。

然后是每个 Channel 的契约测试文件——它们非常简洁：

```python
# tests/contract/channels/test_telegram_contract.py
class TestTelegramChannelContract(ChannelContractTest):
    def create_instance(self) -> "BaseChannel":
        from qwenpaw.app.channels.telegram.channel import TelegramChannel

        process = AsyncMock()
        return TelegramChannel(
            process=process,
            enabled=True,
            bot_token="test_token",
            # ... 必要的构造参数
        )
```

就这么多！`ChannelContractTest` 基类里的 20+ 个测试自动为 TelegramChannel 运行。如果你给 `BaseChannel` 加了新方法，只需要在基类里加一个 `test_xxx` 方法，12 个 Channel 的契约测试全部自动覆盖。

这种模式——基类定义契约、子类提供实例——是 pytest 的一个非常优雅的特性。它确保了：**修改 BaseChannel 时，不可能"忘了"测试某个子类**。

### 第六层：单元测试与契约测试的分工

你可能会问：`test_base_core.py`（1388 行）和 `test_telegram_contract.py`（45 行）有什么区别？它们不是都在测 Channel 吗？

`test_base_core.py` 的注释说得很清楚：

```python
# tests/unit/channels/test_base_core.py (第 7-15 行)
"""
Division of Labor with Contract Tests:
- Contract Tests (tests/contract/channels/):
  Verify external interface contracts, prevent breaking subclasses
- This Unit Test (tests/unit/channels/):
  Verify base class internal logic correctness
"""
```

翻译一下：

| 测试类型 | 关注点 | 示例 |
|---------|--------|------|
| 单元测试 | **内部逻辑对不对** | debounce 缓冲是否正确释放 |
| 契约测试 | **外部接口是否遵守** | 所有子类是否实现了 `start()` |

举个具体例子。`TestNoTextDebounceBuffering` 测试的是 BaseChannel 内部的 debounce（防抖）逻辑——当用户发了一张图片但没有文字时，Channel 应该先缓冲起来，等文字来了再一起处理：

```python
# tests/unit/channels/test_base_core.py (第 277-289 行)
def test_no_text_content_buffered_not_processed(self, base_channel, ...):
    parts = [content_builder.image("http://a.jpg")]
    should_process, merged = base_channel._apply_no_text_debounce(
        "session_1", parts,
    )
    assert should_process is False   # 不应该立刻处理
    assert merged == []               # 没有合并内容
    assert "session_1" in base_channel._pending_content_by_session
```

这是单元测试——验证 debounce 的内部状态是否正确。

而契约测试不会关心 debounce 的内部实现——它只关心"所有 Channel 都有 `channel` 属性"、"所有 Channel 都实现了 `start()` 和 `stop()`"。

这种分工是 QwenPaw 测试体系的精髓：**单元测试保证算法正确，契约测试保证接口一致**。

### 第七层：CI/CD 流水线——自动化的质检员

现在我们有了一堆测试。但测试只有被运行才有价值。这就是 CI/CD 的作用——每次提交代码，GitHub Actions 自动运行所有测试。

QwenPaw 的 CI 流水线定义在 `.github/workflows/tests.yml` 中。让我们画出它的结构：

```
  Push / PR
     │
     v
┌─────────────────────┐
```

流水线分四个 Job：

**Job 1：approval-gate**——维护者审批。不是谁都能往主分支合并代码的。

**Job 2：unit-tests**——单元测试矩阵。注意它的矩阵配置：

```yaml
# .github/workflows/tests.yml (第 40-48 行)
strategy:
  fail-fast: false
  matrix:
    python-version: ["3.10", "3.13"]
    os: [ubuntu-latest]
    include:
      - os: macos-latest
        python-version: "3.10"
      - os: windows-latest
        python-version: "3.10"
```

这意味着每次 PR 都会在 Linux + Python 3.10、Linux + Python 3.13、macOS + Python 3.10、Windows + Python 3.10 上跑测试。`fail-fast: false` 确保即使一个组合失败了，其他组合也会跑完——这样你一次就能看到所有问题。

**Job 3：integrated-tests**——集成测试。目前会检查 `tests/integrated/` 目录是否存在，存在才运行。

**Job 4：coverage-report**——覆盖率报告。它会做一件很酷的事：

```yaml
# .github/workflows/tests.yml (第 217-220 行)
- name: Generate coverage comment on PR
  uses: orgoro/coverage@v3.2
  with:
    coverageFile: coverage.xml
    token: ${{ github.token }}
```

这会在你的 PR 下面自动评论一个覆盖率报告——告诉你覆盖率是升了还是降了，哪些文件的覆盖率不够。这让 Code Review 的时候多了一个客观指标。

还有一个专用的 Channel 测试流水线 `.github/workflows/channel-tests.yml`。它更聪明——它会检测哪些文件被修改了，只运行受影响的 Channel 测试：

```
修改了 src/qwenpaw/app/channels/telegram/ → 只跑 Telegram 测试
修改了 src/qwenpaw/app/channels/base.py   → 跑所有 Channel 测试（因为基类改了）
```

这就是契约测试的价值在 CI 中的体现：基类修改会触发全部 12 个 Channel 的契约测试，确保没有子类被遗漏。

### 第八层：Makefile——测试的快捷入口

QwenPaw 的 `Makefile` 提供了一组简洁的测试命令：

```makefile
# Makefile (节选)
test:              # 跑所有测试
test-unit:         # 只跑单元测试
test-contract:     # 只跑契约测试
test-integration:  # 只跑集成测试
coverage-full:     # 生成完整覆盖率报告
quick:             # 快速检查（遇到第一个失败就停）
test-channel:      # 只跑 Channel 测试
check-contracts:   # 检查所有 Channel 契约
```

日常开发的典型工作流：

```bash
# 写代码时，快速循环
make quick

# 准备提交前，跑完整单元测试
make test-unit

# 修改了 Channel 相关代码
make test-channel
make test-channel-contract

# 想看覆盖率
make coverage-full
# 然后打开 htmlcov/index.html
```

`quick` 命令用了 `-x` 参数（遇到第一个失败就停止）和 `-q`（安静模式），让你的反馈循环尽可能短。这很重要——测试如果太慢，开发者就会不想跑测试。

## 工程权衡

QwenPaw 的测试体系有几个有意为之的权衡，值得理解：

**权衡一：30% 覆盖率门槛，而不是 80%**

QwenPaw 选择 `fail_under = 30` 而不是业界常见的 80%。为什么？因为 QwenPaw 是一个快速增长的开源项目。如果门槛设得太高，贡献者会被迫花大量时间给不重要的代码写测试，这会降低贡献意愿。30% 的门槛确保了核心路径（Channel、Provider、Agent）有基本的覆盖，而不会成为贡献的障碍。

**权衡二：契约测试优先于 100% 单元测试**

QwenPaw 对 Channel 的测试策略是：契约测试覆盖所有 12 个子类（确保接口一致性），但单元测试只覆盖 BaseChannel 和几个核心 Channel（确保逻辑正确性）。这意味着一些边缘 Channel（如 MQTT、Matrix）只有契约测试，没有详细的单元测试。这是一个务实的决定——12 个 Channel 都写完整的单元测试是一个巨大的工程量，而契约测试用很少的代码就保证了最基本的正确性。

**权衡三：E2E 测试预留但不强制**

`tests/e2e/` 目录几乎为空——只有一个 `test_version.py`。QwenPaw 选择把精力集中在单元测试和契约测试上，而不是花力气搭建复杂的 E2E 测试环境（需要启动完整的 LLM API mock、数据库、消息服务）。这是一个"快速迭代优先"的决策。

## 动手：为 weather_tool 写测试

在卷三第十五章，我们写了一个 `weather_tool.py`。现在让我们为它补充完整的测试。

回忆一下，`query_weather` 的核心逻辑是：接收城市名，调用 wttr.in API，返回格式化的天气信息。有三个关键路径需要测试：

1. **正常路径**：API 返回有效数据
2. **城市未找到**：API 返回 404 或空数据
3. **网络错误**：httpx 抛出异常

```python
# tests/unit/agents/tools/test_weather_tool.py
"""Tests for weather_tool — query_weather function."""

import pytest
from unittest.mock import AsyncMock, patch, MagicMock
from agentscope.tool import ToolResponse


# --- Fixtures ---

@pytest.fixture
def mock_weather_data():
    """模拟 wttr.in API 返回的 JSON 数据"""
    return {
        "current_condition": [{
            "temp_C": "22",
            "temp_F": "72",
            "humidity": "65",
            "windspeedKmph": "15",
            "weatherDesc": [{"value": "Partly cloudy"}],
        }]
    }


# --- 正常路径 ---

@pytest.mark.asyncio
async def test_query_weather_success(mock_weather_data):
    """正常查询：返回格式化的天气信息"""
    mock_response = MagicMock()
    mock_response.json.return_value = mock_weather_data
    mock_response.raise_for_status = MagicMock()

    with patch("httpx.AsyncClient") as mock_client_cls:
        mock_client = AsyncMock()
        mock_client.get.return_value = mock_response
        mock_client.__aenter__ = AsyncMock(return_value=mock_client)
        mock_client.__aexit__ = AsyncMock(return_value=False)
        mock_client_cls.return_value = mock_client

        from qwenpaw.agents.tools.weather_tool import query_weather
        result = await query_weather(city="Beijing")

    assert isinstance(result, ToolResponse)
    text = result.content[0].text
    assert "Beijing" in text
    assert "22" in text       # 温度
    assert "Partly cloudy" in text


# --- 华氏度测试 ---

@pytest.mark.asyncio
async def test_query_weather_fahrenheit(mock_weather_data):
    """使用华氏度单位"""
    mock_response = MagicMock()
    mock_response.json.return_value = mock_weather_data
    mock_response.raise_for_status = MagicMock()

    with patch("httpx.AsyncClient") as mock_client_cls:
        mock_client = AsyncMock()
        mock_client.get.return_value = mock_response
        mock_client.__aenter__ = AsyncMock(return_value=mock_client)
        mock_client.__aexit__ = AsyncMock(return_value=False)
        mock_client_cls.return_value = mock_client

        from qwenpaw.agents.tools.weather_tool import query_weather
        result = await query_weather(city="Tokyo", unit="fahrenheit")

    text = result.content[0].text
    assert "72" in text   # 华氏温度
    assert "F" in text


# --- 城市未找到 ---

@pytest.mark.asyncio
async def test_query_weather_city_not_found():
    """城市不存在：返回友好的错误消息"""
    import httpx
    mock_response = MagicMock()
    mock_response.raise_for_status.side_effect = (
        httpx.HTTPStatusError(
            "404", request=MagicMock(), response=MagicMock()
        )
    )

    with patch("httpx.AsyncClient") as mock_client_cls:
        mock_client = AsyncMock()
        mock_client.get.return_value = mock_response
        mock_client.__aenter__ = AsyncMock(return_value=mock_client)
        mock_client.__aexit__ = AsyncMock(return_value=False)
        mock_client_cls.return_value = mock_client

        from qwenpaw.agents.tools.weather_tool import query_weather
        result = await query_weather(city="NonExistentCity999")

    text = result.content[0].text
    assert "not found" in text.lower() or "unavailable" in text.lower()
    # 关键：即使出错也不抛异常，返回 ToolResponse
    assert isinstance(result, ToolResponse)


# --- 网络错误 ---

@pytest.mark.asyncio
async def test_query_weather_network_error():
    """网络故障：返回错误信息，不抛异常"""
    with patch("httpx.AsyncClient") as mock_client_cls:
        mock_client = AsyncMock()
        mock_client.get.side_effect = ConnectionError("Network down")
        mock_client.__aenter__ = AsyncMock(return_value=mock_client)
        mock_client.__aexit__ = AsyncMock(return_value=False)
        mock_client_cls.return_value = mock_client

        from qwenpaw.agents.tools.weather_tool import query_weather
        result = await query_weather(city="Beijing")

    text = result.content[0].text
    assert "Failed" in text or "failed" in text
    # 关键验证：工具函数永远不应该抛出未捕获的异常
    assert isinstance(result, ToolResponse)


# --- 边界条件 ---

@pytest.mark.asyncio
async def test_query_weather_empty_city(mock_weather_data):
    """空城市名：应该正常处理（API 会返回默认位置）"""
    mock_response = MagicMock()
    mock_response.json.return_value = mock_weather_data
    mock_response.raise_for_status = MagicMock()

    with patch("httpx.AsyncClient") as mock_client_cls:
        mock_client = AsyncMock()
        mock_client.get.return_value = mock_response
        mock_client.__aenter__ = AsyncMock(return_value=mock_client)
        mock_client.__aexit__ = AsyncMock(return_value=False)
        mock_client_cls.return_value = mock_client

        from qwenpaw.agents.tools.weather_tool import query_weather
        result = await query_weather(city="")

    # 空城市名不应该导致崩溃
    assert isinstance(result, ToolResponse)
```

这 5 个测试覆盖了 `query_weather` 的所有关键路径：

1. 正常查询（摄氏度）
2. 正常查询（华氏度）
3. 城市未找到（HTTP 错误）
4. 网络故障（连接错误）
5. 边界条件（空城市名）

核心测试原则有两个：

- **Mock 外部依赖**：用 `patch("httpx.AsyncClient")` 替换掉真实的 HTTP 客户端。测试不应该依赖 wttr.in 服务是否在线。
- **验证不变量**：无论发生什么错误，`query_weather` 都必须返回一个 `ToolResponse`，而不是抛出异常。这个不变量比具体的返回内容更重要——因为未捕获的异常会中断 ReAct 循环，导致整个对话崩溃。

运行测试：

```bash
pytest tests/unit/agents/tools/test_weather_tool.py -v
```

## 为贡献者写测试的实用指南

如果你打算给 QwenPaw 贡献代码，这里是一个测试的快速检查清单：

**1. 你的 PR 必须通过现有测试**

在提交 PR 之前：

```bash
make quick          # 快速检查
make test-unit      # 完整单元测试
```

**2. 新功能需要新测试**

| 你在写什么 | 需要什么测试 |
|-----------|-------------|
| 新的 Tool | `tests/unit/agents/tools/test_xxx.py` |
| 新的 Channel | `tests/unit/channels/test_xxx.py` + `tests/contract/channels/test_xxx_contract.py` |
| 新的 Provider | `tests/unit/providers/test_xxx.py` |
| 修改 BaseChannel | 确保所有 12 个 Channel 的契约测试通过 |
| 修改配置逻辑 | `tests/unit/app/test_xxx.py` |

**3. 测试文件命名规则**

- 测试文件以 `test_` 开头
- 测试函数以 `test_` 开头
- 测试类以 `Test` 开头
- 使用 `snake_case`，和被测试模块同名

**4. 使用 conftest.py 中的共享 fixture**

不要重复创建 mock 对象——`conftest.py` 已经提供了 `mock_llm_provider`、`mock_channel`、`temp_workspace` 等常用 fixture。

**5. 契约测试模板**

如果添加新的 Channel，契约测试只需要：

```python
from tests.contract.channels import ChannelContractTest

class TestMyChannelContract(ChannelContractTest):
    def create_instance(self):
        return MyChannel(process=AsyncMock(), ...)
```

基类里的 20+ 个测试会自动运行。
