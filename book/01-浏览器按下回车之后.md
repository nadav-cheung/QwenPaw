# 第一章 浏览器按下回车之后

```
浏览器 ─→ [HTTP/FastAPI] ─→ Runner ─→ Agent ─→ Prompt ─→ ReAct ─→ LLM ─→ Tool ─→ 响应
              |
           你在这里
```

## 问题：按下回车之后发生了什么？

你坐在电脑前，打开 QwenPaw 的网页控制台，在输入框里打了一行字：

> 你好，你能做什么？

按下回车。

屏幕上，AI 的回答开始一个字一个字地蹦出来。看起来很简单，对吧？但这背后，你的消息刚刚完成了一场跨越多个"站点"的旅程。它从浏览器出发，穿过了 HTTP 协议、中间件链、路由匹配、异步流式传输......最终才变成你看到的文字。

这一章，我们要做的，就是跟着这条消息走完它的第一段旅程——从浏览器到 Python 代码。

你可能会想：这有什么好讲的？不就是发个请求吗？

真没那么简单。当你的请求到达服务器时，它首先要穿过三层"保安"（中间件），然后找到正确的"窗口"（路由函数），最后还要把 AI 的回答变成一条不断流动的"溪流"（SSE 流式响应）返回给你。每一步都藏着有趣的设计。

准备好了吗？让我们出发。

## 术语其实很简单

> **术语：HTTP**
> 想象寄一封信——信封上要写收件地址（URL）、收件人（端口）、信的内容（请求体）。HTTP 就是互联网的"写信规范"。浏览器是寄件人，服务器是收件人。POST 是"寄一封有内容的信"，GET 是"麻烦帮我查一下这个地址的信息"。

> **术语：FastAPI**
> 想象一家餐厅的前台。客人（HTTP 请求）来了，前台根据菜单（路由表）把客人领到对应的服务员（处理函数）面前。FastAPI 就是这个前台，它写得又快又准——请求来了，一眼就知道该找谁。你不用自己写"如果 URL 是 /api/console/chat 就调用某某函数"这种 if-else，FastAPI 帮你搞定。

> **术语：中间件（Middleware）**
> 想象一条安检流水线。你的请求就像一件行李，在到达目的地之前要依次通过 X 光机（CORS 检查）、身份验证（认证中间件）、标签贴附（Agent 上下文注入）。每一站都可以放行或拦截。反过来也一样——响应返回时也要经过这条流水线，只不过顺序是反过来的。这种"一层包一层"的结构叫"洋葱模型"，后面我们会画图看。

> **术语：SSE（Server-Sent Events）**
> 想象你打开了一个水龙头，水一直流。SSE 就是服务器端的水龙头——服务器不断往里"倒"数据，浏览器不断"接"数据。和 WebSocket 不同，SSE 是单向的：只有服务器能往客户端发数据。但对于 AI 聊天这个场景，我们只需要服务器往浏览器推文字，SSE 正好够用。

## 探索：追踪一条请求的旅程

现在，让我们打开源码，真的跟着一条请求走一遍。

### 第一步：浏览器发出 POST 请求

当你在输入框按回车时，浏览器会向服务器发送一个 HTTP POST 请求，目标是：

```
POST /api/console/chat
```

请求体（简化后）大概长这样：

```json
{
  "session_id": "abc123",
  "user_id": "default",
  "input": [
    {
      "content": [
        {"text": "你好，你能做什么？", "type": "text"}
      ]
    }
  ]
}
```

这个请求穿过网络，到达 QwenPaw 的 FastAPI 服务器。

### 第二步：FastAPI 应用——服务器的"前台"

让我们看看这个"前台"是怎么搭起来的。

打开 `src/qwenpaw/app/_app.py`，你会看到这样一行：

```python
app = FastAPI(
    lifespan=lifespan,
    docs_url="/docs" if DOCS_ENABLED else None,
    ...
)
```

这就是 FastAPI 应用的创建。`app` 是整个服务器的心脏——所有的路由、中间件都挂在这个对象上。`lifespan` 参数我们后面再说，它管的是服务器启动和关闭时的初始化/清理工作。

### 第三步：穿过中间件的"安检流水线"

请求到了服务器，但还不能直接找路由函数。它得先过中间件这一关。

看 `_app.py` 的这几行（行 518-533）：

```python
# 添加中间件（注意：最后添加的最先执行）
app.add_middleware(AgentContextMiddleware)
app.add_middleware(AuthMiddleware)
if CORS_ORIGINS:
    app.add_middleware(CORSMiddleware, ...)
```

这里有个关键细节：**中间件的添加顺序和执行顺序是反过来的**。你先添加的最后执行，后添加的最先执行。所以实际执行顺序是：

```
请求进入方向 →

1. CORSMiddleware（跨域检查）
   "这个请求的来源网站允许访问吗？"
       |
2. AuthMiddleware（身份验证）
   "你是谁？有通行证吗？"
       |
3. AgentContextMiddleware（Agent 上下文注入）
   "你找哪个 Agent？我帮你登记一下。"
       |
   [路由处理函数]
```

用"洋葱模型"来画，就是这样的：

```
                    请求 ──→
    ┌──────────────────────────────────────┐
    │          CORSMiddleware               │
    │  ┌──────────────────────────────────┐│
    │  │        AuthMiddleware            ││
    │  │  ┌──────────────────────────────┐││
    │  │  │   AgentContextMiddleware     │││
    │  │  │  ┌────────────────────────┐  │││
    │  │  │  │   路由处理函数          │  │││
    │  │  │  │   post_console_chat()  │  │││
    │  │  │  └────────────────────────┘  │││
    │  │  └──────────────────────────────┘││
    │  └──────────────────────────────────┘│
    └──────────────────────────────────────┘
                    ←── 响应
```

请求一层层往里"钻"，到达最中间的处理函数；响应一层层往外"穿"回来。每一层都可以做自己的事情，比如 AuthMiddleware 可以在请求进来时检查身份，在响应出去时添加安全头。

让我们看看每一层具体做了什么。

**CORSMiddleware（跨域检查）**：这不是 QwenPaw 自己写的，是 FastAPI 自带的。它的任务是检查浏览器发来的请求是否来自一个被允许的"源"（域名+端口）。想象你开了一家店，CORS 就是门口的保安，检查来访者是不是你邀请的客人。如果浏览器的地址是 `http://localhost:5173`，而服务器在 `http://localhost:8088`，这就是"跨域"——保安需要确认这种跨域访问是被允许的。

**AuthMiddleware（身份验证）**：这是 QwenPaw 自己写的中间件，在 `src/qwenpaw/app/auth.py` 中。它的核心逻辑用伪代码表示：

```python
async def dispatch(request, call_next):
    if self._should_skip_auth(request):
        return await call_next(request)    # 放行

    token = self._extract_token(request)   # 取出通行证
    if not token:
        return 拦截("Not authenticated")   # 没带通行证？回去！

    user = verify_token(token)             # 验证通行证真伪
    if user is None:
        return 拦截("Invalid token")       # 假的？回去！

    request.state.user = user              # 在请求上贴个标签
    return await call_next(request)        # 放行
```

注意 `_should_skip_auth` 这个方法。它有好几种"免检"条件：认证功能没开、请求来自本机（127.0.0.1）、是公开路径（比如 `/api/version`）。所以在本地开发时，你通常不会感受到认证的存在。

**AgentContextMiddleware（Agent 上下文注入）**：这个中间件做一件很巧妙的事——它从请求的 URL 路径或 HTTP 头中提取出"你要找哪个 Agent"，然后把这个信息存到一个"上下文变量"里，后面的代码就能随时查到。

```python
async def dispatch(request, call_next):
    # 从 URL 路径中提取：/api/agents/{agentId}/...
    # 或从 X-Agent-Id 请求头中提取
    agent_id = 从路径或请求头中获取

    if agent_id:
        set_current_agent_id(agent_id)  # 存入上下文

    return await call_next(request)
```

你可能会问：什么是"上下文变量"？简单说，它就像一个全局变量，但每个异步任务有自己的一份拷贝，互不干扰。想象医院的病历夹——每个病人有自己的病历夹，医生随时可以查看当前病人的信息，不会拿错。

### 第四步：路由匹配——找到正确的"窗口"

穿过中间件之后，请求来到了路由层。FastAPI 怎么知道 `/api/console/chat` 该由谁处理？

答案在 `_app.py` 的路由注册部分（行 610-628）：

```python
# 挂载 API 路由（前缀 /api）
app.include_router(api_router, prefix="/api")
# 挂载 Agent 专用路由（前缀 /api/agents/{agentId}）
agent_scoped_router = create_agent_scoped_router()
app.include_router(agent_scoped_router, prefix="/api")
# 挂载 AgentApp 框架路由（前缀 /api/agent）
app.include_router(agent_app.router, prefix="/api/agent")
```

`api_router` 是一个聚合路由——它把十几个子路由器打包在一起。打开 `src/qwenpaw/app/routers/__init__.py`，你会看到：

```python
router = APIRouter()
router.include_router(console_router)    # /console/*
router.include_router(config_router)     # /config/*
router.include_router(runner_router)     # /runner/*
router.include_router(skills_router)     # /skills/*
# ... 还有十几个
```

所以当请求 `/api/console/chat` 到达时，匹配链是这样的：

```
/api/console/chat
  |__ /api（前缀，匹配 api_router）
       |__ /console（前缀，匹配 console_router）
            |__ /chat（路径，匹配 post_console_chat 函数）
```

就像快递分拣：先按省分（/api），再按市分（/console），最后按街道分（/chat）。层层缩小范围，最终找到唯一的处理函数。

### 第五步：进入路由处理函数

现在请求终于到了目的地——`post_console_chat()` 函数。这个函数在 `src/qwenpaw/app/routers/console.py` 的第 104 行。

让我们看看它做了什么。我会用伪代码展示核心逻辑，省略错误处理等细节：

```python
@router.post("/chat")
async def post_console_chat(request_data, request):
    # 1. 拿到当前请求对应的 Agent 工作区
    workspace = await get_agent_for_request(request)

    # 2. 拿到"控制台"频道（Channel）
    console_channel = await workspace.channel_manager.get_channel("console")

    # 3. 解析请求体，提取用户消息
    native_payload = _extract_session_and_payload(request_data)

    # 4. 获取或创建聊天会话
    chat = await workspace.chat_manager.get_or_create_chat(...)

    # 5. 启动或挂接到流式任务
    tracker = workspace.task_tracker
    queue, _ = await tracker.attach_or_start(
        chat.id, native_payload, console_channel.stream_one
    )

    # 6. 返回 SSE 流式响应
    return StreamingResponse(event_generator(), ...)
```

六步，清晰明了。让我们逐一理解。

**第 1 步：找到 Agent 工作区。** `get_agent_for_request()` 会根据请求中的 agent_id（前面中间件设置好的），从 MultiAgentManager 中找到对应的 Workspace 对象。你可以把 Workspace 想象成一个"工作间"——里面住着一个 Agent，有自己的记忆、工具、聊天记录。QwenPaw 支持同时运行多个 Agent，所以每个请求必须明确找谁。

**第 2 步：拿到控制台频道。** "频道"（Channel）是 QwenPaw 接入不同平台的抽象。控制台是一个频道，钉钉是一个频道，Telegram 也是一个频道。这里我们拿到的是"控制台频道"——也就是网页端的入口。

**第 3 步：解析请求体。** `_extract_session_and_payload()` 把浏览器发来的 JSON 转换成内部格式：

```python
# 转换前（浏览器的格式）
{"session_id": "abc123", "user_id": "default",
 "input": [{"content": [{"text": "你好", "type": "text"}]}]}

# 转换后（内部格式）
{"channel_id": "console", "sender_id": "default",
 "content_parts": [TextPart(text="你好")],
 "meta": {"session_id": "abc123", "user_id": "default"}}
```

这个转换很重要——不管浏览器发什么格式，到了这里都统一了。后面的代码只需要处理一种格式。

**第 4 步：获取或创建聊天会话。** 你每次打开一个新的聊天窗口，就会创建一个新的"会话"（Chat）。如果是在已有窗口继续对话，就复用之前的会话。会话里存着聊天记录、标题等信息。

**第 5 步和第 6 步涉及到流式传输，让我们专门来说。**

### 第六步：SSE 流式响应——为什么文字是"一个字一个字"出来的？

AI 的回答不是一次性全部返回的。它像说话一样，一个词一个词地"蹦"出来。这个效果靠的是 SSE 流式传输。

让我们看看 `event_generator()` 是怎么工作的：

```python
async def event_generator():
    # 从队列中持续读取数据
    stream_it = tracker.stream_from_queue(queue, chat.id)
    try:
        async for event_data in stream_it:
            yield event_data  # 每收到一条就立刻发给浏览器
    finally:
        await stream_it.aclose()
```

整个流程是这样的：

```
用户消息 ─→ Agent 开始"思考"
               |
         Agent 生成一段文字 ─→ 放入队列（queue）
               |
         event_generator 从队列取出 ─→ yield 给浏览器
               |
         Agent 又生成一段文字 ─→ 放入队列
               |
         event_generator 取出 ─→ yield 给浏览器
               |
         ... 循环，直到 Agent 说"我说完了"
```

`TaskTracker` 是这个过程的关键角色。它的 `attach_or_start` 方法做了两件事：如果这个聊天已经在运行了，就"挂接"到已有的流上（这样你刷新页面也不会丢失进度）；如果没有运行，就启动一个新的流式任务。

看 `attach_or_start` 的核心逻辑（简化版）：

```python
async def attach_or_start(self, run_key, payload, stream_fn):
    # 如果已经在运行，挂接到已有队列
    if 已有运行中的任务(run_key):
        q = 创建新队列()
        把已有的事件缓冲复制到 q
        return q, False

    # 否则，启动新任务
    my_queue = 创建新队列()
    异步启动后台任务:
        for event in stream_fn(payload):
            把 event 放入 my_queue
            同时放入事件缓冲（供后来的订阅者回放）
    return my_queue, True
```

这个设计的精妙之处在于"事件缓冲"——所有已发送的事件都会被存一份。如果你中途断开了连接（比如网络波动），重新连接时，`attach()` 方法会把缓冲里的事件先回放给你，然后继续接收新事件。这就是 QwenPaw 支持断线重连的秘密。

最终，这些事件以 SSE 格式发送给浏览器。SSE 的格式长这样：

```
data: {"type": "text", "content": "你"}

data: {"type": "text", "content": "好"}

data: {"type": "text", "content": "！"}

data: {"type": "text", "content": "我"}

data: {"type": "done"}
```

每一条以 `data: ` 开头，以空行结尾。浏览器看到 `data:` 就知道"哦，又来了一条数据"，立刻把它显示出来。就这样，你看到了文字一个个蹦出来的效果。

### 服务器启动时发生了什么？

在请求到达之前，服务器必须先准备好。这个准备工作在 `lifespan()` 函数中完成（`_app.py` 第 218 行）。

lifespan 是 FastAPI 的"生命周期管理"——服务器启动时执行 `yield` 之前的代码，关闭时执行 `yield` 之后的代码。QwenPaw 把启动分成了两个阶段：

```
服务器启动
  |
  ├── 阶段一：快速同步初始化（目标 < 100ms）
  |     - 加载配置
  |     - 创建 MultiAgentManager
  |     - 创建 ProviderManager
  |     - 把管理器挂到 app.state 上
  |     → 服务器开始接受请求！
  |
  └── 阶段二：后台异步初始化
        - 启动所有 Agent
        - 加载插件
        - 执行插件启动钩子
        - 打印就绪横幅
```

为什么要分两个阶段？因为 Agent 的加载可能需要几秒甚至更久（要下载模型、初始化连接）。如果等全部加载完才接受请求，用户启动服务器后要盯着屏幕等半天。

分两阶段之后，服务器几乎瞬间就能接受请求。如果这时有请求访问还没加载好的 Agent 呢？`MultiAgentManager.get_agent()` 内部有"等待机制"——它会等到 Agent 准备好了再返回。用户感知到的就是"服务器很快启动了，第一条消息可能稍微慢一点"。

## 实验：亲手发一个请求

理论看完了，让我们动手试试。打开终端，确保 QwenPaw 正在运行，然后执行：

```bash
curl -X POST http://127.0.0.1:8088/api/console/chat \
  -H "Content-Type: application/json" \
  -d '{
    "session_id": "test-session-001",
    "user_id": "default",
    "input": [{
      "content": [{"text": "你好", "type": "text"}]
    }]
  }'
```

你会看到类似这样的输出（这里只展示了前几行）：

```
data: {"type":"text","content":"你"}

data: {"type":"text","content":"好"}

data: {"type":"text","content":"！"}

data: {"type":"text","content":"我是"}

...
```

这就是 SSE 流！每一行都是一个事件。`curl` 不像浏览器那样会漂亮地渲染，但它忠实地展示了底层发生了什么——服务器在不断地推送数据过来。

你也可以试试带 `X-Agent-Id` 头部：

```bash
curl -X POST http://127.0.0.1:8088/api/console/chat \
  -H "Content-Type: application/json" \
  -H "X-Agent-Id: default" \
  -d '{"session_id":"test-002","user_id":"default","input":[{"content":[{"text":"1+1等于几？","type":"text"}]}]}'
```

加了 `X-Agent-Id: default` 之后，AgentContextMiddleware 就知道你要找的是 `default` 这个 Agent。

## 工程权衡：为什么这样设计？

### 为什么用 SSE 而不是 WebSocket？

这是本章最值得讨论的设计决策。WebSocket 和 SSE 都能实现"服务器推数据"，但它们的设计哲学不同。

**WebSocket** 是双向通道——客户端和服务器可以随时互发消息。想象一部电话，两边可以同时说话。

**SSE** 是单向通道——只有服务器往客户端推数据。想象一个广播电台，你只能听，不能打电话进去。

对于 AI 聊天场景，SSE 几乎总是更好的选择：

1. **请求-响应模式**：用户发一条消息，AI 流式返回回答。这本质上就是"一次请求，多次响应"——SSE 天然适合。WebSocket 需要自己管理"这条消息对应那条回答"的映射关系。

2. **更简单**：SSE 就是普通的 HTTP 响应，只是格式特殊（`data: ...`）。WebSocket 需要单独的握手协议、心跳机制、重连逻辑。代码更复杂，出 bug 的地方更多。

3. **更容易调试**：用 `curl` 就能看 SSE 的输出。WebSocket 需要专门的工具。

4. **天然兼容现有架构**：SSE 走的就是 HTTP，所以中间件、认证、路由全部复用。WebSocket 连接建立后就不再是普通 HTTP 了，中间件可能不生效。

QwenPaw 唯一使用 WebSocket 的地方是实时语音对话（`voice_router`），那是因为语音需要双向实时传输。普通的文字聊天，SSE 完全够用。

### 为什么用洋葱模型中间件？

洋葱模型（中间件链）的核心好处是"关注点分离"。

想象一下，如果不用中间件，你得在每个路由函数里写：

```python
async def post_console_chat(request):
    # 检查 CORS
    if not 检查跨域(request): return 错误
    # 检查认证
    if not 检查token(request): return 错误
    # 提取 Agent ID
    agent_id = 提取agent(request)
    # 终于开始做正事
    ...
```

每个路由函数都要重复这三段代码。如果哪天要加一个新的安全检查，你得改所有函数。

中间件把这些"横切关注点"抽出来，每个中间件只管一件事。加一个新的安全检查？写一个中间件，挂上去，所有路由自动生效。不需要改任何业务代码。

## 小结

这一章，我们跟着一条 HTTP 请求走完了从浏览器到 Python 代码的完整旅程：

```
浏览器
  |  POST /api/console/chat
  |  {"input": [{"content": [{"text": "你好"}]}]}
  v
FastAPI (app)
  |
  v
CORSMiddleware ─→ AuthMiddleware ─→ AgentContextMiddleware
  "跨域检查"       "身份验证"         "注入 Agent ID"
  |
  v
路由匹配: /api + /console + /chat
  |
  v
post_console_chat()
  ├── get_agent_for_request()   → 找到 Agent 工作区
  ├── _extract_session_and_payload() → 解析请求体
  ├── get_or_create_chat()      → 获取/创建会话
  ├── tracker.attach_or_start() → 启动流式任务
  └── StreamingResponse()       → 以 SSE 格式返回
  |
  v
浏览器收到 SSE 流
  data: {"type":"text","content":"你"}
  data: {"type":"text","content":"好"}
  data: {"type":"text","content":"！"}
  ...
```

你学到了：

- **HTTP 请求**的基本结构：方法（POST）、路径（/api/console/chat）、请求体（JSON）
- **FastAPI** 的路由机制：前缀逐层匹配，找到唯一的处理函数
- **中间件洋葱模型**：请求一层层进去，响应一层层出来，每一层各司其职
- **SSE 流式响应**：服务器不断推送数据，浏览器逐条接收，实现"逐字输出"的效果
