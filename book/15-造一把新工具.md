## 卷三开场白：从读者到建设者

前两卷里，我们像侦探一样追踪了一个请求从浏览器到工具执行的完整链路。第一卷（第 1-8 章）是一趟"跟随"之旅，我们逐站看到了请求是怎么被接收、解析、路由、分发、执行的。第二卷（第 9-14 章）是一趟"拆解"之旅，我们把沿途看到的每个模块翻转过来，观察它们底下的设计模式：事件驱动、工厂模式、注册表模式、插件架构……

现在，你站在第三卷的入口。这一卷叫"工坊"——我们要动手了。

理解代码和创造代码是两种不同的能力。理解代码是"看懂别人为什么这么做"，创造代码是"知道自己该怎么做"。好消息是，前两卷打下的基础让第三卷变得非常自然——你已经知道了系统的骨架、接口和约定，现在只需要往骨架上挂新的模块。

这一章，我们从最实在的事情开始：造一把新工具（Tool）。

## 问题：我想让 Agent 能查询天气，怎么写一个新 Tool？

想象一个场景：你的用户说"今天北京天气怎么样？"Agent 收到消息后，大语言模型知道该怎么回答吗？不知道。模型的训练数据只到某个截止日期，它没有实时的天气数据。它需要一个"工具"——一段能调用天气 API、拿到实时数据的代码。

这就是 Tool 存在的意义：**让 Agent 拥有模型本身不具备的能力**。

问题是：怎么写这样一个工具？写完之后怎么让系统知道它的存在？模型又怎么知道什么时候该用它？

让我们从最简单的一个已有工具开始，逐步揭开答案。

## 术语其实很简单

> **术语：Function Calling（函数调用）**
>
> 想象你是一位公司老板，你有一个万能秘书（大语言模型）。秘书什么都知道——历史、文学、数学、编程。但秘书不能出门。你告诉秘书："当你需要查实时天气的时候，填这张表格交给我，我派人去查。"Function Calling 就是这套机制：你提前告诉模型"你有这些工具可以用"（定义工具的名称、参数和描述），模型在回答问题时如果需要某个工具，就输出一个结构化的"工具调用请求"（函数名 + 参数值），然后由你的代码去执行这个函数，把结果返回给模型。模型自己不执行任何代码——它只负责"决定调用什么"。

> **术语：Tool Schema（工具描述）**
>
> 想象你去餐厅吃饭。菜单上写着每道菜的名字、食材、口味描述。你不需要进厨房看厨师怎么做，你看菜单就能决定点什么。Tool Schema 就是工具的"菜单"：它用 JSON 格式描述了工具的名字、功能说明、每个参数的名字和类型。大语言模型看到的不是你的 Python 代码，而是这份 JSON 菜单。它根据菜单来决定要不要"点这道菜"（调用这个工具）。

> **术语：ToolResponse（工具响应）**
>
> 想象你让秘书帮你打电话查快递，秘书打完电话回来跟你说："你的快递明天到。"这就是工具响应——工具执行完毕后，把结果打包成模型能理解的格式，送回给模型。在 QwenPaw 中，这个格式是 `ToolResponse` 对象，里面包含 `TextBlock` 类型的内容块。

## 探索：一个 Tool 的最小形态

### 最简参考：get_current_time

让我们先看 QwenPaw 里最简单的工具之一——`get_current_time`。它做的事情一目了然：返回当前时间。

文件位置：`src/qwenpaw/agents/tools/get_current_time.py`，第 16-48 行：

```python
async def get_current_time() -> ToolResponse:
    """Get the current time in format `%Y-%m-%d %H:%M:%S TZ (Day)`,
    e.g. "2026-02-13 19:30:45 Asia/Shanghai (Friday)".

    Call this tool when the user asks for the current time or when
    the current time is needed for other operations.

    Returns:
        `ToolResponse`:
            The current time string,
            e.g. "2026-02-13 19:30:45 Asia/Shanghai (Friday)".
    """
```

这个函数只有三个要素：

1. **函数签名**：`async def get_current_time() -> ToolResponse`。它是一个异步函数，没有参数，返回值类型是 `ToolResponse`。
2. **文档字符串（docstring）**：用自然语言描述了工具的功能、使用场景和返回值。这段文字会被自动转换为 Tool Schema，供大语言模型阅读。
3. **返回值**：一个 `ToolResponse` 对象，里面包裹着 `TextBlock`。

核心返回逻辑在第 41-48 行：

```python
    return ToolResponse(
        content=[
            TextBlock(
                type="text",
                text=time_str,
            ),
        ],
    )
```

就这么简单。一个 async 函数、一段 docstring、一个 ToolResponse 返回值——这就是一个完整的 Tool。

但等等，模型怎么知道这个工具的存在？答案藏在 docstring 里。

### Docstring 就是 Schema：从自然语言到 JSON

这是 QwenPaw 工具系统最巧妙的设计之一：**函数的 docstring 会被自动解析为 Tool Schema**。

你不需要手写 JSON Schema。你只需要按 Google 风格写 docstring，AgentScope 框架会自动把它转换为模型能理解的 JSON 格式。转换规则大致是：

```
函数签名中的参数    ──→  JSON Schema 的 "parameters" 字段
docstring 的第一段  ──→  JSON Schema 的 "description" 字段
docstring 的 Args   ──→  每个参数的描述
docstring 的 Returns ──→  返回值说明（模型不一定用，但写了更好）
```

以 `get_current_time` 为例，模型看到的 JSON 大致是：

```json
{
  "name": "get_current_time",
  "description": "Get the current time in format ...",
  "parameters": {
    "type": "object",
    "properties": {},
    "required": []
  }
}
```

这个工具没有参数，所以 `properties` 是空的。但如果你有一个带参数的工具，比如 `set_user_timezone`（同文件第 51-95 行），模型会看到：

```json
{
  "name": "set_user_timezone",
  "description": "Set the user timezone...",
  "parameters": {
    "type": "object",
    "properties": {
      "timezone_name": {
        "type": "string",
        "description": "IANA timezone name (e.g. \"Asia/Shanghai\"...)"
      }
    },
    "required": ["timezone_name"]
  }
}
```

这一切都来自于 Python 的类型注解和 docstring。你写的是 Python，模型看到的是 JSON——中间的翻译由框架自动完成。

### 复杂参考：execute_shell_command

看完了最简单的工具，我们再扫一眼最复杂的工具之一——`execute_shell_command`（`src/qwenpaw/agents/tools/shell.py`，第 285-444 行）。它展示了带参数的工具是怎么写的：

```python
async def execute_shell_command(
    command: str,
    timeout: float = 60.0,
    cwd: Optional[Path] = None,
) -> ToolResponse:
    """Execute a shell command and return its output.

    Args:
        command (`str`):
            The shell command to execute.
        timeout (`float`, defaults to `60.0`):
            The maximum time (in seconds) allowed...
        cwd (`Optional[Path]`, defaults to `None`):
            The working directory for the command execution.
```

这个工具有三个参数：`command`（必填）、`timeout`（可选，有默认值）、`cwd`（可选，默认 None）。Python 的类型注解（`str`、`float`、`Optional[Path]`）和默认值会自动映射到 JSON Schema 的类型定义和默认值。

`shell.py` 的实现非常复杂（445 行代码），因为它要处理 Windows/Unix 差异、进程超时、编码问题、换行符处理等边缘情况。但无论工具多复杂，对模型来说它就是一段 JSON 描述——模型不关心你的实现有多复杂，只关心"名字是什么、参数是什么、什么时候该用"。

这就是工具系统的核心契约：**你负责实现，docstring 负责沟通**。

### 注册流程：从代码到 Toolkit

写好了工具函数，接下来要让系统知道它的存在。这个过程叫"注册"。

注册发生在 `src/qwenpaw/agents/react_agent.py` 的 `_create_toolkit()` 方法中（第 190-307 行）。整个流程可以画成一张图：

```
┌──────────────────────────────────────────────────────────────────┐
│                     Tool 注册流程                                 │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  第一步：定义工具映射表                                           │
│  ┌───────────────────────────────────────────────────────────┐   │
│  │  tool_functions = {                                       │   │
│  │      "execute_shell_command": execute_shell_command,      │   │
│  │      "read_file":           read_file,                    │   │
│  │      "get_current_time":    get_current_time,             │   │
│  │      "你的新工具":           你的新函数,       ← 新增这一行│   │
│  │      ...                                                  │   │
│  │  }                                                        │   │
│  └───────────────────────────┬───────────────────────────────┘   │
│                              │                                   │
│  第二步：遍历映射表            │                                   │
│                              ▼                                   │
│  ┌───────────────────────────────────────────────────────────┐   │
│  │  for tool_name, tool_func in tool_functions.items():      │   │
│  │      if not enabled_tools.get(tool_name, True):           │   │
│  │          continue  # 跳过被禁用的工具                      │   │
│  │      toolkit.register_tool_function(tool_func)  # 注册!   │   │
│  └───────────────────────────┬───────────────────────────────┘   │
│                              │                                   │
│  第三步：框架自动提取 Schema   │                                   │
│                              ▼                                   │
│  ┌───────────────────────────────────────────────────────────┐   │
│  │  AgentScope 框架:                                         │   │
│  │    1. 读取 tool_func 的 __doc__                           │   │
│  │    2. 解析函数签名和类型注解                                │   │
│  │    3. 生成 JSON Schema                                    │   │
│  │    4. 存入 Toolkit 的工具注册表                             │   │
│  └───────────────────────────┬───────────────────────────────┘   │
│                              │                                   │
│  第四步：Schema 随请求发送     │                                   │
│                              ▼                                   │
│  ┌───────────────────────────────────────────────────────────┐   │
│  │  Agent 发起 LLM 调用时:                                    │   │
│  │    tools = toolkit.get_tool_schemas()                      │   │
│  │    → 把所有工具的 JSON Schema 作为 tools 参数发给模型       │   │
│  └───────────────────────────────────────────────────────────┘   │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

具体到代码，核心注册逻辑在 `react_agent.py` 第 256-275 行：

```python
for tool_name, tool_func in tool_functions.items():
    if not enabled_tools.get(tool_name, True):
        continue

    toolkit.register_tool_function(
        tool_func,
        namesake_strategy=namesake_strategy,
        async_execution=async_exec,
    )
```

关键调用是 `toolkit.register_tool_function(tool_func)`。你把一个 Python 函数传进去，AgentScope 框架会自动做三件事：

1. **提取函数名**作为工具名（`get_current_time` 就叫 `get_current_time`）
2. **解析 docstring** 生成工具描述和参数描述
3. **分析函数签名**生成参数的 JSON Schema（类型、是否必填、默认值）

注册完成之后，这个工具就会出现在每次 LLM 调用的 `tools` 参数中。模型拿到这些 JSON Schema，就像拿到一份菜单，知道"有什么菜可以点"。

### 导出链：从文件到模块

一个工具从写好到被注册，中间还有一步容易被忽略的环节：**模块导出**。

所有工具都在 `src/qwenpaw/agents/tools/__init__.py` 中被导出：

```python
from .get_current_time import get_current_time, set_user_timezone
```

然后在 `react_agent.py` 的顶部被导入：

```python
from .tools import (
    get_current_time,
    set_user_timezone,
    ...
)
```

所以添加新工具的完整路径是三个文件：

```
tools/your_new_tool.py     ← 1. 写工具函数
       │
       ▼
tools/__init__.py           ← 2. 导出工具函数
       │
       ▼
react_agent.py              ← 3. 导入 + 加入 tool_functions 映射
```

这三个步骤缺一不可。忘了导出？`import` 会报错。忘了加映射表？工具写好了但永远不会被注册。

### Function Calling 端到端时序图

让我们把视角拉远，看一个完整的 Function Calling 端到端流程——从用户问"几点了？"到 Agent 回答"现在是 2026-05-10 15:30:00 Asia/Shanghai (Sunday)"：

```
   │            │                │              │               │
   │ "几点了？" │                │              │               │
   │──────────→│                │              │               │
   │            │ 1.组装请求     │              │               │
   │            │──────────────→│              │               │
   │            │ 2.获取所有    │              │               │
   │            │   Tool Schema │              │               │
   │            │←─────────────│              │               │
   │            │                │              │               │
   │            │ 3.发送消息 + Tools Schema     │               │
   │            │────────────────────────────→│               │
   │            │                │              │               │
   │            │                │ 4.模型推理:  │               │
   │            │                │   "应该调用  │               │
   │            │                │   get_current│               │
   │            │                │   _time"     │               │
   │            │                │              │               │
   │            │ 5.返回 tool_calls:            │               │
   │            │   [{name: "get_current_time", │               │
   │            │     args: {}}] │              │               │
   │            │←────────────────────────────│               │
   │            │                │              │               │
   │            │ 6.查找函数并执行               │               │
   │            │────────────────────────────────────────────→│
   │            │                │              │    7.执行     │
   │            │                │              │    get_current│
   │            │                │              │    _time()    │
   │            │                │              │               │
   │            │ 8.返回 ToolResponse           │               │
   │            │   "2026-05-10 15:30:00 ..."   │               │
   │            │←────────────────────────────────────────────│
   │            │                │              │               │
   │            │ 9.把工具结果追加到对话          │               │
   │            │ 10.再次调用 LLM               │               │
   │            │────────────────────────────→│               │
   │            │                │              │               │
   │            │ 11.模型生成最终回答            │               │
   │            │   "现在是2026年5月10日..."     │               │
   │            │←────────────────────────────│               │
   │            │                │              │               │
   │ "现在是..." │                │              │               │
   │←──────────│                │              │               │
```

这张图揭示了 Function Calling 的关键设计：**模型不执行代码，它只做决策**。

步骤 4 中，模型阅读了所有工具的 Schema，判断出用户的问题需要调用 `get_current_time`。步骤 5 中，模型返回一个结构化的 `tool_calls` 响应，里面包含函数名和参数。步骤 6 中，Agent 框架负责找到对应的 Python 函数并实际执行它。步骤 8 中，执行结果被送回模型。步骤 10-11 中，模型拿到工具返回的结果，生成最终的自然语言回答。

这就是整个 Function Calling 的端到端流程。理解了这个流程，你就理解了工具系统设计背后"为什么"。

## 工程权衡：工具接口设计的三个决策

在动手写代码之前，让我们先思考一下工具接口背后的工程权衡。

### 权衡一：Docstring 驱动 vs 手写 Schema

QwenPaw 选择的是"docstring 驱动"——工具的描述从 Python docstring 自动提取，而不是让开发者手写 JSON Schema。

**好处**：单一来源（Single Source of Truth）。代码和描述永远在一起，不会出现"代码改了但 Schema 忘了更新"的情况。开发者只需要维护一份 docstring。

**代价**：表达能力有限。docstring 能表达"这个参数是字符串类型"，但很难表达"这个参数必须是 1-7 之间的整数"或"这个参数是一个枚举值，只能是 A、B、C 三选一"。如果需要更精确的约束，需要额外使用 Pydantic 模型来定义参数。

对于 QwenPaw 的大多数工具来说，docstring 的表达能力已经足够。模型的推理能力弥补了 Schema 的精度不足——即使 Schema 没有严格约束"timeout 必须是正数"，模型通常也能从描述中理解到这一点。

### 权衡二：async vs sync

QwenPaw 的所有工具函数都是 `async def`。这不是偶然的。

因为 Agent 本身运行在异步环境中（ReAct 循环是 `async` 的），工具函数如果是同步的，会阻塞整个事件循环。特别是像 `execute_shell_command` 这样可能执行数分钟的工具，如果用同步调用，整个服务都会卡住。

但这也意味着工具函数不能直接调用同步的阻塞 I/O（比如 `requests.get()`）。如果必须调用，要用 `asyncio.to_thread()` 把它包装成异步的。

### 权衡三：ToolResponse vs 裸字符串

工具的返回值不是随便一个字符串，而是 `ToolResponse` 对象。这个设计有什么好处？

`ToolResponse` 是一个结构化的容器。它的 `content` 字段是一个列表，可以包含多个 `TextBlock`。这意味着未来可以扩展——比如一个工具同时返回文本和图片（`ImageBlock`），或者返回多个内容块。如果返回值只是一个裸字符串，未来要扩展就必须改接口。

这是一个"为未来留空间"的设计：当前所有工具只返回单个 `TextBlock`，但接口已经为更复杂的返回值做好了准备。

## 动手：从零写一个天气工具

理论讲够了，现在让我们真正动手写一个 `weather_tool.py`。这个工具的功能是：接收城市名，调用天气 API，返回当前天气信息。

### 步骤一：创建工具文件

在 `src/qwenpaw/agents/tools/` 目录下创建 `weather_tool.py`。

先写工具函数的骨架。记住三个要素：async 函数、docstring、ToolResponse 返回值。

```python
# -*- coding: utf-8 -*-
"""Weather query tool for QwenPaw Agent."""

import logging
from typing import Optional

import httpx
from agentscope.message import TextBlock
from agentscope.tool import ToolResponse

logger = logging.getLogger(__name__)


async def query_weather(
    city: str,
    unit: Optional[str] = "celsius",
) -> ToolResponse:
    """Query the current weather for a given city.

    Call this tool when the user asks about weather conditions,
    temperature, or forecasts for any city.

    Args:
        city (`str`):
            The city name to query weather for,
            e.g. "Beijing", "New York", "Tokyo".
        unit (`str`, optional, defaults to "celsius"):
            Temperature unit. Use "celsius" for Celsius
            or "fahrenheit" for Fahrenheit.

    Returns:
        `ToolResponse`: Current weather information for the city.
    """
```

注意 docstring 的写法。它遵循 Google 风格，有三个关键部分：

- **第一段**：简短描述工具的功能。这段文字会变成 Tool Schema 的 `description` 字段，模型靠它来判断"什么时候该用这个工具"。
- **第二段（Call this tool when...）**：告诉模型在什么场景下应该调用这个工具。这是一个非常重要的实践——它能帮助模型更准确地做出"要不要调用"的决策。
- **Args 部分**：描述每个参数的含义。这些描述会变成 JSON Schema 中每个参数的 `description`。

### 步骤二：实现工具逻辑

函数体并不复杂。我们需要调用一个天气 API（这里使用 wttr.in，一个免费的天气服务，不需要 API Key），然后把结果格式化返回：

```python
    # 构造请求 URL
    url = f"https://wttr.in/{city}"
    params = {"format": "j1"}  # 返回 JSON 格式

    try:
        async with httpx.AsyncClient(timeout=10.0) as client:
            resp = await client.get(url, params=params)
            resp.raise_for_status()
            data = resp.json()

        # 提取当前天气
        current = data["current_condition"][0]
        temp = current["temp_C"] if unit == "celsius" else current["temp_F"]
        desc = current["weatherDesc"][0]["value"]
        humidity = current["humidity"]
        wind = current["windspeedKmph"]

        result = (
            f"Weather for {city}:\n"
            f"  Temperature: {temp}°{'C' if unit == 'celsius' else 'F'}\n"
            f"  Condition: {desc}\n"
            f"  Humidity: {humidity}%\n"
            f"  Wind: {wind} km/h"
        )
    except httpx.HTTPStatusError:
        result = f"City '{city}' not found or weather data unavailable."
    except Exception as e:
        logger.error("Weather query failed: %s", e)
        result = f"Failed to query weather: {e}"

    return ToolResponse(
        content=[TextBlock(type="text", text=result)],
    )
```

逻辑很直接：用 `httpx`（一个异步 HTTP 客户端）请求天气 API，解析 JSON 响应，格式化为人类可读的文本，最后用 `ToolResponse` 包装返回。

注意异常处理：天气 API 可能失败（网络错误、城市名无效），所以我们用 try-except 包裹，即使出错了也返回一个有意义的 `ToolResponse`。**工具函数不应该抛出未捕获的异常**——因为异常会中断 ReAct 循环，导致整个请求失败。返回一个包含错误信息的 ToolResponse，让模型知道发生了什么，模型可以向用户解释或者尝试其他方案。

## 深入：写好一个工具的五个要点

写完天气工具之后，让我们总结一下写好一个工具需要注意的五个要点。这些要点来自阅读 QwenPaw 现有工具的经验。

### 要点一：Docstring 是给模型看的，不是给人看的

普通 Python 函数的 docstring 是给人类开发者看的。但工具函数的 docstring 有两个受众：人类（代码审查者）和大语言模型（调用决策者）。

一段好的工具 docstring 应该包含：

- **功能描述**：这个工具做什么？（模型据此判断"要不要用"）
- **触发场景**：什么情况下应该用？（"Call this tool when..."）
- **参数说明**：每个参数是什么意思？有什么限制？
- **返回值说明**：返回什么格式的数据？

看看 `get_token_usage.py` 的 docstring（第 12-29 行）是怎么写的：

```python
"""Query LLM token usage over the past N days.

Use this when the user asks about token consumption, API usage,
or how many tokens have been used.

Args:
    days: Number of days to look back (default: 30).
    model_name: Optional model name to filter by.
    ...
```

它的第二行 "Use this when..." 明确告诉模型触发场景。这种写法能显著提高模型的工具选择准确率。

### 要点二：参数越少越好

每个额外的参数都增加了模型的决策负担。模型需要理解每个参数的含义，然后决定传什么值。参数越多，模型出错的概率越高。

看看 `get_current_time`：零个参数。完美。模型只需要决定"要不要调用"，不需要思考"传什么值"。

如果你的工具有超过 5 个参数，考虑：能不能把一些参数设为可选的、有合理默认值的？能不能把工具拆分成多个更小的工具？

### 要点三：永远不要抛出未捕获的异常

工具函数是 ReAct 循环的一部分。如果一个工具函数抛出了未捕获的异常，整个 ReAct 循环会中断，用户会看到一个错误消息。

正确的做法是：**捕获所有异常，返回包含错误信息的 ToolResponse**。让模型来决定怎么处理这个错误——它可以向用户道歉，可以重试，可以换一个方案。

看看 `shell.py` 的做法（第 436-444 行）：

```python
except Exception as e:
    return ToolResponse(
        content=[TextBlock(type="text", text=f"Error: ... {e}")],
    )
```

最外层总有一个 `except Exception` 兜底。无论内部发生了什么，工具都会返回一个 ToolResponse。

### 要点四：返回结果要简洁且信息丰富

工具返回的文本会作为 LLM 的输入。太长的返回值浪费 token，太短的返回值信息不足。

一个好的返回值应该包含：

- **关键信息**：用户真正关心的数据
- **结构化格式**：用换行和缩进组织信息，方便模型解析
- **上下文**：如果必要，包含一些辅助信息

看看 `get_token_usage.py` 的返回值格式——它用列表的形式组织了 token 用量、按模型分类、按日期分类的信息，既有总览又有细节。

### 要点五：注意异步

工具函数必须是 `async def`。如果内部需要调用同步的阻塞操作（如文件 I/O、CPU 密集计算），使用 `asyncio.to_thread()` 包装：

```python
# 同步操作，放在线程池里执行
result = await asyncio.to_thread(blocking_function, arg1, arg2)
```

如果内部需要发起 HTTP 请求，使用异步 HTTP 客户端（如 `httpx`）而不是同步的 `requests`。

## 回顾：造一把新工具的完整路径

这一章，我们完成了一次"从零到一"的旅程。让我们回顾关键路径：

```
写工具函数 (weather_tool.py)
    │
    │  三要素: async def + docstring + ToolResponse
    │
    ▼
导出工具 (tools/__init__.py)
    │
    │  import + __all__
    │
    ▼
注册工具 (react_agent.py)
    │
    │  import + tool_functions 映射
    │
    ▼
框架自动提取 Schema
    │
    │  docstring + 类型注解 → JSON Schema
    │
    ▼
模型在 ReAct 循环中看到 Schema
    │
    │  "我应该调用 query_weather"
    │
    ▼
框架执行函数，返回 ToolResponse
    │
    │  结果送回模型
    │
    ▼
模型生成最终回答
```

整个过程涉及的关键文件：

| 文件 | 角色 | 改动 |
|------|------|------|
| `tools/weather_tool.py` | 工具实现 | 新增 |
| `tools/__init__.py` | 模块导出 | 添加 import 和 __all__ |
| `react_agent.py` | 工具注册 | 添加 import 和映射条目 |

三个文件，三次小改动，一个新能力就诞生了。这就是 QwenPaw 工具系统的设计目标：**添加新工具的成本尽可能低**。
