# 第十八章 接入一个新频道——Channel 接口契约与消息收发抽象

```
浏览器 ─→ HTTP ─→ Runner ─→ Agent ─→ Prompt ─→ ReAct ─→ LLM ─→ Tool ─→ Skill
              │                                                    |
       [ChannelManager]                                    [BaseChannel]
              │                                                    │
       你在这里 ←──────────────────────────────────────────────────┘
```

`[卷三·工坊]` -- 上一章我们给 Agent 换了一个"大脑"（Provider），让它能使用新的模型服务。这一章，我们要做一件同样底层的事：给 Agent 接一条新的"耳朵和嘴巴"——让它在新的聊天平台上和用户对话。

---

## 问题：怎么让 QwenPaw 支持一个新的聊天平台？

你在公司里用钉钉，朋友们用 Telegram，海外同事用 Discord，还有人在飞书上找你。你的 AI 助手如果只能在一个平台上回复，就像一个人只会说一种语言——能交流，但受众有限。

QwenPaw 的 Channel（频道）机制就是为解决这个问题设计的。每个 Channel 封装了一个聊天平台的通信细节：接收消息、发送回复、处理附件、管理会话。上层代码只需要说"发给用户"，Channel 负责把消息送到正确的平台。

我们在卷二的第十二章已经从设计模式的角度拆解过 Channel 的适配器模式。这一章，我们要从实践出发，拆解 BaseChannel 的接口契约、消息格式转换、Webhook 与长连接的选择，最终亲手实现一个新的 Channel。

## 术语其实很简单

> **术语：Channel（频道）**
>
> 想象一个翻译官。你在北京开会，台下坐着日本人、法国人、巴西人——每个人只懂自己的母语。翻译官的工作是：听到日语就把问题翻译成中文告诉你，听到你的回答就翻译成日语告诉日本人。每个翻译官只负责一种语言，但他们面对的都是同一个你。Channel 就是这些"翻译官"在 QwenPaw 里的角色。每个 Channel 只负责一个聊天平台，它把平台特有的消息格式翻译成系统内部的统一格式，也把系统的回复翻译回平台能理解的格式。Agent 根本不知道自己是在和 Telegram 用户还是钉钉用户对话——它只看到统一的 `AgentRequest`。

> **术语：Webhook（网络钩子）**
>
> 想象你在家等快递。方式一：每隔五分钟给快递员打一次电话问"到了吗？"——这是长轮询（Long Polling）。方式二：告诉快递员你的地址，让他到了按门铃——这就是 Webhook。在聊天机器人的场景里，Webhook 是你告诉聊天平台"我的服务器地址是 `https://example.com/webhook`，有新消息就往这个地址发一个 HTTP 请求"。好处是你不需要反复询问，平台主动推送；前提是你的服务器必须有公网 IP（能被平台访问到）。

> **术语：长连接（Long Connection / WebSocket）**
>
> 想象你在跟朋友打电话。电话接通后，双方随时可以说话，不需要每次拨号。长连接（通常是 WebSocket）就是这种"一直保持通话"的模式：客户端和服务器建立一条持久的双向通道，双方随时可以发数据。与 Webhook 相比，长连接不需要公网 IP（客户端主动连出去就行），适合在内网环境使用。QwenPaw 的飞书 Channel 就是用 WebSocket 长连接来接收消息的。

## 探索：BaseChannel 的接口契约

要接入一个新的聊天平台，你需要理解 BaseChannel 和系统之间的"契约"——也就是基类定义的那些必须实现或可选覆盖的方法。

### BaseChannel 的继承结构

打开 `src/qwenpaw/app/channels/base.py`，第一眼就能看到 BaseChannel 的定义（第 78 行）：

```python
class BaseChannel(ABC):
    """Base for all channels. Queue lives in ChannelManager;
    channel defines how to consume via consume_one()."""
```

BaseChannel 只继承了 `ABC`（抽象基类），不像 Provider 那样还继承了数据模型。Channel 的"数据"（配置信息）是通过 `from_config()` 和 `from_env()` 两个类方法传入的，而不是作为类属性持有。

### 必须实现的六个核心方法

BaseChannel 定义了**六个必须在子类中实现的方法**（四个 `raise NotImplementedError` + 两个 `from_*` 工厂方法）：

| 方法 | 行号 | 用途 | 返回类型 |
|------|------|------|----------|
| `from_env()` | 575-581 | 从环境变量创建实例 | `BaseChannel` |
| `from_config()` | 583-593 | 从配置对象创建实例 | `BaseChannel` |
| `build_agent_request_from_native()` | 642-656 | 平台消息 → 内部请求 | `AgentRequest` |
| `start()` | 1270-1271 | 启动频道（连接平台） | `None` |
| `stop()` | 1273-1274 | 停止频道（断开连接） | `None` |
| `send()` | 1276-1285 | 发送文本消息到平台 | `None` |

### 基类已经帮你做好的事

BaseChannel 最大的价值不在"要求你实现什么"，而在"帮你做了什么"。以下是基类提供的已实现方法：

- **`consume_one(payload)`**（第 697-733 行）——消息消费的主入口，处理防抖（debounce）、批量合并、调用 `_process`
- **`_consume_one_request(payload)`**（第 797-863 行）——把 payload 转成 AgentRequest，跑 Agent 推理，发送回复
- **`send_content_parts()`**（第 1127-1178 行）——拆分文本和媒体，合并发送
- **`send_message_content()`**（第 1050-1074 行）——从 Message 对象提取内容并调用 `send_content_parts()`
- **`build_agent_request_from_user_content()`**（第 607-640 行）——用统一的内容类型构建 AgentRequest
- **`merge_native_items()`**（第 179-208 行）——合并多条原生消息
- **`_check_allowlist()`**（第 315-337 行）——白名单鉴权
- **`clone()`**（第 1226-1251 行）——用新配置克隆实例

这意味着你实现一个新 Channel 时，**消息消费、流式处理、内容渲染、防抖、白名单**这些通用逻辑都不用写。你只需要关注两件事：怎么从平台收到消息（`start()` + `build_agent_request_from_native()`），怎么把消息发回平台（`send()` + `send_media()`）。

## 探索：Console Channel——最简参考实现

理解接口契约最好的方式是看一个最简单的实现。`console/channel.py` 就是那个最简参考。

### 为什么 Console Channel 最简单

Console Channel 不对接任何外部平台。它的"收消息"就是从前端 HTTP 接口获取用户输入，"发消息"就是打印到终端。没有 Webhook，没有长连接，没有 token 刷新，没有附件下载。

让我们逐个看它的核心实现。

**类定义**（第 63 行）：

```python
class ConsoleChannel(BaseChannel):
    """Console Channel: prints agent responses to stdout."""
    channel = "console"
```

`channel = "console"` 是频道标识，全局唯一。ChannelManager 用这个字符串来路由消息。

**`build_agent_request_from_native()`**（第 255-276 行）——消息转换：

```python
def build_agent_request_from_native(self, native_payload: Any) -> Any:
    payload = native_payload if isinstance(native_payload, dict) else {}
    channel_id = payload.get("channel_id") or self.channel
    sender_id = payload.get("sender_id") or ""
    content_parts = payload.get("content_parts") or []
    content_parts = self._resolve_console_upload_refs(content_parts)
    meta = payload.get("meta") or {}
    session_id = self.resolve_session_id(sender_id, meta)
    request = self.build_agent_request_from_user_content(...)
    request.channel_meta = meta
    return request
```

这段代码展示了每个 Channel 都要做的"翻译"工作：从平台原生格式（这里是一个 `dict`）中提取 `sender_id`（谁发的）、`content_parts`（发了什么）、`meta`（附加信息），然后调用基类的 `build_agent_request_from_user_content()` 把它们组装成统一的 `AgentRequest`。

**`send()`**（第 543-560 行）——发送回复：

```python
async def send(self, to_handle: str, text: str, meta=None) -> None:
    if not self.enabled:
        return
    ts = _ts()
    prefix = (meta or {}).get("bot_prefix", self.bot_prefix) or ""
    self._safe_print(
        f"\n{GREEN}{BOLD}Bot [{ts}] -> {to_handle}{RESET}\n"
        f"{prefix}{text}\n",
    )
```

就这么简单——打印到终端。`to_handle` 在 Console Channel 里只是用来标识接收者，实际输出到 stdout。

**`start()` / `stop()`**（第 594-603 行）——生命周期：

```python
async def start(self) -> None:
    if not self.enabled:
        return
    logger.info("Console channel started")

async def stop(self) -> None:
    logger.info("console channel stopped")
```

无需建立任何连接，打印一行日志就完事。

**`health_check()`**（第 580-592 行）——健康检查：

```python
async def health_check(self) -> Dict[str, Any]:
    if not self.enabled:
        return {"channel": self.channel, "status": "disabled", ...}
    return {"channel": self.channel, "status": "healthy", ...}
```

Console 总是健康的——它不需要网络，不会断线。

## 探索：Telegram Channel——Webhook 与轮询的抉择

Console Channel 是"最简参考"。但在真实场景中，Channel 要复杂得多。Telegram Channel 就是一个很好的对照。

### 通信方式的选择：长轮询（Polling）

Telegram Channel 使用**长轮询**（Long Polling）来接收消息。这在 `channel.py` 第 264 行的类注释里说得很清楚：

```python
class TelegramChannel(BaseChannel):
    """Telegram channel: Bot API polling; session_id = telegram:{chat_id}."""
```

长轮询的原理是：客户端向 Telegram 服务器发送一个 HTTP 请求，说"如果有新消息就立即返回给我；如果没有，就等最多 N 秒再返回空"。客户端拿到响应后立即发下一个请求。这样循环往复，就形成了一种"准实时"的消息接收机制。

Telegram Channel 的轮询实现在 `_run_polling()` 方法中（第 991-1031 行）：

```python
async def _run_polling(self) -> None:
    """Run Telegram polling with automatic reconnection."""
    delay = _RECONNECT_INITIAL_S
    while True:
        try:
            self._application = self._build_application()
            await self._polling_cycle(self._application)
            delay = _RECONNECT_INITIAL_S
        except InvalidToken:
            logger.error("invalid bot token -- not retrying")
            return
        except Exception:
            logger.exception("polling failed ...")
        finally:
            if self._application:
                await self._teardown_application(self._application)
        await asyncio.sleep(delay)
        delay = min(delay * _RECONNECT_FACTOR, _RECONNECT_MAX_S)
```

注意几个工程细节：

- **指数退避重连**（`delay * _RECONNECT_FACTOR`）：网络抖动时不会疯狂重试，而是越来越慢地重试，最大间隔 30 秒
- **InvalidToken 不可恢复**：如果 token 无效，重试多少次都没用，直接退出
- **`_build_application()` 每次重建**：每次重连都创建新的 Telegram Application 实例，避免状态污染

### 消息收发的全流程

当一条 Telegram 消息到达时，完整的处理链路是：

```
Telegram 服务器
    │
    │  long polling
    ▼
_handle_message()（第 368-441 行）
    │
    │  解析消息：提取文本、图片、文件等
    │  提取元数据：chat_id、user_id、是否群聊等
    │
    ▼
_build_content_parts_from_message()（第 140-237 行）
    │
    │  把 Telegram 原生消息转成统一的 content_parts
    │  TextContent、ImageContent、FileContent...
    │  下载图片/文件到本地 media_dir
    │
    ▼
self._enqueue(native_dict)
    │
    │  把原生 dict 放入 ChannelManager 的队列
    │  ChannelManager 调用 consume_one()
    │  consume_one() 调用 build_agent_request_from_native()
    │  然后调用基类的 _consume_one_request()
    │  _consume_one_request() 调用 Agent 的 _process()
    │
    ▼
Agent 生成回复
    │
    │  回复是 Message 对象列表
    │  基类调用 send_message_content() → send_content_parts()
    │  send_content_parts() 拆分为文本 + 媒体
    │
    ▼
TelegramChannel.send()（第 605-660 行）
    │
    │  文本: bot.send_message(chat_id=..., text=..., parse_mode=HTML)
    │  媒体: send_media() → bot.send_photo / send_video / send_document
    │
    ▼
Telegram 用户收到回复
```

### Telegram 的消息转换——`build_agent_request_from_native()`

第 1113-1131 行展示了 Telegram 如何把原生 dict 转成 `AgentRequest`：

```python
def build_agent_request_from_native(self, native_payload: Any) -> Any:
    payload = native_payload if isinstance(native_payload, dict) else {}
    channel_id = payload.get("channel_id") or self.channel
    sender_id = payload.get("sender_id") or ""
    content_parts = payload.get("content_parts") or []
    meta = payload.get("meta") or {}
    session_id = self.resolve_session_id(sender_id, meta)
    user_id = str(meta.get("user_id") or sender_id)
    request = self.build_agent_request_from_user_content(...)
    request.user_id = user_id
    request.channel_meta = meta
    return request
```

结构和 Console 几乎一样，但有两个区别：

1. `user_id` 从 `meta` 中提取（Telegram 的 `user_id` 和 `chat_id` 不同）
2. `channel_meta` 携带 `chat_id`、`is_group` 等平台特有的元信息

### Telegram 的发送——分块与格式转换

Telegram 有一个限制：单条消息不能超过 4096 字符。Telegram Channel 用 `_chunk_text()` 方法（第 534-554 行）处理这个问题，按换行符或空格在安全位置切分文本。`send()` 方法（第 605-660 行）先尝试以 HTML 格式发送，如果 Telegram 报错（HTML 格式不合法），就回退到纯文本发送。

这是一个典型的工程实践：**先尝试最佳效果，失败时优雅降级**。

### 与钉钉和飞书的对比

QwenPaw 现在支持十几个频道。它们的通信方式各不相同：

| Channel | 接收方式 | 需要公网 IP | 实现复杂度 |
|---------|---------|------------|-----------|
| Console | HTTP API | 是（前端访问） | 低 |
| Telegram | 长轮询 | 否 | 中 |
| 钉钉 | Stream 长连接 | 否 | 高 |
| 飞书 | WebSocket 长连接 | 否 | 高 |
| Discord | WebSocket 长连接 | 否 | 中 |
| MQTT | MQTT 协议订阅 | 否 | 中 |

钉钉和飞书使用长连接，不需要公网 IP，适合企业内网部署。Telegram 使用轮询，同样不需要公网 IP。如果使用 Webhook 方式（比如某些自定义集成），则需要公网 IP。

## 探索：Channel 注册与生命周期

一个 Channel 从代码中的类定义到运行中的实例，经历了一条清晰的生命周期。

### 注册机制

`registry.py` 是 Channel 的注册中心。它维护了一个字典 `_BUILTIN_SPECS`（第 20-36 行），列出了所有内置频道：

```python
_BUILTIN_SPECS: dict[str, tuple[str, str]] = {
    "imessage": (".imessage", "IMessageChannel"),
    "discord": (".discord_", "DiscordChannel"),
    "dingtalk": (".dingtalk", "DingTalkChannel"),
    "telegram": (".telegram", "TelegramChannel"),
    "console": (".console", "ConsoleChannel"),
    # ... 还有十多个
}
```

每个条目是 `(模块名, 类名)` 对。`get_channel_registry()` 函数（第 190-194 行）会动态导入所有内置频道类，加上从 `custom_channels/` 目录发现的自定义频道类，合并成一个字典返回。

### ChannelManager 的编排

`manager.py` 中的 `ChannelManager` 是所有频道的"指挥官"。它负责：

1. **创建频道实例**（`from_config()` 或 `from_env()`，第 89-216 行）
2. **为每个频道设置入队回调**（第 480-481 行）
3. **启动所有频道**（第 462-493 行）
4. **管理消息队列和消费循环**（第 365-460 行）
5. **停止所有频道**（第 494-540 行）

频道启动的完整流程：

```
ChannelManager.start_all()
    │
    ├── 创建 UnifiedQueueManager（统一队列管理器）
    │
    ├── 遍历每个频道:
    │     │
    │     ├── 如果 uses_manager_queue=True:
    │     │     设置 enqueue 回调 → self._make_enqueue_cb(ch.channel)
    │     │     频道收到消息时调用 self._enqueue → 进入统一队列
    │     │
    │     └── await ch.start()
    │           触发频道建立连接（轮询/WebSocket/等）
    │
    └── UnifiedQueueManager 为每个 (channel, session) 创建消费循环
          消费循环调用 _process_batch() → ch._consume_one_request()
```

### 消息入队的路径

当 Telegram 收到一条消息时：

```
Telegram 服务器
    │
    ▼  long polling
_handle_message()（在 Telegram Application 中）
    │
    │  解析消息，构建 native dict:
    │  {"channel_id": "telegram", "sender_id": "12345",
    │   "content_parts": [TextContent(...)], "meta": {...}}
    │
    ▼
self._enqueue(native)（第 438 行）
    │
    │  _enqueue 是 ChannelManager 设置的回调
    │  实际调用 ChannelManager.enqueue("telegram", native)
    │
    ▼
```

## 探索：消息格式转换的三个阶段

每种聊天平台都有自己的消息格式。Telegram 用 `Update` 对象，钉钉用 `ChatbotMessage`，飞书用事件 JSON。但 QwenPaw 的 Agent 只认识一种格式——`AgentRequest`。Channel 的核心工作就是在平台格式和内部格式之间做转换。

这个转换分为三个阶段：

### 阶段一：平台原生消息 → 统一 content_parts

不同平台的消息结构千差万别。Telegram 的消息可能包含 `text`、`photo`、`document` 等字段；钉钉的消息有 `senderStaffId`、`sessionWebhook` 等特有字段。

Channel 的 `build_agent_request_from_native()` 方法负责从这些各异的结构中提取出统一的 `content_parts`。`content_parts` 是一个列表，元素类型来自 `agentscope_runtime` 的内容模型：

```
content_parts = [
    TextContent(type="text", text="你好"),
    ImageContent(type="image", image_url="file:///tmp/photo.jpg"),
    FileContent(type="file", file_url="file:///tmp/doc.pdf", filename="doc.pdf"),
]
```

Telegram 的提取逻辑在 `_build_content_parts_from_message()` 中（第 140-237 行）。它做了大量工作：解析消息实体（识别 @机器人）、下载图片/文件到本地、构建 `TextContent` / `ImageContent` 等。

### 阶段二：content_parts → AgentRequest

这一步是通用的，由基类的 `build_agent_request_from_user_content()` 完成（第 607-640 行）：

```python
def build_agent_request_from_user_content(
    self, channel_id, sender_id, session_id, content_parts, channel_meta=None,
):
    msg = Message(type=MessageType.MESSAGE, role=Role.USER, content=content_parts)
    return AgentRequest(
        session_id=session_id,
        user_id=sender_id,
        input=[msg],
        channel=channel_id,
    )
```

它把 `content_parts` 包装成一条 `Message`（角色是 USER），再包装成 `AgentRequest`。所有 Channel 共享这一步，不需要子类操心。

### 阶段三：AgentResponse → 平台原生回复

Agent 的回复是一系列 `Message` 对象，包含 `TextContent`、`ImageContent` 等内容。Channel 需要把这些内容翻译回平台能理解的格式。

基类的 `send_content_parts()`（第 1127-1178 行）提供了默认实现：把文本合并成一个字符串发送，媒体作为 URL 附加在文本后面。对于 Telegram 这种原生支持图片/文件的平台，子类会覆盖 `send_media()` 来真正上传附件。

消息转换的完整流程图：

## 工程权衡：接入新频道的四个决策

在动手实现之前，让我们思考接入新频道时的几个关键决策。

### 权衡一：轮询 vs Webhook vs 长连接

这是接入新频道时最基础的架构决策。三种方式的对比：

**轮询（Polling）**：定时向平台 API 请求新消息。

- 优点：实现最简单，不需要公网 IP，不需要额外的 HTTP 端点
- 缺点：有延迟（取决于轮询间隔），空轮询浪费资源
- 适用：Telegram（官方推荐的长轮询）、简单集成

**Webhook**：告诉平台"有新消息就往这个 URL 发 POST 请求"。

- 优点：实时性最好，资源消耗最低（没有空轮询）
- 缺点：需要公网 IP 和 HTTPS 证书，需要处理重试和幂等性
- 适用：面向公众的服务、有固定服务器的部署

**长连接（WebSocket/Stream）**：建立持久的双向通道。

- 优点：实时、双向、不需要公网 IP
- 缺点：实现复杂（心跳、重连、线程安全），需要平台的 SDK 支持
- 适用：企业内网部署、钉钉/飞书等平台

QwenPaw 的选择策略：如果平台 SDK 推荐某种方式就跟着走（如钉钉用 Stream、飞书用 WebSocket），否则优先轮询（如 Telegram），除非有实时双向通信的需求。

### 权衡二：消息防抖的必要性

有些平台会把一条"图片+文字"消息拆成两条推送——先推图片、再推文字，间隔可能几百毫秒。如果 Channel 分别处理这两条消息，Agent 会被调用两次，第一次只看到图片（没有上下文），体验很差。

BaseChannel 提供了 `_apply_no_text_debounce()` 机制（第 281-313 行）：如果收到的消息没有文本（只有图片/文件），先缓存起来；等收到包含文本的消息时，把缓存的内容合并在一起处理。

Telegram Channel 覆盖了这个方法（第 445-459 行），让包含媒体的消息立即处理：

```python
def _apply_no_text_debounce(self, session_id, content_parts):
    has_media = any(
        getattr(part, "type", None) not in (ContentType.TEXT, ContentType.REFUSAL)
        for part in content_parts
    )
    if has_media:
        pending = self._pending_content_by_session.pop(session_id, [])
        return True, pending + list(content_parts)
    return super()._apply_no_text_debounce(session_id, content_parts)
```

是否需要防抖取决于平台的消息推送行为。如果你的平台总是把一条完整消息作为一次推送，就不需要。

### 权衡三：是否使用管理器队列

BaseChannel 有一个类属性 `uses_manager_queue`（默认 `True`）。如果设为 `True`，ChannelManager 会为这个频道创建消息队列和消费循环，频道只需要调用 `self._enqueue(payload)` 把消息放进队列。

Console Channel 没有设置这个属性（使用默认的 `True`），但它的消息不是从外部推送的，而是从前端 HTTP 请求直接调用 `stream_one()` 处理。大多数使用管理器队列的频道（Telegram、钉钉、飞书……）都是外部推送消息的模式。

### 权衡四：媒体处理策略

媒体（图片、视频、文件）处理是 Channel 实现中最复杂的部分。你需要决定：

1. **下载还是引用**：Telegram Channel 选择下载到本地（`_download_telegram_file()`），这样后续发送给 Agent 时用的是本地路径；某些平台可以直接传 URL
2. **大小限制**：Telegram 限制 50MB（`TELEGRAM_MAX_FILE_SIZE_BYTES`），超出需要提示用户
3. **格式转换**：发送时，Agent 输出的 Markdown 需要转成 Telegram 的 HTML 格式（`markdown_to_telegram_html()`）

如果你的平台不支持媒体，继承基类的 `send_media()` 默认实现（no-op）就行。

## 动手：实现一个简易 Webhook Channel

理论讲够了。让我们从零实现一个最小化的 Channel。假设我们要接入一个名叫 "SimpleChat" 的简单平台，它通过 Webhook 推送消息给我们。

### 需求分析

SimpleChat 的 API 规格如下：

- **接收消息**：SimpleChat 向 `https://your-server/api/simplechat/webhook` 发 POST 请求
  - 请求体：`{"user_id": "u123", "text": "你好", "chat_id": "c456"}`
- **发送回复**：我们向 `https://api.simplechat.example.com/v1/messages` 发 POST 请求
  - 请求体：`{"chat_id": "c456", "text": "回复内容"}`

### 最小化实现

```python
# custom_channels/simplechat.py
import httpx
from typing import Any, Dict, List, Optional
from pathlib import Path

from qwenpaw.app.channels.base import (
    BaseChannel, ProcessHandler, OnReplySent, OutgoingContentPart,
)
from qwenpaw.app.channels.schema import ChannelType


class SimpleChatChannel(BaseChannel):
    """SimpleChat: Webhook receive, REST API send."""

    channel: ChannelType = "simplechat"

    def __init__(
        self,
        process: ProcessHandler,
        enabled: bool,
        api_url: str,
        api_token: str,
        on_reply_sent: OnReplySent = None,
    ):
        super().__init__(process, on_reply_sent=on_reply_sent)
        self.enabled = enabled
        self._api_url = api_url
        self._api_token = api_token

    # ── 工厂方法 ──────────────────────────────────────────────

    @classmethod
    def from_env(cls, process, on_reply_sent=None):
        import os
        return cls(
            process=process,
            enabled=os.getenv("SIMPLECHAT_ENABLED", "0") == "1",
            api_url=os.getenv("SIMPLECHAT_API_URL", ""),
            api_token=os.getenv("SIMPLECHAT_API_TOKEN", ""),
            on_reply_sent=on_reply_sent,
        )

    @classmethod
    def from_config(cls, process, config, on_reply_sent=None, **kwargs):
        return cls(
            process=process,
            enabled=getattr(config, "enabled", False),
            api_url=getattr(config, "api_url", ""),
            api_token=getattr(config, "api_token", ""),
            on_reply_sent=on_reply_sent,
        )

    # ── 消息转换 ──────────────────────────────────────────────

    def resolve_session_id(self, sender_id, channel_meta=None):
        meta = channel_meta or {}
        chat_id = meta.get("chat_id")
        if chat_id:
            return f"simplechat:{chat_id}"
        return f"simplechat:{sender_id}"

    def build_agent_request_from_native(self, native_payload):
        payload = native_payload if isinstance(native_payload, dict) else {}
        from agentscope_runtime.engine.schemas.agent_schemas import (
            ContentType, TextContent,
        )
        text = payload.get("text", "")
        content_parts = [TextContent(type=ContentType.TEXT, text=text)]
        sender_id = payload.get("user_id", "")
        meta = {
            "chat_id": payload.get("chat_id", ""),
            "user_id": sender_id,
        }
        session_id = self.resolve_session_id(sender_id, meta)
        request = self.build_agent_request_from_user_content(
            channel_id=self.channel,
            sender_id=sender_id,
            session_id=session_id,
            content_parts=content_parts,
            channel_meta=meta,
        )
        request.channel_meta = meta
        return request

    # ── 发送 ──────────────────────────────────────────────────

    async def send(self, to_handle, text, meta=None):
        if not self.enabled:
            return
        meta = meta or {}
        chat_id = meta.get("chat_id") or to_handle
        async with httpx.AsyncClient() as client:
            await client.post(
                self._api_url,
                json={"chat_id": chat_id, "text": text},
                headers={"Authorization": f"Bearer {self._api_token}"},
                timeout=10,
            )

    # ── 生命周期 ──────────────────────────────────────────────

    async def health_check(self):
        if not self.enabled:
            return {"channel": self.channel, "status": "disabled"}
        return {"channel": self.channel, "status": "healthy"}

    async def start(self):
        if not self.enabled:
            return
        # Webhook 模式：不需要主动建立连接
        # 消息由 AgentApp 的 HTTP 路由接收后调用 enqueue
        logger.info("SimpleChat channel started")

    async def stop(self):
        logger.info("SimpleChat channel stopped")
```

### Webhook 路由注册

SimpleChat 使用 Webhook 接收消息，需要注册一个 HTTP 路由。在同一个文件中添加：

```python
# custom_channels/simplechat.py（续）
def register_app_routes(app):
    """注册 Webhook 路由，由 registry.py 自动调用。"""
    from fastapi import Request

    @app.post("/api/simplechat/webhook")
    async def simplechat_webhook(request: Request):
        body = await request.json()
        manager = app.state.channel_manager
        manager.enqueue("simplechat", body)
        return {"status": "ok"}
```

`registry.py` 在启动时会扫描 `custom_channels/` 目录，如果模块有 `register_app_routes` 函数就自动调用（第 135-187 行）。这样 Webhook 路由就自动注册到了 FastAPI 应用上。

### 部署文件

把 `simplechat.py` 放到 `custom_channels/` 目录下，QwenPaw 启动时会自动发现并注册。然后在 `agent.json` 中配置：

```json

  "channels": {
    "simplechat": {
      "enabled": true,
      "api_url": "https://api.simplechat.example.com/v1/messages",
      "api_token": "your-token-here"
    }
  }

```

在 SimpleChat 平台那端，把 Webhook URL 配置为 `https://your-server/api/simplechat/webhook`。消息通道就打通了。
