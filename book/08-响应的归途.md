# 第八章 响应的归途

```
浏览器 ─→ HTTP ─→ Runner ─→ Agent ─→ Prompt ─→ ReAct ─→ LLM ─→ Tool ─→ [响应流回浏览器]
                                                                              |
                                                                           你在这里
```

`[响应归途]` -- 第一卷的最后一站。

## 问题：Agent 生成的回复，是怎么回到浏览器的？为什么能逐字显示？

前几章里，我们跟着用户的消息走过了一条漫长的路：它穿过了 HTTP 路由（第一章），被 Runner 接收并分发（第二章），催生了一个 Agent 实例（第三章），装上了系统提示词和工具列表（第四章），进入了 ReAct 循环（第五章），被发送到远端的大模型 API（第六章），触发了工具调用（第七章）。

现在，大模型终于吐出了文字。工具也执行完了。Agent 把最终回复组装好了。

这条消息要走完它的最后一段旅途：从 Python 的内存，一路回到你的浏览器屏幕上。而且不是等全部生成完了一次性显示——它要"一个字一个字"地蹦出来。

这是怎么做到的？

如果中途网络断了，你刷新了页面，之前生成了一半的内容会丢失吗？

这一章，我们要追踪的就是这条"归途"——从 Agent 产出的最后一条消息，到浏览器里你看到的每一个字。

这也是第一卷的最后一站。走到这里，我们就完成了对一整条请求链路的理解。

## 术语其实很简单

> **术语：SSE（Server-Sent Events）**
> 想象你打开了一个水龙头，水一直流。SSE 就是服务器端的水龙头——服务器不断往里"倒"数据，浏览器不断"接"数据。和 WebSocket 不同，SSE 是单向的：只有服务器能往客户端发数据。格式也很简单：每条数据以 `data: ` 开头，后面跟着内容，最后用一个空行分隔。

> **术语：消息队列（asyncio.Queue）**
> 想象一条传送带。生产者（Agent）把生成的文字放到传送带上，消费者（SSE 发送器）从传送带上取走文字并发给浏览器。传送带的好处是：生产者和消费者不需要同时工作——如果 Agent 生成得快，文字就先堆在传送带上；如果网络慢，传送带就积攒一些，等网络好了再发。

> **术语：哨兵值（Sentinel）**
> 想象一场接力赛，最后一棒跑完之后，裁判吹响哨子表示"比赛结束"。在编程里，哨兵值就是一个特殊的标记，放在队列末尾，告诉消费者"后面没有更多数据了，可以收工"。

## 探索：从 Agent 到浏览器的三级管道

### 第一级：Agent 把消息推入队列

还记得第五章讲的 ReAct 循环吗？Agent 在循环中不断"思考-行动-观察"，最终产出一个纯文本回复。这个回复不是直接发给浏览器的——它先被放进一个 `asyncio.Queue` 里。

这个过程由 `_stream_printing_messages_interruptible()` 函数完成。它在 `src/qwenpaw/app/runner/runner.py` 的第 79 行。我们来看看它的核心逻辑：

```python
async def _stream_printing_messages_interruptible(
    *, agents, coroutine_task,
):
    queue = asyncio.Queue()
    # 让 agent 把生成的消息放进这个队列
    for agent in agents:
        agent.set_msg_queue_enabled(True, queue)

    task = asyncio.create_task(coroutine_task)
    # Agent 任务完成后，往队列里放一个结束信号
    task.add_done_callback(
        lambda _: queue.put_nowait(_PRINT_END_SIGNAL)
    )
```

这段代码做了三件事：

1. **创建一个空的队列**。这个队列就是传送带。
2. **告诉 Agent："你生成的每一条消息，都放到这个队列里。"** `set_msg_queue_enabled(True, queue)` 这个调用把队列"挂"到了 Agent 上。之后 Agent 每生成一段文字（哪怕只是推理过程中的中间消息），都会自动放进队列。
3. **注册一个回调：任务结束后放一个哨兵值。** `_PRINT_END_SIGNAL` 的值是字符串 `"[END]"`。它告诉下游的消费者："Agent 已经说完了，不要再等了。"

然后是一个简洁的消费循环：

```python
while True:
    printing_msg = await queue.get()     # 阻塞等待，直到有消息
    if printing_msg == _PRINT_END_SIGNAL:  # 收到哨兵值，退出
        break
    msg, last, _ = printing_msg
    yield msg, last                      # 把消息传给下一级
```

`yield` 是 Python 异步生成器的关键字——它不是 `return`，不会结束函数，而是把当前的值"送出去"，然后暂停，等下游要下一个值时再继续。这就像一条流水线：每生产一件产品就传给下一站，不用等产品全部做完。

### 第二级：TaskTracker 的广播和缓冲

消息从 Agent 出来后，进入了 `TaskTracker` 管辖的地盘。TaskTracker 在 `src/qwenpaw/app/runner/task_tracker.py` 中，它是整个流式系统的"交通枢纽"。

TaskTracker 要解决三个问题：

**问题一：怎么把消息发给浏览器？**

答案是通过 SSE。但 Agent 和浏览器之间不能直接通信——Agent 跑在后台任务里，浏览器在等 HTTP 响应。中间需要一个"中转站"。这个中转站就是 TaskTracker。

**问题二：如果有多个订阅者呢？**

比如你在手机和电脑上同时打开了同一个聊天窗口。两个浏览器都在等消息。Agent 只生产一份消息，但需要发给两个消费者。这就是"广播"。

**问题三：如果中途断线了怎么办？**

你的网络抖了一下，SSE 连接断了。等网络恢复后，你重新连接。之前已经生成的内容还要不要？当然要。那怎么保证不丢失？

TaskTracker 的答案是**事件缓冲（buffer）**。让我们看看它的核心数据结构：

```python
@dataclass
class _RunState:
    task: asyncio.Future              # 后台任务
    queues: list[asyncio.Queue]       # 每个订阅者的队列
    buffer: list[str]                 # 事件缓冲（所有已发送过的 SSE 事件）
```

每个正在运行的任务对应一个 `_RunState`。`queues` 是一个列表——每个订阅者（每个浏览器的 SSE 连接）都有自己的队列。`buffer` 是一个列表，存着所有已经发送过的 SSE 事件字符串。

当 Agent 产生一条新消息时，`_producer` 协程这样广播：

```python
async def _producer():
    async for sse in stream_fn(payload):
        async with tracker.lock:
            run.buffer.append(sse)      # 存入缓冲
            for q in run.queues:        # 广播给所有订阅者
                q.put_nowait(sse)
    # 任务结束，向所有队列放入哨兵值
    for q in run.queues:
        q.put_nowait(_SENTINEL)
```

锁（`tracker.lock`）保证了广播的原子性——不会出现"消息放进了一半的队列"的情况。

当消费者（浏览器的 SSE 连接）从队列里取数据时，`stream_from_queue()` 方法这样工作：

```python
async def stream_from_queue(self, queue, run_key):
    try:
        while True:
            event = await queue.get()     # 阻塞等待
            if event is _SENTINEL:        # 哨兵值 = 结束
                break
            yield event                   # 送给浏览器
    finally:
        # 无论什么原因结束（正常完成、断线、取消），都要清理
        await self.detach_subscriber(run_key, queue)
```

`finally` 块非常关键。无论消费者因为什么原因停止——正常结束、网络断开、用户关闭页面——`finally` 都会执行，把当前订阅者的队列从订阅列表中移除。这样就不会有"幽灵订阅者"一直占着内存。

**断线重连**是这样实现的：

```python
async def attach(self, run_key):
    async with self._lock:
        state = self._runs.get(run_key)
        if state is None or state.task.done():
            return None
        q = asyncio.Queue()
        # 先把缓冲里的事件全部回放
        for sse in state.buffer:
            q.put_nowait(sse)
        state.queues.append(q)
        return q
```

当你刷新页面时，浏览器会重新发起请求，带上 `reconnect=true`。路由函数调用 `tracker.attach()`，TaskTracker 就创建一个新的队列，把缓冲里积攒的所有事件先灌进去，然后把这个队列加入订阅列表。之后新产生的事件也会照常推送。

你刷新页面的瞬间，浏览器看到的不是空白——它先快速回放已经生成的内容，然后继续接收新内容。整个过程对用户来说就像什么都没断过。

### 第三级：路由函数把 SSE 事件发给浏览器

现在消息已经到了订阅者的队列里。最后一步是由路由函数中的 `event_generator()` 把它们以 SSE 格式发送出去。

这段代码在 `src/qwenpaw/app/routers/console.py` 的第 156 行：

```python
async def event_generator():
    stream_it = tracker.stream_from_queue(queue, chat.id)
    try:
        async for event_data in stream_it:
            yield event_data
    except Exception as e:
        yield f"data: {json.dumps({'error': str(e)})}\n\n"
    finally:
        await stream_it.aclose()
```

`event_generator` 是一个异步生成器。FastAPI 的 `StreamingResponse` 会持续调用它，每次 `yield` 出一个值就立刻发送给浏览器。

但等等——`event_data` 是什么格式的？

让我们追溯一下。在控制台频道的 `stream_one()` 方法（`src/qwenpaw/app/channels/console/channel.py` 第 332 行）中，原始的 Agent 事件被序列化为 JSON 字符串，然后包装成 SSE 格式：

```python
async for event in self._process(request):
    # 把 Event 对象序列化为 JSON
    if hasattr(event, "model_dump_json"):
        data = event.model_dump_json()
    else:
        data = json.dumps({"text": str(event)})
    # 包装成 SSE 格式
    yield f"data: {data}\n\n"
```

SSE 格式非常简单。每一条事件的格式是：

```
data: {"object":"content","type":"text","data":{"output":[{"type":"text","text":"你"}]}}\n\n
```

以 `data: ` 开头，后面是 JSON 内容，最后是两个换行符（一个空行）。浏览器看到空行就知道"这一条事件结束了"，立刻处理。

最终，`StreamingResponse` 把这些 SSE 事件逐条推给浏览器：

```python
return StreamingResponse(
    event_generator(),
    media_type="text/event-stream",
    headers={
        "Cache-Control": "no-cache",
        "Connection": "keep-alive",
    },
)
```

`media_type="text/event-stream"` 告诉浏览器"这是 SSE 流，请用 SSE 协议来解析"。`Cache-Control: no-cache` 确保浏览器不会缓存这些事件（每条事件都是实时数据，缓存没有意义）。`Connection: keep-alive` 保持 TCP 连接不断开，服务器可以持续推送。

### SSE 事件的真实模样

浏览器接收到的 SSE 事件流看起来是这样的（简化后）：

```
data: {"object":"response","status":"in_progress",...}

data: {"object":"content","type":"text","status":"in_progress","data":{"output":[{"type":"text","text":"你"}]}}

data: {"object":"content","type":"text","status":"in_progress","data":{"output":[{"type":"text","text":"好"}]}}

data: {"object":"content","type":"text","status":"in_progress","data":{"output":[{"type":"text","text":"！"}]}}

data: {"object":"content","type":"text","status":"in_progress","data":{"output":[{"type":"text","text":"我是 QwenPaw"}]}}

...（更多 content 事件）

data: {"object":"message","status":"completed",...}

data: {"object":"response","status":"completed",...}
```

三种事件类型，各有分工：

- `object: "response", status: "in_progress"` -- 响应开始了，告诉浏览器"后面会有内容"
- `object: "content", status: "in_progress"` -- 一小段文字内容。每一条都是增量——不是全部文字，而是新生成的那几个字
- `object: "message", status: "completed"` -- 一条完整的消息结束了
- `object: "response", status: "completed"` -- 整个响应结束了

浏览器的 JavaScript 代码收到每个 `content` 事件后，把文字追加到聊天界面上。因为事件是逐条到达的，所以你看到的文字就是"一个字一个字"蹦出来的。

### 流终止：怎么知道"说完了"？

Agent 的回复不会无限地流下去。有三个信号标志着流的结束：

**信号一：`_PRINT_END_SIGNAL`**（在 Runner 层）。Agent 的协程任务执行完毕后，`_stream_printing_messages_interruptible()` 收到 `"[END]"` 信号，停止从队列中读取消息。

**信号二：`_SENTINEL`**（在 TaskTracker 层）。值为 `None`。`_producer` 协程在所有事件发送完毕后，向所有订阅者队列放入 `None`。`stream_from_queue()` 看到 `None` 就停止迭代。

**信号三：`object: "response", status: "completed"`**（在 SSE 协议层）。这是浏览器能看到的最终信号——一个 `completed` 状态的响应事件。浏览器收到它后关闭 SSE 连接，显示最终结果。

三个信号在不同层级工作，构成了一个完整的终止链：

```
Agent 协程完成
  |  _PRINT_END_SIGNAL
  v
_stream_printing_messages_interruptible() 退出循环
  |  yield 结束
  v
stream_one() 的 for 循环结束
  |  _producer 广播 _SENTINEL
  v
stream_from_queue() 退出循环
  |  yield 结束
  v
event_generator() 退出循环
  |  yield 结束
  v
StreamingResponse 关闭连接
  |
  v
浏览器收到最后的事件，关闭 SSE 连接
```

就像一列火车从起点站开出，经过每一站都会有人下车，直到终点站全部清空。

### 中途取消：用户点"停止"怎么办？

有时候用户不想等了，点了页面上的"停止"按钮。浏览器会向 `/api/console/chat/stop` 发送一个 POST 请求。路由函数调用 `tracker.request_stop(chat_id)`，TaskTracker 取消后台任务。

取消后，Agent 的协程会收到 `CancelledError` 异常。`_stream_printing_messages_interruptible()` 捕获这个异常，执行清理工作：取消 Agent 任务、关闭队列。

```python
except asyncio.CancelledError:
    await _cancel_streaming_agent_task(task)
    raise
```

取消操作像一根针一样穿透了整个管道——从 TaskTracker 到后台任务到 Agent 到模型调用。所有层都能感知到取消，各自清理自己的资源。

回想一下你在这条路上走过的每一步：

在**第一章**，你看到了浏览器的 HTTP 请求如何穿过三层中间件，被路由到 `post_console_chat()` 函数。你第一次见到了 SSE 流式响应的样子。

在**第二章**，你跟着请求进入了 Runner。`query_handler()` 是一个超级函数——它负责从解析请求到创建 Agent 的全部工作。你看到了它怎么加载配置、注入上下文、启动会话。

在**第三章**，你见证了 Agent 的诞生。`QwenPawAgent()` 被实例化，系统提示词、工具集、MCP 客户端、记忆管理器——所有组件都被装配到这个 Agent 实例上。就像一辆汽车在工厂里被组装：引擎、方向盘、轮胎，一个一个装上去。

在**第四章**，你钻进了提示词的拼装过程。AGENTS.md 定义了 Agent 的人格，SOUL.md 写了它的灵魂，PROFILE.md 描述了它的能力。工具列表被转换成 JSON Schema。环境变量被注入。最终拼成了一段长长的系统提示词，告诉大模型"你是谁、你能做什么、你应该怎么回答"。

在**第五章**，你进入了 ReAct 循环。Agent 开始"思考-行动-观察"的循环。它不是一问一答——它会思考要不要调用工具，调用了工具之后会观察结果，然后继续思考。这个循环可能转很多圈，直到 Agent 认为已经可以给出最终回答。

在**第六章**，你看到了大模型 API 的调用。请求穿过 Provider 层、重试机制、限流器，最终到达远端的模型服务。流式响应一个 token 一个 token 地回来。

在**第七章**，你追踪了工具的执行。大模型返回的 `tool_use` 被解析成工具名和参数，然后通过 Toolkit 分发给具体的工具函数。执行结果被存入记忆，供下一轮思考使用。

现在，在**第八章**，你看到了回复怎么回到浏览器。Agent 的消息被推入队列，TaskTracker 广播给所有订阅者，SSE 格式化后通过 HTTP 连接推给浏览器。断线重连靠事件缓冲保证不丢失。取消操作穿透整条管道。

八个站点，一条完整路径。

从你在浏览器里按下回车，到屏幕上出现第一个字，中间经过了多少层抽象、多少次转换、多少个设计精巧的机制？这就是 QwenPaw——或者说，任何一个现代 AI 应用的内部世界。看起来简单的"一问一答"，背后是一场穿越多个站点的长途旅行。

## 实验：在 DevTools 里观察 SSE 事件流

纸上得来终觉浅。让我们亲手看看浏览器接收到的 SSE 事件是什么样的。

### 步骤

1. 打开 QwenPaw 的网页控制台（通常是 `http://127.0.0.1:8088`）。
2. 按 F12 打开浏览器的开发者工具（DevTools）。
3. 切换到 **Network（网络）** 标签。
4. 在聊天输入框里输入一句话，比如"说三个字"，然后按回车。
5. 在 Network 标签里，找到类型为 `fetch` 或 `XHR` 的请求——它应该是对 `/api/console/chat` 的 POST 请求。
6. 点击这个请求，在右侧面板中选择 **EventStream** 标签（如果看不到，选择 **Response** 标签）。

你会看到一条一条的事件实时出现。每一条都是 `data: {...}` 格式的 JSON。注意观察：

- 事件的 `object` 字段——你会看到 `"response"`、`"content"`、`"message"` 三种类型交替出现
- `content` 事件的 `data.output[0].text` 字段——这就是逐字生成的文字
- 最后一条 `response` 事件的 `status` 会变成 `"completed"`

如果 QwenPaw 没有运行，用 `curl` 也能看到相同的效果：

```bash
curl -N -X POST http://127.0.0.1:8088/api/console/chat \
  -H "Content-Type: application/json" \
  -d '{"session_id":"ch8-test","user_id":"default",\
"input":[{"content":[{"text":"说三个字","type":"text"}]}]}'
```

`-N` 禁用缓冲，你能实时看到每个 SSE 事件到来。

## 工程权衡：为什么这样设计？

### 为什么用 SSE 而不是 WebSocket？

这个问题在第一章已经讨论过，但站在第一卷的结尾回看，我们可以给出更完整的答案。

SSE（Server-Sent Events）和 WebSocket 都能实现"服务器推数据"。但 QwenPaw 选择 SSE，原因不止一个：

**协议简单性。** SSE 就是普通的 HTTP 响应，只是 `Content-Type` 设为 `text/event-stream`，格式是 `data: ...\n\n`。不需要握手、不需要心跳、不需要子协议协商。整个实现就是一个 `yield` 循环加一个 `StreamingResponse`。代码量少，出 bug 的地方就少。

**请求-响应模型的天然匹配。** 用户发一条消息（HTTP POST），AI 流式返回回答（SSE 流）。这就是一次 HTTP 请求对应一次 SSE 流。WebSocket 需要自己管理"哪条消息对应哪条回答"的映射关系——在多会话、多用户的场景下，这很容易出错。

**中间件全兼容。** SSE 走的是 HTTP，所以第一张里讲的中间件链（CORS、Auth、AgentContext）全部生效。WebSocket 连接建立后就不再是普通 HTTP 了，中间件可能失效。

**调试友好。** 用 `curl -N` 就能看到 SSE 的原始输出。WebSocket 需要专门的工具。

**自动重连。** 浏览器的 `EventSource` API 内置了重连机制——连接断开后会自动尝试重新连接。QwenPaw 的 TaskTracker 缓冲正好配合这个特性。

QwenPaw 唯一使用 WebSocket 的地方是实时语音对话，那是因为语音需要双向实时传输。普通的文字聊天，SSE 完全够用。

### 为什么 TaskTracker 需要事件缓冲？

事件缓冲（buffer）看似浪费内存——每条事件都存一份副本，运行时间越长，缓冲越大。但这个设计解决了两个真实问题：

**断线重连。** 移动端网络不稳定。用户在地铁上用 QwenPaw，进了隧道连接断了，出来后重新连接。没有缓冲的话，之前生成的内容全丢了——用户只能看到从重连那一刻开始的新内容。有了缓冲，`attach()` 方法会先把缓冲里的历史事件全部回放，然后继续接收新事件。用户看到的就像什么都没断过。

**多订阅者。** 两个浏览器窗口看同一个聊天。第二个窗口打开时，Agent 可能已经生成了一半的内容。没有缓冲的话，第二个窗口只能看到后半段。有了缓冲，第二个窗口打开时先快速回放前半段，然后和第一个窗口同步接收新内容。

缓冲的内存开销是可控的——一个 SSE 事件通常只有几百字节，一场对话的总事件量很少超过几 MB。任务完成后，`_producer` 的 `finally` 块会从 `self._runs` 中移除整个 `_RunState`，缓冲随之被垃圾回收。

### 为什么用 asyncio.Queue 而不是直接 yield？

你可能会想：Agent 生成消息，直接 yield 给路由函数不就行了吗？为什么要搞一个队列中转？

原因是**解耦**。Agent 和 HTTP 响应是两个独立的生命周期：

- Agent 可能在 HTTP 连接断开后还在运行（比如工具调用耗时很长）
- HTTP 连接可能在 Agent 完成前就断了（用户关闭页面）
- 同一个 Agent 的输出可能需要发给多个 HTTP 连接（多窗口）

`asyncio.Queue` 把"生产"和"消费"解耦了。Agent 不需要知道有多少个消费者、消费者是否还活着。消费者也不需要知道消息是哪个 Agent 生产的。TaskTracker 在中间当"经纪人"，负责广播、缓冲、清理。

这种"生产者-消费者"模式在编程中极其常见。不是过度设计，而是解决真实问题的标准方案。

## 第一卷小结

八站旅程，到此结束。

你从一个"按了回车之后到底发生了什么"的好奇心出发，穿过 HTTP 路由、Runner 调度、Agent 创建、提示词拼装、ReAct 循环、LLM 调用、工具执行、响应流回，最终看到了整条链路的全貌。

```
  [1] 浏览器 ─→ HTTP ─→ FastAPI ─→ [2] Runner ─→ [3] Agent ─→ [4] Prompt
                                                                    |
  [8] 浏览器渲染 ←─ SSE ←─ StreamingResponse ←─ TaskTracker ←─ [5] ReAct
                                               |                  |
                                               |            [6] LLM API
                                               |                  |
                                               +───── [7] Tool ←─┘
```

这八站不是孤立的。它们是一条链——每一站都依赖上一站的输出，为下一站准备输入。理解了这条链，你就能够：

- **定位 bug**：当 AI 回答出问题时，你能判断是提示词拼错了（第四章），还是工具执行失败了（第七章），还是模型本身回答不好（第六章）。
- **理解新代码**：当你打开一个没见过的源码文件时，你能判断它属于哪一站，上下游是谁。
- **做出贡献**：修一个小 bug、改进一段提示词、添加一个工具——你知道代码应该放在哪里。

第一卷的目标是"能追踪请求流程、定位 bug、修小问题"。如果你读到这里，能在脑海中画出上面那张全景图，并且对每一站都能说出"做了什么、涉及哪些文件"，那么第一卷的目标就达到了。

第二卷将带你进入更深层的设计模式——依赖注入、插件架构、配置热加载。但那是新的旅程了。

在第一卷的最后一页，让我们记住一句话：**任何复杂的系统，都是一条条简单链路的组合。追踪链路，理解系统。**

这就是源码阅读的核心方法。
