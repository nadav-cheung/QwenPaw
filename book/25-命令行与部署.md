`[卷四·纵深·第六章]` -- 上一章我们拆解了 Plugin 系统——它让开发者可以用 Python 代码扩展 QwenPaw 的核心能力。但所有这些代码、所有这些架构，最终都要从一个入口启动起来。当你敲下 `qwenpaw app` 的时候，到底发生了什么？如果你想把 QwenPaw 部署到一台远程服务器上，让它 7x24 小时运行，又该怎么做？

这就是本章要回答的问题：**`qwenpaw app` 做了什么？怎么部署到服务器？**

---

## 问题：`qwenpaw app` 做了什么？

如果你一路读到这里，你已经在脑海中追踪过一条 HTTP 请求从浏览器到 LLM 的完整路径。但我们一直没有回答一个看似简单的问题：**这条路径是怎么建立起来的？** 服务端是怎么从零开始启动、加载配置、初始化 Agent、注册路由、最终开始监听 8088 端口的？

答案从你的终端开始。当你在命令行输入：

```bash
qwenpaw app
```

一条启动链就开始了。这条链从操作系统的包管理器（pyproject.toml 中的 `console_scripts`）出发，经过 Click 框架的命令分发，到达 `app_cmd.py` 中的 uvicorn 启动，最终进入 `_app.py` 中的 FastAPI 应用初始化。

而当你想在生产环境中运行时，单进程的 `qwenpaw app` 就不够了——你需要 Docker 容器、进程管理器、持久化存储、环境变量配置。这就是部署的故事。

## 术语其实很简单

> **术语：Click（命令行框架）**
>
> 想象一家餐厅的前台。客人进来以后不需要知道厨房在哪、厨师是谁、冰箱里有什么——只需要告诉前台"我要一份宫保鸡丁"，前台就会把订单转到正确的窗口。Click 就是这个"前台"。你敲下 `qwenpaw app`，Click 负责把 `app` 这个关键词路由到对应的处理函数（`app_cmd.py`）。它还帮你处理参数解析（`--host`、`--port`、`--log-level`）、帮助信息（`-h`）、版本号（`--version`）等琐碎但必需的事情。Click 是 Python 世界最流行的命令行框架之一，由 Armin Ronacher（Flask 作者）创建。

> **术语：懒加载（Lazy Loading）**
>
> 想象一栋大楼有 30 层，每层住着不同的人。如果每天早上所有 30 层的人都要下楼集合报到，那效率太低了。更好的做法是：只在大厅登记谁住在哪层，等谁被叫到了才让他下来。懒加载就是这个策略——CLI 启动时不加载所有子命令模块，只在用户实际调用某个命令时才 `import` 对应的 Python 文件。QwenPaw 有 20 多个子命令，懒加载让 CLI 的启动速度从"导入所有模块"变成了"只导入核心"。

> **术语：Docker Compose**
>
> 想象你在搭积木。一块积木是数据库，一块是应用服务器，一块是缓存。Docker Compose 就是一张"搭积木说明书"——你只需要写一个 YAML 文件，告诉它需要哪些积木（服务）、它们之间怎么连接（网络）、数据存在哪里（卷）。一条 `docker compose up` 命令就能把所有积木搭好。QwenPaw 的 Docker Compose 配置只有几十行，但它包含了容器编排的核心理念。

## 探索：CLI 入口点——从终端到 Click

### pyproject.toml 中的入口声明

一切从 `pyproject.toml` 开始。第 73-75 行：

```toml
[project.scripts]
qwenpaw = "qwenpaw.cli.main:cli"
copaw   = "qwenpaw.cli.main:cli"
```

这两行声明了两个命令行入口：`qwenpaw` 和 `copaw`（历史兼容名）。当你用 `pip install .` 安装 QwenPaw 时，setuptools 会生成两个可执行脚本，它们都指向同一个 Python 函数：`qwenpaw.cli.main:cli`。

当你在终端输入 `qwenpaw app`，操作系统做了这几步：

```
终端: qwenpaw app
    │
    ├── 1. 查找 PATH 中的 qwenpaw 可执行文件
    │       (pip 安装时生成在 venv/bin/ 下)
    │
    ├── 2. 执行脚本，脚本内容类似:
    │       from qwenpaw.cli.main import cli
    │       cli()
    │
    └── 3. Click 接管，解析 "app" 子命令
```

### LazyGroup：懒加载的魔法

`main.py` 最核心的设计是 `LazyGroup`（第 58-92 行）。它继承自 `click.Group`，重写了两个方法：

```python
class LazyGroup(click.Group):
    def list_commands(self, ctx):
        base = super().list_commands(ctx)
        return sorted(set(base) | set(self.lazy_subcommands.keys()))

    def get_command(self, ctx, cmd_name):
        cmd = super().get_command(ctx, cmd_name)
        if cmd is not None:
            return cmd
        if cmd_name in self.lazy_subcommands:
            module_path, attr_name, label = self.lazy_subcommands[cmd_name]
            module = __import__(module_path, fromlist=[attr_name])
            cmd = getattr(module, attr_name)
            self.add_command(cmd, cmd_name)  # 缓存
            return cmd
```

`list_commands` 返回所有命令名（包括尚未加载的懒加载命令）。`get_command` 是真正的懒加载入口：先在已注册的命令中查找，如果找不到，就从 `lazy_subcommands` 字典中取出模块路径，动态 `import` 它。

为什么需要懒加载？看看 `lazy_subcommands` 字典有多大——20 多个子命令（第 98-151 行）：

```python
lazy_subcommands={
    "acp":      ("qwenpaw.cli.acp_cmd",      "acp_cmd",       ".acp_cmd"),
    "app":      ("qwenpaw.cli.app_cmd",       "app_cmd",       ".app_cmd"),
    "channels": ("qwenpaw.cli.channels_cmd",  "channels_group",".channels_cmd"),
    "daemon":   ("qwenpaw.cli.daemon_cmd",    "daemon_group",  ".daemon_cmd"),
    "chats":    ("qwenpaw.cli.chats_cmd",     "chats_group",   ".chats_cmd"),
    "clean":    ("qwenpaw.cli.clean_cmd",     "clean_cmd",     ".clean_cmd"),
    "cron":     ("qwenpaw.cli.cron_cmd",      "cron_group",    ".cron_cmd"),
    "env":      ("qwenpaw.cli.env_cmd",       "env_group",     ".env_cmd"),
    "init":     ("qwenpaw.cli.init_cmd",      "init_cmd",      ".init_cmd"),
    "models":   ("qwenpaw.cli.providers_cmd", "models_group",  ".providers_cmd"),
    "skills":   ("qwenpaw.cli.skills_cmd",    "skills_group",  ".skills_cmd"),
    "doctor":   ("qwenpaw.cli.doctor_cmd",    "doctor_cmd",    ".doctor_cmd"),
    # ... 还有更多
}
```

每个值是一个三元组：`(模块路径, 属性名, 计时标签)`。如果你只是运行 `qwenpaw app`，那么 `channels_cmd`、`chats_cmd`、`doctor_cmd` 等模块永远不会被加载。这把 CLI 的冷启动时间从"导入所有模块"缩减到"只导入必要的几个"。

### 启动计时的精巧设计

`main.py` 中还有一个容易忽略但设计精巧的计时系统（第 24-49 行）：

```python
_init_timings: list[tuple[str, float]] = []
_t0_main = time.perf_counter()
_init_timings.append(("main.py loaded", 0.0))

# 每个导入都包裹在计时中
_t = time.perf_counter()
from ..config.utils import read_last_api
_record("..config.utils", time.perf_counter() - _t)

_t = time.perf_counter()
from ..__version__ import __version__
_record("..__version__", time.perf_counter() - _t)
```

但有一个问题：这些计时在 `main.py` 加载时记录，此时日志级别还没有设置（日志级别在 `app_cmd.py` 中设置）。所以这些 `logger.debug()` 调用会被默认级别过滤掉，看不到。

解决方案是 `log_init_timings()` 函数（第 52-55 行）——它把计时数据保存到 `_init_timings` 列表中，等 `app_cmd.py` 中设置了 debug 级别之后，再调用它重新输出：

```python
# app_cmd.py 第 93-96 行
if log_level in ("debug", "trace"):
    from .main import log_init_timings
    log_init_timings()
```

这种"先记录、后输出"的设计在启动场景中非常常见——你需要在日志系统初始化之前就开始测量，但只有日志系统就绪后才能看到结果。

## 探索：`qwenpaw app` 的完整启动流程

现在让我们从 `app_cmd.py` 开始，追踪完整的启动链路。

### app_cmd.py：启动的指挥中心

`app_cmd.py` 只有 112 行，但它做了启动流程中所有关键的准备工作（第 55-111 行）：

```
qwenpaw app --host 127.0.0.1 --port 8088
    │
    ├── 1. 持久化 host/port 到文件
    │      write_last_api() → 其他终端可读取
    │
    ├── 2. 设置环境变量
    │      os.environ[LOG_LEVEL_ENV] = log_level
    │      os.environ["QWENPAW_RELOAD_MODE"] = "1" (如果 --reload)
    │
    ├── 3. 初始化日志系统
    │      setup_logger(log_level)
    │
    ├── 4. 输出启动计时 (debug 模式)
    │
    ├── 5. 配置访问日志过滤器
    │      SuppressPathAccessLogFilter
    │
    └── 6. 启动 uvicorn
           uvicorn.run("qwenpaw.app._app:app", ...)
```

**持久化 host/port**（第 79-82 行）是一个贴心的设计。当你用 `qwenpaw app --port 3000` 启动后，其他终端窗口运行 `qwenpaw chats` 等命令时，CLI 会自动读取上次使用的地址和端口，不需要每次都指定。这通过 `write_last_api()` 和 `read_last_api()` 实现（config/utils.py 第 672-682 行）。

**--workers 参数的废弃处理**（第 65-76 行）也是一个有趣的历史痕迹。QwenPaw 曾经支持多 worker 模式，但后来发现单 worker 更稳定（因为 Agent 状态是进程内的，多 worker 会导致状态不一致）。废弃参数没有直接删除，而是打印警告后忽略——这是 API 兼容性的标准做法。

### uvicorn：从命令行到 ASGI

`app_cmd.py` 的最后一行（第 104-111 行）是启动的核心：

```python
uvicorn.run(
    "qwenpaw.app._app:app",
    host=host,
    port=port,
    reload=reload,
    workers=1,
    log_level=log_level,
)
```

`"qwenpaw.app._app:app"` 是一个 import 字符串——uvicorn 会 `import qwenpaw.app._app`，然后取出其中的 `app` 变量（一个 FastAPI 实例）。当 `reload=True` 时，uvicorn 会监控源文件的变化，自动重启服务。

这个 import 字符串的格式值得注意。它不是文件路径，而是 Python 模块路径。uvicorn 内部用 `importlib.import_module()` 来加载它。这和 `LazyGroup` 的懒加载机制是同一套 Python 动态导入体系。

### _app.py：两阶段启动

当 uvicorn 加载 `_app.py` 时，真正有趣的事情开始了。这个文件是整个 QwenPaw 后端的"心脏"，它的启动分为两个阶段。

**模块级代码**（第 1-206 行）在 uvicorn import 时就执行了。这部分是"快同步初始化"——创建 `DynamicMultiAgentRunner`、创建 `AgentApp`、创建 `FastAPI` 实例。注意这些操作都是纯内存操作，不涉及磁盘 I/O 或网络请求。

**lifespan 异步上下文管理器**（第 218-508 行）是启动的"第二阶段"。它使用了 FastAPI 的 lifespan 机制——在服务开始接受请求之前执行一段异步初始化代码。这个 lifespan 被精心设计为两个阶段：

```
lifespan 启动
    │
    ├── Phase 1: 快同步初始化 (< 100ms)
    │   ├── 自动注册认证用户 (auto_register_from_env)
    │   ├── 遥测数据收集 (一次性的)
    │   ├── 迁移旧版配置
    │   ├── 创建 MultiAgentManager / ProviderManager
    │   ├── 挂载到 app.state
    │   └── 输出 "Server ready in X.XXXs"
    │
    ├── yield (服务开始接受请求)
    │
    ├── Phase 2: 后台异步初始化
    │   ├── start_all_configured_agents()    ← 加载 Agent、模型、工具
    │   ├── PluginLoader.load_all_plugins()  ← 加载插件
    │   ├── 注册插件 Provider
    │   ├── 执行插件 startup hooks
    │   ├── 设置 Approval Service
    │   └── 输出 ready banner
    │
    └── shutdown (finally 块)
        ├── 执行插件 shutdown hooks
        ├── 停止本地模型服务
        └── 停止 MultiAgentManager
```

**关键设计决策**：Phase 1 结束后，服务就开始接受 HTTP 请求了。Phase 2 在后台异步执行。这意味着即使 Agent 还在加载中，HTTP 服务器已经可以响应健康检查等请求。如果此时有请求需要使用 Agent，`MultiAgentManager.get_agent()` 会通过事件等待机制阻塞到 Agent 加载完成。

这个"先响应、后加载"的设计在第 283-286 行有明确的注释：

```python
fast_elapsed = time.time() - startup_start_time
logger.info(
    f"Server ready in {fast_elapsed:.3f}s (agents loading in background)",
)
```

## 探索：QwenPaw 的其他 CLI 命令

QwenPaw 的 CLI 远不止 `app` 命令。`src/qwenpaw/cli/` 目录下有 30 个 Python 文件，构成了一个完整的运维工具集。让我们快速了解几个重要的命令。

### 初始化：`qwenpaw init`

`init_cmd.py`（586 行）是安装 QwenPaw 后第一个要运行的命令。它会交互式地引导用户完成初始配置：选择 Provider、配置 API Key、设置 Channel、启用 Skill。`--defaults` 和 `--accept-security` 选项支持非交互式初始化——Docker 构建时就使用了这个模式（Dockerfile 第 93 行）：

```dockerfile
RUN qwenpaw init --defaults --accept-security
```

### 诊断：`qwenpaw doctor`

`doctor_cmd.py`（36549 行，整个 CLI 中最大的文件）是一个全面的健康检查工具。它会检查配置文件是否有效、Provider 连接是否正常、Agent 工作区是否可写、浏览器自动化是否可用等等。当你遇到问题时，`qwenpaw doctor` 通常是排障的第一步。

### 清理：`qwenpaw clean`

`clean_cmd.py`（77 行）是最简单的命令之一。它清空 `WORKING_DIR`（默认 `~/.qwenpaw`）中的所有内容，支持 `--dry-run` 预览和 `--yes` 跳过确认。

### 进程管理：`qwenpaw shutdown`

`shutdown_cmd.py` 负责优雅地停止正在运行的 QwenPaw 进程。它通过端口查找进程 PID，然后发送 SIGTERM 信号。Windows 上有不同的实现路径。

### 命令之间的关系

这些命令构成一个完整的使用流程：

```
qwenpaw init          初始化配置
    │
qwenpaw models        查看和配置 Provider / 模型
    │
qwenpaw app           启动服务
    │
qwenpaw chats         查看聊天历史
qwenpaw doctor        诊断问题
qwenpaw daemon status 查看运行状态
    │
qwenpaw shutdown      停止服务
qwenpaw clean         清理数据（慎用）
qwenpaw update        更新到新版本
```

## 探索：Docker 部署

本地 `qwenpaw app` 适合开发和测试，但生产环境需要更强的保障：自动重启、进程管理、浏览器环境（Playwright 需要）、持久化存储。这就是 Docker 部署的用武之地。

### Dockerfile：多阶段构建

QwenPaw 的 Dockerfile（`deploy/Dockerfile`）使用了两阶段构建：

**Stage 1：构建前端**（第 3-7 行）

```dockerfile
FROM node:slim AS console-builder
WORKDIR /app
COPY console /app/console
RUN cd /app/console && npm ci --include=dev && npm run build
```

Dockerfile 中有几个精巧的设计决策：

**使用系统 Chromium 而不是 Playwright 自带的**（第 72-79 行）：

```dockerfile
RUN sed -i 's/^CHROMIUM_FLAGS=""/CHROMIUM_FLAGS="--no-sandbox"/' /usr/bin/chromium
ENV PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium

```

Docker 容器中不能使用沙箱（需要 `--no-sandbox`），而且 Playwright 默认会下载自己的 Chromium 二进制——在 Docker 中这既浪费时间又增加镜像大小。直接使用系统安装的 Chromium 是更优的选择。`QWENPAW_RUNNING_IN_CONTAINER` 环境变量让代码知道自己在容器中运行，可以跳过某些不适用于容器的逻辑。

### entrypoint.sh：环境变量替换

`entrypoint.sh` 只有 9 行，但它做了一件关键的事情：

```sh
export QWENPAW_PORT="${QWENPAW_PORT:-8088}"
envsubst '${QWENPAW_PORT}' \
  < /etc/supervisor/conf.d/supervisord.conf.template \
  > /etc/supervisor/conf.d/supervisord.conf
exec /usr/bin/supervisord -c /etc/supervisor/conf.d/supervisord.conf
```

`envsubst` 把 supervisord 配置模板中的 `${QWENPAW_PORT}` 替换为实际的环境变量值。这允许用户在运行容器时通过 `-e QWENPAW_PORT=3000` 来修改端口，而不需要重新构建镜像。`exec` 确保 supervisord 替换 entrypoint 进程，让 Docker 的信号处理正常工作。

### supervisord：多进程管理

QwenPaw 的 Docker 容器中有四个进程需要同时运行。`supervisord.conf.template` 描述了它们：

```
┌─────────────────────────────────────────────────┐
│              supervisord 管理的进程               │
│                                                 │
│  [program:xvfb]    priority=10                  │
│    Xvfb :1 -screen 0 1280x800x24               │
│    → 虚拟 X 显示服务器，给 Chromium 提供显示环境    │
│                                                 │
│  [program:dbus]    (无优先级)                    │
│    dbus-daemon --system                         │
│    → D-Bus 系统总线，xfce4 依赖它                 │
│                                                 │
│  [program:xfce4]   priority=20                  │
│    startxfce4                                   │
│    → 桌面环境，提供完整的 GUI 支持                  │
│                                                 │
│  [program:app]     priority=30                  │
│    qwenpaw app --host 0.0.0.0 --port ${PORT}   │
│    → QwenPaw 主应用                              │
│                                                 │
│  启动顺序: xvfb(10) → xfce4(20) → app(30)       │
│  dbus 与 xvfb 并行启动                            │
└─────────────────────────────────────────────────┘
```

为什么一个后端服务需要桌面环境？因为 QwenPaw 的浏览器自动化功能（Playwright）需要一个显示服务器来渲染网页。在物理机上，你的显示器就是显示服务器；在 Docker 容器中，Xvfb 模拟了一个虚拟显示器。这个设计让 QwenPaw 可以在无头服务器上执行"截图网页"、"点击按钮"等需要浏览器渲染的任务。

### docker-compose.yml：一键部署

`docker-compose.yml` 只有 26 行，但包含了生产部署的核心要素：

```yaml
version: '3.8'

volumes:
  qwenpaw-data:       # 工作目录
  qwenpaw-secrets:    # 密钥存储
  qwenpaw-backups:    # 备份数据

services:
  qwenpaw:
    image: agentscope/qwenpaw:latest
    container_name: qwenpaw
    restart: always
    ports:
      - "127.0.0.1:8088:8088"
    volumes:
      - qwenpaw-data:/app/working
      - qwenpaw-secrets:/app/working.secret
      - qwenpaw-backups:/app/working.backups
```

几个值得注意的设计决策：

**`restart: always`**：容器异常退出时自动重启。这是生产部署的基本要求。

**`"127.0.0.1:8088:8088"` 而不是 `"8088:8088"`**：只绑定到 localhost，不直接暴露到外网。如果需要外网访问，应该在前端放一个反向代理（Nginx），而不是直接暴露容器端口。这是安全的默认值。

**三个独立的 Docker 卷**：工作数据、密钥、备份分开存储。这允许你独立备份和恢复不同类型的数据。密钥卷可以设置更严格的权限。

**注释掉的认证配置**（第 18-20 行）：

```yaml
# environment:
#   - QWENPAW_AUTH_ENABLED=true
#   - QWENPAW_AUTH_USERNAME=admin
#   - QWENPAW_AUTH_PASSWORD=yourpassword
```

默认不启用认证，但提供了清晰的注释指引。生产环境中你应该取消注释并设置强密码。

## 探索：生产配置最佳实践

### 环境变量：配置的外部化

QwenPaw 使用环境变量作为生产配置的主要手段。`constant.py` 中的 `EnvVarLoader` 类（第 28-48 行）提供了类型安全的环境变量读取。它还有一个贴心的 `COPAW_` 前缀兼容机制——旧版本的环境变量名仍然有效：

```python
def _get_env(key: str, default: str = "") -> str:
    if key in os.environ:
        return os.environ[key]
    if key.startswith("QWENPAW_"):
        legacy_key = "COPAW_" + key[len("QWENPAW_"):]
        if legacy_key in os.environ:
            return os.environ[legacy_key]
    return default
```

这意味着你不需要修改已有的部署配置就能升级到新版本。向后兼容在生产环境中至关重要。

### 日志配置

生产环境的日志策略和开发环境有本质区别：

- **日志级别**：开发用 `debug`，生产用 `info` 或 `warning`。`debug` 级别会产生大量输出（包括每次 HTTP 请求的详细信息），在流量大的生产环境中会成为性能负担。
- **日志文件轮转**：`logging.py` 第 12-13 行定义了日志轮转参数——每个日志文件最大 5MB，保留 3 个备份。这防止日志文件无限增长占满磁盘。
- **访问日志过滤**：`SuppressPathAccessLogFilter`（`app_cmd.py` 第 46-49 行）可以过滤掉特定路径的访问日志。默认过滤 `/console/push-messages`——这是一个高频轮询端点，如果不过滤，日志中会全是它的访问记录。

### 认证与安全

Docker Compose 配置中注释掉的认证选项（第 18-20 行）只是安全的起点。更完整的生产部署应该考虑：

1. **启用认证**：取消 `QWENPAW_AUTH_ENABLED` 的注释，设置强用户名和密码。
2. **反向代理 + HTTPS**：在容器前面放一个 Nginx 或 Caddy，配置 TLS 证书。永远不要让 QwenPaw 直接暴露在公网上。
3. **密钥管理**：API Key 等敏感信息不要放在环境变量或配置文件中。使用 Docker Secrets 或外部的密钥管理服务。
4. **网络隔离**：QwenPaw 容器只需要暴露一个 HTTP 端口。不需要暴露 SSH、数据库等其他端口。
5. **资源限制**：在 `docker-compose.yml` 中添加 `deploy.resources` 限制 CPU 和内存使用，防止一个失控的 Agent 耗尽宿主机资源。

### 持久化策略

Docker Compose 使用了三个命名卷（第 4-9 行）：

| 卷名 | 挂载点 | 内容 | 备份频率 |
|------|--------|------|----------|
| `qwenpaw-data` | `/app/working` | config.json、聊天记录、技能 | 每日 |
| `qwenpaw-secrets` | `/app/working.secret` | API Key 等敏感数据 | 创建后静态 |
| `qwenpaw-backups` | `/app/working.backups` | 自动备份 | 由应用管理 |

命名卷的生命周期独立于容器。即使你删除容器、更新镜像、重新创建，数据卷中的数据仍然存在。这是 Docker 部署中数据持久化的标准模式。

## 工程权衡：部署设计中的选择

### 为什么用 supervisord 而不是直接运行？

QwenPaw 在 Docker 中用 supervisord 管理四个进程（xvfb、dbus、xfce4、app），而不是让 `qwenpaw app` 直接作为 PID 1 运行。这个选择基于几个理由：

1. **多进程协调**：浏览器自动化需要 Xvfb 先启动、xfce4 再启动、最后才启动应用。supervisord 的 `priority` 参数精确控制了这个顺序。
2. **自动重启**：如果某个进程崩溃（比如 Xvfb 崩溃），supervisord 会自动重启它。如果直接运行，一个辅助进程崩溃后整个容器可能需要重启。
3. **日志分离**：每个进程有独立的日志文件（`stderr_logfile` / `stdout_logfile`），方便排查问题。

代价是镜像更大（supervisord + xfce4 + Xvfb 增加了几百 MB）和配置更复杂。如果你不需要浏览器自动化功能，可以考虑使用精简版镜像。

### 为什么不用 Gunicorn？

QwenPaw 使用单 worker 的 uvicorn，而不是传统的 Gunicorn + uvicorn worker 模式。`app_cmd.py` 第 109 行硬编码了 `workers=1`，甚至 `--workers` 参数已经被标记为废弃。

这个看似"退步"的设计实际上是有意为之。QwenPaw 不是无状态的 Web 服务——它在内存中维护了大量有状态的对象：

```
app.state.multi_agent_manager   → 所有 Agent 的运行时状态
app.state.provider_manager      → Provider 连接池和配置
app.state.plugin_loader         → 插件注册表
app.state.plugin_registry       → 插件能力和 Hook
```

如果使用多 worker，每个 worker 进程都会有自己独立的一套状态，它们之间无法共享。用户在 worker A 中创建的聊天记录，在 worker B 中看不到。Agent 在 worker A 中加载的模型，worker B 还需要重新加载一次。

对于需要水平扩展的场景，正确的做法不是多 worker，而是多实例 + 外部状态存储（数据库、Redis）。但 QwenPaw 目前是一个"个人助手"定位的单机应用，单 worker 模式是合理的。

### 为什么 Click 的懒加载不用 Click 自带的机制？

Click 没有内置的子命令懒加载功能。Click 的标准做法是 `@cli.command()` 装饰器，这会在模块加载时就注册命令——也就是"急加载"。

`LazyGroup` 通过继承 `click.Group` 并重写 `get_command()` 实现了自定义的懒加载。这个模式在 Click 社区中是常见的做法（Flask 的 CLI 也使用了类似的技术）。核心思路是：把模块路径作为字符串存储，在需要时才 `__import__()` 它。

懒加载的三个元组格式 `(module_path, attr_name, label)` 也是精心设计的：`label` 用于启动计时日志，让你能看到每个命令加载花了多少时间。

### 为什么 Dockerfile 使用两个别名（qwenpaw 和 copaw）？

`pyproject.toml` 第 74-75 行注册了两个命令行入口：

```toml
qwenpaw = "qwenpaw.cli.main:cli"
copaw   = "qwenpaw.cli.main:cli"
```

`copaw` 是旧版本的项目名。保留它作为别名，让现有的脚本和工具不需要修改就能继续使用。这个"双入口"策略会在几个大版本后移除。

## 探索：定时任务系统

Agent 不只是被动等用户说话。QwenPaw 的定时任务系统让 Agent 可以按计划主动行动——每天早上推送天气、每小时做健康检查、深夜整理记忆。这套系统藏在 `src/qwenpaw/app/crons/` 目录下，基于 APScheduler 构建。

### 为什么 Agent 需要定时任务？

想象一个 7x24 小时运行的助手。如果没有定时任务，它就只是一个"你问我答"的被动工具。但有了定时任务，它可以：

- **心跳**：定期主动问候用户，保持对话活跃（类似手机上的"每日推送"）
- **记忆整理（Dream）**：在深夜用户不在线时，自动压缩和优化历史记忆
- **定时提醒**：用户说"每天早上 9 点提醒我开会"，系统就可以注册一个 cron 任务
- **后台巡检**：定期检查外部服务的状态、清理过期数据

### 架构：CronManager + CronExecutor + JsonJobRepository

```
┌─────────────────────────────────────────────┐
│                CronManager                   │
│  ┌────────────────────────────────────────┐ │
│  │      AsyncIOScheduler (APScheduler)    │ │
│  │                                        │ │
│  │   Job: _heartbeat   Job: _dream       │ │
│  │   Job: cron_job_1    Job: cron_job_2   │ │
│  └────────────────────────────────────────┘ │
│                                              │
│  CronExecutor ──→ ChannelManager.send_*()    │
│  CronExecutor ──→ Runner.stream_query()      │
└──────────────────────────┬───────────────────┘
                           │
                 ┌─────────▼─────────┐
                 │  JsonJobRepository │
                 │  (jobs.json)       │
                 └────────────────────┘
```

三个核心组件分工明确：

**CronManager**（`manager.py:34`）：调度器核心。它封装了 APScheduler 的 `AsyncIOScheduler`，负责任务的注册、更新、删除和生命周期管理。每个 Workspace 有自己独立的 CronManager 实例——Agent A 的定时任务不会影响 Agent B。

**CronExecutor**（`executor.py:14`）：任务执行器。它负责实际执行任务，支持两种任务类型：
- `text`：发送固定文本到指定渠道（比如每小时发一条"系统正常"）
- `agent`：把请求交给 Runner 处理，然后把 Agent 的回复发送到渠道（比如"查询今天天气"然后推送结果）

**JsonJobRepository**（`repo/json_repo.py:20`）：持久化仓库。把任务配置保存到 `jobs.json` 文件。写入时使用原子操作——先写 `.tmp` 临时文件，再用 `shutil.move()` 替换，避免程序崩溃导致文件损坏。

### 任务执行中的并发控制

每个任务有独立的 `asyncio.Semaphore` 控制并发。如果 `max_concurrency=1`（默认），同一个任务在执行中收到下一次触发时会被跳过（状态标记为 `skipped`），而不是排队或重复执行。不同任务之间互不影响——Job A 的慢执行不会阻塞 Job B。

每个任务还有超时保护（默认 120 秒），超过时间会被强制取消。这在 Agent 调用 LLM 可能卡住时尤其重要。

### 心跳与 Dream：两种特殊的定时任务

**心跳**不是独立的机制，而是注册到 CronManager 的特殊任务。`CronManager.start()` 启动时通过 `get_heartbeat_config()` 读取配置，调用 `_register_heartbeat()` 把心跳任务注册到 APScheduler。心跳支持间隔触发（`"30m"`、`"1h30m"`）和 Cron 表达式两种格式，还可以配置活跃时段（`active_hours`）——比如只在早 9 点到晚 10 点之间发心跳，避免深夜打扰用户。

**Dream** 是定时执行的记忆优化任务，调用 `memory.compact` 技能整理历史对话。同样注册到 APScheduler，和心跳共享同一个调度器实例。

### Cron 表达式的兼容处理

标准 cron 是 5 字段格式（分 时 日 月 周），但 QwenPaw 还兼容 3 字段和 4 字段格式，会自动补全。例如 4 字段 `30 9 * * *` 会补全为 `0 30 9 * * *`。还有一个容易踩的坑：crontab 的星期编号（0=周日）和 APScheduler 的 ISO 编号（0=周一）不同。QwenPaw 在验证时自动把数字转换为缩写名称（`0→sun, 1→mon`），避免语义错乱。

### REST API：通过 HTTP 管理定时任务

定时任务还暴露了一组 REST 端点（`api.py`），支持完整的 CRUD 操作：

| 方法 | 端点 | 用途 |
|------|------|------|
| GET | `/cron/jobs` | 列出所有任务 |
| POST | `/cron/jobs` | 创建任务 |
| PUT | `/cron/jobs/{id}` | 替换任务 |
| DELETE | `/cron/jobs/{id}` | 删除任务 |
| POST | `/cron/jobs/{id}/pause` | 暂停 |
| POST | `/cron/jobs/{id}/resume` | 恢复 |
| POST | `/cron/jobs/{id}/run` | 手动触发（fire-and-forget） |
| GET | `/cron/jobs/{id}/state` | 查看运行状态 |

这意味着你可以通过 HTTP API 动态管理定时任务，不需要重启服务。

### 定时任务在整个架构中的位置

回到前面章节讲过的 Workspace，CronManager 就是 Workspace 的一个服务组件。它在 ServiceManager 中以优先级 40 启动——在 Runner（10）和 ChannelManager（30）之后，因为定时任务的执行依赖于它们。每个 Workspace 的 CronManager 独立运行，互不干扰。
