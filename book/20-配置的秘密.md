# 第二十章 配置的秘密——改动是怎么生效的

```
浏览器 ─→ HTTP ─→ Runner ─→ Agent ─→ Prompt ─→ ReAct ─→ LLM ─→ Tool ─→ Skill
              │                                           |
       [ChannelManager]                            [BaseChannel]
              │                                           │
       [ProviderManager]                          [你的新代码在这里]
              │                                           │
              └──────────────→ CI/CD 流水线 ←─────────────┘
                                    │
                              PR Review
                                    │
                                 Merge!

         ════════════════ 卷四·纵深·开篇 ════════════════

              config.json ──→ load_config() ──→ Config 对象
                    │                              │
              agent.json ──→ load_agent_config() ──→ AgentProfileConfig
                    │                              │
              envs.json  ──→ load_envs() ────────→ os.environ
                    │                              │
              AgentConfigWatcher ──────────→ 热更新？
```

`[卷四·纵深·第一章]` -- 卷一我们追着 HTTP 请求跑完了全程。卷二我们学会了读源码的"内功心法"。卷三我们在工坊里亲手打造了 Tool、Skill、Provider 和 Channel，然后把作品提交成了 PR。

现在，我们进入卷四——纵深。

"纵深"是什么意思？前三个卷，你看到的是 QwenPaw 的"前台"：请求怎么进来、Agent 怎么响应、组件怎么扩展。但支撑这些"前台"运转的，是一套精密的"后台"基础设施：配置系统、记忆系统、任务调度、多智能体协作、插件机制、命令行工具、测试体系。这些基础设施平时藏在幕后，但它们决定了系统的稳定性、灵活性和可维护性。

卷四就是要把这些幕后机制拉到台前来，一个一个拆给你看。

第一章，我们从"配置"开始。因为配置是所有其他子系统的基石——Agent 的行为、Channel 的参数、LLM 的重试策略，全都受配置驱动。你改了 config.json 里的一行，到底经历了什么，才最终影响了 Agent 的行为？

---

## 问题：改了 config.json 的配置项，改动怎么生效的？

你在 config.json 里加了一个 Channel 的 bot_token，或者把最大迭代次数从 100 改成了 200。保存文件。然后呢？

- 需要重启服务吗？
- 还是系统会自动检测到文件变化？
- 如果系统在读配置的时候文件坏了（JSON 语法错误），会发生什么？
- 配置项的值怎么从 JSON 文件一路传递到最终使用它的代码？

这些问题看似简单，背后涉及一整套设计：配置的加载、校验、容错、热更新、以及值在系统中的传播路径。这一章我们就来拆解这套设计。

## 术语其实很简单

> **术语：热更新（Hot Reload）**
>
> 想象你家客厅的灯。如果你想把暖光灯换成冷光灯，你需要先关灯、拆旧灯泡、装新灯泡、再开灯——这是"冷更新"。但如果有一个智能灯泡，你用手机 App 改个设置，灯泡立刻变色，不用关灯也不用换灯——这就是"热更新"。在软件世界里，"热更新"指的是不重启进程就能让新的配置生效。QwenPaw 通过 `AgentConfigWatcher` 实现了部分配置的热更新（比如 Channel 参数和 Heartbeat 调度），但不是所有配置都支持。

> **术语：冷更新（Cold Reload）**
>
> 继续用灯泡的比喻。有些"灯泡"不支持远程变色——你想换颜色，就得关灯重来。软件里也一样：有些配置项（比如 LLM 的并发数限制、上下文压缩比例）在进程启动时就读取并固化了，改了配置文件也不会自动生效，必须重启进程。这就是"冷更新"——成本更高，但实现更简单。

> **术语：Context 模式**
>
> 想象你在公司上班。公司有一份"通讯录"（配置文件），记录了每个部门的电话。但每个员工需要记住的不是整本通讯录，而是"我当前正在联系的那个人"的号码。Python 的 `contextvars.ContextVar` 就是这个"随身便签"：系统从配置文件里读出值，然后写到当前执行上下文的"便签"上。不同的请求（不同的 async 协程）可以携带不同的"便签"，互不干扰。在多智能体环境中，每个 Agent 可以有自己独立的 workspace 目录，就是通过 Context 模式传递的。

## 探索：配置加载流程

### 第一站：config.json 在哪里？

QwenPaw 的配置文件路径由 `WORKING_DIR` 决定。打开 `src/qwenpaw/constant.py` 第 89-101 行：

```python
# WORKING_DIR 优先级：
# 1. QWENPAW_WORKING_DIR 环境变量 → 使用它
# 2. ~/.copaw 存在（历史安装）→ 兼容旧路径
# 3. 默认 → ~/.qwenpaw
_explicit_working_dir = _get_env("QWENPAW_WORKING_DIR")
if _explicit_working_dir:
    WORKING_DIR = Path(_explicit_working_dir).expanduser().resolve()
else:
    _legacy_copaw_dir = Path("~/.copaw").expanduser()
    if _legacy_copaw_dir.exists():
        WORKING_DIR = _legacy_copaw_dir.resolve()
    else:
        WORKING_DIR = Path("~/.qwenpaw").expanduser().resolve()
```

这段代码体现了三个设计考量：

1. **环境变量优先**：`QWENPAW_WORKING_DIR` 可以覆盖默认路径。这在容器化部署（Docker/K8s）中非常有用——你可以把配置目录挂载到任意位置。
2. **向后兼容**：如果检测到旧版安装目录 `~/.copaw`，自动沿用旧路径，不让老用户突然找不到配置。
3. **合理的默认值**：`~/.qwenpaw` 遵循 Unix 惯例（点开头目录存用户配置），开箱即用。

配置文件的完整路径就是 `WORKING_DIR / "config.json"`（`utils.py` 第 391-393 行的 `get_config_path()` 函数）。

### 第二站：load_config() 做了什么？

`load_config()` 是配置系统的入口。它定义在 `src/qwenpaw/config/utils.py` 第 491-530 行。让我们逐步拆解：

```
┌─────────────────────────────────────────────────────────────────┐
│                    load_config() 流程                            │
│                                                                 │
│  ① 文件是否存在？                                                │
│     ┌─→ 不存在 ──→ 返回 Config()（全默认值）                      │
│     │                                                           │
│     └─→ 存在 ──→ ② 读取并解析 JSON                               │
│                    │                                            │
│              ┌─────┴──────┐                                     │
│              │ _read_config_data()                              │
│              │                                                │
│              │  a. 读取原始文本                                 │
│              │  b. 尝试 json.loads()                            │
│              │     └─→ 失败？用 json_repair 自动修复              │
│              │  c. 修复也失败？备份文件 + 返回 None               │
│              └─────┬──────┘                                     │
│                    │                                            │
│              ③ 路径归一化                                        │
│              _normalize_working_dir_bound_paths()               │
│              把 ~/.copaw 时代的旧路径修正为当前 WORKING_DIR       │
│                    │                                            │
│              ④ 向后兼容处理                                      │
│              last_api_host / last_api_port → last_api           │
│                    │                                            │
│              ⑤ Pydantic 校验                                    │
│              Config.model_validate(data)                        │
│              │                                                  │
│              ├─→ 成功 ──→ 返回 Config 对象                       │
│              │                                                  │
│              └─→ 校验失败？                                      │
│                 尝试删除问题字段后重新校验                         │
│                 └─→ 再失败？备份文件 + 返回默认 Config            │
└─────────────────────────────────────────────────────────────────┘
```

这个流程里有几个精妙的设计值得细看。

**JSON 容错：json_repair**

`_read_config_data()` 函数（`utils.py` 第 456-488 行）在 JSON 解析失败后不会直接放弃，而是调用 `json_repair` 库尝试自动修复：

```python
try:
    data = json.loads(raw)
except json.JSONDecodeError:
    data = repair_json(raw, return_objects=True)
```

为什么需要这个？因为 config.json 是用户手动编辑的文件。用户可能：
- 末尾多了一个逗号
- 忘了加引号
- 混入了注释（标准 JSON 不支持注释，但很多人习惯加）
- BOM 头（Windows 记事本保存 UTF-8 时会加）

`json_repair` 能处理这些常见问题，让系统不会因为一个多余逗号就启动失败。

**Pydantic 校验 + 自动降级**

`Config.model_validate(data)` 用 Pydantic 做类型校验和转换。如果用户在 config.json 里写了 `"max_iters": "abc"`（字符串而不是整数），Pydantic 会报 `ValidationError`。

QwenPaw 的处理策略很聪明（`utils.py` 第 513-530 行）：先尝试把出错的字段从 data 中删除，然后重新校验。这样，一个坏字段不会导致整个配置文件失效——其他正确的字段仍然能正常加载。只有当删除字段后仍然校验失败，才会备份文件并回退到全默认配置。

### 第三站：Config 对象长什么样？

`Config` 类定义在 `config.py` 第 1409-1430 行。它是整个配置的根：

```python
class Config(BaseModel):
    """Root config (config.json)."""
    channels: ChannelConfig = ChannelConfig()
    mcp: MCPConfig = MCPConfig()
    tools: ToolsConfig = Field(default_factory=ToolsConfig)
    agents: AgentsConfig = Field(default_factory=AgentsConfig)
    security: SecurityConfig = Field(default_factory=SecurityConfig)
    acp: ACPConfig = Field(default_factory=ACPConfig)
    show_tool_details: bool = True
    user_timezone: str = Field(default_factory=detect_system_timezone)
    plugins: Dict[str, Dict[str, Any]] = Field(default_factory=dict)
    # ... 还有 last_api、last_dispatch 等
```

注意 `user_timezone` 的默认值不是硬编码的字符串，而是 `detect_system_timezone`——一个函数调用。这意味着如果用户没有在 config.json 里写 `user_timezone`，系统会自动检测服务器的时区。

### 第四站：两级配置结构

QwenPaw 的配置不是一个大文件包打天下，而是采用了**两级结构**：

```
~/.qwenpaw/
├── config.json            ← 全局配置（频道、MCP、安全、插件等）
└── workspaces/
    └── default/
        └── agent.json     ← Agent 级配置（运行参数、提示词、频道覆盖等）
```

`config.json` 存的是全局共享的配置，而每个 Agent 有自己的 `agent.json`，存 Agent 专属的设置。这种分离的好处是：

1. **多 Agent 互不干扰**：每个 Agent 可以有独立的 Channel 配置、不同的最大迭代次数、不同的系统提示词文件。
2. **权限分离**：全局配置修改影响所有 Agent；Agent 级配置只影响自己。
3. **向后兼容**：`config.json` 中仍然保留了 `running`、`llm_routing` 等旧字段（`config.py` 第 952-953 行），确保降级到旧版本时不丢失配置。

`load_agent_config()` 函数（`config.py` 第 1508-1553 行）负责加载 Agent 级配置。如果 `agent.json` 不存在，它会调用 `build_fallback_agent_profile_config()` 从全局配置中提取默认值，然后自动创建这个文件。

## 探索：热更新 vs 冷更新

不是所有配置改了都能立刻生效。QwenPaw 区分了热更新和冷更新两种机制。

### AgentConfigWatcher：热更新的守护者

`src/qwenpaw/app/agent_config_watcher.py` 定义了 `AgentConfigWatcher` 类。它的工作原理可以用一句话概括：每 2 秒检查一次 `agent.json` 的修改时间，如果变了就重新加载，然后对比哪些配置项发生了变化。

```
┌──────────────────────────────────────────────────────────────┐
│              AgentConfigWatcher 工作流程                       │
│                                                              │
│   每 2 秒                                                     │
│     │                                                        │
│     ▼                                                        │
│   agent.json 的 mtime 变了吗？                                │
│     │                                                        │
│     ├─→ 没变 ──→ 跳过，等下一轮                               │
│     │                                                        │
│     └─→ 变了 ──→ load_agent_config() 重新加载                │
│                   │                                          │
│             ┌─────┴──────────────┐                            │
│             │                     │                            │
│        Channel 变了？       Heartbeat 变了？                    │
│             │                     │                            │
│        逐个对比每个       通知 CronManager                     │
│        Channel 的配置    重新调度心跳任务                       │
│        （hash 对比）                                            │
│             │                     │                            │
│        变了的 Channel     更新 hash 快照                       │
│        → clone + replace                                          │
│        没变的跳过                                              │
│                                                              │
│   还会检查 memory_summary.dream_cron 是否变化                  │
│   → 通知 CronManager 重新调度记忆优化任务                      │
└──────────────────────────────────────────────────────────────┘
```

关键设计细节：

1. **mtime 检测**（第 288-297 行）：先看文件的修改时间戳，只有时间戳变了才去读文件内容。这避免了每 2 秒都做一次完整的文件读取和 JSON 解析——大多数时候配置没变，mtime 比对非常快。

2. **hash 对比**（第 147-149 行）：即使文件被"触碰"了（比如编辑器保存时改了 mtime 但内容没变），Watcher 会把配置序列化成 JSON 字符串然后算 hash。hash 没变就不做任何操作。

3. **Channel 粒度热更新**（第 191-229 行）：不是"改了一个 Channel 就重启所有 Channel"，而是逐个对比每个 Channel 的配置 dump，只 reload 真正变了的那一个。而且，如果 reload 失败，会自动回退到旧配置。

4. **心跳和记忆任务的热更新**（第 231-274 行）：Heartbeat 的调度间隔变了？Watcher 会通知 CronManager 重新调度。Memory 的 dream_cron 变了？同样会重新调度。

### 哪些配置支持热更新？

| 配置项 | 热更新？ | 机制 |
|--------|---------|------|
| Channel 参数（bot_token、proxy 等） | 是 | AgentConfigWatcher |
| Heartbeat 间隔和活跃时段 | 是 | AgentConfigWatcher → CronManager |
| Memory dream_cron | 是 | AgentConfigWatcher → CronManager |
| max_iters（最大推理迭代次数） | 否 | 每次对话启动时从配置读取 |
| LLM 重试参数（backoff、concurrent） | 否 | 进程启动时初始化 |
| 上下文压缩比例（memory_compact_ratio） | 否 | 嵌入在 Agent 运行时对象中 |
| 安全规则（tool_guard、file_guard） | 否 | 进程启动时初始化 |
| user_timezone | 否 | 写入配置后下次读取生效 |

一个有趣的发现：**"冷更新"不一定是坏事**。像 `max_iters` 这种参数，每次对话启动时都会重新读取配置（`load_config()` 每次调用都从文件读取），所以你改了配置后，新对话会使用新值——只是正在进行的对话不会中断。这种"对话级冷更新"在很多场景下其实够用了。

## 探索：Context 模式——配置值的传播路径

配置从文件加载后，怎么传递到最终使用它的代码？QwenPaw 用了两种主要模式：**直接加载**和 **Context 传递**。

### 直接加载模式

大多数代码采用"需要时就读"的模式。比如 `get_active_agent_id()`（`agent_context.py` 第 115-125 行）：

```python
def get_active_agent_id() -> str:
    try:
        config = load_config()
        return config.agents.active_agent or "default"
    except Exception:
        return "default"
```

每次调用都会重新读取 config.json。这意味着配置文件的最新值总是能被获取到——但频繁的文件 I/O 在高并发场景下可能有性能开销。

### Context 传递模式

在多智能体环境中，有些值需要随请求传播，不能每次都读文件。比如"当前请求对应哪个 Agent 的 workspace"。这个值在一个请求的处理过程中是固定的，但不同的请求可能对应不同的 Agent。

QwenPaw 使用 Python 的 `contextvars.ContextVar` 来解决这个问题。`src/qwenpaw/config/context.py` 定义了两个上下文变量：

```python
# 当前 Agent 的 workspace 目录
current_workspace_dir: ContextVar[Path | None] = ContextVar(
    "current_workspace_dir", default=None,
)

# 当前 Agent 的 recent_max_bytes 限制
current_recent_max_bytes: ContextVar[int | None] = ContextVar(
    "current_recent_max_bytes", default=None,
)
```

配合 getter/setter 函数使用：

```python
def get_current_workspace_dir() -> Path | None:
    return current_workspace_dir.get()

def set_current_workspace_dir(workspace_dir: Path | None) -> None:
    current_workspace_dir.set(workspace_dir)
```

**Context 模式为什么重要？** 因为 QwenPaw 是一个异步系统（基于 FastAPI + asyncio）。一个 Python 进程同时处理多个请求，每个请求在不同的 async 协程中执行。如果所有请求共享一个全局变量来存"当前 Agent"，那请求 A 的值会被请求 B 覆盖——数据就乱了。

`ContextVar` 是 Python 3.7 引入的异步安全的"线程局部变量"。每个 async 协程有自己独立的上下文副本，互不干扰。你可以把它想象成一个"多层抽屉"：每个请求有自己的抽屉，里面放着属于自己的配置值。

同样，`agent_context.py` 中也用 ContextVar 来追踪当前的 Agent ID 和 Session ID：

```python
_current_agent_id: ContextVar[Optional[str]] = ContextVar(
    "current_agent_id", default=None,
)
_current_session_id: ContextVar[Optional[str]] = ContextVar(
    "current_session_id", default=None,
)
```

```
│                 │                                                    │
│                 │ ⑨ 写入 ContextVar                                  │
│                 │ set_current_recent_max_bytes(50000)                │
│                 │                                                    │
│                 │ ⑩ 异步协程中通过 Context 读取                      │
│                 │ get_current_recent_max_bytes()                     │
│                 │ → 50000（每个协程独立）                             │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

这个图揭示了配置传播的三种路径：

1. **路径 ① ③ ⑤ ⑥ ⑦**：启动时加载，传给对应的 Manager 或工厂。适合"一次设置，全程使用"的配置。
2. **路径 ④**：运行时按需读取。适合"值可能频繁变化"或"只在特定场景使用"的配置。
3. **路径 ⑧ ⑨ ⑩**：Agent 级配置通过 Context 传递。适合"不同请求需要不同值"的场景。

## 探索：时区处理——一个特殊的配置项

时区配置是 QwenPaw 配置系统中一个特别有趣的部分。它涉及系统级检测、配置文件默认值、以及工具运行时覆盖三个层次。

### 自动检测系统时区

打开 `src/qwenpaw/config/timezone.py`。`detect_system_timezone()` 函数（第 21-30 行）是一个"永不出错"的函数——任何异常都被捕获，最坏情况下返回 `"UTC"`。

它的内部策略是**逐层探测**（第 33-48 行）：

```
探测顺序（Linux/macOS）：
  ① Python 运行时 → datetime.now().astimezone().tzname()
  ② 环境变量 $TZ
  ③ /etc/timezone 文件（Debian/Ubuntu）
  ④ /etc/localtime 符号链接解析
  ⑤ /etc/sysconfig/clock 文件（CentOS/RHEL）
  ⑥ timedatectl 命令（systemd）

探测顺序（Windows）：
  ① Python 运行时
  ② 环境变量 $TZ
  ③ Windows 注册表 TimeZoneKeyName
```

为什么要这么多探测方式？因为不同操作系统、不同发行版存储时区信息的方式不一样。Debian 用 `/etc/timezone`，CentOS 用 `/etc/sysconfig/clock`，systemd 用 `timedatectl`，Windows 用注册表。每种方式都可能因为权限、文件缺失等原因失败，所以需要逐个尝试。

而且有一个巧妙的判断函数 `_is_iana()`（第 16-18 行）：

```python
def _is_iana(name: Optional[str]) -> bool:
    """Return True if *name* looks like an IANA tz id."""
    return bool(name and "/" in name)
```

IANA 时区 ID（如 `Asia/Shanghai`、`America/New_York`）都包含斜杠。而系统返回的可能是缩写（如 `CST`、`EST`），这些不是 IANA 格式，会被过滤掉。这样确保返回的一定是标准的 IANA 时区 ID。

### Windows 注册表映射

对于 Windows，`timezone.py` 内置了一个映射表 `_WIN_TO_IANA`（第 72-99 行），把 Windows 的时区名称翻译成 IANA 格式：

```python
_WIN_TO_IANA = {
    "China Standard Time": "Asia/Shanghai",
    "Tokyo Standard Time": "Asia/Tokyo",
    "Eastern Standard Time": "America/New_York",
    "Pacific Standard Time": "America/Los_Angeles",
    # ... 共 20 多个映射
}
```

这个映射表是硬编码的，不是动态查询的。为什么？因为 Windows 的时区名称和 IANA 标准是两套命名体系，不硬编码就得依赖额外的库（如 `tzdata`），增加了依赖复杂度。20 多个条目已经覆盖了绝大部分使用场景。

### 时区配置的三层覆盖

```
优先级从低到高：

  ① 系统时区检测 → detect_system_timezone()
     └─→ 作为 config.json 中 user_timezone 的默认值

  ② 配置文件覆盖 → config.json 中的 "user_timezone": "Asia/Shanghai"
     └─→ 用户手动指定，覆盖系统检测值

  ③ 工具运行时覆盖 → set_user_timezone 工具
     └─→ Agent 在对话中通过工具调用修改
```

这种"系统检测 → 配置覆盖 → 运行时覆盖"的三层设计在其他配置项中也能看到（比如 Channel 配置：全局默认 → Agent 级覆盖 → 运行时参数），是 QwenPaw 配置系统的一个通用模式。

## 探索：环境变量的多层体系

除了 config.json，QwenPaw 还有另一套配置维度：环境变量。环境变量的管理分散在三个地方。

### EnvVarLoader：类型安全的环境变量读取

`constant.py` 第 28-86 行定义了 `EnvVarLoader` 类，提供了 `get_bool`、`get_int`、`get_float`、`get_str` 四个方法，带类型转换和边界检查：

```python
class EnvVarLoader:
    @staticmethod
    def get_int(env_var: str, default: int = 0,
                min_value: int | None = None,
                max_value: int | None = None) -> int:
        value = int(_get_env(env_var, str(default)))
        if min_value is not None and value < min_value:
            return min_value
        if max_value is not None and value > max_value:
            return max_value
        return value
```

注意 `_get_env()` 函数（第 12-25 行）还有一个"COPAW 兼容层"：如果 `QWENPAW_*` 环境变量没设置，会自动尝试 `COPAW_*` 前缀。这是项目从 "CoPaw" 改名为 "QwenPaw" 后的平滑迁移手段。

### envs.json：持久化的环境变量

`src/qwenpaw/envs/store.py` 管理一个独立的 `envs.json` 文件（位于 `SECRET_DIR` 下），用于持久化环境变量。它的设计考虑了安全性：

1. **加密存储**：写入时用 `encrypt()` 加密值，读取时用 `decrypt()` 解密。这意味着 `envs.json` 里存的是密文，不是明文 API Key。
2. **明文自动升级**：如果检测到旧的明文值，会自动重新加密写入（`_rewrite_encrypted`，第 183-195 行）。
3. **文件权限**：`_chmod_best_effort` 尝试把文件权限设为 `0o600`（只有文件所有者可读写）。
4. **双层同步**：`save_envs()` 不仅写入文件，还会同步到 `os.environ`（`_sync_environ`），确保子进程也能读取。

### 环境变量 vs config.json 的分工

```
┌─────────────────────────────────────────────────────────┐
│                                                         │
│   环境变量负责：                                          │
│   · API Key、Secret 等敏感信息                           │
│   · 部署环境相关（WORKING_DIR、CONTAINER、PORT）          │
│   · 跨进程共享的配置（子进程也能读到）                     │
│                                                         │
│   config.json 负责：                                     │
│   · 功能开关（enabled/disabled）                         │
│   · 行为参数（max_iters、backoff、compact_ratio）        │
│   · Channel / Provider / MCP 的连接参数                  │
│   · 用户偏好（timezone、language、show_tool_details）    │
│                                                         │
│   agent.json 负责：                                      │
│   · Agent 级的个性化覆盖                                 │
│   · 每个 Agent 独立的运行参数                             │
│   · Agent 级的 Channel 配置                              │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

简单说：环境变量管"在哪跑、用什么密钥"，config.json 管"怎么跑"，agent.json 管"这个 Agent 怎么跑"。

## 探索：频道启用与禁用的环境变量控制

一个值得一提的细节是 `get_available_channels()`（`utils.py` 第 343-371 行）。它通过环境变量 `QWENPAW_ENABLED_CHANNELS` 和 `QWENPAW_DISABLED_CHANNELS` 来控制哪些 Channel 生效：

```python
def get_available_channels() -> Tuple[str, ...]:
    # 白名单模式：只启用指定的 Channel
    raw_enabled = EnvVarLoader.get_str("QWENPAW_ENABLED_CHANNELS", "")
    if raw_enabled:
        enabled = {ch.strip() for ch in raw_enabled.split(",")}
        return tuple(k for k in all_keys if k in enabled) or all_keys

    # 黑名单模式：禁用指定的 Channel
    raw_disabled = EnvVarLoader.get_str("QWENPAW_DISABLED_CHANNELS", "")
    if raw_disabled:
        disabled = {ch.strip() for ch in raw_disabled.split(",")}
        return tuple(k for k in all_keys if k not in disabled) or all_keys

    # 默认：全部启用
    return all_keys
```

白名单优先于黑名单。这个设计在容器化部署中很实用——你可能只需要 Telegram 一个 Channel，不想启动其他十几个 Channel 的连接。一个环境变量就能搞定。

## 工程权衡：为什么配置系统设计成这样？

### 无缓存 vs 缓存

`load_config()` 每次调用都重新读取文件。没有缓存层。这意味着：

- **优点**：配置永远是"最新"的。任何文件改动都能立刻被下一次调用读到。
- **缺点**：高并发下可能有性能开销（频繁的文件 I/O 和 JSON 解析）。

为什么不用缓存？因为 QwenPaw 的配置读取频率其实不高——主要是启动时读一次，以及 API 端点被调用时读一次。对话处理的核心路径（ReAct 循环、LLM 调用、工具执行）并不频繁读配置文件。所以缓存的收益不大，反而增加了"缓存失效"的复杂度。

### 自动修复 vs 严格校验

`load_config()` 的容错策略非常宽容：JSON 语法错误能修复、坏字段能删除、实在不行回退到默认值。但 `strict_validate_config_file()`（`utils.py` 第 533-570 行）则完全相反——它用于诊断，不做任何自动修复，直接报告所有错误。

这两者并不矛盾：前者保证了"系统能启动"，后者保证了"你能发现问题"。正常运行用宽容模式，排错时用严格模式。

### Agent 级配置的独立性

每个 Agent 有自己的 `agent.json`，而不是在全局 `config.json` 里用一个巨大的嵌套结构。这意味着：

- **优点**：Agent 的配置可以独立读写，不会互相影响。添加一个新 Agent 只需要创建一个新的 workspace 目录和 agent.json。
- **缺点**：全局配置和 Agent 配置之间可能出现不一致。比如全局 `channels.telegram` 和某个 Agent 的 `channels.telegram` 可能不同。

QwenPaw 通过 `build_fallback_agent_profile_config()`（`config.py` 第 1454-1505 行）处理了这个问题：如果 Agent 的 `agent.json` 不存在，就从全局配置中继承默认值。

## 动手项目：追踪一个配置项的完整路径

让我们选一个具体的配置项，从 JSON 文件追踪到实际使用它的代码。我选择 `max_iters`——Agent 的最大推理迭代次数。

### 第一步：找到配置定义

`max_iters` 定义在 `AgentsRunningConfig` 类中（`config.py` 第 652-658 行）：

```python
class AgentsRunningConfig(BaseModel):
    max_iters: int = Field(
        default=100,
        ge=1,
        description="Maximum number of reasoning-acting iterations for ReAct agent",
    )
```

默认值 100，最小值 1。

### 第二步：找到 JSON 路径

在 `config.json` 中，路径是 `agents.running.max_iters`。或者在 `agent.json` 中，路径是 `running.max_iters`。

### 第三步：追踪加载

1. `load_config()` 读取 `config.json`，Pydantic 把 `agents.running.max_iters` 解析成 `config.agents.running.max_iters`（类型为 `int`）。
2. 或者 `load_agent_config(agent_id)` 读取 `agent.json`，得到 `agent_config.running.max_iters`。

### 第四步：追踪使用

在 ReAct Agent 中，`max_iters` 决定了"思考-行动"循环最多跑多少轮。这个值在创建 Agent 实例时从 `AgentProfileConfig.running` 中读取，作为 `for` 循环的上界。如果用户把 `max_iters` 从 100 改成 200，保存 `agent.json` 后，下一次创建的 Agent 实例就会使用 200——但正在运行的 Agent 实例的循环次数不会变。

### 第五步：思考热更新

`max_iters` 目前不在 `AgentConfigWatcher` 的监控列表中。也就是说，如果你在 Agent 运行期间改了 `max_iters`，它不会热更新。这合理吗？

从设计角度看，是合理的。`max_iters` 是一个安全上限——防止 Agent 陷入无限循环。如果在运行过程中动态改变这个值，可能导致正在执行的第 150 轮循环突然因为"上限变成了 100"而被截断。这比"需要重启才能生效"更危险。

### 练习

试着追踪另一个配置项的完整路径。建议选择：

- `channels.telegram.bot_token`：从 config.json 到 Telegram Channel 实例
- `running.context_compact.memory_compact_ratio`：从 agent.json 到上下文压缩触发逻辑
- `security.tool_guard.enabled`：从 config.json 到 ToolGuard 检查逻辑

对于每个配置项，回答三个问题：

1. 它在哪里定义默认值？
2. 它通过什么路径传递到最终使用它的代码？
3. 它支持热更新吗？为什么？
