## 概述

QwenPaw 的应用启动流程采用**两阶段启动**设计，确保服务器能在 100ms 内开始接受 HTTP 请求，而重型初始化（agents 启动、插件加载）在后台并行执行。本章解析 FastAPI 生命周期管理、中间件机制和插件系统的完整架构。

**源码路径**: `src/qwenpaw/app/_app.py`, `src/qwenpaw/plugins/`

| `@ConditionalOnClass` | `min_version` 检查 | 条件化加载 |
| `BeanFactoryPostProcessor` | `PluginLoader` | 早期 bean/插件处理 |

**关键理解**：
- Java/Spring 用 **SpringApplication.run()** 驱动启动，Python/FastAPI 用 **lifespan 异步上下文管理器**
- 两者都支持**后台异步初始化**：不让启动阻塞请求
- Java 的 SPI (`ServiceLoader`) 与 Python 的 `PluginRegistry` 思想一致：发现机制 + 中心注册表
- Spring 的 `@ConditionalOnClass` 类似 Python 的 `min_version` 检查，都是为了条件化加载
- FastAPI 中间件的"后注册先执行"对应 Spring `FilterChain` 的顺序机制

## 1. 应用启动流程 — _app.py

### 1.1 两阶段启动架构

```
┌─────────────────────────────────────────────────────────┐
│  FastAPI lifespan 异步上下文管理器                          │
│                                                          │
│  Phase 1: 同步快速设置（< 100ms）                        │
│  ├─ 认证初始化                                          │
│  ├─ 遥测收集（可选）                                     │
│  ├─ 遗留配置迁移                                         │
│  └─ 核心管理器实例化（无 I/O）                            │
│         ↓                                                 │
│  app.state 暴露管理器                                    │
│         ↓                                                 │
│  Phase 2: 后台重型初始化（_background_startup）          │
│  ├─ 启动所有配置的 agents                                 │
│  ├─ 恢复本地模型                                         │
│  ├─ 初始化插件系统                                        │
│  └─ 执行插件钩子                                         │
└─────────────────────────────────────────────────────────┘
```

### 1.2 生命周期管理 — lifespan

源码路径：`src/qwenpaw/app/_app.py:194`

```python
# src/qwenpaw/app/_app.py:194
async def lifespan(app: FastAPI):
    """FastAPI 生命周期 — 异步上下文管理器"""

    # ── Phase 1: 快速同步设置 ──
    auto_register_from_env()  # 从环境变量注册管理员

    # 遗留迁移
    migrate_legacy_workspace_to_default_agent()
    ensure_default_agent_exists()
    migrate_legacy_skills_to_skill_pool()

    # 核心管理器（无 I/O，直接实例化）
    multi_agent_manager = MultiAgentManager()
    provider_manager = ProviderManager.get_instance()
    local_model_manager = LocalModelManager.get_instance()

    # 暴露到 app.state
    app.state.multi_agent_manager = multi_agent_manager
    app.state.provider_manager = provider_manager
    app.state.local_model_manager = local_model_manager
    app.state.plugin_loader = None
    app.state.plugin_registry = None

    # ── Phase 2: 后台重型初始化 ──
    _bg_task = asyncio.create_task(_background_startup(
        multi_agent_manager,
        provider_manager,
        local_model_manager,
        app,
    ))

    try:
        yield  # 服务器运行中
    finally:
        # ── Shutdown ──
        if not _bg_task.done():
            _bg_task.cancel()
        # 执行插件 shutdown hooks
        # 关闭本地模型服务器
        # 停止所有 agents
```

### 1.3 后台启动 — _background_startup

源码路径：`src/qwenpaw/app/_app.py:230`

```python
async def _background_startup(multi_agent_manager, provider_manager, local_model_manager, app):
    """后台重型初始化 — 服务器已可接受请求后才开始"""

    # 1. 并行启动所有配置的 agents
    await multi_agent_manager.start_all_configured_agents()

    # 2. 恢复本地模型
    provider_manager.start_local_model_resume(local_model_manager)

    # 3. 初始化插件系统
    plugin_loader = PluginLoader()
    plugin_registry = await plugin_loader.load_all_plugins()

    # 4. 注册插件控制命令
    for cmd_reg in plugin_loader.registry.get_control_commands():
        register_command(cmd_reg.handler)

    # 5. 执行插件启动钩子（按 priority 排序）
    startup_hooks = plugin_loader.registry.get_startup_hooks()
    for hook in sorted(startup_hooks, key=lambda h: h.priority):
        result = hook.callback()
        if inspect.iscoroutine(result):
            await result

    # 6. 审批服务设置
    get_approval_service().set_channel_manager(
        multi_agent_manager.get_default_agent().channel_manager
    )
```

### 1.5 AuthMiddleware — 认证跳过逻辑

```python
@staticmethod
def _should_skip_auth(request: Request) -> bool:
    """以下情况跳过认证"""
    # 认证未启用 → 跳过
    if not is_auth_enabled() or not has_registered_users():
        return True

    # OPTIONS 预检请求 → 跳过
    if request.method == "OPTIONS":
        return True

    # 公开路径 → 跳过
    if path in _PUBLIC_PATHS:
        return True

    # 非 /api/ 路径 → 跳过
    if not path.startswith("/api/"):
        return True

    # localhost → 跳过
    return request.client.host in ("127.0.0.1", "::1")
```

    "/api/auth/status",
    "/api/auth/register",
    "/api/version",
    "/api/settings/language",
    "/api/plugins",
}

## 2. 插件系统

QwenPaw 的插件系统允许开发者通过标准接口扩展功能，包括注册自定义 LLM Provider、启动/关闭钩子和控制命令。插件系统在 Phase 2 后台启动阶段初始化。

### 2.1 插件加载流程（启动阶段集成）

插件加载在 `_background_startup` 中执行，与 Agent 启动并行：

```
_background_startup
    ├─► 启动所有 agents
    ├─► 恢复本地模型
    ├─► PluginLoader.load_all_plugins()      # 发现 + 加载
    │       ├─► 扫描插件目录，查找 plugin.json
    │       ├─► 动态导入 backend 模块（importlib.util）
    │       └─► 调用 plugin.register(api)
    └─► 执行 startup_hooks（按 priority 排序）
```

**关闭阶段**：取消后台任务 → 执行 shutdown_hooks → 关闭本地模型服务器 → 停止所有 agents。

### 2.2 核心架构概述

| 组件 | 职责 |
|------|------|
| `PluginManifest` | 插件清单（id、name、version、entry points、dependencies） |
| `PluginLoader` | 发现和加载机制（文件系统扫描 + 动态导入） |
| `PluginRegistry`（单例） | 中心注册表，管理 Provider、startup/shutdown hooks、control commands |
| `PluginApi` | 插件开发者接口，暴露 `register_provider`、`register_startup_hook` 等方法 |

> 详见 [18-插件系统](./18-插件系统.md)，包含 PluginManifest 完整数据模型、PluginLoader 动态导入源码解析、PluginRegistry 注册机制、PluginApi 接口详解、插件目录结构示例和生命周期流程图。

## 3. 设计思维

### 3.1 两阶段启动的意义

传统应用启动模式：所有组件初始化完成后才接受请求 → 启动时间长

QwenPaw 的两阶段启动：
- **Phase 1**（< 100ms）：只做配置加载和内存分配，不执行 I/O
- **Phase 2**（后台）：启动 agents、加载插件（I/O 密集），不阻塞请求

**类似工程模式**：Kubernetes 的 readinessProbe / livenessProbe 分离

### 3.2 中间件顺序的设计

中间件顺序影响请求处理链：

```
请求 ──► AgentContextMiddleware ──► AuthMiddleware ──► CORSMiddleware ──► 路由
                                                      │                    │
响应 ◄────────────────────────────────────────────────┘                    │
        (CORSMiddleware 最后注册，最先处理响应)                            │
```

### 3.3 插件系统的核心设计

1. **发现机制**：文件系统扫描 `plugin.json` → 零配置接入
2. **动态加载**：`importlib.util` → 不影响主程序导入
3. **中心注册表**：单例 `PluginRegistry` → 避免竞争条件
4. **生命周期钩子**：priority 排序 → 可控的执行顺序
5. **Provider 扩展**：插件可注册自定义 LLM Provider → 无需修改核心代码

> 插件系统完整设计分析见 [18-插件系统](./18-插件系统.md)。

## 4. 常见问题

### Q1: 为什么 FastAPI 需要两阶段启动？

**A**: 主要原因：
1. **用户体验**：服务器可以快速响应，无需等待所有组件初始化
2. **资源优化**：按需初始化，节省启动时间和内存
3. **可靠性**：即使后台初始化失败，HTTP 服务仍然可用

### Q2: 中间件注册顺序有什么讲究？

**A**: FastAPI 中间件遵循"后进先出"原则：
- **请求处理**：最后注册的中间件最先处理
- **响应处理**：最后注册的中间件最后处理

因此，如果需要 CORS 在所有请求上生效，CORS 中间件必须最后注册。

### Q3: 插件加载失败会影响应用启动吗？

**A**: 不会。插件加载在 Phase 2 后台进行，失败只会导致该插件不可用，不影响其他组件。

> 更多插件相关问题见 [18-插件系统](./18-插件系统.md)。

### 启动流程最佳实践

1. **Phase 1 保持轻量**：只做配置加载和内存分配，不执行 I/O 操作
2. **后台任务可取消**：`_background_startup` 使用 `asyncio.create_task`，关闭时可安全取消
3. **中间件顺序正确**：CORS 最后注册确保所有请求都经过 CORS 处理

### 8.4 如何避免破坏架构

**启动流程规则**：
- 启动阶段必须在正确的顺序中执行
- 每个阶段失败必须正确回滚
- 启动超时必须被正确处理

**生命周期规则**：
- 关闭信号必须触发优雅关闭
- 所有资源必须在关闭时释放
- 生命周期钩子必须按正确顺序执行

**插件集成规则**：
- 插件初始化必须在应用启动后、接受请求前完成
- 插件必须在关闭时正确注销
- 插件加载失败不能阻止应用启动（除非是必需插件）

**测试要求**：
- 修改启动逻辑后，必须运行 `pytest tests/app/ -v`
- 修改生命周期后，必须测试优雅关闭
- 添加新启动阶段必须验证依赖顺序
