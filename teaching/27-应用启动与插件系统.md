# 应用启动流程与插件系统

## 概述

QwenPaw 的应用启动流程采用**两阶段启动**设计，确保服务器能在 100ms 内开始接受 HTTP 请求，而重型初始化（agents 启动、插件加载）在后台并行执行。本章解析 FastAPI 生命周期管理、中间件机制和插件系统的完整架构。

**源码路径**: `src/qwenpaw/app/_app.py`, `src/qwenpaw/plugins/`

### 🐍 来自 Java 的你

| Java | Python | 说明 |
|------|--------|------|
| `SpringApplication.run()` | FastAPI `lifespan` | 应用入口与生命周期 |
| `@PostConstruct` / `ApplicationRunner` | `startup_hooks` | 启动后初始化回调 |
| `@PreDestroy` / `DisposableBean` | `shutdown_hooks` | 关闭前清理回调 |
| `Spring Boot` 事件机制 | Plugin lifecycle hooks | 生命周期事件通知 |
| `SPI` (`ServiceLoader`) | `PluginRegistry` | 服务发现与注册 |
| `spring.factories` / `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` | `plugin.json` | 插件/自动配置声明 |
| `@ConditionalOnClass` | `min_version` 检查 | 条件化加载 |
| `BeanFactoryPostProcessor` | `PluginLoader` | 早期 bean/插件处理 |
| `SmartInitializingSingleton` | `_background_startup` | 所有单例初始化完成后回调 |

**关键理解**：
- Java/Spring 用 **SpringApplication.run()** 驱动启动，Python/FastAPI 用 **lifespan 异步上下文管理器**
- 两者都支持**后台异步初始化**：不让启动阻塞请求
- Java 的 SPI (`ServiceLoader`) 与 Python 的 `PluginRegistry` 思想一致：发现机制 + 中心注册表
- Spring 的 `@ConditionalOnClass` 类似 Python 的 `min_version` 检查，都是为了条件化加载
- FastAPI 中间件的"后注册先执行"对应 Spring `FilterChain` 的顺序机制

```python
# src/qwenpaw/app/_app.py:194
async def lifespan(app: FastAPI):
    """FastAPI 生命周期 — 异步上下文管理器"""

    # ── Phase 1: 快速同步设置 ──
    auto_register_from_env()  # 从环境变量注册管理员

    # 遗留迁移
    migrate_legacy_workspace_to_default_agent()
    ensure_default_agent_exists()
    migrate_legacy_skills_to_skill_pool()

    # 核心管理器（无 I/O，直接实例化）
    multi_agent_manager = MultiAgentManager()
    provider_manager = ProviderManager.get_instance()
    local_model_manager = LocalModelManager.get_instance()

    # 暴露到 app.state
    app.state.multi_agent_manager = multi_agent_manager
    app.state.provider_manager = provider_manager
    app.state.local_model_manager = local_model_manager
    app.state.plugin_loader = None
    app.state.plugin_registry = None

    # ── Phase 2: 后台重型初始化 ──
    _bg_task = asyncio.create_task(_background_startup(
        multi_agent_manager,
        provider_manager,
        local_model_manager,
        app,
    ))

    try:
        yield  # 服务器运行中
    finally:
        # ── Shutdown ──
        if not _bg_task.done():
            _bg_task.cancel()
        # 执行插件 shutdown hooks
        # 关闭本地模型服务器
        # 停止所有 agents
```

### 1.3 后台启动 — _background_startup

源码路径：`src/qwenpaw/app/_app.py:230`

```python
async def _background_startup(multi_agent_manager, provider_manager, local_model_manager, app):
    """后台重型初始化 — 服务器已可接受请求后才开始"""

    # 1. 并行启动所有配置的 agents
    await multi_agent_manager.start_all_configured_agents()

    # 2. 恢复本地模型
    provider_manager.start_local_model_resume(local_model_manager)

    # 3. 初始化插件系统
    plugin_loader = PluginLoader()
    plugin_registry = await plugin_loader.load_all_plugins()

    # 4. 注册插件控制命令
    for cmd_reg in plugin_loader.registry.get_control_commands():
        register_command(cmd_reg.handler)

    # 5. 执行插件启动钩子（按 priority 排序）
    startup_hooks = plugin_loader.registry.get_startup_hooks()
    for hook in sorted(startup_hooks, key=lambda h: h.priority):
        result = hook.callback()
        if inspect.iscoroutine(result):
            await result

    # 6. 审批服务设置
    get_approval_service().set_channel_manager(
        multi_agent_manager.get_default_agent().channel_manager
    )
```

```python
def discover_plugins(self) -> list[tuple[PluginManifest, Path]]:
    """扫描插件目录，查找 plugin.json"""
    discovered = []
    for plugin_dir in self.plugin_dirs:
        for item in plugin_dir.iterdir():
            if not item.is_dir():
                continue
            manifest_path = item / "plugin.json"
            if manifest_path.exists():
                manifest = self._load_manifest(manifest_path)
                discovered.append((manifest, item))
    return discovered
```

### 2.4 插件加载流程 — PluginLoader.load_plugin

```python
async def load_plugin(self, manifest: PluginManifest, source_path: Path, config: dict | None = None):
    """加载单个插件"""

    # 1. 检查是否已加载
    if manifest.id in self._loaded_plugins:
        return self._loaded_plugins[manifest.id]

    # 2. 动态导入后端模块
    spec = importlib.util.spec_from_file_location(
        module_name,
        backend_entry_file,
        submodule_search_locations=[plugin_dir_str],
    )
    module = importlib.util.module_from_spec(spec)
    sys.modules[module_name] = module
    spec.loader.exec_module(module)

    # 3. 创建 PluginApi 并调用 register()
    api = PluginApi(manifest.id, config or {}, manifest_dict)
    api.set_registry(self.registry)
    result = plugin_def.register(api)
    if inspect.iscoroutine(result):
        await result

    # 4. 创建插件记录
    record = PluginRecord(
        manifest=manifest,
        source_path=source_path,
        enabled=True,
        instance=plugin_def,
    )
    self._loaded_plugins[manifest.id] = record
    return record
```

## 3. 设计思维

### 3.1 两阶段启动的意义

传统应用启动模式：所有组件初始化完成后才接受请求 → 启动时间长

QwenPaw 的两阶段启动：
- **Phase 1**（< 100ms）：只做配置加载和内存分配，不执行 I/O
- **Phase 2**（后台）：启动 agents、加载插件（I/O 密集），不阻塞请求

**类似工程模式**：Kubernetes 的 readinessProbe / livenessProbe 分离

### 3.2 中间件顺序的设计

中间件顺序影响请求处理链：

```
请求 ──► AgentContextMiddleware ──► AuthMiddleware ──► CORSMiddleware ──► 路由
                                                      │                    │
响应 ◄────────────────────────────────────────────────┘                    │
        (CORSMiddleware 最后注册，最先处理响应)                            │
```

### 3.3 插件系统的核心设计

1. **发现机制**：文件系统扫描 `plugin.json` → 零配置接入
2. **动态加载**：`importlib.util` → 不影响主程序导入
3. **中心注册表**：单例 `PluginRegistry` → 避免竞争条件
4. **生命周期钩子**：priority 排序 → 可控的执行顺序
5. **Provider 扩展**：插件可注册自定义 LLM Provider → 无需修改核心代码

## 4. 常见问题

### Q1: 为什么 FastAPI 需要两阶段启动？

**A**: 主要原因：
1. **用户体验**：服务器可以快速响应，无需等待所有组件初始化
2. **资源优化**：按需初始化，节省启动时间和内存
3. **可靠性**：即使后台初始化失败，HTTP 服务仍然可用

### Q2: 中间件注册顺序有什么讲究？

**A**: FastAPI 中间件遵循"后进先出"原则：
- **请求处理**：最后注册的中间件最先处理
- **响应处理**：最后注册的中间件最后处理

因此，如果需要 CORS 在所有请求上生效，CORS 中间件必须最后注册。

### Q3: 插件加载失败会影响应用启动吗？

**A**: 不会。插件加载在后台进行，失败只会导致该插件不可用，不影响其他组件。

### Q4: 如何调试插件问题？

**A**: 方法：
1. 检查插件 `plugin.json` 格式是否正确
2. 查看启动日志中的插件加载信息
3. 检查插件依赖是否满足
4. 尝试禁用部分插件排查冲突

### Q5: 插件可以访问哪些系统功能？

**A**: 通过 `PluginApi` 提供：
- 注册 LLM Provider
- 注册启动/关闭钩子
- 注册控制命令
- 访问运行时辅助函数

```java
    void stop();

// 插件注册中心
public class PluginRegistry {
    private final Map<String, Plugin> plugins = new ConcurrentHashMap<>();

    public void register(Plugin plugin) {
        plugins.put(plugin.getId(), plugin);

            .sorted(Comparator.comparingInt(Plugin::getPriority))
```

## 练习题

### 基础练习

1. **两阶段启动的并发设计**
   `_background_startup` 在 Phase 2 中并行调用了 `start_all_configured_agents()`、`start_local_model_resume()` 和 `load_all_plugins()`。请分析：如果这三个操作不是并行而是串行执行，会对应用启动时间产生什么影响？`asyncio.create_task` 在其中扮演了什么角色？

2. **中间件注册顺序分析**
   `AuthMiddleware` 和 `CORSMiddleware` 的注册顺序不同会影响请求处理链。请说明：后注册的中间件在请求阶段和响应阶段分别处于什么位置？如果需要认证和 CORS 都生效，应该如何调整注册顺序？

3. **PluginLoader 的动态导入机制**
   `load_plugin` 使用 `importlib.util.spec_from_file_location` 和 `spec.loader.exec_module` 实现动态导入。请说明：这种方式相比普通的 `import` 语句有什么优势？`sys.modules[module_name] = module` 这行代码的作用是什么？插件卸载时需要如何清理？

4. **PluginRegistry 单例模式**
   `PluginRegistry` 使用 `__new__` 实现单例。请说明这种实现方式与 `metaclass` 方式的区别，以及在多线程环境（FastAPI workers）下可能出现的问题。

### 进阶练习

1. **实现插件依赖解析**

   - 输入：多个插件的 `PluginManifest` 列表及其 `dependencies`

   - 已加载插件的 `shutdown_hooks` 执行
   - `MultiAgentManager` 的优雅停止
   - 本地模型服务器的关闭

3. **中间件与请求上下文的隔离**
   `AgentContextMiddleware` 在每个请求中设置 `contextvars`，而 FastAPI workers 是多进程/多线程的。请分析：
   - `contextvars` 在多 worker 环境下是否共享？
   - 如果需要在多进程间传递 `agent_id`，应该使用什么机制？
   - 当前设计在哪些场景下可能出问题？

### 实战练习

**综合项目：实现插件热重载功能**

为 QwenPaw 添加插件热重载支持，使得插件修改后无需重启服务器即可生效：

- **新增路由**：`POST /api/plugins/{plugin_id}/reload`
  - 卸载旧插件实例
  - 重新扫描插件目录
  - 重新加载插件
  - 返回加载结果和错误信息
- **文件监控**：使用 `watchdog` 或 `inotify` 监控 `plugins/` 目录
  - 检测到 `plugin.json` 变更时自动触发重载
  - 检测到 `plugin.py` 变更时自动触发重载
- **状态保持**：重载期间保持已有会话不中断
  - 已在运行的 Agent 不受影响
  - 新请求使用新插件

**提示**：
- 参考 `PluginLoader.load_plugin` 的实现设计卸载逻辑
- 插件的 `shutdown_hooks` 应该在卸载前执行
- 需要处理 `PluginRegistry` 中的旧注册信息清理
