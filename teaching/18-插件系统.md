## 概述

QwenPaw 支持插件扩展机制，允许开发者通过插件添加新功能、集成外部服务或自定义行为。本文档介绍插件系统的架构、使用方法和开发指南。

## 2. 使用插件

### 2.1 安装插件

```bash
# 从目录安装
qwenpaw plugin install ./my_plugin

# 从 URL 安装
qwenpaw plugin install --from-url https://example.com/plugin.zip

# 从市场安装
qwenpaw plugin install my_plugin --from-market
```

### 2.2 管理插件

```bash
# 列出已安装插件
qwenpaw plugin list

# 启用/禁用插件
qwenpaw plugin enable my_plugin
qwenpaw plugin disable my_plugin

# 更新插件
qwenpaw plugin update my_plugin

# 卸载插件
qwenpaw plugin uninstall my_plugin
```

### 2.3 查看插件信息

```bash
# 查看插件详情
qwenpaw plugin info my_plugin

# 查看插件配置
qwenpaw plugin config my_plugin
```

## 3. 开发插件

### 3.1 创建插件结构

```bash
mkdir -p ~/.qwenpaw/plugins/my_plugin
cd ~/.qwenpaw/plugins/my_plugin
```

### 3.2 插件配置文件

`config.json`:

```json
{
  "name": "my_plugin",
  "version": "1.0.0",
  "description": "我的自定义插件",
  "author": "Your Name",
  "entry_point": "my_plugin:main",
  "dependencies": [],
  "permissions": ["network", "filesystem"]
}
```

### 3.3 插件入口文件

`__init__.py`:

```python
"""我的自定义插件"""

from qwenpaw.plugins import Plugin, PluginManager

class MyPlugin(Plugin):
    """插件类"""
    
    name = "my_plugin"
    version = "1.0.0"
    
    def on_load(self) -> None:
        """插件加载时调用"""
        print(f"插件 {self.name} 已加载")
    
    def on_unload(self) -> None:
        """插件卸载时调用"""
        print(f"插件 {self.name} 已卸载")
    
    def on_agent_start(self, agent_id: str) -> None:
        """智能体启动时调用"""
        pass
    
    def on_agent_message(self, agent_id: str, message: dict) -> None:
        """智能体消息处理时调用"""
        pass

def main():
    """插件入口函数"""
    return MyPlugin()
```

## 4. 插件功能

插件可以注册自定义工具：

```python

            my_custom_tool,
            name="my_tool",
```

| `on_agent_start` | 智能体启动 | 准备环境 |
| `on_agent_stop` | 智能体停止 | 清理状态 |

### 8.10 PluginLoader 核心实现

**源码路径**: `src/qwenpaw/plugins/loader.py`

**PluginLoader 类** (第30-84行):

```python
class PluginLoader:
    """插件加载器，负责插件的发现和加载"""

    def __init__(self, plugin_dirs: List[Path]):
        self.plugin_dirs = [Path(d) for d in plugin_dirs]
        self.registry = PluginRegistry()
        self._loaded_plugins: Dict[str, PluginRecord] = {}

    def discover_plugins(self) -> List[Tuple[PluginManifest, Path]]:
        """发现插件目录中的所有插件"""
        discovered = []
        for plugin_dir in self.plugin_dirs:
            if not plugin_dir.exists():
                continue
            for item in plugin_dir.iterdir():
                if not item.is_dir():
                    continue
                manifest_path = item / "plugin.json"
                if not manifest_path.exists():
                    continue
                manifest = self._load_manifest(manifest_path)
                discovered.append((manifest, item))
        return discovered
```

**插件加载流程** (`load_plugin` 方法, 第87-177行):

```
discover_plugins() 扫描插件目录
         │
         ▼
_load_manifest(plugin.json) 解析清单
         │
         ▼
importlib.util.spec_from_file_location() 创建模块规范
         │
         ▼
sys.modules[module_name] = module 缓存模块
         │
         ▼
spec.loader.exec_module(module) 执行模块代码
         │
         ▼
检查 module.plugin 对象
         │
         ▼
创建 PluginApi(api) 并调用 plugin.register(api)
         │
         ▼
返回 PluginRecord 实例
```

**关键设计**:
- `submodule_search_locations=[plugin_dir_str]` 使插件内相对导入可用
- 支持 async 和 sync 的 `register()` 方法
- 已加载插件会被缓存到 `_loaded_plugins` 字典

## 10. 最佳实践

### 10.1 开发建议

1. **最小化依赖**: 只引入必要的第三方库
2. **版本兼容性**: 声明最低 QwenPaw 版本要求
3. **错误处理**: 插件应捕获并处理所有异常
4. **资源清理**: 在 `on_unload` 中正确释放资源

### 10.2 安全建议

1. **权限最小化**: 只申请必要的权限
2. **输入验证**: 验证所有用户输入
3. **安全传输**: 使用 HTTPS 而非 HTTP
4. **敏感数据**: 不要在插件中硬编码 API Key

### 10.3 性能建议

1. **按需加载**: 懒加载非必要组件
2. **缓存结果**: 重复操作使用缓存
3. **后台处理**: 耗时任务异步执行
4. **限制资源**: 设置合理的超时和重试限制

3. **PluginApi 接口**: 开发者接口，提供 register_provider、register_startup_hook 等方法
4. **生命周期钩子**: on_load → on_agent_start → on_agent_message → on_agent_stop → on_unload
5. **前端插件加载**: Blob URL 包装 + dynamic import() 实现同源执行

### 关键配置

| 配置项 | 说明 |
|--------|------|
| `~/.qwenpaw/plugins/<plugin>/config.json` | 插件配置 |
| `~/.qwenpaw/plugins/<plugin>/mcp.json` | MCP 服务器配置 |
| `config.json` plugins | 全局插件启用状态 |

## 13. 如果你来自 Java...

如果你有 Java 开发背景，理解 QwenPaw 的插件系统会很容易，因为许多核心概念是相通的。

### 13.1 Java SPI vs QwenPaw 插件机制

| 概念 | Java SPI | QwenPaw 插件 |
|------|----------|--------------|
| 服务发现 | `META-INF/services/` 配置文件 | `plugin.json` 清单文件 |
| 加载器 | `ServiceLoader.load()` | `PluginLoader` 类 |
| 注册机制 | `ServiceLoader` 迭代发现 | `PluginRegistry` 单例注册 |
| 扩展点 | 接口/抽象类 | `Plugin` 基类 |
| 实现方式 | 反射实例化 | 直接导入模块 |

### 13.2 Java SPI 代码对比

**Java SPI 示例**：

```java
// 1. 定义服务接口
public interface Plugin {
    void init();
}

// 2. 实现服务 (META-INF/services/com.example.Plugin)
public class MyPlugin implements Plugin {
    @Override
    public void init() {
        System.out.println("Plugin initialized");
    }
}

// 3. 加载服务
ServiceLoader<Plugin> loader = ServiceLoader.load(Plugin.class);
for (Plugin plugin : loader) {
    plugin.init();
}
```

**QwenPaw 等效实现**：

```python
# __init__.py
class MyPlugin:
    async def register(self, api):
        # 注册到全局注册表
        api.register_provider(
            provider_id="my-plugin",
            provider_class=MyProvider,
            label="My Plugin"
        )

plugin = MyPlugin()
```

### 13.3 关键差异

| 差异点 | Java SPI | QwenPaw |
|--------|----------|---------|
| 模块边界 | JAR 包级别 | 目录级别 |
| 生命周期 | 被动发现，无生命周期 | 主动加载，有完整生命周期 |
| 依赖注入 | 无内置 DI | `PluginApi` 主动注入 |
| 前端支持 | 仅后端 | 前后端一体化 |
| 配置格式 | properties | JSON |

## 14. 行业标准：MCP 协议

### 14.1 什么是 MCP

**MCP (Model Context Protocol)** 是 Anthropic 于 2024 年 11 月推出的开放标准，旨在为 LLM 与外部数据源、工具和服务之间提供**标准化、安全的双向通信接口**。

MCP 被业界称为 "AI 世界的 USB-C 接口"——就像 USB-C 让各种设备可以即插即用，MCP 让各种 AI 应用可以无缝连接外部工具和数据源。

### 14.2 MCP 核心概念

```
┌─────────────┐         ┌─────────────┐
│   Host      │◄───────►│   Client    │
│  (AI App)   │  MCP    │  (LLM)      │
└─────────────┘         └─────────────┘
       │
       ▼
┌─────────────┐
│   Server    │
│ (Data/Tools)│
└─────────────┘
```

| 组件 | 角色 |
|------|------|
| **Host** | AI 应用主程序 (如 QwenPaw、Claude Desktop) |
| **Client** | LLM 模型连接器 |
| **Server** | 外部工具/数据源 (文件系统、API、数据库等) |

### 14.3 MCP 在 QwenPaw 中的应用

QwenPaw 插件可以包含 MCP 服务器配置：

```json
// mcp.json
{
  "mcp_servers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/path/to/dir"]
    },
    "database": {
      "command": "python",
      "args": ["/path/to/mcp_database_server.py"]
    }
  }
}
```

### 14.4 MCP vs 传统插件架构

| 特性 | MCP | 传统插件 |
|------|-----|----------|
| 标准化程度 | 跨框架统一协议 | 框架私有实现 |
| 工具发现 | 自动发现 | 手动配置 |
| 类型安全 | 强类型 Schema | 动态类型 |
| 生态 | 快速增长的社区 | 框架绑定 |

### 14.5 MCP 资源类型

MCP 定义了三种主要资源类型：

| 类型 | 说明 | 示例 |
|------|------|------|
| **Tools** | AI 可调用的函数 | `filesystem.read_file`, `database.query` |
| **Resources** | AI 可读取的数据 | 文件内容、API 响应 |
| **Prompts** | 预定义提示模板 | `code_review`, `documentation` |

## 15. 知识检查

### 检查 1

PluginLoader 在加载插件时，如何发现并验证一个目录是合法的插件？`plugin.json` 在这个流程中扮演什么角色？

<details>
<summary>参考答案</summary>

PluginLoader 通过 `discover_plugins()` 方法遍历配置的插件目录，对每个子目录检查是否存在 `plugin.json` 文件。存在则解析为 PluginManifest（包含 id、name、version、entry 等字段），不存在则跳过。`plugin.json` 是插件的唯一标识文件，相当于 Java SPI 中 `META-INF/services/` 配置文件的角色，声明了插件的元数据和入口点。

</details>

### 检查 2

PluginApi 提供了哪些注册方法？请说明 `register_provider` 和 `register_startup_hook` 的区别和各自的适用场景。

<details>
<summary>参考答案</summary>

PluginApi 主要提供四个注册方法：`register_provider`（注册自定义 LLM Provider）、`register_startup_hook`（注册启动钩子）、`register_shutdown_hook`（注册关闭钩子）、`register_control_command`（注册控制命令）。`register_provider` 用于扩展模型后端，让智能体可以使用自定义的 LLM 服务，适合接入私有模型。`register_startup_hook` 用于在应用启动时执行初始化逻辑（如建立数据库连接、预热缓存），适合需要在运行时准备资源的场景。两者核心区别：Provider 是长期驻留的服务提供者，而 Hook 是一次性执行的回调。

</details>

### 检查 3

MCP 协议与传统插件架构相比有什么根本性差异？为什么说 MCP 是"AI 世界的 USB-C 接口"？

<details>
<summary>参考答案</summary>

根本差异在于标准化程度：传统插件架构是框架私有的，每个框架定义自己的扩展接口（如 QwenPaw 的 PluginApi、VS Code 的 Extension API），插件只能绑定单一框架。MCP 是跨框架的开放协议，定义了统一的 Host-Client-Server 通信标准，同一个 MCP Server 可以被 QwenPaw、Claude Desktop、Cursor 等任何支持 MCP 的应用使用。"USB-C 接口"的比喻强调的是即插即用的标准化 -- 开发一次 MCP Server，所有支持 MCP 的 AI 应用都能直接使用，无需针对每个框架单独适配。

</details>
