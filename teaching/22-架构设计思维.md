## 一、多智能体管理 — Workspace 隔离模式

### 问题背景

当一个系统需要同时运行多个 AI Agent 时，核心挑战是：**如何让每个 Agent 独立运行而不互相干扰？**

干扰可能来自：
- 共享状态（如全局变量、文件系统路径）
- 并发竞争（多个 Agent 同时访问同一资源）
- 配置耦合（一个 Agent 的配置影响另一个）

### 方案选择

QwenPaw 采用 **Workspace 隔离模式**：每个 Agent 拥有完全独立的运行时组件。

```
MultiAgentManager
    └── Workspace (per agent)
        ├── AgentRunner
        ├── ChannelManager
        ├── TaskTracker
        ├── MemoryManager
        ├── CronManager
        └── MCPClientManager
```

### 源码解析

**动态路由层**：`src/qwenpaw/app/_app.py:70-125`

```python
class DynamicMultiAgentRunner:
    """Runner wrapper that dynamically routes to the correct workspace runner.

    This allows AgentApp to work with multiple agents by inspecting
    the X-Agent-Id header on each request.
    """

    async def _get_workspace(self, request):
        from .agent_context import get_current_agent_id
        agent_id = get_current_agent_id()  # 从请求上下文获取 agent_id
        workspace = await self._multi_agent_manager.get_agent(agent_id)
        return workspace
```

**Workspace 定义**：`src/qwenpaw/app/workspace/workspace.py:49-89`

```python
class Workspace:
    """Single agent workspace with complete runtime components.

    Each Workspace is an independent agent instance with its own:
    - Runner: Processes agent requests
    - ChannelManager: Manages communication channels
    - BaseMemoryManager: Manages conversation memory
    - MCPClientManager: Manages MCP tool clients
    - CronManager: Manages scheduled tasks
    """

    def __init__(self, agent_id: str, workspace_dir: str):
        self.agent_id = agent_id
        self.workspace_dir = Path(workspace_dir).expanduser()
        self._service_manager = ServiceManager(self)
        self._task_tracker = TaskTracker()
        self._register_services()
```

**关键设计**：Workspace 使用 `ServiceManager` 统一管理所有服务组件，每个服务通过 `ServiceDescriptor` 声明式注册。

### 权衡取舍

| 优点 | 缺点 |
|------|------|
| 完全隔离，无状态共享 | 内存占用较高（每个 Agent 独立组件） |
| 支持热重载（不影响其他 Agent） | 服务间通信需要通过 ChannelManager |
| 并行启动优化 | 配置复杂度增加 |

### 可改进方向

- **资源池化**：对于资源受限场景，可考虑池化 MemoryManager 等重型服务
- **轻量级隔离**：使用 `asyncio.Task` 而非完整 Workspace 处理简单任务

## 二、工具守卫 — Mixin 继承模式

### 问题背景

AI Agent 的工具调用面临安全风险：用户可能通过提示词注入（Prompt Injection）让 Agent 执行恶意操作。如何在**不修改核心 Agent 代码**的情况下，为工具调用添加安全检查？

核心挑战：
- 安全检查逻辑与 Agent 核心逻辑应该**解耦**
- 每次工具调用**必须**经过检查（不能依赖 Agent 主动调用）
- Mixin 类需要**覆盖**现有方法而非新增方法

### 方案选择

QwenPaw 采用 **Mixin 继承模式**，利用 Python 的 MRO（方法解析顺序）将安全检查注入到工具调用流程。

```python
class QwenPawAgent(ToolGuardMixin, ReActAgent):
    """MRO: QwenPawAgent → ToolGuardMixin → ReActAgent"""
```

### 源码解析

**Mixin 定义**：`src/qwenpaw/agents/tool_guard_mixin.py:68-74`

```python
class ToolGuardMixin:
    """Mixin that adds tool-guard interception to a ReActAgent.

    At runtime this class is always combined with
    ``agentscope.agent.ReActAgent`` via MRO, so ``super()._acting``
    and ``super()._reasoning`` resolve to the concrete agent methods.
    """
```

**关键方法覆盖**：`src/qwenpaw/agents/tool_guard_mixin.py:291-344`

```python
async def _acting(self, tool_call) -> dict | None:
    """Intercept sensitive tool calls before execution.

    1. If tool is in *denied_tools*, auto-deny unconditionally.
    2. If tool is in the guarded scope, check for a one-shot
       pre-approval, then run all guardians.
    3. For non-guarded tools, run only ``always_run`` guardians
       (e.g. sensitive file path checks).
    4. If findings exist, enter the approval flow.
    5. Otherwise, delegate to ``super()._acting``.
    """
    self._ensure_tool_guard()

    action: _GuardAction | None = None
    async with self._tool_guard_lock:  # 锁保护决策过程
        try:
            action = await self._decide_guard_action(tool_call)
        except Exception as exc:
            logger.warning(...)

    if action is not None:
        return await self._execute_guard_action(action, tool_call)

    # 关键：最终委托给原始的 _acting
    result = await super()._acting(tool_call)
    return result
```

**并行安全**：`asyncio.Lock` 确保多个并发工具调用不会竞争 Mixin 状态：

```python
async with self._tool_guard_lock:
    action = await self._decide_guard_action(tool_call)
```

实际工具执行在锁外进行，保证真正的并行。

### Mixin vs 装饰器 vs 中间件

| 方案 | 侵入性 | 覆盖粒度 | 适用场景 |
|------|--------|----------|----------|
| Mixin | 中 | 方法级 | 需要覆盖核心方法（如 `_acting`） |
| 装饰器 | 低 | 函数级 | 单一功能增强 |
| 中间件 | 低 | 请求级 | HTTP/消息拦截 |

### 权衡取舍

| 优点 | 缺点 |
|------|------|
| 无需修改 ReActAgent 源码 | MRO 顺序敏感（Mixin 顺序很重要） |
| 方法级覆盖，确保检查必执行 | 调试时需要理解 MRO |
| 保持核心逻辑纯净 | Mixin 之间不能有循环依赖 |

### 可改进方向

- 使用 `__getattr__` 委托实现更细粒度的拦截
- 考虑使用 Protocol + 组合替代继承

## 三、配置系统 — 三层分离架构

### 问题背景

配置来源多样：
- **环境变量**：容器化、CI/CD 部署
- **JSON 配置文件**：团队共享、应用级配置
- **Agent 配置**：每个 Agent 的独立设置

如何设计一个既**统一**又**灵活**的配置系统？

### 方案选择

QwenPaw 采用**三层分离**架构，每层有明确职责：

```
环境变量 (EnvVarLoader)
    ↓ 基础设施级别
config.json (load_config)
    ↓ 应用级配置
agent.json (per-agent)
    ↓ Agent 级配置
运行时覆盖
```

### 源码解析

**环境变量加载**：`src/qwenpaw/constant.py` 中的 `EnvVarLoader`

```python

    @classmethod
    def get_str(cls, key: str) -> str:
        """从环境变量获取字符串"""
```

### 分层职责表

| 层级 | 来源 | 用途 | 示例 |
|------|------|------|------|
| 环境变量 | `os.environ` | 基础设施、敏感信息 | `QWENPAW_SECRET_DIR` |
| config.json | 文件 | 应用全局配置 | `log_level`, `cors_origins` |
| agent.json | 文件 | 单个 Agent 配置 | `max_iters`, `tools` |
| 运行时 | 代码 | 动态覆盖 | `request_context` |

### 权衡取舍

| 优点 | 缺点 |
|------|------|
| 职责清晰，边界明确 | 需要文档说明各层优先级 |
| 支持热重载 | 配置项可能重复 |
| 环境适配灵活 | 调试时需要追踪配置来源 |

## 四、消息渠道 — 插件化架构

### 问题背景

系统需要接入多种即时通讯平台（Discord、Telegram、飞书等），每个平台的消息格式和处理逻辑各异。如何设计一个**统一**但**可扩展**的渠道系统？

### 方案选择

QwenPaw 采用**插件化架构**：
- 统一的 `BaseChannel` 抽象类
- `ChannelRegistry` 管理所有渠道
- 支持内置渠道和自定义渠道

### 源码解析

**抽象基类**：`src/qwenpaw/app/channels/base.py:78-130`

```python
class BaseChannel(ABC):
    """Base for all channels. Queue lives in ChannelManager; channel defines
    how to consume via consume_one().
    """

    channel: ChannelType

    async def consume_one(self, payload: Any) -> None:
        """Process one payload from the manager-owned queue."""
        if self._debounce_seconds > 0 and self._is_native_payload(payload):
            # 时间防抖逻辑...
            return
        await self._consume_one_request(payload)

    async def send(
        self,
        to_handle: str,
        text: str,
        meta: Optional[Dict[str, Any]] = None,
    ) -> None:
        """Subclass implements: send one text"""
        raise NotImplementedError
```

**渠道注册表**：`src/qwenpaw/app/channels/registry.py:190-194`

```python
def get_channel_registry() -> dict[str, type[BaseChannel]]:
    """Built-in channel classes + custom channels from custom_channels/."""
```

**自定义渠道发现**：`src/qwenpaw/app/channels/registry.py:97-129`

```python
def _discover_custom_channels() -> dict[str, type[BaseChannel]]:
    """Load channel classes from CUSTOM_CHANNELS_DIR."""
    if not CUSTOM_CHANNELS_DIR.is_dir():
        return out

    for path in sorted(CUSTOM_CHANNELS_DIR.iterdir()):
        if path.suffix == ".py" and path.stem != "__init__":
            name = path.stem
            mod = importlib.import_module(name)
            for obj in vars(mod).values():
                if isinstance(obj, type) and issubclass(obj, BaseChannel):
                    key = getattr(obj, "channel", None)
                    if key:
                        out[key] = obj
    return out
```

### 插件化设计模式

```
BaseChannel (抽象基类)
    ├── IMessageChannel
    ├── DiscordChannel
    ├── TelegramChannel
    └── FeishuChannel
        └── CustomChannel (用户实现)
```

新渠道只需：
1. 继承 `BaseChannel`
2. 实现 `send()` 和 `build_agent_request_from_native()`
3. 放置到 `custom_channels/` 目录

### 权衡取舍

| 优点 | 缺点 |
|------|------|
| 统一接口，多渠道一致 | 抽象可能限制特殊功能 |
| 用户可自定义渠道 | 需要维护渠道兼容性 |
| 动态发现，热插拔 | 调试时需要理解渠道协议 |

## 五、异步优先 — asyncio 原生设计

### 问题背景

AI Agent 系统涉及大量 I/O 操作：
- LLM API 调用（网络请求）
- 文件系统操作
- 外部服务集成（数据库、消息队列）

这些操作如果用同步方式处理，会严重限制系统吞吐量。

### 方案选择

QwenPaw 采用 **asyncio 原生**设计，所有 I/O 操作异步化。

### 关键实践

**1. `async with` 替代 try-finally 资源管理**

```python
# src/qwenpaw/app/_app.py:126-152
async for item in runner.stream_query(request, *args, **kwargs):
    yield item
finally:
    # 始终清理
    if workspace is not None and run_key is not None:
        await workspace.task_tracker.unregister_external_task(run_key)
```

**2. `asyncio.Lock` 替代 `threading.Lock`**

```python
# src/qwenpaw/agents/tool_guard_mixin.py:315
async with self._tool_guard_lock:
    action = await self._decide_guard_action(tool_call)
```

**3. `asyncio.gather` 并发执行**

```python
# src/qwenpaw/app/multi_agent_manager.py:502-505
results = await asyncio.gather(
    *[start_single_agent(agent_id) for agent_id in agent_ids],
    return_exceptions=False,
)
```

**4. 异步生成器流式响应（SSE）**

```python
# src/qwenpaw/app/workspace/workspace.py:463-477
async def _stream_with_tracker(
    self,
    payload: Any,
) -> AsyncGenerator[str, None]:
    """Stream events through TaskTracker for task tracking."""
    async for event in self._process(request):
        yield f"data: {data}\n\n"
```

### 异步 vs 多线程

| 维度 | asyncio | 多线程 |
|------|---------|--------|
| 适用场景 | I/O 密集 | CPU 密集 |
| 上下文切换 | 协程切换（轻量） | 线程切换（重量） |
| 并发模型 | 单线程事件循环 | 多线程并行 |
| 调试难度 | 较高（异步堆栈） | 较低 |

### 权衡取舍

| 优点 | 缺点 |
|------|------|
| 高并发，低资源 | 调试困难（异步堆栈） |
| 无锁竞争 | 不能利用多核（单线程） |
| 适合 I/O 密集型 | CPU 密集型需要额外处理 |

## 六、安全 — 纵深防御

### 问题背景

AI Agent 的工具调用面临多层安全威胁：
- **路径遍历**：访问不该访问的文件
- **命令注入**：通过参数执行恶意 shell 命令
- **提示词注入**：用户输入包含恶意指令

单一安全措施不足以防御所有威胁。

### 方案选择

QwenPaw 采用**纵深防御**策略，三层防线互补：

```
┌─────────────────────────────────────┐
│ Layer 1: 文件路径守卫 (FilePathGuardian) │
│ 检查文件路径是否在允许范围内           │
├─────────────────────────────────────┤
│ Layer 2: 正则规则守卫 (RuleBasedGuardian) │
│ 检查工具参数是否符合安全规则          │
├─────────────────────────────────────┤
│ Layer 3: Shell 混淆检测 (ShellEvasionGuardian) │
│ 检测 shell 命令注入特征              │
└─────────────────────────────────────┘
```

### 源码解析

**三层守卫**：`src/qwenpaw/security/tool_guard/guardians/`

```python
# file_guardian.py - 路径检查
class FilePathGuardian:
    async def check(self, tool_name: str, tool_input: dict) -> GuardResult:
        if "path" in tool_input:
            path = Path(tool_input["path"])
            if not self._is_in_allowed_dir(path):
                return GuardResult(findings=[...])

# rule_guardian.py - 正则规则
class RuleBasedGuardian:
    async def check(self, tool_name: str, tool_input: dict) -> GuardResult:
        patterns = self._get_patterns_for_tool(tool_name)
        for key, value in tool_input.items():
            if self._matches_dangerous_pattern(value, patterns):
                return GuardResult(findings=[...])

# shell_evasion_guardian.py - 注入检测
class ShellEvasionGuardian:
    async def check(self, tool_name: str, tool_input: dict) -> GuardResult:
        if "command" in tool_input:
            cmd = tool_input["command"]
            if self._detect_injection(cmd):
                return GuardResult(findings=[...])
```

**守卫引擎**：`src/qwenpaw/security/tool_guard/engine.py`

```python
class ToolGuardEngine:
    def guard(
        self,
        tool_name: str,
        tool_input: dict,
        only_always_run: bool = False,
    ) -> GuardResult | None:
        """运行所有匹配的守卫，返回检测结果。"""
        results = []
        for guardian in self._get_matching_guardians(tool_name, only_always_run):
            result = await guardian.check(tool_name, tool_input)
            if result:
                results.append(result)
        return GuardResult(findings=results) if results else None
```

### 审批流程

当检测到风险时，系统进入审批流程：

```
Tool Call → Guard Check → [有风险] → Pending Approval
                              ↓
                         User Approves → Execute Tool
```

### 权衡取舍

| 优点 | 缺点 |
|------|------|
| 多层防御，单层失效不崩溃 | 性能开销（多次检查） |
| 灵活配置（按工具配置守卫） | 配置复杂度 |
| 可扩展（新增守卫类型） | 误报可能影响体验 |

## 七、密钥管理 — 分层存储 + 认证加密

### 问题背景

系统需要存储多种敏感信息：
- LLM API Keys
- 数据库密码
- Webhook 回调密钥

如何安全存储且在多种环境下工作？

### 方案选择

QwenPaw 采用**分层存储 + AEAD 加密**：

```
┌─────────────────────────────────────┐
│ Layer 1: OS Keychain (主密钥)        │
│ macOS Keychain / Linux keyring      │
├─────────────────────────────────────┤
│ Layer 2: 文件存储 (降级方案)         │
│ SECRET_DIR/.master_key (mode 0600)  │
├─────────────────────────────────────┤
│ Layer 3: 内存缓存 (快速路径)         │
│ _cached_master_key                  │
└─────────────────────────────────────┘
```

### 源码解析

**密钥获取（双重检查锁）**：`src/qwenpaw/security/secret_store.py:154-188`

```python
def _get_master_key() -> bytes:
    """Return the 32-byte master key, creating one if it does not exist.

    Uses double-checked locking to guarantee that only one thread ever
    generates or loads the key, even when multiple FastAPI worker
    threads start up concurrently.
    """
    global _cached_master_key
    if _cached_master_key is not None:  # 快速路径
        return _cached_master_key

    with _master_key_lock:  # 锁保护
        if _cached_master_key is not None:  # 再次检查
            return _cached_master_key

        key_hex = _try_keyring_get()  # 尝试 Keychain
        if not key_hex:
            key_hex = _read_key_file()  # 降级到文件
        if not key_hex:
            key_hex = _generate_master_key()  # 生成新密钥

        _cached_master_key = bytes.fromhex(key_hex)
        return _cached_master_key
```

**优雅降级**：`src/qwenpaw/security/secret_store.py:49-68`

```python
def _should_skip_keyring() -> bool:
    """Return ``True`` when the OS keyring is unlikely to be available.

    Covers Docker containers, headless Linux servers, and CI
    environments where attempting keyring access could hang on D-Bus.
    """
    if EnvVarLoader.get_bool("QWENPAW_RUNNING_IN_CONTAINER"):
        return True

    if sys.platform == "linux" and not (
        os.environ.get("DISPLAY") or os.environ.get("WAYLAND_DISPLAY")
    ):
        return True

    if os.environ.get("CI", "").lower() in ("true", "1"):
        return True

    return False
```

```python
    return _ENC_PREFIX + token.decode("ascii")

def decrypt(value: str) -> str:
    """Decrypt *value* if it carries the ``ENC:`` prefix; pass through
    otherwise.

    Returns the original *value* unchanged when decryption fails
    (e.g. master key changed, data corrupted) so callers can degrade
    gracefully instead of crashing.
    """
    if not value or not value.startswith(_ENC_PREFIX):
        return value
    try:
        f = _get_fernet()
        token = value[len(_ENC_PREFIX) :].encode("ascii")
        return f.decrypt(token).decode("utf-8")
    except Exception:
        logger.warning("Failed to decrypt value; returning raw ciphertext")
        return value  # 降级：返回原始密文
```

## 九、常见问题

### Q1: 为什么选择 Mixin 而不是装饰器？

**A**: 装饰器适合增强单一函数，但 `ToolGuardMixin` 需要**拦截** `_acting()` 方法的所有调用。如果使用装饰器，ReActAgent 的内部调用链不会经过装饰器。Mixin 通过 MRO 覆盖方法，确保所有调用都经过安全检查。

### Q2: Workspace 隔离的开销是否可接受？

**A**: 对于大多数场景，每个 Agent 独立组件的开销是必要的：
- 隔离确保一个 Agent 的错误不影响其他 Agent
- 热重载可以实现零停机更新
- 如果内存紧张，可以考虑池化重型服务（如 MemoryManager）

### Q3: 为什么使用三重配置层次？

**A**: 三层设计解决了不同场景的需求：
- **环境变量**：适合容器化、CI/CD、敏感信息
- **config.json**：适合团队共享的应用配置
- **agent.json**：适合每个 Agent 的独立配置
- **运行时覆盖**：适合动态调整

### Q4: 异步编程的常见陷阱？

**A**: 主要陷阱包括：
1. **阻塞主事件循环**：避免同步 I/O，使用异步替代
2. **忘记 await**：导致协程对象而非结果
3. **竞态条件**：多个协程同时修改共享状态
4. **取消作用域**：跨任务取消可能导致资源泄漏

### Q5: 如何选择合适的密钥存储方案？

**A**: 按优先级选择：
1. **OS Keychain**：最安全，用于桌面环境
2. **文件存储**：降级方案，需要文件权限保护
3. **环境变量**：仅用于容器/CI 环境

## 架构演进与未来展望

随着 AI Agent 技术的快速发展，QwenPaw 的架构也在持续演进。以下分析当前架构的设计空间和可能的演进方向。

### 分布式 Agent 协调

**当前状态**：单进程多 Workspace，所有 Agent 运行在同一进程中。

**演进方向**：
- **Workspace 间 IPC 通信**：当前 Agent 间通信需要通过外部消息队列。未来可通过共享内存或消息管道实现进程内直接通信。
- **分布式任务队列**：引入 Celery/RQ 等任务队列，将长时间运行的任务分发到独立工作进程。
- **跨 Workspace 消息路由**：设计统一的消息路由层，支持 Agent 间的点对点和广播通信。

**设计挑战**：
- 通信延迟与一致性：分布式环境下如何保证消息的有序性和可靠性
- 服务发现：Agent 如何动态发现和注册到集群
- 故障隔离：单个 Agent 的故障不应影响整个集群

### 多租户隔离增强

**当前状态**：Workspace 隔离提供目录级和服务级隔离。

**演进方向**：
- **命名空间隔离**：在 Workspace 之上引入命名空间概念，支持团队/组织级别的资源隔离
- **资源配额**：为每个 Workspace 设置 CPU、内存、API 调用次数等资源上限
- **计量计费**：基于 Token 消耗、API 调用次数、存储使用量等进行计量

**设计挑战**：
- 配额粒度：如何平衡配额精度与系统开销
- 多层级配额继承：命名空间 -> 团队 -> Agent 的配额如何层层分配
- 超限处理：配额耗尽时的优雅降级策略

### 增强的记忆系统

**当前状态**：ReMeLight 记忆系统支持向量搜索和全文搜索。

**演进方向**：
- **多模态记忆**：支持图像、音频等非文本记忆的存储和检索
- **主动记忆优化（Dream）**：Agent 空闲时自动整理、压缩、关联记忆
- **长期记忆压缩**：定期将短期记忆总结为长期知识，减少存储和检索开销

### 增强的多模态支持

**当前状态**：基础的多模态内容探测和处理。

**演进方向**：
- **图像理解增强**：支持图像描述、OCR、图像对比等高级视觉能力
- **语音交互**：支持语音输入（STT）和语音输出（TTS），实现语音对话
- **视频分析**：支持视频关键帧提取、场景识别、时间线分析

### 演进路径的设计原则

在进行架构演进时，应遵循以下原则：

1. **声明式优于命令式**：通过 `ServiceDescriptor` 声明服务依赖和优先级，而不是在代码中硬编码启动顺序，使系统更易于理解和修改。
2. **安全性默认启用**：ToolGuard 默认启用，敏感路径默认保护，认证可选但推荐启用。任何新功能都不应降低安全水位。
3. **优雅降级优先**：新功能应在旧环境中有合理的降级行为，而非直接报错（参考密钥管理的 Keychain -> 文件 -> 生成策略）。
4. **渐进式演进**：每个演进方向都应可以独立实现和部署，不需要一次性重构整个系统。

## 架构思维总结

### SOLID 原则在 QwenPaw 中的体现

| 原则 | 实践 |
|------|------|
| **单一职责 (SRP)** | Workspace 只负责管理单一 Agent 的运行时组件 |
| **开放封闭 (OCP)** | BaseChannel 对扩展开放，对修改封闭 |
| **里氏替换 (LSP)** | 所有 Channel 子类可替换 BaseChannel |
| **接口隔离 (ISP)** | BaseChannel 方法精简，Mixin 提供专用接口 |
| **依赖倒置 (DIP)** | ServiceManager 依赖 ServiceDescriptor 声明，而非具体实现 |

### 设计模式应用

| 模式 | 应用位置 |
|------|----------|
| **策略模式** | ToolGuardMixin 支持多种守卫策略 |
| **观察者模式** | AgentConfigWatcher 监控配置变化 |
| **单例模式** | MultiAgentManager、ProviderManager |
| **工厂模式** | ServiceDescriptor 创建服务实例 |
| **装饰器模式** | 异步上下文管理器封装资源管理 |

### 微架构决策

1. **关注点分离**：每个模块只关注自己的职责
2. **依赖倒置**：高层模块不依赖低层模块，而是依赖抽象
3. **组合优于继承**：使用 Mixin 和 ServiceManager 组合功能
4. **优雅降级**：Keychain 不可用时降级到文件存储
5. **最小惊讶**：API 设计符合直觉，错误处理一致

## 如果你来自 Java...

对于有 Java 背景的开发者，理 QwenPaw 的架构设计时可以通过以下类比来理解：

| Python 概念 | Java/Spring 对应 | 说明 |
|-------------|-----------------|------|
| `Workspace` | `@Scope("prototype")` Bean 容器 | 每个 Agent 有独立的组件实例 |
| `Mixin` | AOP Aspect / Strategy Pattern | 功能横向扩展，类似 Spring AOP |
| `ServiceManager` | BeanFactory / ApplicationContext | 统一管理服务生命周期 |
| `ToolGuardMixin` | Spring Security Filter Chain | 拦截器模式，安全检查 |
| `BaseChannel` | Strategy Interface | 抽象算法族，支持多种实现 |
| `AgentConfigWatcher` | `@RefreshScope` + `EnvironmentChangeEvent` | 配置变更监听与热重载 |
| `SafeJSONSession` | `HttpSession` + `@SessionAttributes` | 会话状态持久化 |
| 多租户隔离 | Spring Cloud TenantContext / Multitenancy | 多租户隔离设计 |

### 关键架构差异

**1. Workspace 隔离 vs Spring Bean 管理**

Java/Spring 中，所有 Bean 通常共享同一个容器：
```java
// Spring: 所有服务共享同一个容器
@Service
public class MyService {
    @Autowired
    private SharedResource resource;  // 所有实例共享
}
```

QwenPaw 的 Workspace 模式为每个 Agent 创建独立的运行时：
```python
# QwenPaw: 每个 Workspace 有独立的组件
class Workspace:
    def __init__(self, agent_id):
        self._runner = AgentRunner()      # 独立的 Runner
        self._memory_manager = MemoryManager()  # 独立的内存管理
```

**2. Mixin vs AOP**

Spring AOP 使用代理：
```java
@Aspect
@Component
public class LoggingAspect {
    @Around("@annotation(Logged)")
    public Object log(ProceedingJoinPoint pjp) {
        // 前置/后置处理
        return pjp.proceed();
    }
}
```

QwenPaw 的 Mixin 直接修改 MRO（方法解析顺序）：
```python
class QwenPawAgent(ToolGuardMixin, ReActAgent):
    # MRO: QwenPawAgent → ToolGuardMixin → ReActAgent
    async def _acting(self, tool_call):
        # Mixin 直接覆盖方法
        result = await self._guard_tool(tool_call)
        if result.blocked:
            return result
        return await super()._acting(tool_call)
```

**3. 配置管理**

Spring 使用 `@ConfigurationProperties` + `@RefreshScope`：
```java
@ConfigurationProperties(prefix = "agent")
@RefreshScope
public class AgentProperties {
    private int maxIters;
}
```

QwenPaw 使用三层配置 + Pydantic 验证：
```python
# config.json → agent.json → 环境变量
class AgentConfig(BaseModel):
    max_iters: int = 50
    request_timeout_seconds: int = 120
```

### 迁移建议

如果你从 Java Spring 迁移到 QwenPaw：
- 忘掉依赖注入注解，关注**组合而非继承**
- 使用 **Mixin** 而不是 **AOP 注解**
- 使用 **Python asyncio** 而不是 **Java CompletableFuture**
- 使用 **Pydantic** 而不是 **@ConfigurationProperties**
- 使用 **JSON 文件** 而不是 **数据库** 做轻量持久化
