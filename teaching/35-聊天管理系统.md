## 2. get_or_create_chat 模式

源码路径：`src/qwenpaw/app/runner/manager.py:80`

### 2.1 核心实现

```python
# src/qwenpaw/app/runner/manager.py:80
async def get_or_create_chat(
    self,
    session_id: str,
    user_id: str,
    channel: str = DEFAULT_CHANNEL,
    name: str = "New Chat",
) -> ChatSpec:
    """获取现有聊天或创建新聊天。

    用于来自渠道的聊天自动注册。
    """
    async with self._lock:
        # 尝试通过 session_id 查找现有
        existing = await self._repo.get_chat_by_id(
            session_id, user_id, channel,
        )
        if existing:
            return existing

        # 创建新的
        spec = ChatSpec(
            session_id=session_id,
            user_id=user_id,
            channel=channel,
            name=name,
        )
        await self._repo.upsert_chat(spec)
        return spec
```

### 4.2 JsonChatRepository

```python
# src/qwenpaw/app/runner/repo/json_repo.py:13
class JsonChatRepository(BaseChatRepository):
    """chats.json 仓库（单文件存储）"""

    async def save(self, chats_file: ChatsFile) -> None:
        """原子保存到 JSON 文件"""
        tmp_path = self._path.with_suffix(self._path.suffix + ".tmp")
        payload = chats_file.model_dump(mode="json")
        tmp_path.write_text(
            json.dumps(payload, ensure_ascii=False, indent=2, sort_keys=True),
        )
        shutil.move(str(tmp_path), str(self._path))  # 原子替换
```

## 7. 聊天生命周期

```
1. 渠道接收消息
         ↓
2. Channel._consume_with_tracker() 调用 chat_manager.get_or_create_chat()
         ↓
3. ChatManager 检查仓库中现有聊天
   - 找到：返回现有 ChatSpec
   - 未找到：创建新 ChatSpec（带 UUID）
         ↓
4. TaskTracker.attach_or_start() 链接任务到 chat.id
         ↓
5. Runner 从 SafeJSONSession 加载会话状态
   - 文件：{user_id}_{session_id}.json
         ↓
6. 智能体处理消息，记忆更新
         ↓
7. Runner 保存会话状态到 SafeJSONSession
         ↓
8. Runner 调用 chat_manager.touch_chat() 更新时间戳
```

## 11. 常见问题

### Q1: chats.json 损坏？

**可能原因**：写入时被强制终止。

**解决方案**：使用原子写入（先写 `.tmp` 再 `move`），可恢复旧文件。

### Q2: 聊天未找到？

**排查**：
1. 确认 `session_id` 格式正确
2. 确认 `user_id` 匹配
3. 确认 `channel` 正确

### Q3: 多实例共享 chats.json？

**问题**：可能导致数据竞争。

**说明**：每个 Workspace 独立文件，不共享。不支持多实例共享同一 Workspace。

### Q4: 如何清理旧聊天？

**方式**：
1. 手动删除：`DELETE /api/chats/{chat_id}`
2. 批量删除：`POST /api/chats/batch-delete`
3. 只删除 ChatSpec，不删除会话文件

### Q5: 会话文件与聊天不同步？

**说明**：这是预期行为。ChatSpec 管理聊天元数据，会话文件管理记忆历史。删除聊天不会自动删除会话文件。

## 附录：企业级聊天管理进阶

### 分布式会话挑战

QwenPaw 当前采用 **文件级隔离** 的聊天管理策略，每个 Workspace 独立 `chats.json`。这在单机部署下工作良好，但分布式场景下存在问题：

| 场景 | 当前方案 | 企业级方案 |
|------|----------|-----------|
| 多实例部署 | 不支持（文件锁冲突） | Redis Cluster / PostgreSQL |
| 实时同步 | 依赖轮询 | WebSocket 推送 / SSE |
| 会话迁移 | 不支持 | 分布式缓存（如 Redis） |
| 消息持久化 | JSON 文件 | 数据库（SQL/NoSQL） |

**如果你的场景需要多实例：**

1. **切换 Repository 实现**：将 `JsonChatRepository` 替换为 `PostgresChatRepository`
2. **使用 Redis Session**：替代 `SafeJSONSession`
3. **消息队列**：使用 RabbitMQ / Kafka 解耦消息处理

### 聊天状态机设计

生产级聊天系统通常需要完整的状态机：

```
     ┌─────────┐
     │  IDLE   │ ← 初始状态
     └────┬────┘
          │ 收到消息
          ▼
     ┌─────────┐
     │ RUNNING │ ← 处理中
     └────┬────┘
          │ 处理完成/超时
          ▼
     ┌─────────┐
     │  IDLE   │ ← 返回空闲
     └─────────┘
          │
          │ 用户关闭/超时
          ▼
     ┌─────────┐
     │ ARCHIVED │ ← 归档（可选）
     └─────────┘
```

QwenPaw 的 `ChatSpec.status` 目前只支持 `idle` / `running` 二态，如需更复杂的状态流转，可以扩展此字段。

### 性能优化技巧

| 优化点 | 当前实现 | 优化建议 |
|--------|----------|----------|
| 列表查询 | 全量加载后过滤 | 添加索引字段（user_id, channel, updated_at） |
| 原子写入 | shutil.move 原子替换 | 大并发场景可加文件锁 |
| 内存占用 | 全量加载 chats.json | 分页加载 + LRU 缓存 |

**关键区别：**
- Java 使用 JPA 注解声明式定义模型，Python 使用 Pydantic 字段定义
- Java 事务由 Spring 管理，Python 并发由 asyncio.Lock 控制
- Java 需要数据库 migration，QwenPaw 使用文件存储（更适合单机场景）
- QwenPaw 的 `get_or_create_chat` 模式等效于 Spring Data 的 `findOrCreate`

### 答案

1. **B** - ChatSpec.status 只支持 `idle` / `running`

5. 文件存储优点：简单、无依赖、适合单机。瓶颈：多实例部署、高并发写入、跨机器同步
